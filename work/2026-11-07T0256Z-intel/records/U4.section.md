Rapid7's Metasploit wrap-up of 2026-11-06 lists an exploit module for an unauthenticated SQL injection on Cisco Secure Email Gateway that ends in command execution as root, and says "we have reason to believe this maps to CVE-2026-76443" ([Rapid7, 2026-11-06](https://www.rapid7.com/blog/post/pt-metasploit-wrapup-unauth-rce-modules-in-network-perimeter-devices-and-much-more/)). The module was merged on 2026-10-28; its author wrote that he found it while diffing the fix for the exploited CVE-2026-76461 and tested a gateway on AsyncOS 15.5.1-055 "which has the "S/MIME Public Key Harvesting" feature enabled for inbound mail" ([Rapid7 Metasploit pull request 22018, 2026-10-15](https://github.com/rapid7/metasploit-framework/pull/22018)). The module sends one signed S/MIME email carrying 500 certificate addresses to the gateway's SMTP listener ([Rapid7 Metasploit pull request 22018, 2026-10-15](https://github.com/rapid7/metasploit-framework/pull/22018)); its documentation says "Public-key harvesting must be enabled on the inbound mail flow policy for the target to be exploitable" and describes a stacked COPY TO PROGRAM statement, the pattern Cisco's own log check already searches for ([Rapid7 Metasploit module documentation, 2026-10-15](https://github.com/rapid7/metasploit-framework/pull/22018.diff)). Whether harvesting is on by default is not stated, and Cisco's advisories say the flaws affect the product "regardless of device configuration" ([Cisco PSIRT, hardening-release advisory, 2026-09-14](https://sec.cloudapps.cisco.com/security/center/content/CiscoSecurityAdvisory/cisco-sa-hardening-esa-dfCrfXkm)).

Cisco's hardening advisory lists CVE-2026-76443 with the other grouped CVEs and its fixed-release table gives 15.5.5-014 for 15.5 and earlier, 16.5.0-780 for 16.5 and "Migrate to a fixed release." for 16.0 ([Cisco PSIRT, hardening-release advisory, 2026-09-14](https://sec.cloudapps.cisco.com/security/center/content/CiscoSecurityAdvisory/cisco-sa-hardening-esa-dfCrfXkm)). A 16.0 appliance on 16.0.4-302 therefore has no named fix for the flaw the module most likely uses; moving to 16.5.0-780 closes it. Rapid7 does not report exploitation of the module's flaw, and Cisco does not say whether the injection it lists as exploited is the one the module uses.
