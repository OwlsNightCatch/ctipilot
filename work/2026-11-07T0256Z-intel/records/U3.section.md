Umut Bayram of Picus Security, who found the flaw, shows that the update which installs the fix still unpacks its files with the site's old, unpatched code ([Picus Security, 2026-11-05](https://www.picussecurity.com/resource/blog/cve-2026-119977-when-updating-wordpress-becomes-the-vulnerability); [The Hacker News, 2026-11-06](https://thehackernews.com/2026/11/installing-fix-for-exploited-wordpress.html)). Picus says the new code's skip of wp-config.php already works in that first update but the randomised folder name does not, so the temporary installer sits at a predictable path on sites running 5.9 or later and, on 4.4 to 5.8, behind a random suffix that hides it unless the site leaks the path ([Picus Security, 2026-11-05](https://www.picussecurity.com/resource/blog/cve-2026-119977-when-updating-wordpress-becomes-the-vulnerability)). Bayram told The Hacker News the deciding factor "isn’t partial versus complete. It’s whether the updater already installed on the site has been fixed", and The Hacker News found WordPress.org offering an in-branch move such as 7.1.3 to 7.1.4 as a partial package, automatic updates included; only once 7.1.4 or the branch fix is installed do later updates use a random folder ([The Hacker News, 2026-11-06](https://thehackernews.com/2026/11/installing-fix-for-exploited-wordpress.html)). WordPress 4.6 and earlier get no fix ([The Hacker News, 2026-11-06](https://thehackernews.com/2026/11/installing-fix-for-exploited-wordpress.html)).

The order matters: Picus advises denying web access to wp-content/upgrade/ in the web server configuration first, confirming that the path answers 403, and only then updating; this does not break updates, because WordPress reaches the folder through the filesystem ([Picus Security, 2026-11-05](https://www.picussecurity.com/resource/blog/cve-2026-119977-when-updating-wordpress-becomes-the-vulnerability)). An .htaccess file placed inside the folder does not work, because the old updater deletes the folder's contents before unpacking, and WP-CLI's wp core update is no substitute because it uses the same updater and folder ([Picus Security, 2026-11-05](https://www.picussecurity.com/resource/blog/cve-2026-119977-when-updating-wordpress-becomes-the-vulnerability)). None of these sources reports an attack on that update window; CISA's listing and Wordfence's probing telemetry above are unchanged.
