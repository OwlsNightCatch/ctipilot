###### Update: 17 November 2026 22:00

##### SEVERITY AND IMPACT:

- Java4Shell is a memory-corruption vulnerability in the hardware-accelerated Base64 decoder used by affected Java runtimes. Successful exploitation can expose sensitive memory, including credentials and tokens, and allow attackers to execute code with the permissions of the Java application.
- Calif reports **pre-authentication RCE**, requiring neither credentials nor user interaction, in several widely deployed products. Other demonstrated attack paths require authenticated access.
- Compromise of identity systems, development platforms or deployment infrastructure could expose connected applications, software repositories and sensitive business information.
- **Banking and financial applications can also be affected** where they use a vulnerable Java runtime on the relevant hardware and expose an exploitable processing path. Operators should urgently clarify their exposure with application suppliers.
- **Severity:** CVSS v4.0 **9.2, CRITICAL**, according to Calif; CVSS v3.1 **8.1, HIGH**, according to OpenJDK.
- **Exploitation in the wild:** UNKNOWN. The published research demonstrates exploitation; it does not establish malicious exploitation in operational environments.

##### AFFECTED PRODUCTS AND ENVIRONMENTS:

The vulnerability affects the OpenJDK HotSpot Base64 implementation, including affected builds distributed through **Oracle Java SE, Oracle OpenJDK, Oracle GraalVM for JDK, Amazon Corretto, Eclipse Temurin, Microsoft Build of OpenJDK, Azul Zulu, BellSoft Liberica, SAP SapMachine and Red Hat OpenJDK**.

- **Versions:** Calif traces the affected implementation to OpenJDK **17.0.6**. The OpenJDK advisory identifies affected builds in the **17, 21, 25 and 27** release families. Calif additionally identifies the Oracle Java 8 performance build **8u511b33-perf**. Check the exact distribution and build against the provider’s advisory.
- **Hardware:** Exploitation requires **x86-64 processors with AVX-512 VBMI support** and use of the affected decoder implementation. Relevant processors include certain Intel Xeon generations and AMD Zen 4 or newer processors. **ARM64 is not affected by this CVE.**
- **Deployment scope:** Check standalone runtimes, application-bundled Java, containers, appliances and externally managed services. Calif also reports a client-side exploitation path involving a Java application connecting to a malicious TLS server.

##### APPLICATIONS WITH DEMONSTRATED RCE:

Calif reports successful exploitation in its tested configurations:

**Pre-authentication RCE, without login credentials:**

- Keycloak
- Atlassian Jira
- Atlassian Confluence
- JFrog Artifactory
- Jenkins
- PingFederate

**Post-authentication RCE, requiring authenticated access:**

- Apache Kafka Broker
- Apache Solr
- Elasticsearch
- Gerrit
- Netflix Spinnaker

**This list is not exhaustive.** Calif also demonstrated RCE in sample applications built with Apache Struts and Spring Boot. Exposure depends on the runtime, hardware and application-specific processing paths. A product name alone does not establish whether a particular deployment is exploitable.

##### AVAILABLE FIXES AND REQUIRED ACTIONS:

**Apply the security update provided for the deployed Java distribution without delay.** Oracle has published the following updated JDK versions:

| Oracle JDK release family | Updated version |
| --- | --- |
| 17 | **17.0.21.1** |
| 21 | **21.0.13.1** |
| 25 | **25.0.5.1** |
| 27 | **27.0.1.1** |

These are Oracle version identifiers. Other distributions and product vendors may use different package versions or release schedules. [oracle.com](https://www.oracle.com/java/technologies/javase/17-0-21-1-relnotes.html?utm_source=chatgpt.com)

- **Identify exposure:** Record the Java distribution, exact running build, processor capabilities and responsible supplier. Prioritise internet-facing applications, identity infrastructure and business-critical systems.
- **Update bundled components:** Obtain application or appliance updates where Java is supplied as part of the product. Confirm remediation with hosting and software providers.
- **Restart and verify:** Restart affected Java processes and rebuild or redeploy containers as required. Verify that the running applications actually use the patched runtime.
- **Review for compromise:** Investigate unexpected Java crashes, suspicious processes and unusual authentication or application activity. Updating does not remove an existing compromise.

##### TEMPORARY MITIGATION:

If immediate patching is not feasible, Calif documents disabling Base64 intrinsics with this JVM startup option:

```text
-XX:-UseBASE64Intrinsics
```

Restart each affected Java process with the option and verify that it is effective. Assess application behaviour and performance.

Alternatively, Calif documents:

```text
-XX:UseAVX=2
```

**Use this alternative only on x86-64 systems. Applying it on ARM can prevent the JVM from starting.**

These options address the Java4Shell attack path and do not replace the other security fixes in the release. Restrict unnecessary access while remediation is pending. Request buffering or a Web Application Firewall should not be relied upon as a complete mitigation.
