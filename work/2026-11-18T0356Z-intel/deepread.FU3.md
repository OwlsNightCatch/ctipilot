### 3.9 Contradictions with the first pass (S3 item 4 and S4 item 2)

1. **"Contractor" is not the source's word.** Both Barracuda pages say third-party **vendor** ("a company working in AI"); the Trust Center says "third party". The first pass (title, summary, notes) and the composer brief say "AI contractor" / "contractor-held key". Use "third-party vendor".
2. **October date source.** First pass S4 attributes the October compromise to the "Trust Center update of 2026-11-13". That update gives no month; "In October, the vendor's own development environment was compromised" is in the blog (2026-11-11), hedged by "That appears to be where the attacker found our key". The 11-13 Trust Center update then says the investigation "has confirmed" the key sat in a configuration file in the third party's GitHub repository.
3. **"Diversion" is BleepingComputer's, not Barracuda's.** S4 first pass: Barracuda "does not rule out that wallet hunting was a diversion or that AI-service credentials were also a target". Barracuda's pages say a "third motive cannot be ruled out" (AI-service credentials); the word "diversion" appears only in BleepingComputer (verified absent from the Trust Center and blog). Carry the Barracuda wording; attribute "diversion" to BleepingComputer if used at all.
4. **ARTEX strength differs by document.** The first pass (S3 item 4 title: "ARTEX-consistent"; summary: "match ARTEX") flattened three wordings: advisory 11-10 "consistent with recently reported automated, AI-driven intrusion activity" (no ARTEX name); advisory update 11-13 "consistent with publicly reported characteristics of ARTEX"; blog 11-11 "all match ARTEX" and "tells us how the attacker operated, not who it was". Cite each as stated; the blog is the strongest.
5. **"About ten cloud accounts in 44 hours".** Correct as Barracuda's phrase, but the stated first call (11-01 04:33 UTC) and last activity (11-02 23:31 UTC) are 42 h 58 min apart. Quote "roughly 44 hours" as Barracuda's; do not present an arithmetic duration.
6. **Container removal time.** First pass: "removed the container on the evening of 2026-11-04". Barracuda: "evening of November 4, Pacific time" (the blog's timeline is otherwise UTC).
7. **Source code.** The blog says the attacker reached "a source-code access token" and pushed short-lived branches to "a handful of repositories"; it does not say source code was read, copied or exfiltrated. BleepingComputer widens this to "source-code repositories". The first pass listed "source-code access token" correctly; do not upgrade it to a source-code breach.
8. **GitHub naming detail.** First pass: GitHub workflow files and branches "with the same 'i<digits>' naming". Trust Center: workflow files named with an "i" + digits + letters pattern, on branches that begin with the same string plus a hyphen; the "no hyphen" statement is about cloud and Kubernetes resource names.
9. **New in the 2026-11-13 update and absent from the first pass:** two internal automation servers retired, access keys removed, access records reviewed, no attacker activity found on them; other Barracuda credentials in the same file had expired or were revoked; "Barracuda's investigation has confirmed how the attacker obtained initial access".
10. **Confirmed correct, with a scope note:** the first-pass window "2026-11-01 04:33 to 2026-11-02 23:31" is the blog's UTC timeline; the Trust Center states only "November 1 and November 2, 2026" for access to the credential-storing system.

- The number of customers notified, which specific credentials per integration (Microsoft 365 app registrations, Google service-account keys, endpoint agent API tokens) -- the Campus page only says "API keys, tokens, and client secrets used by Barracuda XDR integrations" and defers to an attached PDF (not read). No customer, public or Swiss, is named.

### 4.8 Contradictions with the first pass (S4 item 1)

1. **"(up to 4,597 users)" in the title.** 4,597 is the count for the user-authentication system records (4,222 Fugaku + 375 Rikyu); for Rikyu users only name and e-mail are listed. The SSH-key/home-directory category (2) is stated for Fugaku users' home directories and carries NO count. The first-pass title ties the keys and the 4,597 together; the release does not.
2. **"software vulnerability that was abused".** The Japanese "悪用されたソフトウェアの脆弱性" is ambiguous, and RIKEN's own English page renders it as "any vulnerabilities in the exploited software". It appears only in the list of measures before restart, while the intrusion method is "under investigation". The first pass presented the Japanese-literal reading as RIKEN's phrase; carry RIKEN's English wording and do not state a vulnerability was exploited as established. The first-pass T1190 mapping rests on the dashboard-foothold statement plus this phrase; since RIKEN says the method is under investigation, T1190 is an inference (the ids in the first-pass lists are all active in the pinned v20.1 dataset; none of the RIKEN, Kyodo, Mainichi, BleepingComputer or Piyolog pages names an ATT&CK id).
3. **An English page exists** (dated Nov. 17, 2026; the first pass cites only the Japanese release). It carries a typo: "up to 4,224 individuals" for Fugaku users in section 3 (the overview and the Japanese page say 4,222). Dates: Japanese release 16 Nov; English page 17 Nov.
4. **BleepingComputer is not a clean corroboration of the details.** It says the keys were "stored on users' computers" (RIKEN: home directories on Fugaku) and that the intruder planted "malware that targeted user data" (RIKEN: unauthorized programs / system tampering, no targeting statement), and it reads the vulnerability line as definite. Its dashboard sentence ("exploited the public dashboard ... to gain access to multiple internal servers") matches the release.
5. **Mainichi 17 Nov is paywalled** (about 270 of 622 characters readable). The readable part gives 12 Nov and "about 4,200 users", plus an unnamed-source claim that home-directory files were *read*. The first pass's "re-check analyses run 11-12 to 11-15" is present only in Piyolog (citing the paywalled Mainichi piece) and is not in RIKEN's release; the first pass did attribute it to Piyolog, which is right.
6. **The Swiss precedent as written in the first pass is partly unsupported.** The first-pass assessment cites "CSCS 2020 notice; Netzwoche 2020" together for "hit ETH Zürich and CSCS Lugano and targeted EPFL and the University of Basel ... with the University of Basel describing initial access as compromised SSH keys ... obtained from other HPC centres". The CSCS notice states none of that (it is generic and says the cause is unclear); every one of those statements rests on Netzwoche alone (and Basel's is a professor's statement relayed by Netzwoche; the EPFL spokesperson denied evidence of a real intrusion). The phrase "SSH keys harvested at one HPC centre and replayed at others" is the analyst's summary; the nearest sourced wording is Basel's "keys ... obtained from other HPC centres".
7. **"RIKEN says programs were planted"** is a fair paraphrase of "不正なプログラムの設置など、システムの改ざん" / "installation of malicious programs".
8. **Confirmed correct:** dashboard foothold, window 10-13 Nov, SSH private keys and access keys in home directories, replay attempts against other systems, all-jobs-stopped and all-login-keys-invalidated on 15 Nov, outsourced maintenance, reports to the PPC / MEXT / HPCI organisations, no attribution named, no concrete evidence research results left.
9. **First pass omitted:** RIKEN's user warning about phishing e-mails impersonating Fugaku/RIKEN; the plan to review the operations/maintenance responsibility split; "AI-based security measures" among restart conditions; Kyodo's MEXT statement (the system hit is the one users connect to; scope depends on what users registered) and "recovery date undecided".

### 4.9 Open gaps

- **Software/vulnerability:** not named; no CVE; the exact intrusion method is under investigation (RIKEN). Whether the dashboard host and the management servers share a network segment is not stated (the release says only that the dashboard was the foothold into the "operations internal network").

- **Replay outcome:** which external systems received connection attempts, and whether any succeeded, is not stated ("secondary damage" under investigation). No foreign (incl. Swiss) HPC centre is named as a destination.
- **Actor / motive:** none named by RIKEN or any outlet.
- **Time zone:** RIKEN gives local clock times without a time zone (Japanese local time presumed).
- **Mainichi remainder and the Nikkei report** (Toyota, Sumitomo Rubber; linked from Piyolog) were not read (paywall / not fetched).
- **Swiss exposure:** no source says any Swiss institution or user is affected. Treat any link as analyst assessment only.
