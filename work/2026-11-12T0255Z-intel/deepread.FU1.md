## A. NEW — Apache HTTP Server CVE-2026-119618 (mod_http2 `assign_headers()` race)

Entry-level facts (S1 item 1 and S3 item 11 are the same finding; one entry).

### A.1 Answers to the questions asked

1. **Exact affected range.** Apache HTTP Server 2.4.55 through 2.4.70 (project advisory, CVE record `lessThanOrEqual 2.4.70` with `defaultStatus unaffected`, ENISA EUVD `2.4.55 ≤2.4.70`). Standalone `mod_h2` from GitHub: 2.0.8 through 2.0.42. Fixed in Apache HTTP Server 2.4.71, released 2026-11-11, by commit 824beab9b9424d6cfb29595248fdbf6c3dddeab1 in 2.4.x (a cherry-pick of 5ed39287660daacd1233cb9bbc984b25fa9a4fe3, commit title "mod_http2: assign_headers update table (#975) (#977)"). Apache rates it **critical**; it publishes **no CVSS** (CVE record: textual severity only; EUVD `baseScore 0.0`). Red Hat computes CVSS 3.1 9.8 (`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`) and rates RHEL 9 and 10 Important.
2. **Does it need HTTP/2 enabled?** Apache's page, post, CVE record and announcement are silent on the precondition (the component is mod_http2). Red Hat Product Security states it outright: only servers with HTTP/2 enabled through `Protocols` (`h2` or `h2c`) are affected, and HTTP/1.1-only servers are not. Wiz scopes it to "deployments utilizing HTTP/2". The third-party Sploitus listing README gives the same lever (drop `h2`/`h2c` from `Protocols`). So the working prerequisite is: mod_http2 loaded **and** `Protocols` listing `h2` and/or `h2c` for the server or virtual host. That prerequisite comes from Red Hat, not from Apache; Apache publishes no workaround or mitigation of its own.
3. **Is HTTP/2 on by default in the project's own packaging?** No. The project documents `Protocols http/1.1` as the default ("By default, only the http/1.1 protocol (which includes the compatibility with 1.0 and 0.9 clients) is allowed"), the how-to shows HTTP/2 as two manual steps (a `LoadModule http2_module` line, then a `Protocols h2 http/1.1` line), mod_http2 is built only with libnghttp2, linked shared and "requires loading", and the source-tree default config templates carry a `@@LoadModule@@` placeholder and no `Protocols h2` line. Distribution packaging read today (Ubuntu `apache2`, branch `ubuntu/devel`): `http2` is not in the list of modules enabled on a fresh install, but once enabled (`a2enmod http2`) its configuration file sets **`Protocols h2 h2c http/1.1`**, so enabling the module turns on cleartext HTTP/2 (h2c) as well as TLS h2. Caveats: `ubuntu/devel` is the development branch, not the 22.04 or 24.04 package; Debian's own packaging repository could not be read (proof-of-work wall); RHEL's defaults were not read. No source says how many deployments enable HTTP/2; Wiz's "51% publicly exposed" figure "does not take configuration into account".
4. **mod_h2 standalone fixed version.** What each source says: Apache (authoritative) names none and says mod_h2 2.0.8 through 2.0.42 are affected. Wiz's table says patched mod_h2 is "2.0.24 and newer" (inconsistent with its own affected range, and its page heading carries the wrong CVE id, CVE-2026-111497) while its text says to move to "a version newer than 2.0.42". Authoritative reading: **no fixed standalone mod_h2 exists and none will be released from GitHub**. The `icing/mod_h2` repository was archived on 2026-06-09 and is read-only; its README says the repository is no longer maintained and the module "lives on as part of the Apache httpd project"; the newest release, v2.0.42 (2026-05-29), is itself inside the affected range. Fix path: httpd 2.4.71, or a distribution's own mod_http2 package (RHEL ships `mod_http2` 2.0.26 on RHEL 9 and 2.0.29 on RHEL 10 as separate packages, patched by backport; see point 6).
5. **Exploitation / PoC as of 2026-11-12.** Apache's advisory page carries no exploitation, PoC, workaround or mitigation statement (the CVE-2026-119618 block ends at its `Affects` line, anchored in the table). Not in the CISA KEV catalogue (catalogVersion 2026.11.10, released 2026-11-10T19:03Z, the newest release at read time; `kev-window.txt` of this run reports no KEV additions since 2026-11-11). Statements that disagree: (a) **Wiz, 2026-11-11**: "no exploit is available and there are no reports of exploitation in the wild" at publication. (b) **Red Hat Product Security** (CVE page, public 2026-11-11 12:52Z): "public research has demonstrated a reliable exploit against a default-configured server with the mod_http2 module enabled", with no link to that research; this is a capability claim, not an in-the-wild claim. (c) **Sploitus** (aggregator, 2026-11-11) lists a third-party "PoC exploit for CVE-2026-119618" by account `realslimsud0`; the mirrored README is a root-cause note (an unsynchronised write to `req->headers` in `assign_headers`, fix commit 5ed3928), a deterministic Content-Length "detection oracle" and a scanner, and does not itself claim an RCE chain; the GitHub repository it names returns HTTP 404 and the account lists no public repositories, so it was removed or never public. Net: the root cause is public in some form, a reliable RCE is claimed by Red Hat but the research was not located, and no source reports exploitation in the wild.
6. **Distro backports.** *Debian tracker (read 2026-11-12):* bookworm 2.4.68-1~deb12u1 and bookworm-security 2.4.67-1~deb12u3, trixie 2.4.68-1~deb13u1 and trixie-security 2.4.69-1~deb13u1, forky 2.4.69-1: all **vulnerable**; only sid 2.4.71-1 is fixed (Debian bug 1153732). *Red Hat:* RHEL 8 and earlier not affected; RHEL 9 and 10 fixed on 2026-11-11 through `mod_http2` package errata (RHEL 9 `mod_http2-0:2.0.26-7.el9_9.1` in RHSA-2026:98981; RHEL 10 `mod_http2-0:2.0.29-5.el10_3.1` in RHSA-2026:98978; EUS and E4S streams RHSA-2026:98953, 98954, 98968, 98979, 98982), rated Important; Red Hat JBoss Core Services and Red Hat Hardened Images are still listed Affected with no fix. *Ubuntu and SUSE:* no tracker page yet (HTTP 404). The check is the distribution advisory, not the upstream version string.

## B. NEW — Plone security fix 20261110 (hotfix Products.PloneHotfix20261110)

### B.1 Answers to the questions asked

1. **Affected versions.** The Plone/Zope Security Team: all supported lines (6.0, 6.1, 6.2) and, per the team, older versions "back to at least Plone 4.3". Per package, from the GitHub advisories' structured fields: Products.CMFEditions up to 5.0.1 (6.2 line) and up to 4.0.6 (6.0 and 6.1 lines); Products.CMFPlone up to 6.2.2, 6.1.5 and 6.0.15; Products.MimetypesRegistry up to 4.0.1 and 3.0.1; plone.batching up to 3.0.2 and 2.0.7; plone.restapi up to 10.2.0 and 9.15.7.
2. **Fixed packages (Buildout notation, community post).** Plone 6.2: CMFPlone 6.2.3, CMFEditions 5.0.2, MimetypesRegistry 4.0.2, plone.batching 3.0.3, plone.restapi 10.2.1. Plone 6.1: CMFPlone 6.1.6, CMFEditions 4.0.7, MimetypesRegistry 3.0.2, plone.batching 2.0.8, plone.restapi 9.15.8. Plone 6.0: CMFPlone 6.0.16 with the same helper versions as 6.1 (CMFEditions 4.0.7, MimetypesRegistry 3.0.2, plone.batching 2.0.8, plone.restapi 9.15.8). plone.restapi can be skipped if not installed. All eleven fixed package versions exist on PyPI with upload times 2026-11-10 13:11Z to 13:26Z (parsed from the pypi.org JSON API; not quote-checked). **Hotfix `Products.PloneHotfix20261110` 1.0 (2026-11-10)** for any version from 4.3 to 6.2; the PyPI page is more precise than the announcement on Python: Plone 6.2, 6.1, 6.0 on Python 3; 5.2 on Python 2.7 and 3; 5.1, 5.0 and 4.3 on Python 2.7. Restart all Zope instances afterwards. The fixed packages make the hotfix unnecessary. Plone 5.2 and older are out of security support; the team made an exception.
3. **Does anonymous exploitation need a non-default setting?** No source states any. The anonymous entry point is `Products.CMFEditions`: the conditional modifiers in `portal_modifier` had no security declarations, so an anonymous visitor can change a modifier's TALES condition (GitHub: CVSS network, low complexity, **privileges none**, 9.8, CWE-862) and then trigger it. The code-execution step needs the sandbox escape that the other advisories close (allow_module on whole modules in CMFPlone, MimetypesRegistry, plone.batching; json module in plone.restapi). Taken alone, those three are each rated 9.1 with **privileges High** and scoped to "sites where untrusted or low-trust users can author restricted code" (Manager-level by default), and plone.restapi is Moderate 4.7 and "on its own ... does not let anonymous users run restricted code"; the chain is what makes anonymous RCE. `portal_modifier` is reachable at any path depth through Zope acquisition (pre-announcement). CMFEditions alone, per the team, already lets an attacker run code with an editor's privileges when an editor saves versioned content.
4. **CVE ids.** None assigned: the announcement says CVE numbers "have been requested", and all five GitHub advisories show "No known CVE" as of 2026-11-12.
5. **Exploitation / PoC status.** No source reports exploitation. **The CMFEditions advisory states "A working proof of concept exists."** (not published; S1 did not carry this). The team says details are public from 2026-11-10 and that with current AI tools it "may not take long to turn them into a working exploit". A pre-announcement dated **2026-11-02** (S1 did not carry it) already told operators that an RCE exists in all supported versions, named the fix date (Tuesday 10 November 2026, about 13:00 UTC) and gave the workaround; it also warned that an AI might build an exploit from that information alone.
6. **Workaround.** Block any URL containing `portal_modifier` at the front web server (works on any Plone version; at any path depth; Apache, nginx, Traefik, Varnish recipes in the pre-announcement; Varnish does not decode percent-encoding, so rely on Apache, nginx or Traefik for that case; it only helps if Zope's own port, for example 8080, is not reachable directly). The team says to keep the block after updating.
7. **Post-patch check.** A modified modifier condition persists in the database after the fix. With updated CMFEditions: log in as Manager and open `@@check-modifier-conditions` on the Plone site root (compares `portal_modifier` conditions with the defaults and lets you revert). With the hotfix: at startup it logs `POSSIBLE ATTACK: MODIFIED VERSIONING CONDITIONS FOUND` or `No changed modifier conditions found.` A difference is not necessarily an attack (defaults changed over time, add-ons and admins may change them), but "if you do not recognize the condition, treat your server as compromised".
8. **Compatibility cost.** After the fix, restricted code (Python Scripts, TALES) can import only the names Plone itself needs from the closed modules; custom scripts importing other names get an `Unauthorized` error, and with the updated plone.restapi the same holds for anything from `json` (the hotfix still allows `json.dumps` and `json.loads`).
