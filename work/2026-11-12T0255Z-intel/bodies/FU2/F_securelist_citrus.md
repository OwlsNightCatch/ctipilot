In recent years, cyberthreats have increasingly taken a hybrid approach, combining time-tested techniques for advancing through infrastructure, modern methods of evading network filters, and automation powered by large language models. This is also the approach of Citrus Ransomware, a previously undocumented group whose toolset includes VLESS tunnels (used to disguise traffic as regular HTTPS) and a ransomware Trojan from the Sn00py family. The attackers also integrate LLMs (large language models) into the process of infrastructure compromise.

In this article, we review the tactics and techniques the group used in recent incidents.

## Initial Access: attacks through contractors

The attackers gain initial access to victims’ infrastructure through compromised contractors. They use credentials stolen from these contractors’ employees to connect to corporate VPNs or directly to internet-facing terminal servers over RDP.

## Execution: commands, LLMs, and Impacket

The attackers run commands on compromised systems through the standard Windows command interpreter and PowerShell. As the attack progresses, they create and run PowerShell scripts, batch files, and commands generated by LLMs. One example of the latter is the commands below, which disable the account of one of the administrators.

## Privilege Escalation: vulnerabilities and configuration flaws

In every case we know of, the contractor domain account used for initial access had very limited privileges, so the attackers tried to escalate them.

To do this, they attempted to exploit the authentication bypass vulnerability [CVE-2026-54121 (Certighost)](https://techcommunity.microsoft.com/blog/microsoftthreatprotectionblog/detecting-cve-2026-54121-certighost-with-microsoft-defender/4542861); these attempts created machine accounts with telltale names in Active Directory, such as:

- GHOSTAUFTAFGS
- GHOSTCZYQVAZS
- GHOSTIVPRLDZA
- GHOST{8 random letters}

These names are generated by scripts making use of an exploit published on GitHub.

The exploit works like this: on behalf of the newly created account, it requests a certificate based on the Machine template from the system holding the AD CS role. The `Attributes`, `Subject`, and `SubjectAlternativeName` fields contain parameters like these:

| 1 2 3 4 | \<Data Name='Attributes'>CertificateTemplate:Machine\nSAN:dns=dc01.victim.domain\ncdc:91.210.109\[.\]118\nrmd:dc01.victim.domain \</Data> \<Data Name='Subject'>CN=GHOSTABUIEFAD.victim.domain\</Data> \<Data Name='SubjectAlternativeName'>DNS name =dc01.victim.domain\r\n\</Data> | 

The cdc attribute specifies the IP address or name of the system that the certification authority must contact to verify the data. The attackers specify the address of a system they control (in this case, 91.210.109\[.\]118) and send forged data from it. If exploitation succeeds, the certification authority issues a certificate with the specified parameters, based on the specified template.

Once the certificate is issued, the domain controller name in its `SubjectAlternativeName` field lets the attackers authenticate as the domain controller account.

In one case, the attackers also uploaded an executable for persistence, on behalf of which PowerShell scripts were launched with nonstandard `HostName (Имя узла)` field value.

On top of the configuration flaws, 1C:Enterprise systems are frequently accessed by support staff and administrators who hold elevated privileges in Active Directory. Together, these factors make it easy for attackers to escalate privileges and start moving laterally.

## Stealth: covering tracks and masquerading

To hinder incident response, the attackers delete their tools and output files and clear the command history.

While the tools are still in use in the victim’s infrastructure, the attackers typically give them and their auxiliary objects legitimate-looking names:

- KasperskyGPO\_Deploy\_64.exe and KasperskyGPO\_Deploy\_64\_FIXED.exe are self-extracting archives. They contain the Deploy-KasperskyGPO.ps1 script, a directory with a malicious Group Policy Object, and one of two archives, KasperskyAgent.exe or agent.exe.
- KasperskyAgentInstaller.exe, KasperskyAgent.exe, and agent.exe are self-extracting archives containing the ransomware Trojan executable and auxiliary files.
- Kaspersky GPO is the name of the Group Policy Object that distributes the ransomware Trojan in the victim’s infrastructure.
- KasperskyAgentInstallTask and Sysvc are names used for the scheduled task that runs the self-extracting ransomware archive files.
- Deploy-KasperskyGPO.ps1 is the PowerShell script that creates the malicious Kaspersky GPO.
- Kaspersky\_GPO\_Deployment.log is the log of the Deploy-KasperskyGPO.ps1 script.

Note that using the Kaspersky name in malicious file names doesn’t help the attackers avoid detection. Kaspersky solutions successfully detect and block these malicious files.

## Defense Impairment: weak access policies for security tools play into attackers’ hands

To stay under the radar longer, the attackers clear event logs on some systems using the built-in wevtutil utility.

In addition, once they have sufficient privileges, they disable antivirus protection on hosts, which lets them run tools such as mimikatz.

The attackers also go after the centralized management consoles for security solutions, which they then use to disable protection en masse.

At the Impact stage, the attackers also use a Group Policy Object that modifies Windows Defender settings in the registry to switch it off. As a result, the antivirus did not respond when the ransomware was launched.

Finally, if they have sufficient privileges, the attackers manually add their malicious tools to the antivirus exclusion list.

## Credential Access: mimikatz, a keylogger, and extraction of credentials from files

To capture keystrokes on a compromised system, the attackers use a modified version of the peeping-tom keylogger, whose source code is available on GitHub. The keylogger executable and its log file are located at the following paths:

- C:\ProgramData\Oracle\Java\jhost.exe
- C:\Users\\\<username>\AppData\Roaming\Microsoft\CLR\ErrorLog.txt

In the sample we found, stolen data was sent to 91.210.109\[.\]118. Persistence for the keylogger is provided by the scheduled task described above in the Persistence section.

To dump credentials from memory, the attackers use mimikatz. Files related to mimikatz are located at the following paths:

- C:\ProgramData\x64\mimidrv.sys
- C:\ProgramData\x64\mimikatz.exe
- C:\ProgramData\x64\mimilib.dll
- C:\ProgramData\x64\mimispool.dll

To hunt for credentials and other secrets (SSH keys, access tokens, and the like) in files on accessible network shares, the group uses Snaffler. To simplify running the tool, the attackers drop a configuration file on the system:

Besides data from network shares, the attackers were interested in data stored in password managers (for example, KeePass) on administrator workstations.

## Discovery: the standard toolkit

### Local discovery

After gaining control of a compromised system, the attackers ran a basic set of commands to identify the current user, running processes, network interface settings, the system’s external IP address, and so on:

| 1 2 3 4 5 | whoami tasklist quser ipconfig curl 2ip\[.\]io | 

### Remote discovery

In the early stages, the attackers used the fscan scanner to gather information on the internal infrastructure. They were particularly interested in the following ports:

- 135 (RPC)
- 139 (NetBIOS-SSN)
- 1433 (Microsoft SQL)
- 8006 (Proxmox VE)

Once they had the access they needed and had moved laterally, the attackers ran ADRecon on domain controllers and SharpHound on one of the workstations.

The attackers also used PowerShell to run LDAP queries against the controllers of adjacent domains, pulling lists of domain systems, users, and groups.

## Lateral Movement: SSH, RDP, and WinRM

For lateral movement, the group relies on standard remote administration protocols: SSH, WinRM, and RDP. The attackers connect to systems either through previously deployed tunnels or directly from the compromised host.

### Creating tunnels with Xray

The certutil and BITS commands shown above are what the attackers used to download Xray onto victim systems. They then used Xray to set up reverse VLESS tunnels to the command-and-control server. The configuration file, stored alongside the Xray executable, was usually named config.json. ## Collection & Exfiltration: data from messaging apps

Right before encrypting the data, the attackers connected to one of the domain controllers and ran the PowerShell script steal\_tgs.ps1, which created the tdatas directory. According to the NTFS USN journal, while the script ran, 7-Zip created archives in this directory with telltale names hinting at their contents:

| 1 | \<system\_name>\_\<date>\_\<username>\_tdata.zip | 

The directory name tdatas and the substring tdata may refer to the C:\Users\\\<username>\AppData\Roaming\Telegram Desktop\tdata directory. The Telegram messaging app uses this directory to store authorization keys, session data, app settings, and other session information.

So the attackers were harvesting messaging app data from remote systems they could reach, packing it with 7-Zip and uploading it to an external web service through Google Chrome.

## Impact: Sn00py ransomware Trojan

The Citrus group uses ransomware from the Sn00py family to encrypt data. It’s written in Go and uses the RSA-2048 and ChaCha20 algorithms to encrypt user files (but not system files) on Windows systems. Encrypted files receive the .citrus extension. For now, decryption is impossible without the attackers’ private key.

When launched, the ransomware opens a console on the victim’s device, where it outputs the commands it runs. It also attempts to modify the boot configuration data (BCD) by invoking a nonexistent executable, `bcedit` (likely a typo for `bcdedit`):

The ransomware’s console output contains the string:

| 1 | We\`re going to do something special today :). Made with RaaS platform Sn00py. | 

The string likely means the ransomware is distributed under the ransomware-as-a-service model, where attackers don’t write the malware themselves but subscribe to a ready-made offering.

As mentioned above, the group uses malicious Group Policy Objects to launch the ransomware across victim systems en masse. The GPOs are created by self-extracting archives, of which we have seen two versions. Each archive contains:

- A self-extracting archive with the ransomware Trojan and auxiliary files.
- A directory containing the Group Policy Object. The policy drops the ransomware archive on the target system, creates a scheduled task that runs the archive with the parameters `/quiet /norestart`, enables the WinRM service, and disables the Volume Shadow Copy service and Windows Defender antivirus protection. It also sets a desktop wallpaper displaying the ransom note.
- A PowerShell script that copies the ransomware archive to the \\\\\<current\_domain\_name>\SYSVOL directory on the domain controller and links the malicious GPO to the domain using the `Import-GPO` and `New-GPLink`

## Links to Toy Ghouls

While analyzing Citrus activity, we noticed several similarities to Toy Ghouls. Although their infrastructures don’t directly overlap, the two groups share TTPs: they encrypt their victims’ systems, use a similar set of tools (1C-Shell for remote command execution on 1C:Enterprise servers, mimikatz, PsExec, and ADRecon), and store these tools in the same directories. What’s more, both groups are Russian-speaking and attack Russian companies only. In several incidents, we saw the same infrastructure compromised simultaneously by both Toy Ghouls and Citrus.

## Conclusion

What makes Citrus interesting is its unconventional approach to network tunneling and its use of AI to generate auxiliary tools. Even so, the attackers largely rely on well-known tools and techniques, which makes early detection somewhat easier. Kaspersky solutions detect all the activity described in this article.

That said, the Citrus attacks are another reminder that contractor access to an organization’s infrastructure must be tightly controlled and restricted. After all, compromising contractor accounts is exactly how the attackers get into their victims’ networks. We’ll continue to track the group’s activity and report new techniques as we discover them.
