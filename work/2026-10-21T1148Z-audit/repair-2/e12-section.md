The leak was not tied to package-resolution errors: GitHub's new format for GitHub App installation tokens contains a hyphen, fails Composer's character validation when its configuration loads, and the exception prints the full token to stderr, so any workflow with such a token in Composer's auth hit it on the default path, including the auto-injected `GITHUB_TOKEN` ([Packagist, 2026-05-13](https://blog.packagist.com/composer-2-9-8-and-2-2-28-fix-github-actions-token-disclosure-in-error-messages/)). Personal access tokens are not part of the issue. Packagist's relevant permission point is that App tokens can carry permissions broader than the workflow's own `permissions:` declaration, not that every `GITHUB_TOKEN` can write workflow files ([Packagist, 2026-05-13](https://blog.packagist.com/composer-2-9-8-and-2-2-28-fix-github-actions-token-disclosure-in-error-messages/)).

The exposure was bounded: hosted-runner tokens usually expired with the failing job, self-hosted runner tokens stay valid for up to 24 hours and App tokens for up to an hour, and GitHub rolled the format change back on 2026-05-13 before planning a new rollout from 2026-05-18 ([Packagist, 2026-05-13](https://blog.packagist.com/composer-2-9-8-and-2-2-28-fix-github-actions-token-disclosure-in-error-messages/)). Neither the Packagist post nor the advisory mentions Mini Shai-Hulud or exploitation; the advisory rates the flaw High 7.5, fixed in 2.9.8, 2.2.28 and 1.10.28 ([Composer, 2026-05-13](https://github.com/composer/composer/security/advisories/GHSA-f9f8-rm49-7jv2)).
