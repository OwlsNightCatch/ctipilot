    ### Summary

PHP's session upload progress feature can write attacker-controlled data using one session serialization format and later read it using another. A mismatched decoder can interpret part of a session key as serialized object data. An application with a suitable object gadget chain can then execute code with the privileges of the PHP worker.

This is a configuration-dependent deserialization issue, separate from the stale global state vulnerability in CVE-2026-109619 ([GHSA-6wmf-4rv5-p3rp](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp)). Session upload progress was introduced in PHP 5.4.0, so older unsupported releases may also be affected.

### Details

The affected setup has the following conditions:

- Session upload progress is enabled, and an attacker can submit a multipart upload to a context using `php_binary` or `php_serialize` as its session serializer.
- A later or concurrent operation can access the same stored session, using the same session ID and the `php` serializer.
- For code execution, the reading application has a suitable deserialization gadget chain available.

The mismatch can arise when an application changes `session.serialize_handler` to `php` before calling `session_start()`. It can also arise between separate applications, pools, virtual hosts, or command-line processes with different fixed INI settings. With the `files` handler, this requires the same session storage directory, the same session ID, and permissions allowing both sides to access that file. Separate FPM pools do not automatically provide separate session storage. A runtime configuration change is not required, but workers using the same serializer do not create this mismatch.

During multipart processing, PHP appends the submitted `PHP_SESSION_UPLOAD_PROGRESS` value to an upload-progress session key and persists it. The `php` format separates each key from its serialized value with `|`. The other formats represent keys differently. If their output is read as `php`, an attacker-supplied delimiter can cause bytes inside the key to be passed to PHP's unserialization machinery.

Objects may be created and their deserialization or destruction callbacks invoked before trailing data causes the session decoder to reject the record. The 127-byte key limit in `php_binary` does not prevent payloads that span multiple session records.

### Impact

Successful exploitation can cause remote code execution, file modification, session corruption, or denial of service. The report includes command execution using a Guzzle object gadget on PHP 8.2.35, 8.3.36, 8.4.27, and 8.5.12. Command execution was also reproduced with a Monolog 2.11.1 gadget using a `php_serialize` writer and a `php` reader. Exploitability depends on the shared session configuration, access to the writing and reading paths, and the classes available to the reader.

An application that never changes its serializer at runtime can still be affected if another application or process writes incompatible data into the same session store.

### Affected versions

Session upload progress has been affected since it was introduced in PHP 5.4.0. The variant that uses a `php_serialize` writer requires PHP 5.5.4 or later. This is based on code inspection.

### Mitigation

Upgrade to the fixed release for your PHP branch when it becomes available. The fix disables session upload progress by default and rejects runtime changes to session settings, including `session.serialize_handler`, while upload progress is enabled. Keeping the feature disabled removes the upload-progress attack path described in this advisory. Check for existing configuration that explicitly enables it, because an explicit setting overrides the new default.

**If session upload progress is explicitly enabled in any application or pool, all readers and writers of the session data it can access must use the same `session.serialize_handler`, even after the update.** The fix does not enforce matching serializers across separate configurations.

For installations that need the feature, check the effective settings in php.ini, FPM pools, virtual hosts, application overrides, and command-line jobs. Isolate session storage when applications require different formats. When changing an existing store's format, migrate or expire its old records instead of reading them with the new serializer.

Otherwise, keep `session.upload_progress.enabled=0` in every configuration that can write to the affected session store. Set this administratively before request input is processed. Calling `ini_set()` from the application is too late. Do not rely on upload-progress cleanup to prevent a concurrent read.
