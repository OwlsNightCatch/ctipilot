    ### Summary

An attacker who can modify an OpenSSL-signed Phar archive without changing its trusted public key can make PHP accept arbitrary archive contents. The attacker changes the archive's signature type to a keyless hash such as SHA-256 and replaces the OpenSSL signature with a matching digest. Applications that execute the archive may then run attacker-controlled PHP code.

### Details

PHP stores an OpenSSL signature in the Phar archive, but obtains the verification key from a separate `<archive>.pubkey` file. For the native phar format, the archive controls the signature type through the four bytes before the `GBMB` magic. Tar- and zip-based phars control it through the first four bytes of `.phar/signature.bin`.

The verifier treats this type as authoritative when selecting the verification method. Only the OpenSSL signature types read and use `<archive>.pubkey`. MD5, SHA-1, SHA-256 and SHA-512 compare a digest that anyone can recompute. An attacker can therefore replace the archive contents and OpenSSL signature, select SHA-256 and satisfy `phar.require_hash=1` without possession of the private key. The trusted public key is not consulted.

Native, tar- and zip-based executable phars are affected. Explicitly signed tar- and zip-based `PharData` archives use the same verification path. This behaviour has been present since OpenSSL Phar signatures were introduced in PHP 5.3.0. The fix rejects a non-OpenSSL signature when an adjacent `.pubkey` file indicates that OpenSSL verification is expected. Archives without such a sidecar retain their existing signature behaviour.

### Impact

Exploitation requires the application to rely on an OpenSSL-signed Phar with a public key installed through a trusted channel, an attacker able to alter or replace the archive but not that public key, and the application subsequently loading the archive. Executing the modified archive can run attacker-controlled PHP code with the privileges of the affected process, compromising its data and availability.

The `.pubkey` file is PHP's external trust anchor and is not embedded or pinned in the Phar. If an attacker can also remove or replace it, they can already provide an archive signed with their own OpenSSL key. the fix does not protect that deployment. `phar.require_hash` alone provides corruption detection and does not authenticate keyless signatures.

### Affected versions

The affected code has been present since PHP 5.3.0. This is based on code inspection.

### Mitigation

Upgrade to the fixed release for your PHP branch when it becomes available. Obtain the publisher's public key through an authenticated channel and install it as `<archive>.pubkey` with permissions that prevent the archive update or download path from removing or replacing it. If the key cannot be protected independently, verify the archive using another mechanism that pins a trusted key before PHP loads it.
