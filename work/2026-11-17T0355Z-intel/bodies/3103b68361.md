# Poisoned Scripts on BBC, Zoom and Other Major Websites Linked to iPhone Exploit Loaders

Poisoned third-party JavaScript on major websites connects two threats: **browser-based financial theft and delivery of iPhone exploit-kit stages**. Hudson Rock recovered malicious Optimizely project files and a minute-ly loader. Additional evidence supplied by **Kirk from Ohey** extends the affected delivery infrastructure to Kissmetrics and StorifyMe and links the mobile branch to **Coruna and DarkSword**. [\[14\]](https://www.infostealers.com#hr-oj-source-14)

The scale of the websites matters: **BBC.com alone reports an average monthly audience of 149 million outside the UK.** That is audience context, not a count of affected visitors. The number of malicious page loads, successful thefts and compromised devices remains unknown. [\[5\]](https://www.infostealers.com#hr-oj-source-5)

## Four providers served poisoned code

**The confirmed compromise is malicious code inside responses served from third-party providers’ own script and widget endpoints.** The affected files are not simply innocent names appearing in a request’s initiator stack. Kirk’s expanded evidence records the response bytes, size and SHA-256 for 15 website captures, spanning 16 vendor responses. Hudson Rock independently matched those hashes to the supplied archive records and directly recovered nine poisoned vendor files. [\[14\]](https://www.infostealers.com#hr-oj-source-14)

In Optimizely’s case, the injection sits inside customer `projectJS` configurations, alongside legitimate experimentation code. Some versions use a plain loader, others encode the URL, and the BBC and HSBC UAE specimens embed a complete fallback payload. The code is not uniformly an identical line at the end of every customer file.

The shared responses and repeated injection establish a multi-customer delivery problem. They do not identify whether the original access involved provider infrastructure, publishing credentials, integrations or separate customer accounts. The evidence also does not establish a compromise of the named websites’ backend systems or every customer of these providers.

Hudson Rock also reviewed [Amirul Cyber’s OptimJack research](https://amirulcyber.com/2026/11/16/optimjack-optimizely-skimmer/). Its asset leads helped expand the original sample set. Kirk’s later response-body evidence strengthens the findings for several sites that the first version of this report treated as researcher-reported leads. In its November 5 report, updated November 6, Ohey documented a related router with C10 disabled and unavailable on the hosts checked. ## Blocking the attacker domain can leave the malware running

The BBC and HSBC UAE scripts contain more than a reference to an external file. Each embeds the same **24,392-byte malicious payload in Base64**, already present inside the Optimizely response.

The loader decodes that payload locally, then attempts to fetch remote `track.js`. If the request errors, or has not completed after **2.5 seconds**, it attempts to execute the embedded copy. A later check can retry retrieval through `fetch` and XMLHttpRequest when the expected execution marker is absent.

**A DNS or network block is useful, but it does not remove the poisoned trusted script.** It may stop requests to the blocked host while leaving local wallet-address substitution available from the embedded code. The separate iOS hosts are additional destinations. A site’s CSP may constrain execution paths, but containment should verify removal of the injected project code and the bytes delivered to visitors.

The live and embedded payloads are different variants. The live sample has additional request and function hooks, raw-format TON handling and a second iOS loading path. Their card-skimming module is byte-identical. The comparison establishes different capabilities, not a proven development chronology.

## Wallet substitution and card skimming accompany the mobile branch

The behavior below comes from Hudson Rock’s recovered live payload and decoded fallback. Their wallet and card modules are not restricted to desktop visitors; iOS detection adds secondary loading rather than replacing those modules.

### 1. Cryptocurrency address replacement

The script contains hardcoded replacement destinations for Ethereum/EVM-style addresses, Bitcoin, TRON, TON, Solana, Litecoin, Bitcoin Cash and Dogecoin. It recognizes address formats and validates checksums for several families before substituting the destination. EVM recognition is format-based, while Solana matching includes heuristics.

Its targets include visible text, input and textarea values, selected element attributes, links, copy events and clipboard API calls. The live variant also attempts to modify address-bearing strings in some request bodies, request URLs, navigation/history operations and sharing calls. Mutation observation and a **50 ms scan interval while the page is visible** help it revisit content that changes after load.

The effect can be a payment sent to a destination the attacker placed into the page or copied value. The code does not need to obtain a private key to attempt this diversion. In the recovered samples, we did not identify seed extraction, wallet-signing calls or a mechanism proving an automatic on-chain transfer.

Address replacement is not uniformly restricted to payment-related keywords. In the core text-replacement function, context affects whether an original address is recorded for collection; valid matches can still be replaced without that logging condition. URL processing has its own additional checks.

### 2. Payment-card skimming

The card module hooks form submissions and POST bodies sent through `fetch` and XMLHttpRequest. It can inspect JSON-like bodies, URL-encoded parameters and FormData for a card number, expiry and security code.

Before attempting transmission, it requires a recognized card-number prefix, a Luhn-valid number, an expiry matching its checks and a three- or four-digit CVV/CVC. It then attempts to send the complete tuple to `1688360[.]cc/card.php`, using `sendBeacon` when available.

```
card.php fields
n = card number
e = expiry
c = CVV / CVC
u = page URL
```
This is implemented card-skimming behavior, not evidence that every affected page presented a payment form or that a card was actually transmitted. The code does not demonstrate bypass of cross-origin hosted-payment-frame isolation. [\[12\]](https://www.infostealers.com#hr-oj-source-12)

### 3. Conditional cookie and page-image collection

A separate routine prepares a POST to `1688360[.]cc/hit.php` containing the page URL, JavaScript-readable cookies, recorded address matches and an optional JPEG rendering of the viewport. It uses `html2canvas`, requesting the helper from the attacker host if a usable instance is not already present.

**This path is conditional, not a beacon that runs for every visitor.** The screenshot routine requires recorded address matches, follows relevant visible changes and is guarded to run once per page. If rendering fails, the routine can attempt to send its other fields without an image.

The constructed fields include up to 500 characters of URL and 8,000 characters from `document.cookie`. A readable session cookie could therefore be included, but **HttpOnly cookie values remain unavailable to this JavaScript API**. We did not identify a localStorage extraction routine. [\[11\]](https://www.infostealers.com#hr-oj-source-11)

The image is a rendering of page content. It is not an operating-system screenshot and does not by itself show access to unrelated tabs or applications.

### 4. iOS-specific loading in the recovered variant

The live sample recognizes iPhone, iPad and iPod user agents and an iPad-style Macintosh/touch combination. It inserts two `boot.js` references with the `02111110` channel marker. A separate branch adds `JIUJIU888/weifile.html` when the parsed major/minor iOS version is 18.6 or below; patch versions are not distinguished by that check.

Hudson Rock’s initial direct requests received small *Site Unavailable* pages. Kirk’s later supplied captures show that other request conditions obtained router and entry-stage responses. An unavailable response in one retrieval is therefore not evidence that the downstream delivery was universally inactive.

**No mining implementation was identified in the recovered variants.** The SHA-256 code is used for cryptocurrency-address checksum validation. Its presence does not establish cryptocurrency mining.

A malicious file received at 21:00 and a different response received by another researcher at 21:10 can reflect an intervening change or different cache responses. Neither observation establishes the state of every edge cache, page or already-open browser session.

The early GitLab scan records delivery without a `card.php` or `hit.php` request. The later iOS-directed scans provide additional routing evidence. Delivery, completed response, exploit execution and data theft are separate findings and must not be treated as interchangeable.

## Remove the delivery code and investigate both forms of exposure

1. **Preserve and remove the affected third-party code.** Retain actual response bytes, hashes, headers, timestamps and project revisions before restoring or disabling the relevant project or resource. Inspect Optimizely `projectJS`, the affected Kissmetrics/StorifyMe endpoints and minute-ly’s loader where used. Verify what visitors actually receive after changes.
2. **Block both delivery paths and the observed downstream hosts.** Cover `1688360[.]cc`, `webshell[.]lol` and the current mobile-router indicators. Domain blocks are only one layer: the BBC and HSBC UAE specimens already contain a complete embedded payload.
3. **Preserve responses and network traces, not just the final page DOM.** The minute-ly specimen schedules removal of its own and related script elements after three seconds. Removing elements does not undo executed code, but it can make a later DOM-only inspection incomplete.
4. **Separate financial-theft exposure from mobile-stage delivery.** Hunt for `card.php` and `hit.php` POST attempts, boot/entry-stage requests and state/telemetry calls as separate events. An endpoint named `pe_ok` or a result parameter is not independent proof that privilege escalation occurred.
5. **Scope sensitive pages and device exposure individually.** Determine whether payment, login, account or other sensitive paths loaded the affected file during the relevant period. Check applicable browser/device versions and seek device-level forensic evidence if exploit exposure is suspected. Refresh affected software and follow verified vendor guidance. Invalidate exposed sessions or coordinate payment-data response where the evidence supports it.
6. **Investigate the publishing path.** Review project changes, publication history, account activity, API credentials and integrations with the relevant providers. Shared malicious output establishes the integrity problem; it does not by itself reveal how the attacker gained access.

For visitors, the relevant questions are which page was loaded, when, on which device, and what was entered or copied. Cryptocurrency payment destinations should be checked through an independent trusted view. An organization-specific exposure notice should guide any payment or session response; membership in a large customer population alone does not establish compromise.

**The new evidence changes the scope of the investigation.** This activity combines ordinary browser theft with delivery infrastructure associated with iPhone exploit kits. Containment must address the poisoned trusted scripts and both downstream delivery paths, while incident reporting keeps requested stages, executed code and confirmed losses distinct.

## What the combined evidence establishes

Hudson Rock retrieved JavaScript and supporting HTML as data, preserved bytes and SHA-256 hashes, decoded the embedded Base64 payload without evaluating it, compared variants and reviewed existing scan records. No malicious code was executed in Hudson Rock’s analysis, no new scan was submitted, and no collection endpoint was supplied victim data.

The expanded source is Kirk’s updated November 16 research note, supplied directly to Hudson Rock. It records 15 website captures containing 16 poisoned vendor responses. Hudson Rock independently corroborated all 16 recorded hashes and vendor URLs, and directly recovered the minute-ly loader in addition to the original eight Optimizely assets. For historical bodies unavailable in our retrieval, their code interpretation remains explicitly attributed to Kirk.

The two iOS-directed scan records also corroborate response hashes and route selection. URLScan’s Chrome engine makes these delivery tests, not real-device exploit validations. Kirk had not fully read the later DarkSword stages or decoded the Coruna module maps in the supplied account. The initial compromise mechanism, operator identity, visitor count and successful theft or device-compromise totals remain unresolved.
