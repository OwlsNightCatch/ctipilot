- CVE-2026-119618 is a critical remote code execution vulnerability in Apache HTTP Server mod\_http2 that impacts VMware Aria Operations/VMware Cloud Foundation Operations.
- This vulnerability and its impact on the mentioned VMware products are documented in the following VMware Security Advisory (VMSA), review this document before continuing: [VMSA-2026-0010](https://support.broadcom.com/web/ecx/support-content-notification/-/external/content/SecurityAdvisories/0/39625)

- VMware Aria Operations 8.18.x
- VMware Cloud Foundation Operations 9.x

- Note: Below steps do not need to be applied to Cloud Proxy nodes as they are not impacted

The script `cve-2026-119618-v2.sh`  performs the same activities as the manual mitigation on all nodes of a cluster from a single computer. The script can also be used to revert the workaround.

The script connects to each VCF Operations analytic node (primary, primary replica, data, witness) over SSH as root and works on the nodes one at a time. Nothing is copied to the nodes.

1. Log in to the VCF Operations Admin UI at  *`https://<primary-node-FQDN-or-IP>/admin`* and enable SSH for all nodes.
2. Download the script attached to the bottom of this article and SCP copy it to the `/root` directory on the VCF Operations primary node
   - Note**:** if you are unable to copy the script to the primary node, see the Additional Information section in this article for the requirements to run the script from an alternative computer.
3. Log in to the VCF Operations primary node as root via SSH or vSphere console
4. Check the cluster. Change `<node-IP-or-FQDN>` to the IP or FQDN of the primary node.
`bash /root/cve-2026-119618-v2.sh --check --node <node-IP-or-FQDN>` The script asks for the root password, then prints a summary for each node. (For unattended runs, provide the root password in the CVE\_ROOT\_PASSWORD environment variable.) Example output: ```
NODE               APACHE   CVE FIX  HTTP/2  ALPN      RESULT
##.##.##.##         2.4.68   no       on      h2        AFFECTED, run --apply
##.##.##.##         2.4.68   no       on      h2        AFFECTED, run --apply
##.##.##.##         2.4.68   no       on      h2        AFFECTED, run --apply
```
5. If any node shows `AFFECTED` in step 3, apply the workaround:
`bash /root/cve-2026-119618-v2.sh --apply --node <any-node-IP-or-FQDN>` Type *yes* to confirm. On each node the script backs up the configuration file, makes the necessary changes, runs httpd -t, restarts Apache and checks that HTTP/2 is no longer offered. The RESULT column must show workaround applied for every node.
Example output :
```
NODE              APACHE       CVE FIX    HTTP/2  ALPN             RESULT
##.##.##.##      2.4.66       no         off       http/1.1        workaround applied
##.##.##.##      2.4.66       no         off       http/1.1        workaround applied
##.##.##.##      2.4.66       no         off       http/1.1        workaround applied
```

`bash /root/cve-2026-119618-v2.sh --revert --node <any-node-IP-or-FQDN>`
- Note**:** --revert undoes only changes made by the script. If you applied the workaround manually, revert it manually.


1. Log in to each VCF Operations analytic node as `root` via SSH or vSphere console
2. Run the following commands: ```
httpd -v
rpm -q --changelog httpd | grep -i CVE-2026-119618
```
Possible results : 
   - Apache 2.4.71 or later: the fix is included. No change is required
   - Apache 2.4.70 or earlier, and the changelog mentions CVE-2026-119618: the fix was added to the older version without changing its number. No change is required
   - Apache 2.4.70 or earlier, and the changelog shows nothing: Environment is affected. Process with steps in Step 2.

Proceed with following steps on every Affected node, because each node runs its own Apache.

1. Log in to each affected node as root via SSH or vSphere console
2. Back up and open the file for editing ```
cp -p /usr/lib/vmware-vcopssuite/utilities/conf/vcops-photon-apache.conf /root/vcops-photon-apache.conf.bak
vi /usr/lib/vmware-vcopssuite/utilities/conf/vcops-photon-apache.conf
```
3. Press `i` to enter insert mode
4. Change these three lines (line numbers vary by version): Find Change to `LoadModule http2_module /usr/lib64/httpd/modules/mod_http2.so``#LoadModule http2_module /usr/lib64/httpd/modules/mod_http2.so``Protocols h2 h2c http/1.1``Protocols http/1.1``H2WindowSize 983025``#H2WindowSize 983025`
5. Press `Esc` to exit insert mode and then type `:wq` and press `Enter to save the changes.`
6. Test the configuration `httpd -t`
   - The output must be  **`Syntax OK`** . If that is the case, proceed restarting Apache (Step 7).
   - If it is not, do not restart Apache; instead proceed with restoring the backup. See the [Reverting the workaround](https://knowledge.broadcom.com/external/article/463005#revert-workaround) section.
7. Restart Apache (this briefly interrupts access on that node): `service httpd restart`
8. Verify `echo | openssl s_client -connect 127.0.0.1:443 -alpn h2,http/1.1 2>/dev/null | grep ALPN` Expected Output : "ALPN protocol: http/1.1"


To re-enable HTTP/2, restore the backup on each node where you applied the workaround, test the configuration and restart Apache:

1. Log in to each VCF Operations analytic node as `root` via SSH or vSphere console
2. Run the following commands: ```
cp -p /root/vcops-photon-apache.conf.bak /usr/lib/vmware-vcopssuite/utilities/conf/vcops-photon-apache.conf
httpd -t
service httpd restart
```


If the backup file is no longer available, undo the three changes made in the Manual Mitigation:

1. Open the file for editing`vi /usr/lib/vmware-vcopssuite/utilities/conf/vcops-photon-apache.conf`
2. press `i` to enter insert mode
3. Change these three lines (line numbers vary by version):Find Change to `#LoadModule http2_module /usr/lib64/httpd/modules/mod_http2.so``LoadModule http2_module /usr/lib64/httpd/modules/mod_http2.so``Protocols http/1.1``Protocols h2 h2c http/1.1``#H2WindowSize 983025``H2WindowSize 983025`
4. Press `Esc` to exit insert mode and then type `:wq` and press `Enter to save the changes.`
5. Run `httpd -t`
6. Restart Apache `service httpd restart`
7. Verify with the command from Step 2.4. It should print ALPN protocol: `h2`.

- Collectors, agents and the API are not affected.
- The UI may feel slower.

- Every upgrade also replaces the shipped vcops-photon-apache.conf, so HTTP/2 is re-enabled automatically, even if you disabled it before. After each upgrade, repeat the workaround on every node unil a future VCF Operations releases with an upgraded version of Apache that includes the fix for CVE-2026-119618.

| Exit Code | Description | 
|---|---|
| `0` | All nodes OK | 
| `1` | At least one node affected ( `--check`) | 
| `2` | Error | 

Script Options

| Option | Description | 
|---|---|
| `--check` | Report the state of each node. Read-only. This is the default. | 
| `--apply` | Disable HTTP/2 on each affected node. | 
| `--revert` | Undo the changes made by `--apply`. | 
| `--node HOST` | Any cluster node. The full node list is read from it. | 
| `--nodes H1,H2,...` | Use this list of nodes instead of reading it from the cluster. | 
| `--nodes-file FILE` | Read the node list from a file, one node per line. | 
| `--yes` | Do not ask for confirmation before `--apply` or `--revert`. | 

- Before changing anything, the script checks that every node is reachable. If a node fails this check, no node is changed.
- If httpd -t fails or Apache does not start, the script restores the backup on that node and stops. The remaining nodes are not changed.
- Running --apply again on a node where the workaround is already in place changes nothing.
- If a node cannot be reached over SSH during the run (for example, a mistyped password), the summary shows FAILED: SSH connection failed, node not changed and prints the command to re-run for the nodes that were not completed.
- Backups are saved on each node as /root/vcops-photon-apache.conf.bak-CVE-2026-119618-\<timestamp>. The script logs its actions on each node to /var/log/cve-2026-119618.log, and writes a local log to the directory you run it from.
- --revert undoes only changes made by the script. If you applied the workaround manually, revert it manually.
- After each upgrade, run --check again (see After upgrades).
- Tested on multi-node clusters of VMware Aria Operations 8.18.6 and VCF Operations 9.x

- A Linux or macOS machine with bash and OpenSSH. With OpenSSH older than 8.4, also install sshpass (for example apt install sshpass); otherwise ssh asks for the root password once per node.
- SSH enabled on every cluster node, and port 22 reachable from that machine.
- The root password of the nodes (the same on all nodes), or SSH key access as root.
- The node FQDNs must resolve from that machine. If they do not, list the node IPs with --nodes.
