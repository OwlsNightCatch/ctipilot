## 1.6 Workaround text (verbatim from the GHSAs, chain steps)

- Step 4 (GHSA-hgm3-wq4h-8vvq): "Remove `rememberme` from the web filter chain (**Security > Authentication**, filter chain `web`)." / "Otherwise change the key in `security/config.xml` to a long random value, and protect the data directory from disclosure." / "Changing the key in `security/config.xml` does not help when the same file disclosure also reveals the key." / "If you suspect exposure, change administrator passwords."
- Step 2 (GHSA-rv5g-g2r9-58rj): "Block requests whose `service` parameter contains `/`, in the query string or in the `service` attribute of an XML request, at a proxy in front of GeoServer." / "Review the data directory `wfs/query` and `workspaces/*/wfs/query` folders for stored queries you did not create."
- Step 3 (GHSA-39mw-5chv-jh47): "Restrict or disable the WFS service for anonymous users using service security, or disable WFS if it is not required."
- Step 1 (GHSA-4v26-c537-jvxc): "None needed beyond upgrading; the path alone gives no access."
- Step 5 (GHSA-9wf2-fcgq-vxhq): "Limit administrator access to trusted users, and restrict access to the REST API `/rest/resource` and `/rest/security` endpoints to trusted networks."
- CVE-2025-53607: "There is no configuration workaround, upgrade to a patched release." / "Blocking outgoing connections from the GeoServer host prevents the attacker's schema from being fetched."
- Other rows: WPS VRT `GDAL_SKIP=VRT` or remove GDAL extension; printing: remove the `!legends` block; OGC API Styles: add `styles.addStyle=ROLE_ADMINISTRATOR` (and four sibling rules) or remove the module; GeoFence/ACL: overwrite `X-Forwarded-For` at the proxy and do not allow direct access.
- Post-fix operator effects stated by the project: the fixed releases use a random per-node remember-me key and invalidate existing remember-me cookies on upgrade, a cluster sets `GEOSERVER_REMEMBERME_KEY`; X-Forwarded-For is honoured only from proxies listed in `GEOSERVER_TRUSTED_PROXIES`; OGC API Styles management is off by default after the fix; JDBC services accept only known drivers and parameters.
- The 2.27 line is end-of-life; the 2.27.7 announcement says "Please apply this update as a mitigation measure only, and plan to upgrade to a stable or maintenance release of GeoServer." The project post says "Please upgrade to a supported release at least once a year to continue receiving security fixes."

## 2.5 Default state, port, Cloud: what the sources do and do not establish

- **Splunk's advisory never says the empty secret is the default.** Its wording is conditional: CVE-2026-76535 "Splunk Enterprise accepts an empty shared secret when it authenticates RapidDiag task-collection requests" with the workaround "Turn off requests authenticated with an empty shared secret by setting `pass4SymmKey = <non-empty value>` ... if you do not use an empty shared secret". CVE-2026-76536 "accepts the empty clustering shared secret as a shared-authentication candidate on a standalone instance when clustering is turned off".
- **Indirect evidence the vulnerable state is the unconfigured state (reading by this analyst, not a Splunk statement):** the server.conf reference (10.6.0) says of the `[clustering]` stanza key "No default." and that Splunk falls back to `[general]` when it is unset; the pass4SymmKey doc says the key is something an administrator sets per service and gives a minimum length of 12. Together with CVE-2026-76536 being scoped to a standalone instance with clustering turned off (the state of any instance that never configured clustering), an instance that was never given a secret is the exposed case. CVE-2026-131190 goes further and calls the RapidDiag-accepted key "a factory-default shared key". Whether a stock install ships with an empty value in the effective `[clustering]`/`[general]` configuration is **not demonstrated by any fetched primary**; it is checkable on the instance (the effective value of `pass4SymmKey` and its source file) and the entry should say "check", not "default vulnerable".
- **Standalone vs clustered:** CVE-2026-76536 and CVE-2026-131192 are described for standalone instances (and, for 131192, a search head that is not an indexer-cluster member); CVE-2026-76535 and CVE-2026-131190 are described without a deployment-mode qualifier. A properly configured cluster that sets a non-empty secret is not stated to be affected; none of the texts says a clustered instance is vulnerable only when the secret is empty, but all the described mechanisms are "accepts an empty/default key".
- **RapidDiag:** per the 9.3 documentation page, "The RapidDiag app is included with Splunk Enterprise 8.1.1 and later." and "The RapidDiag app is available on Linux-based Splunk Enterprise installations only." (documentation statement; the advisory itself does not state a platform limit).
- **Port and endpoints:** the advisory names REST API endpoints (cluster configuration REST endpoint; RapidDiag task collection; "the Representational State Transfer (REST) API") and **never names a port**. The splunkd management port is 8089 over HTTPS per Splunk's REST documentation (the page fetched is the 7.3.2 version; the convention is long-standing but this page is old). The advisory says nothing about internet exposure.
- **Splunk Cloud:** the advisory states no Cloud Platform impact and no Cloud remediation. Splunk's Cloud REST documentation says "Splunk Support opens port 8089 for REST access." on request and restricts REST users to the search tier. This supports "port 8089 is not open by default on Cloud" but is not a statement about these CVEs; treat Cloud as not addressed.
- **Workarounds differ per CVE:** 76535 → non-empty `pass4SymmKey` in `server.conf` (stanza not named; same value on each participating node; restart). 76536 → strong unique `pass4SymmKey`, at least 12 characters, in the `[clustering]` stanza including standalone instances, `etc/system/local/server.conf`, restart. 131192 → strong `pass4SymmKey` under `[clustering]`. **131190 → "Turn off or remove the RapidDiag app."** (a `pass4SymmKey` is not offered for it, consistent with a hard-coded key). 131196, 76545, 131189: "None".
