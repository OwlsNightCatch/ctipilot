    OVHcloud CLI: release binaries of already-published versions were replaced on 2026-10-19 with a build that steals secrets from disk, uploaded through a developer's GitHub account

    OVHcloud's founder says a hacker used the GitHub account of one of its developers to add to the official command-line tool's releases a binary whose job is to retrieve secrets from the disk, that versions v0.11.0 to v0.15.0 are compromised, and that v0.10.0 and v0.16.0 are clean (Octave Klaba, 2026-10-19). A user whose CI pins a SHA-256 reported on GitHub that the assets of v0.13.0 to v0.15.0 were replaced between about 12:47 and 13:12 UTC, weeks after publication, by an uploader who is not a public member of the ovh organisation, with a local build of a later commit that has uncommitted changes and no release version flag, while the v0.15.0 tag and the Go module proxy still point at the original commit (GitHub issue #300, 2026-10-19). An OVHcloud maintainer replied that all the binaries involved were deleted at 16:21 (GMT+2) and that v0.16.0, with a signed tag, is an immutable release (GitHub issue #300, 2026-10-19). OpenSourceMalware, working from GitHub's server-side records, says no tag was pushed and no release workflow ran, ties the same account's earlier force-pushes carrying a hidden loader (from 2026-03-05) to the GlassWorm campaign while saying that whether the same actor did both is its inference, notes that the project's release tooling replaces existing assets as normal behaviour, and says it has not analysed the payload because the files were deleted before anyone archived them (OpenSourceMalware, 2026-10-19). OVHcloud's advisory gives the root cause: the account belongs to a developer who installed the editor extension color-picker-universal 2.8.91 on a personal MacBook on 2025-10-20, and the releases were replaced with stolen keys, not from that laptop; the malicious assets were online for 1h33 and downloaded about 250 times (OVHcloud, 2026-10-20). Whether any secret was stolen is not public.

    Exposure
    OVHcloud says only users who installed or updated the tool between 14:47 and 16:21 (UTC+2) on 2026-10-19, which is 12:47 to 14:21 UTC, are affected, and that a v0.11.0 to v0.15.0 download from before that day is not (OVHcloud, 2026-10-20); OpenSourceMalware reads the channels as macOS, Linux (x86_64, arm64) or Windows (x86_64) through the install script, the Homebrew cask, a direct download of a v0.11.0 to v0.15.0 asset or a CI step that fetches the release tarball, and says go install, builds from source and the vendor's Docker image were not affected (OpenSourceMalware, 2026-10-19).
    Detection
    An archive whose SHA-256 differs from the original release's for an unchanged version number, which is how the reporter caught it; release-API records of weeks-old assets replaced by an uploader who is not the original publisher; and, on a retained binary, build metadata showing a modified working tree and no release version (GitHub issue #300, 2026-10-19). OVHcloud says each run of the malicious binary leaves a working folder named envchecker followed by digits in the temporary directory and never deletes it, so its presence on a host that ran the tool shows exposure; the stealer reads the databases and histories of AI coding assistants and agents (VS Code, Cursor, Continue, Sourcegraph Cody, OpenCode, Hermes, Claude) as well as cloud, Kubernetes, Terraform, npm, SSH and Git credentials, and exfiltrates through Solana RPC calls and an upload endpoint (OVHcloud, 2026-10-20). Deleting the binary does not undo a run: OVHcloud says to change all the secrets on the disk (Octave Klaba, 2026-10-19).

    Triage: a replaced asset alone is not proof, since the project's release tooling replaces assets routinely; the discriminators are an uploader who is not the original publisher, a modified-tree build without the release version, and a digest that changed without a version bump (OpenSourceMalware, 2026-10-19; GitHub issue #300, 2026-10-19).

    Defender takeaway
    A host that installed or updated the tool from a release asset between 12:47 and 14:21 UTC on 2026-10-19, the window as OpenSourceMalware reads it (OpenSourceMalware, 2026-10-19), needs its secrets rotated, not just the binary removed (Octave Klaba, 2026-10-19), and then v0.16.0 or later (GitHub issue #300, 2026-10-19); pinning release digests or building from the source tag, as the reporter did, is the durable lever against a swapped asset on a mutable release.

Daily CyberSecurity reports that F5 has confirmed no public proof of concept for any of the three, and no exploitation is reported (Daily CyberSecurity, 2026-10-14). The other two are CVE-2026-95101 (with HTTP/3, part of an unknown frame might be treated as the request body, bypassing client_max_body_size or injecting data into the proxied request) and CVE-2026-97629 (with TLS session ticket key rotation, one key was left uninitialised, which might allow forging a session) (nginx.org change log, 2026-10-14); nginx.org rates all five medium (nginx.org, 2026-10-14).

    Exposure
    Nginx 0.1.29 to 1.31.6 depending on the flaw, with branches older than 1.30 outside the range of CVE-2026-93479, and NGINX Plus R33 to R36 and 37.0.0 to 37.1.0 for the first two (nginx.org, 2026-10-14; Centre for Cybersecurity Belgium, 2026-10-19).     ROUTINENATOA2

    BACS publishes five security classes for authentication methods: static secrets should in principle no longer be used, and only session-bound methods resist real-time phishing

    BACS published on 2026-10-19 the technology assessment "Sicherheitsklassen für Authentifikationsverfahren, -mittel und -dienste", which sorts authentication methods, tokens and services into the three classes tief (low), mittel (medium) and hoch (high), with mittel and hoch each split further, five classes in all (BACS, 2026-10-19). The scheme follows the NIST authentication assurance levels 1 to 3 with slight adjustments and extends them for resistance to real-time phishing; BACS says the classification gives no basis for formal testing or certification and can serve organisations as a basis for security requirements and recommendations (BACS, 2026-10-19). In the assessment, class tief covers any method whose authentication information is static and identical at every login, such as a password or a cryptographic key, and the class does not rise when the secret travels over TLS; BACS concludes that methods in this class should in principle no longer be used (BACS, 2026-10-19). Class mittel needs authentication information generated anew for each login plus at least one further security feature, and the starred variant additionally needs session binding, which ties the session cryptographically to the authentication information or to the device, network or application; the assessment names TLS channel binding, Device Bound Session Credentials and OAuth DPoP as examples, against session hijacking, real-time phishing and adversary-in-the-middle attacks (BACS, 2026-10-19). BACS says the difference between mittel and hoch lies mainly in the use of additional hardware to store the cryptographic keys (BACS, 2026-10-19). Its annex of examples places a password, a static API key and a secret held in a cookie such as a session ID in tief; a password with an SMS code, a software authenticator app, Kerberos tickets, bearer tokens (SAML, OIDC, OAuth, JWT) and synced passkeys in mittel, the passkeys starred; and hardware OTP tokens, hardware certificates in TLS and FIDO2 without synchronisation or key export in hoch, with a footnote that SMS verification should be used only where no better alternative exists (BACS, 2026-10-19).

    Defender takeaway
    The classification binds no one and sets no deadline; it is a rough guideline (BACS's own term) that cantonal and communal bodies can use when writing authentication requirements. A login that rests on a static secret is class tief, which BACS says should in principle no longer be used, and a login resists real-time phishing and session hijacking only where it is session-bound (the starred classes) (BACS, 2026-10-19).
