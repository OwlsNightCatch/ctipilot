    NOTABLECVE-2021-33044 +1exploitedNATOA2

    Dahua cameras and recorders: CERT-UA warns that attackers take devices over through the Easy4IP cloud relay even when no port is exposed, then view video, change configuration and add accounts

    CERT-UA's alert (CERT-UA, 2026-10-23; dated 2026-10-23 by Security Affairs, 2026-10-27) reports recorded compromises of Dahua IP cameras and DVRs in which attackers had the video stream, changed the device configuration and created accounts of their own (The Hacker News, 2026-10-27). The main vector is Easy4IP, Dahua's peer-to-peer remote-access feature: a device with it enabled opens an outbound connection to Dahua's cloud and registers by serial number, and access then runs through the cloud, bypassing NAT and firewall, with no published port and no public address (CERT-UA, 2026-10-23; Security Affairs, 2026-10-27). Serial numbers follow a predictable pattern, a 10-character model prefix and a five-character hexadecimal counter that rises almost sequentially, so attackers can guess them at scale and learn which devices are cloud-connected without hitting rate limits (The Hacker News, 2026-10-27). Authentication is then beaten with weak or known passwords or with the authentication-bypass flaws CVE-2021-33044 and CVE-2021-33045 in outdated firmware, which CISA added to its Known Exploited Vulnerabilities catalogue on 2024-08-21, although their use in the October cases remains unconfirmed (eSecurity Planet, 2026-10-27). Dahua fixed both in 2021 with model-specific firmware builds and rates them CVSS 8.1 (Dahua, 2021-11-15). CERT-UA does not say who was targeted, how many devices are affected or who is behind the activity (The Hacker News, 2026-10-27).

    The Hacker News says the activity shares similarities with Hunt.io's earlier Operation CameraSwarm, which reported more than 14,530 Dahua cameras compromised between 2026-06-17 and 2026-07-22 with brute-forced credentials and the same two-flaw chain, nearly 2,000 of them given a backdoor account that survives a password change and, on most firmware, a factory reset (The Hacker News, 2026-10-27); eSecurity Planet says no connection to the October incidents has been established (eSecurity Planet, 2026-10-27). Dutch intelligence services warned in July that Russian state actors compromise IP cameras to collect intelligence on military transports (The Hacker News, 2026-10-27).

    Exposure
    Any Dahua IP camera, NVR or DVR with Easy4IP enabled, whether or not it has a public address; CERT-UA warns that such devices may be vulnerable even when they cannot be reached directly from the internet (Security Affairs, 2026-10-27).
    Detection
    In each device's audit log, DVRIP authentication events from the local address 127.0.0.1, which CERT-UA reads as a sign of access through the P2P cloud, plus accounts nobody created and unauthorized configuration changes; text overlaid on the video image is another sign, but its absence proves nothing (The Hacker News, 2026-10-27; Security Affairs, 2026-10-27).

    Triage: a login from 127.0.0.1 shows only that the session arrived through the P2P relay, so where staff or an installer legitimately use Easy4IP it is normal; the account name, the time and the configuration change that follows separate the two.

    Defender takeaway
    Turn Easy4IP off wherever it is not needed, keep cameras off the internet and reach them through a VPN limited to authorized addresses, review the account list and the cloud accounts linked to each device, and update the firmware by hand, CERT-UA's four steps (CERT-UA, 2026-10-23; Security Affairs, 2026-10-27); check all Dahua devices on the network, forgotten ones included (Security Affairs, 2026-10-27), and do not count on a password on outdated firmware, since those flaws make knowing it unnecessary (CERT-UA, 2026-10-23).

    ROUTINENATOB2

    NIK C2: Talos documents a Go Windows implant that sends operator prompts to the OpenAI API from the infected host and falls back to the victim's own API key

    Cisco Talos found a command-and-control framework it calls NIK C2, with a live server, whose 64-bit Go implant for Windows takes more than 52 commands: browser and Wi-Fi credential theft, keylogging, screen, camera, microphone and clipboard capture, hidden VNC, RDP session interaction, an embedded SOCKS5 and HTTP proxy with a reverse tunnel for lateral movement, AMSI patching, UAC bypass and process hollowing (Cisco Talos, 2026-10-29). It talks to its server over TLS WebSockets on port 443 with an HTTP polling fallback about every 250 milliseconds under AES-256-GCM, persists through registry Run keys and COM hijacking, masquerades under a system-process name such as svchost.exe and runs a watchdog process (Cisco Talos, 2026-10-29). The new part is the ai_generate command: the implant builds an OpenAI Chat Completions request from an operator prompt on the infected host, posts it to OpenAI from the victim's address and returns the answer to the panel; if the operator gives no key it reads the OPENAI_API_KEY environment variable, so OpenAI charges the victim's payment method and its logs show the victim's key (Cisco Talos, 2026-10-29; Infosecurity Magazine, 2026-10-29). A screen-locking ransomware module encrypts no files: PowerShell copies the boot sector to a temporary file, and a looping batch file reopens a lock page shown through mshta.exe (Cisco Talos, 2026-10-29). Talos sees at least three implant versions and assesses with moderate confidence that the framework is functional; its post names no victims, sector or delivery method (Cisco Talos, 2026-10-29).

    Exposure
    Windows hosts; the post gives no initial-access method, so exposure cannot be read from an estate's configuration. A host that holds an OPENAI_API_KEY in its environment lends that key to the operator.
    Detection
    In egress and proxy telemetry, requests to the OpenAI API from a process that is not a sanctioned AI client, in particular a process named like a system binary such as svchost.exe that runs from the user's Roaming Microsoft Network folder, the install location the post describes; in process and registry telemetry, the fodhelper.exe UAC-bypass pattern (a command written under the ms-settings shell key and removed within seconds), an AMSI patch in a PowerShell session and, from the lock-screen module, a Run key that launches a looping batch file (Cisco Talos, 2026-10-29); on the OpenAI side, usage or billing under a key the owner did not use.
    Defender takeaway
    Add the OpenAI API (and other LLM endpoints) to the list of destinations that only sanctioned clients may reach, and rotate any OpenAI key found on a host where this framework ran, because the implant bills and logs it as the victim's own.

    NOTABLECVE-2026-58882updatedNATOB2

    Android telephony ('SMS of Death'): one hidden WAP Push message crashes the phone process and drops calls, emergency calls included; fixed for Android 14 to 17 at the 2026-11-01 security patch level per Google's bulletin row for CVE-2026-58882, the identifier BleepingComputer gives; Android 12 and 13 stay exposed, public proof of concept

    A researcher who signs as Mark B published a working proof-of-concept app on 2026-10-29 for a zero-click remote denial of service in Android's telephony framework (smsofdeath.com, 2026-10-29). One malformed WAP Push data message to port 2948 makes WapPushOverSms.decodeWapPdu() cast a 64-bit header length to a signed 32-bit integer and allocate a negative-sized array; the uncaught NegativeArraySizeException kills the com.android.phone process, which drops active calls, emergency calls included, and cuts service for one to two seconds per message (smsofdeath.com, 2026-10-29). The poison message stays in the pending queue and is retried on every boot and on carrier redelivery: the researcher reports that about 20 messages leave a device unusable and that one Android 12 phone rebooted into recovery roughly every 90 seconds until the messages were deleted over ADB (smsofdeath.com, 2026-10-29). The crash reproduced on Android 12 to 16, on a Pixel 9 and on Samsung Galaxy and A-series phones (smsofdeath.com, 2026-10-29); Security Affairs restates the mechanism and the October fix for Android 14 to 17 (Security Affairs, 2026-11-01).

    Google's fix, titled "Fix remote DoS in decodeWapPdu", catches the exceptions the malformed messages trigger and deletes the malicious messages from the SMS database (BleepingComputer, 2026-10-31); per the researcher it shipped in the October 2026 update for Android 14 to 17, so Android 12 and 13 phones outside the update window run the same code unfixed (smsofdeath.com, 2026-10-29). Google's November 2026 bulletin lists CVE-2026-58882, the identifier BleepingComputer gives, as a critical denial of service in the System component fixed at the 2026-11-01 security patch level for Android 14, 15, 16, 16-qpr2 and 17 (Google, 2026-11-02; BleepingComputer, 2026-10-31). BleepingComputer adds that the fix is not listed in Google's October bulletin (BleepingComputer, 2026-10-31). The proof-of-concept app and its source are public (smsofdeath.com, 2026-10-29; BleepingComputer, 2026-10-31), and none of the sources reports use in the wild.

    Exposure
    Any Android phone below the 2026-11-01 security patch level, which Google names as the fix level of CVE-2026-58882, BleepingComputer's identifier for the flaw (Google, 2026-11-02), and Android 12 and 13 phones outside the security-update window, which receive no fix; the attack needs only the target's phone number (smsofdeath.com, 2026-10-29). The patch level in device-management inventory shows which handsets have the fix.
    Detection
    On managed handsets, repeated crashes of the com.android.phone process in the device log, with a NegativeArraySizeException raised in WapPushOverSms.decodeWapPdu, calls that end with disconnect cause CS_DEATH, and a phone that restarts into recovery about every 90 seconds (smsofdeath.com, 2026-10-29); the message never appears in the inbox and the sender is not shown, so the crash log is the only trace on the phone.

    Triage: a single telephony restart has many benign causes; a restart that recurs on every boot or on each carrier redelivery, with the exception above in the crash log, matches this flaw.

    Defender takeaway
    Move every managed Android handset to the 2026-11-01 security patch level or later, emergency-service and on-call staff first, and list for replacement the Android 12 and 13 phones outside the security-update window, which receive no fix and stay crashable by one message. A phone stuck in the loop should not be wiped from the recovery prompt: the researcher documents deleting the pending WAP Push rows over ADB from a computer, which avoids a factory reset (smsofdeath.com, 2026-10-29).

    Defender takeaway
