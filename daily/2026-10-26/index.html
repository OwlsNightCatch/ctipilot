    NOTABLENATOA2

    Japan's wave of personal-data theft from web systems: JPCERT/CC and NICT describe attackers who decompile the published Android app to find internal APIs, drop JSP web shells as .war files on application servers, and run AI penetration-testing platforms against exposed web applications and WSUS servers

    JPCERT/CC's alert of 2026-10-08, updated on 2026-10-23, says that around September 2026 Japanese organisations disclosed a run of personal-data leaks through unauthorised access, and singles out an attack type that may be increasing: systems the operator never expected strangers to reach, such as business-intelligence tools and staff-management systems, were hit alongside public apps (JPCERT/CC, 2026-10-23). It does not tie them to one method and groups them in five: per-target scanning for known flaws and exposed configuration and backup files; unauthorised calls to application management APIs; the Metabase SQL injection CVE-2026-72898; .war files carrying a JSP web shell that runs commands passed in query parameters, placed on application servers reachable from the public web server; and, added on 2026-10-23, attempts through AI penetration-testing platforms it names as Cairn, CyberStrikeAI and ARTEX, including against exposed WSUS servers (JPCERT/CC, 2026-10-23).

    In the API case the attackers analyse the published smartphone app to find endpoints and keys, then attack internal APIs the app screens cannot reach: changing user rights, creating accounts, toggling a header or sending malformed tokens to compare responses, and blind NoSQL injection to find account data; some use API keys stolen elsewhere (JPCERT/CC, 2026-10-23). NICT calls this an app-to-backend attack: the app need not be vulnerable, and backend authentication, authorisation or input-validation faults leak data (NICT, 2026-10-13). On attack servers JPCERT/CC found Android packages, reverse-engineering tools and a Python script that answers requests with HTTP 302 redirects and appears to have been used to test for server-side request forgery (JPCERT/CC Eyes, 2026-10-21).

    No source names an actor. JPCERT/CC says it confirmed that the attackers used AI to scan for known vulnerabilities and attack through APIs (JPCERT/CC Eyes, 2026-10-21), while Macnica could not confirm AI use (Recorded Future, 2026-10-22). API-attack access also arrives through Tor exit nodes and residential proxies (JPCERT/CC, 2026-10-23).

    Exposure
    An organisation that publishes a mobile app with a backend API, runs internet-facing web applications, or leaves BI tools, staff-management systems or WSUS servers reachable from the internet (JPCERT/CC, 2026-10-23); NICT asks operators to inventory public APIs and servers and check their access logs (NICT, 2026-10-13).
    Detection
    In API and web access logs, calls to internal or management endpoints from clients that never load the app screens, role-change and account-creation calls outside the admin console, one endpoint called in sequence with and without a header or with malformed tokens, blind NoSQL-injection-style probing of account lookups, and use of API keys extracted from the app; in web server telemetry, scans for exposed configuration and backup files and .war deployments to application servers (JPCERT/CC, 2026-10-23).

    Triage: the app's own User-Agent proves nothing, because JPCERT/CC saw attack requests carrying it; the endpoints called and the sequence (header toggling, malformed tokens, role changes) discriminate, and a TLS fingerprint that matches a generic Python client does not identify the attacker alone (JPCERT/CC, 2026-10-23).

    Defender takeaway
    Treat the published app package as public and test the backend for authorisation gaps on internal endpoints (IDOR and BOLA), server-side request forgery, remote code execution and SQL injection (NICT, 2026-10-13). JPCERT/CC's measures are per-endpoint and per-method access control including non-public APIs, expiring least-privilege API tokens with fast revocation, rate limits on login, password reset, SMS and search, no long-lived secrets in apps, and no management functions on the internet (JPCERT/CC, 2026-10-23; JPCERT/CC Eyes, 2026-10-21).

    NOTABLECVE-2026-111497 +3exploitedupdatedNATOA2

    CVE-2026-111497 / CVE-2026-70197, Microsoft .NET: an out-of-band release fixes a Brotli decoder flaw and delivers the Windows sockets fix that the 13 October update did not contain, in 8.0.33, 9.0.22 and 10.0.14 (CVSS 3.1 8.1)

    Microsoft released out-of-band security updates for .NET 8, .NET 9 and .NET 10, with .NET 11 Release Candidate 3, on 2026-10-25 (.NET Blog, 2026-10-25). .NET Framework is not affected (.NET Blog, 2026-10-25). CVE-2026-111497 is a buffer overflow in the Brotli decoder that .NET uses and may let an unauthenticated attacker read or corrupt process memory, leading to information disclosure, denial of service or elevation of privilege (.NET Blog, 2026-10-25); Microsoft scores it CVSS 3.1 8.1, marked it publicly disclosed and not exploited on 2026-10-25, and rates it Exploitation More Likely (MSRC, 2026-10-25). Node.js fixed the same CVE on 2026-10-21 (Node.js project, 2026-10-21). Microsoft says an application is exposed only if it decompresses attacker-controlled Brotli data through ASP.NET Core request decompression, HttpClient automatic response decompression that includes Brotli, or the BrotliStream and BrotliDecoder APIs, and that ASP.NET Core and HttpClient do not decompress Brotli by default (dotnet/announcements #494, 2026-10-25).

    The release also corrects two fixes of 2026-10-13: Microsoft says that release did not fully address CVE-2026-70197 and CVE-2026-102870 (.NET Blog, 2026-10-25). CVE-2026-70197 is a Windows-only out-of-bounds write: reusing one SocketAsyncEventArgs instance across IPv4 and IPv6 datagram sockets can keep an undersized cached native address buffer, and an unauthenticated attacker can then write out of bounds during ReceiveFromAsync (CVSS 3.1 8.1, high attack complexity) (dotnet/runtime #136445, 2026-10-25); the Security Update Guide rates it not exploited, not publicly disclosed and Exploitation Less Likely (MSRC, 2026-10-25). CVE-2026-102870 is code execution in the Blazor WebAssembly debugger when a developer evaluates an expression that involves attacker-controlled application data (CVSS 3.1 8.8, user interaction required); it needs the standalone Server and DevServer package references updated, because updating only the shared runtime is not a substitute (dotnet/announcements #492, 2026-10-25). CVE-2026-114148 is a local privilege escalation through incorrect file ownership in Linux tarballs (CVSS 3.1 7.8), affecting ASP.NET Core tarballs of .NET 8 and 9 and source-built tarballs of .NET 8 to 11 (dotnet/announcements #495, 2026-10-25). No source reports an attack on .NET, but CISA lists CVE-2026-111497 as exploited since 2026-10-27 (CISA, 2026-10-27).

    Exposure
    A framework-dependent host shows its runtime with dotnet --list-runtimes, which must list 8.0.33, 9.0.22 or 10.0.14; self-contained applications and container images carry their own runtime and must be checked per artifact (.NET Blog, 2026-10-25). The Brotli path is any code that enables request or response Brotli decompression or calls the Brotli APIs on untrusted data; CVE-2026-70197 needs Windows code that reuses one SocketAsyncEventArgs across IPv4 and IPv6 datagram sockets (dotnet/announcements #494, 2026-10-25; dotnet/runtime #136445, 2026-10-25).
    Detection
    No source describes an exploitation indicator. The telemetry that would show an attempt on the Brotli path is web access logs with a Brotli request content encoding on endpoints that decompress request bodies, followed by crashes of the hosting process.
    Defender takeaway
    Install the updated runtime on every .NET host, including Windows hosts patched on 2026-10-13, which still carry CVE-2026-70197 (.NET Blog, 2026-10-25), and treat the Brotli flaw as exploited, as CISA lists it (CISA, 2026-10-27). SDKs installed through Visual Studio update when Visual Studio itself is updated (dotnet/runtime #136445, 2026-10-25). Where an update has to wait, Microsoft advises avoiding decompression of attacker-controlled Brotli data: remove the br entry from an existing request decompression configuration or Brotli from an existing automatic decompression setting, and do not add decompression where an application does not already use it (dotnet/announcements #494, 2026-10-25).
