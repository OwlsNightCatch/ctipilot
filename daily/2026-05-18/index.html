    NOTABLEupdatedNATOB2

    THORChain vault drain, about $10.7M from one vault: a newly joined validator exploited GG20 threshold signing (Switzerland-based protocol)

    On 2026-05-15 an attacker drained about $10.7M from one of THORChain's five vaults, and the other four were unaffected (THORChain, 2026-05-20); THORChain's post-mortem of 2026-07-03 puts the loss at about $10M (THORChain, 2026-07-03). The Record reported one of six vaults and about $10.7M (The Record, 2026-05-15), and TRM Labs more than USD 11M across nine chains (TRM Labs, 2026-05-15). THORChain, a cross-chain liquidity protocol founded in 2018 and based in Switzerland, said initial indications were that user funds were safe and only protocol-owned funds were affected (The Record, 2026-05-15).

    THORChain confirmed on the evening of 2026-05-15 that the attack exploited its GG20 threshold-signature (TSS) implementation to leak key material progressively, and that the attacker was a node operator churned into the validator set two days earlier (THORChain, 2026-05-20). Its post-mortem describes the chain: at vault setup the attacker published a Paillier key built from several small primes instead of two large ones, which passed because the library only screened out a handful of tiny factors; it then deliberately failed the MTA step of signing 864 times over two and a half days, each failure looking like routine node flakiness while leaking a fragment of other validators' key shares, until it could sign outbound transactions alone (THORChain, 2026-07-03). Two further weaknesses made the leak deterministic, a range proof whose two halves were never tied together and a blinding value drawn from far too small a range; all three sat in THORChain's fork (v0.1.6) of Binance's tss-lib, which upstream had fixed as individually minor issues in v2.0.0 (August 2023) and v3.0.0 (2024) (THORChain, 2026-07-03). THORChain says only the Paillier-modulus condition matches public research, the class documented in 2023 as BitForge and TSSHOCK (THORChain, 2026-07-03); the 2023 disclosures include Fireblocks' CVE-2023-33241 on unchecked Paillier moduli (Fireblocks, 2023-08-09) and Verichains' TSSHOCK attacks on threshold-signing proofs and their encoding (Verichains, 2023-08-10).

    The solvency checker halted signing and trading on several chains within about 52 minutes, but only after the funds had left, because the attacker signed with the reconstructed key (THORChain, 2026-05-20). Chainalysis traced attacker-linked funds through Monero, Hyperliquid and Arbitrum from late April, including the ETH that bonded the malicious validator, CryptoTimes reports (CryptoTimes, 2026-05-17). TRM Labs had not attributed the theft to any actor as of 2026-05-15, while calling THORChain the bridge of choice for laundering North Korea's largest thefts (TRM Labs, 2026-05-15). Every validator has since upgraded to v3.19.1, and THORChain plans to replace GG20 with DKLS or Schnorr-based signing (THORChain, 2026-07-03).

    Exposure
    ECDSA threshold-signing deployments running GG20 code derived from Binance's tss-lib from before its v2.0.0 and v3.0.0 fixes, wherever a party that could be malicious joins the signing committee, which on THORChain is anyone who bonds a validator; EdDSA signing, as on Solana, is not exposed (THORChain, 2026-07-03).
    Detection
    Per-participant signing-protocol telemetry: THORChain names a single validator responsible for a disproportionate share of signing failures over a short period as the signal it missed, and is adding monitoring of key-sign failures per validator (THORChain, 2026-07-03). Balance-based solvency checks fire only after the funds move once the key has been rebuilt (THORChain, 2026-05-20).

    Triage: failed signing rounds are routine, since validators go offline or miss timing windows; the discriminator is the aggregate, one recently admitted participant failing the same signing step far more often than its peers over days (THORChain, 2026-07-03).

    Defender takeaway
    For any GG20 threshold-signing deployment built on tss-lib, confirm the library carries tss-lib's v2.0.0 and v3.0.0 fixes, including verification that each party's Paillier modulus is well formed, and alert on each participant's share of signing failures (THORChain, 2026-07-03). Organisations without threshold-signing infrastructure have no decision to make.

    CVE-2026-42897: Exchange OWA cross-site scripting exploited by TA488 with the OWAReaper implant; fixed since the June 2026 Security Update, which does not remove the mitigation

    CVE-2026-42897 is a cross-site scripting flaw in Outlook Web Access on Exchange Server 2016, 2019 and Subscription Edition; Microsoft scores it 8.1, marks it exploited (Microsoft Security Response Center, 2026-07-14), and CISA added it to its Known Exploited Vulnerabilities catalog on 2026-05-15 (CISA KEV catalog, 2026-05-15). Exchange Online is not affected (Microsoft Exchange Team Blog, 2026-05-14). Microsoft first protected on-premises servers with mitigation M2, a URL Rewrite configuration delivered by the Exchange Emergency Mitigation Service (Microsoft Learn). The EM service runs on Mailbox servers (installed with the September 2021 CU or later) and needs outbound HTTPS to officeclient.microsoft.com, which must also be excluded from SSL inspection; servers that cannot reach it never receive the mitigation, and Get-ExchangeServer | Format-List Name,MitigationsApplied shows what each server has applied (Microsoft Learn). A server running an Exchange Server build older than March 2023 cannot check for new mitigations at all (Microsoft Exchange Team Blog, 2026-05-14).

    The fix shipped in the June 2026 Security Update (Microsoft Exchange Team Blog, 2026-06-09), and Microsoft recommends the July 2026 Security Update, which also addresses the related CVE-2026-55008; installing either does not remove the earlier mitigation, which stays in place until administrators remove it by hand (Microsoft Exchange Team Blog, 2026-06-09) (Microsoft Exchange Team Blog, 2026-07-14) (Microsoft Security Response Center, 2026-07-14). From 2026-07-22 Proofpoint observed TA488 (Void Blizzard, LAUNDRY BEAR) exploiting the flaw against government, telecommunications, finance, hospitality and aerospace targets in the US and Europe with the OWAReaper implant, whose server-side persistence survives password resets and re-imaging (Proofpoint, 2026-07-29); the update below carries the detail.

    Exposure
    On-premises Exchange Server 2016, 2019 or Subscription Edition below the June 2026 Security Update; Exchange 2016 and 2019 receive fixes only through the Period 2 Extended Security Update programme (Microsoft Exchange Team Blog, 2026-07-14).
    Update31 Jul 2026 04:09 UTCrun 2026-07-31T0409Z-intelactionsaffected_productscvesentitiesevidencereferencesregionssectorssourcestagstechniquesbody

    CVE-2026-42897 was first an Exchange OWA flaw whose interim protection depended on the EM Service auto-mitigation. Two things changed. Proofpoint has now attributed in-the-wild exploitation to a named Russia-aligned actor and published the implant's full mechanics (Proofpoint, 2026-07-29), and the mitigation is no longer the remediation: the security updates are, with the mitigation now something Microsoft says administrators should remove (Microsoft Exchange Team Blog, 2026-07-14). NCSC-CH appended the Proofpoint reporting to its own advisory on 2026-07-30 (NCSC Switzerland, 2026-07-30).

    The actor is TA488 (also tracked as Void Blizzard and LAUNDRY BEAR), the Russia-aligned email-espionage actor behind the Zimbra campaign that Proofpoint documented in a joint release with the NSA (Proofpoint, 2026-07-29). Proofpoint assesses OWAReaper as an evolution of that campaign's ZimReaper payload, citing shared code including the same sized, invisible pop-up and highly similar error handling (Proofpoint, 2026-07-29). Campaign activity began 2026-07-22 against government, telecommunications, finance, hospitality and aerospace targets across the US and Europe, using deliberately banal lure subjects with no call to action; Proofpoint says the unusual breadth may have been intentional blending with bulk mail. Its stated infrastructure-creation date of March 2026 precedes Microsoft's May disclosure by two months, which is the basis for its assessment that zero-day use is feasible; that is an inference from infrastructure dating, not a confirmed finding.

    Execution. The flaw is a failure to sanitise HTML in the message body, so a loader script in an onload= handler reassembles a Base64 fragment from the rest of the message and evaluates it: no link click and no attachment open, only viewing the message in OWA. The exploit and payload fragments are hidden inside the message's social-media icon elements, with next-stage data placed after # fragment markers where the browser's Base64 image parser stops reading, so the payload is not visible to casual inspection of the HTML. On execution OWAReaper first rewrites the delivered message server-side to strip the exploit content and suppresses OWA pop-ups and right-click, then enumerates the victim's address, username and settings (Proofpoint, 2026-07-29).

    Credential and token theft. It creates two invisible input elements and waits for the browser's own autofill to populate them with the saved OWA username and password. Separately it enumerates installed Outlook add-ins holding ReadWriteMailbox permission and, where one exists, abuses it to call GetClientAccessToken and obtain OAuth tokens (Proofpoint, 2026-07-29).

    Persistence, in three independent layers. Client-side, the implant writes an encrypted copy of itself and a decryption wrapper into browser localStorage under a settings field of the legitimate PageDataPayload.OwaUserDefaultSettings key, which OWA itself evaluates during its own sync-restore flow, so every ordinary OWA tab-open re-launches it with no separate loader. A second client-side layer adds a hidden iframe to messages cached in OWA's offline IndexedDB store, so opening the cached message re-infects an endpoint even after a full re-image. The third is server-side and is the one that matters most: the implant calls UpdateFolder to grant Owner-level permission on every mail folder to the low-privilege "Default" preset alias that exists in every Exchange organisation. Proofpoint is explicit that this "requires deliberate removal from the Exchange server" and that credential rotation and re-imaging will not evict it (Proofpoint, 2026-07-29).

    Command and control. Two channels, both over infrastructure defenders generally trust. The implant polls GitHub's public Commit Search API every 24 hours for crafted commit messages containing the target's own email address, decrypting matches to a four-character command header that selects toolkit replacement, C2-domain rotation, or one-off code execution; in parallel it re-parses cached inbound messages every five minutes for the same command structure. Exfiltration runs primarily over HTTPS with encrypted URI paths, either relayed through a set of legitimate image-CDN domains or sent directly to the actor-controlled server when those proxies fail; if the HTTPS method fails altogether, the implant switches to DNS label tunnelling, packing the data into the subdomain labels of ordinary DNS queries for an actor-controlled domain. Notably, Proofpoint states there is no mass mailbox exfiltration here, unlike the Zimbra campaign, so the mapped behaviour is browser-session and credential access rather than bulk email collection (Proofpoint, 2026-07-29).

    Patching. The fix first shipped in the June 2026 Security Update (Microsoft Exchange Team Blog, 2026-06-09), and Microsoft now recommends the July 2026 Security Update, available as Exchange SE RTM publicly and for Exchange 2019 CU14/CU15 and Exchange 2016 CU23 only through the Period 2 Extended Security Update programme; organisations that were enrolled only in Period 1, which ended in April 2026 (Microsoft Exchange Team Blog, 2026-05-14), do not receive it (Microsoft Exchange Team Blog, 2026-07-14). Microsoft's own vulnerability record scores the flaw 8.1 and marks it exploited (Microsoft Security Response Center, 2026-07-14). Installing the update does not remove a previously applied mitigation: administrators who used the EM Service should remove the M2.1.0 IIS rules through the documented rollback, and those who ran the downloadable mitigation script should run its rollback (Microsoft Exchange Team Blog, 2026-07-14). The known operational side effects of the mitigation era (broken OWA calendar printing, inline-image rendering problems, OWA-light failing, and false-unhealthy calendar-proxy health alerts) are listed in the May post (Microsoft Exchange Team Blog, 2026-05-14), and the July post ties their clearing to installing the update and removing the mitigation (Microsoft Exchange Team Blog, 2026-07-14).

    Detection
    The highest-value signal is in mailbox audit and Exchange Web Services telemetry: a folder-permission change granting Owner rights to the "Default" alias, applied across many folders of one mailbox in quick succession. Client-side, monitor for writes to the OWA user-default-settings localStorage key outside the browser's own sync flow, and for OWA sessions in which invisible form inputs are created and immediately populated. On the network side, two egress patterns stand out from a mail client's normal behaviour: repeated polling of a public source-code hosting search API on a roughly daily cadence, and DNS queries with the label-length and entropy profile of tunnelled data.

    Triage: OWA legitimately reads and writes its own settings keys constantly, so the presence of localStorage activity is not the signal; the discriminator is the specific settings-field path carrying an encrypted blob, and its correlation with a message open. For the server-side artifact the discrimination is cleaner: administrators do grant folder permissions, but they grant them to named users or groups for a specific folder, not Owner rights to the built-in "Default" alias across an entire mailbox. Treat any such grant as compromise until proven otherwise.

    Defender takeaway
    For any on-premises Exchange estate, "we patched in May" is the wrong answer to this one: May shipped a mitigation, June shipped the fix, July is the recommended update, and neither update removes the mitigation, which comes off by hand afterwards. Because the actor's durable foothold is a mailbox permission rather than anything on the endpoint, an organisation that resets passwords and re-images the affected workstation can still be read, since Proofpoint says the grant needs deliberate removal from the Exchange server (Proofpoint, 2026-07-29); the folder-permission audit is the part that actually evicts them.

    HIGHupdatedNATOB2

    Tycoon 2FA after the March 2026 takedown: operators add OAuth device-code phishing against Microsoft 365 alongside the credential-relay kit

    eSentire's Threat Response Unit analyzed in late April 2026 a campaign by operators of the Tycoon 2FA phishing-as-a-service kit, which kept running after the March 2026 takedown led by Microsoft and Europol, that keeps the kit's in-browser tradecraft but ends in Microsoft's legitimate device-login flow instead of a credential-relay proxy (eSentire TRU, 2026-05-12). The device-code variant runs beside the relay kit: eSentire still names the OfficeHome AppId as the primary marker of the credential-relay variant and treats the two AppIds as one detection set (eSentire TRU, 2026-05-12), and BleepingComputer reports that the kit now supports device-code phishing (BleepingComputer, 2026-05-17).

    The lure, a forwarded vendor-invoice reminder, carries a Trustifi click-tracking URL whose clean-reputation domain launders the link, and Trustifi redirects to a throwaway Cloudflare Workers subdomain that returns an AES-GCM-encrypted page decrypted in the browser (eSentire TRU, 2026-05-12). The decrypted controller blanks the page for headless browsers and Burp, suppresses developer-tool shortcuts, redirects to microsoft.com when a debugger timing trap fires, checks the visitor's network owner against 230 cloud, sandbox, security-vendor, VPN and AI-crawler names, and stops rendering after a hardcoded expiry date (eSentire TRU, 2026-05-12). A Microsoft-branded fake CAPTCHA then queries a Tycoon 2FA Check Domain, which serves suspected analysts a benign decoy website and real victims a Microsoft 365 voicemail lure (eSentire TRU, 2026-05-12).

    The voicemail page displays a user code that the operator's backend obtained from Microsoft's device-code endpoint, copies it and opens microsoft.com/devicelogin; the victim signs in at login.microsoftonline.com, approves the MFA push and consents to Microsoft Authentication Broker, and Microsoft issues access and refresh tokens to the operator's polling client, after which the kit sends the victim to their real Outlook inbox (eSentire TRU, 2026-05-12). A victim already signed in sees no authentication step at all, only the consent prompt (eSentire TRU, 2026-05-12). Because the Broker is a Microsoft first-party application it does not trigger unverified-publisher OAuth detections, and its token can be exchanged for Exchange, Graph and OneDrive tokens without further interaction (eSentire TRU, 2026-05-12). The backend traffic still uses the CryptoJS AES-CBC layer with a hardcoded key and IV unchanged since eSentire's April 2025 analysis, which works as a kit fingerprint rather than protection, and the operators' token traffic came from Alibaba (US) hosting, which eSentire has seen across both kit variants since about 2026-04-10 in addition to the hosting providers documented before (eSentire TRU, 2026-05-12).

    Exposure
    Microsoft Entra ID tenants that allow the OAuth device-code flow for end users; the protocol does not bind the device that requested a code to the user, so anyone who starts a device-code grant for a Microsoft first-party AppId can collect tokens from any user who consents (eSentire TRU, 2026-05-12).
    Detection
    In Entra ID sign-in logs, successful device-code authentications (AuthenticationProtocol deviceCode, ResultType 0) from sources with no prior device-code activity, tokens issued to Microsoft Authentication Broker (AppId 29d9ed98-a469-4536-ade2-f981bc1d605e), and the user agents node or undici against that AppId in non-interactive sign-ins, with axios/1.x marking the credential-relay variant (eSentire TRU, 2026-05-12). After revocation, repeated ResultType 50173 events with those user agents against one account show the operator still trying (eSentire TRU, 2026-05-12). Revoking the session does not undo what the operator already set up: after a confirmed device-code phish eSentire revokes the refresh-token chain and reviews mailbox rules, OAuth consents and forwarding (eSentire TRU, 2026-05-12).

    Triage: a device-code sign-in alone can be a legitimate command-line tool or input-constrained device; eSentire's discriminators are a source with no prior device-code activity and Node.js user agents against the Broker AppId in non-interactive sign-ins, which it calls highly anomalous in production environments (eSentire TRU, 2026-05-12).

    Defender takeaway
    Block the device-code flow with Conditional Access for all users except documented exceptions: Microsoft recommends getting as close as possible to a unilateral block (Microsoft Learn), and eSentire calls it the single control that removes this attack class for affected users (eSentire TRU, 2026-05-12). eSentire adds admin consent for third-party applications, Continuous Access Evaluation and device-compliance requirements (eSentire TRU, 2026-05-12).
