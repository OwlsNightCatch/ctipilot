    COLD RELIC: Mandiant shows the FSB-linked group reusing data stolen from one US organisation as the impersonation pretext for the next, then holding cloud tenants through MFA push fatigue and enrolled passkeys, backup codes and MFA devices that survive password and session resets

    Mandiant reports a series of linked intrusions in which COLD RELIC, the name Google Threat Intelligence Group (GTIG) now uses for the group formerly tracked as COLDRIVER and UNC4057 (also Star Blizzard, Callisto and Gossamer Bear), turned data stolen in one US organisation into the pretext for the next (GTIG, 2026-11-17). GTIG cites a US Department of Justice assessment that the group operates within Russia's FSB and names government officials, defense contractors and NGOs in Europe and North America among its targets (GTIG, 2026-11-17). In 2026 the operators approached a second US organisation over an encrypted messaging app while impersonating an employee of the first, shared phishing links that stole Entra ID credentials and tokens and sent the victim on to document lures matching the conversation, and registered a new MFA device on the account (GTIG, 2026-11-17).

    In the late-2025 case the operators used the stolen credentials of a Super Admin account from a US residential proxy network close to the victim, pressed the user with MFA push notifications until one was accepted, registered a device model new to the tenant and kept access with passkeys, MFA backup codes and rogue MFA devices (GTIG, 2026-11-17). They took the whole cloud drive by mass sharing to an operator-run mailbox and by direct download, queried the admin investigation and email audit logs to check defensive visibility, viewed, modified and deleted Alert Center notifications, exported the employee list and ran a tenant-wide Customer Takeout export (GTIG, 2026-11-17). Access lasted several months through OAuth mail sync to an external client and re-authentication with enrolled passkeys that survived password and session resets, and in one case a password reset without revoking sessions did not evict the operators (GTIG, 2026-11-17). They searched for credentials, personnel data and .pst archives (GTIG, 2026-11-17).

    Exposure
    Google Workspace tenants, and Entra ID tenants that federate sign-in to Workspace as in the second case, whose privileged or staff accounts accept push, SMS or voice MFA or let users enrol passkeys, backup codes and devices without a second approval (GTIG, 2026-11-17).
    Detection
    In authentication logs, repeated failed logins or MFA challenges followed by a success from the same address, privileged sign-ins from residential-proxy networks that geolocate near the user, logins with a backup code, and new passkey or device registrations. In administrator audit logs, Customer Takeout creation, user-list downloads, audit-log investigation queries and Alert Center batch deletions. In Drive and OAuth logs, download spikes, external sharing to free mail providers, and authorisations of broad mail scopes to unapproved clients such as Thunderbird or Proton (GTIG, 2026-11-17). After a compromise, password changes alone are insufficient: revoke all sessions, refresh tokens and third-party OAuth permissions and remove unauthorised passkeys, backup codes and MFA devices (GTIG, 2026-11-17).

    Triage: a directory export, a Customer Takeout or a passkey or device enrolment by an administrator can be routine; the cues in GTIG's account are an unfamiliar device, a non-corporate or residential-proxy network, or an enrolment right after an MFA-fatigue pattern (GTIG, 2026-11-17).

    Defender takeaway
    Move administrators and exposed staff to FIDO2 or WebAuthn hardware keys, which GTIG says cannot be approved through fatigue or intercepted by reverse proxies, require existing-administrator or out-of-band approval for new MFA devices and passkeys, and write session and OAuth revocation into compromise playbooks (GTIG, 2026-11-17).

    NOTABLENATOB1

    Microsoft's agent-framework package on PyPI, versions 1.26.1 and 1.26.2 published on 2026-11-17, carried a credential stealer that a .pth startup hook runs every time Python starts, collecting environment secrets and requesting Azure managed-identity, Azure DevOps and GitHub Actions OIDC tokens; both versions were removed and 1.26.0 is the last clean release

    Socket reports that the Microsoft agent-framework PyPI package was compromised on 2026-11-17, in versions 1.26.1 and 1.26.2, both of which install Python startup hooks that collect credentials, environment data and cloud identity tokens and send them to a web endpoint (Socket, 2026-11-17). SafeDep, which flagged both releases independently, says the project is Microsoft's official metapackage, published under the microsoft account on PyPI, that 1.26.1 appeared at 20:35 UTC and 1.26.2 at 21:08 UTC, that each is a single wheel where earlier releases shipped a wheel and a source archive, and that both were removed from PyPI and 1.26.0 is the last clean release (SafeDep, 2026-11-18). The attacker published 1.26.2 after 1.26.1 was gone, so removing one version did not stop it, and how it obtained publishing access is not known (SafeDep, 2026-11-18).

    Nothing has to import the package: a .pth file runs on Python startup, imports a module and launches collection in a background process or thread, so a pip install in a CI job is enough (Socket, 2026-11-17; SafeDep, 2026-11-18). 1.26.1 routes through the package's own initializer, while 1.26.2 moves the payload to a new top-level module and restores the legitimate initializer byte for byte, so checking only the initializer misses it (Socket, 2026-11-17). The code matches environment variables by substring, such as TOKEN, SECRET, KEY and AZURE, reads other processes' environments and credential files for pip, npm, netrc, git, Docker, Hugging Face and Foundry, and actively requests fresh Azure managed-identity and Azure DevOps tokens, with GitHub Actions OIDC tokens added in 1.26.2; it compresses the result and posts it to a web endpoint and downloads no further code (Socket, 2026-11-17). There is no persistent on-disk marker, so fresh process trees can trigger collection again (Socket, 2026-11-17).

    Exposure
    Any developer machine, CI job or container that installed agent-framework 1.26.1 or 1.26.2 and then ran Python; lockfiles and requirements files show the installed version, and the last clean release is 1.26.0 (SafeDep, 2026-11-18).
    Detection
    Lockfiles and requirements files naming the two versions, and a .pth file added to site-packages by the package, looked for on disk without starting the environment's Python, because starting it runs the stealer again (SafeDep, 2026-11-18); outbound POSTs to a web-hook service from build and developer hosts; because the stealer requests identity tokens, review sign-in and activity logs for the managed identities and federated credentials the environment could use, from the install time onward (SafeDep, 2026-11-18).
    Defender takeaway
    Remove both versions, rotate every secret and federated identity a host or job could read, and pin agent-framework to a known clean version; Socket advises rotating potentially exposed credentials where either version was installed (Socket, 2026-11-17).

    RIKEN Fugaku and Rikyu supercomputers: an intruder entered the internal operational network through the internet-facing operating-status dashboard, planted malicious programs on internal servers and took users' stored SSH private keys and access keys, then tried them on other systems

    RIKEN's Center for Computational Science says that between 2026-11-10 and 2026-11-13 an external third party entered Fugaku's internal operational network through the publicly accessible web page that displays the supercomputer's operating status, and that the exact method is still under investigation (RIKEN, 2026-11-17). The intruder tampered with multiple internal servers, some of them with malicious programs, and took or may have taken files in users' home directories and user-authentication data, including credentials users had stored for connecting to other systems, such as SSH private keys and access keys; up to 4,222 Fugaku users and 375 Rikyu users are affected (RIKEN, 2026-11-17). RIKEN has confirmed that the intruder tried some of the obtained credentials against other systems and is checking whether damage or secondary misuse followed (RIKEN, 2026-11-17).

    RIKEN and the external provider that maintains the system began investigating suspicious network traffic on 2026-11-12, confirmed the access on 2026-11-13 and suspended Fugaku on 2026-11-14 (RIKEN, 2026-11-17). It replaced the administrative keys, invalidated the public keys all users use to log in and halted all running and queued jobs, and it names no actor; it says there is no evidence yet that research data was exfiltrated (RIKEN, 2026-11-17; BleepingComputer, 2026-11-17).

    Exposure
    A shared compute or research system whose operating-status page is reachable from the internet and sits on a network path to its internal operations servers, and whose users keep SSH private keys or cloud access keys in their home directories (RIKEN, 2026-11-17). Relevant to Swiss research and high-performance-computing operators as a transferable pattern of exposure.
    Detection
    Authentications to other systems with keys that belong to users of the affected host, arriving from unfamiliar addresses, and changes or unknown programs on the servers that run the system's operation; RIKEN's own reviews cover the network configuration and the rebuilding of compromised servers (RIKEN, 2026-11-17).
    Defender takeaway
    Treat every private key and access key stored on a compromised host as stolen: RIKEN asks users to revoke the matching public key at each external service where it is authorised and to generate a new pair, and to replace any other stored credential through the service concerned (RIKEN, 2026-11-17). A status page that is public should not give a route into the operations network.

    Barracuda's own account of a 44-hour intrusion into its cloud: a key given to an AI vendor and never retired, found in that vendor's compromised development environment, led an intruder across about ten cloud accounts to Kubernetes; notified Managed XDR customers must recreate their integration credentials

    Barracuda says the attacker did not break in but used a valid cloud access key that Barracuda had issued to a third-party vendor, a company working in AI, for an earlier project and had not retired when the work ended (Barracuda Blog, 2026-11-11). The key had been stored in a configuration file in the vendor's GitHub repository, which was exposed when the vendor's development environment was compromised (Barracuda Trust Center, 2026-11-13). The first call with the key came on 2026-11-01 at 04:33 UTC; within minutes the attacker was mapping what the key reached and reading stored secrets such as AWS access keys and Azure service principal secrets, and each secret opened the next system, from cloud accounts to a data analytics system, to a source-code access token and on to Kubernetes clusters (Barracuda Blog, 2026-11-11). In just under four hours on 2026-11-02 it pushed short-lived branches to a handful of repositories to trigger a build workflow written to print the build system's secrets into the job log, encoded so that log masking would not hide them, and its last recorded activity was at 23:31 UTC, about 10 cloud accounts and 44 hours after the start (Barracuda Blog, 2026-11-11).

    In a Kubernetes cluster the attacker deployed a container that mounted the underlying server's file system read-only, enough to harvest that server's credentials, and tried to create a new administrative cloud identity, which was blocked (Barracuda Blog, 2026-11-11). On servers where it had a shell, its commands searched for environment variables named WALLET, MNEMONIC, SEED and PRIV, Ethereum keystore files, extended private keys, seed phrase files and Kubernetes secrets with wallet-related names, and Barracuda calls the activity consistent with a financially motivated actor seeking cryptocurrency and reusable credentials (Barracuda Trust Center, 2026-11-13). Barracuda says the resource names, the sequence of activity and the credential and wallet hunting routines match ARTEX, which many groups use, so the match shows how the attacker operated, not who it was (Barracuda Blog, 2026-11-11).

    Exposure
    A system the attacker reached stores the credentials Barracuda Managed XDR uses to collect data from customers' connected systems such as Microsoft 365, Google Workspace and endpoint security platforms; only organisations using the API integration for Managed XDR Cloud or Monitored Endpoint are affected, and Barracuda notified those with potentially affected credentials (Barracuda Trust Center, 2026-11-13). Logging in that environment was not detailed enough to rule out access to the credentials (Barracuda Blog, 2026-11-11). Relevant as a supplier incident for any organisation whose monitoring runs on Managed XDR, and as a worked example of ARTEX-style cloud tradecraft.
    Detection
    In cloud control-plane audit logs, a long-lived key used by a non-vendor address, secret-store reads followed by use of those secrets in other accounts, resources named with the letter i followed by digits and no hyphen, short-lived branches in a handful of repositories that trigger a workflow, and container deployments that mount the node's file system (Barracuda Trust Center, 2026-11-13; Barracuda Blog, 2026-11-11).
    Defender takeaway
    A notified customer revokes and recreates its integration credentials and reviews connected-system activity since 2026-11-01 (Barracuda Trust Center, 2026-11-13). Barracuda's own lesson is to remove standing credentials, especially long-lived keys held by third parties (Barracuda Blog, 2026-11-11), and to expire vendor credentials when an engagement ends (Barracuda Trust Center, 2026-11-13).

    Java4Shell, CVE-2026-114938, OpenJDK 17.0.6 and later and Oracle Java SE on x86-64 CPUs with AVX-512 VBMI: a heap overflow in the Base64 decoder that its discoverer chains into pre-authentication code execution in Keycloak, Jira, Confluence, Artifactory, Jenkins and PingFederate; fixed in 17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1, GreyNoise reports exploitation attempts, none confirmed successful against its sensors (CVSS 3.1 8.1)

    Oracle's Critical Security Patch Update and the OpenJDK advisory of 2026-11-17 list CVE-2026-114938 in the hotspot compiler component, which Oracle rates CVSS 3.1 8.1 with high attack complexity (Oracle, 2026-11-17; OpenJDK, 2026-11-17). Calif, which found it, says HotSpot's x86-64 Base64 intrinsic, which uses AVX-512 VBMI instructions, calculates a negative output length for a short padded input and that length becomes a full 64-byte write that sends 62 bytes past the end of the array; only the landing position of the write is controllable, a misplaced write can crash the JVM (Calif, 2026-11-17). It scores the flaw CVSS 4.0 9.2 and reports pre-authentication code execution in the default configurations of Keycloak, Jira, Confluence, Artifactory, Jenkins and PingFederate, authenticated execution in several further server products, and a client-side path in which a Java program that opens a TLS connection to a malicious server is compromised (Calif, 2026-11-17). Tenable relays Immersive's claim of a working exploit with no release stated (Tenable, 2026-11-17).

    The flaw needs an x86-64 processor with AVX-512 VBMI and affects OpenJDK from 17.0.6 on, ARM64 hosts are not affected (Calif, 2026-11-17). CISA published an alert to patch immediately (CISA, 2026-11-17), and the NCSC.ch Cyber Security Hub says the published research demonstrates exploitation without establishing malicious exploitation (NCSC.ch, 2026-11-17); Talos has seen no exploitation in the wild yet and expects probing (Talos, 2026-11-18), while Tenable relays GreyNoise's report of exploitation attempts as of 2026-11-18, none confirmed successful against its sensors, and VulnCheck's statement that a working RCE exploit is available to its customers (Tenable, 2026-11-17).

    Exposure
    A Java 17, 21, 25 or 27 runtime, or the Java 8 performance build, at or below the affected builds (Oracle, 2026-11-17), BACS says to check that the running applications actually use the corrected Java version (BACS, 2026-11-18). The CPU must report the avx512f, avx512bw, avx512vbmi and bmi2 flags, which means Intel Ice Lake to Granite Rapids and AMD Zen 4 or newer (Upwind, 2026-11-17). Pre-authentication reach depends on the application decoding attacker-controlled Base64 with the basic or URL decoder of java.util.Base64 before it authenticates the caller (Upwind, 2026-11-17). Cisco's advisory (version 1.3) lists Secure Network Analytics and Secure Workload as affected and Catalyst Center, IOS XE and ISE as not (Cisco, 2026-11-20); Fortinet lists FortiOS, FortiProxy, FortiWeb and others as not impacted, dozens of products as under investigation and none as affected (Fortinet, 2026-11-18); BACS adds internal systems and supplier-run Java software, banking software among it (translated from German) (BACS, 2026-11-18).
    Detection
    Unexplained hs_err_pid crash logs on internet-facing Java applications, where the log may not name Base64 because the crash comes later (Equixly, 2026-11-17); child processes of the server and administrative activity on identity, build and artifact platforms follow from Calif's chains. In request and application logs, Upwind suggests Base64-alphabet tokens of 32 or more characters that end in = with a length not a multiple of 4, starting with Authorization headers, and bursts of IllegalArgumentException from java.util.Base64$Decoder or of restarts (Upwind, 2026-11-17). An update does not remove a compromise that has already happened (BACS, 2026-11-18).
    Defender takeaway
    Update and restart, internet-reachable and identity services first. Where an update waits, Calif gives two JVM options, -XX:-UseBASE64Intrinsics, which disables the hardware-accelerated Base64 path, or -XX:UseAVX=2 on x86-64 hosts only, because OpenJDK on ARM does not recognize it and fails to start (Calif, 2026-11-17).
