    BabidiGhost: a jailbroken Hermes-based AI agent run against more than 50 targets, mostly in Belgium, France and Switzerland, exported an insurer's customer database and 13 municipalities' archives through public flaws and exposures; MFA, IP allow-listing and server-side validation stopped it

    SOCRadar recovered the exposed home directory of a hijacked French staging server and reconstructs a nine-day operation, 2026-11-06 to 2026-11-14, in which a low-skill French-speaking operator, BabidiGhost, typed plain-language orders to a jailbroken Hermes-based AI agent that wrote the scanners, exploits and exfiltration scripts (SOCRadar, 2026-11-20). The agent targeted more than 50 organisations and datasets, mostly in Belgium, France and Switzerland; of 14 analysed in depth, two were breached and three partly breached; SOCRadar says every successful intrusion used an exposed, unpatched analytics tool, a readable secret, a weak password or an unauthenticated endpoint, with no zero-day (SOCRadar, 2026-11-20).

    An internet-facing, unpatched Metabase vulnerable to CVE-2023-38646 let the agent in; it then ran commands on the server beneath the dashboard, read cloud database credentials from the container environment, exported the customer database and planted a database trigger that relaunched its implant on every new record. A shared IT provider's storage-management interface was exposed to the internet and a weak administrator password opened it, giving 23 archives of about 8.6 GB from more than 13 municipalities and 10 other public bodies; SOCRadar says this one server drives Belgium's share of more than half of the targets and names no Swiss municipality. Against banks the agent mapped the attack surface through certificate logs and a sign-in error oracle confirmed 48 valid corporate accounts, while a crawler swept Swiss websites for IBANs, email addresses and phone numbers. TOTP second factors, an IP allow-list and server-side business validation stopped the same agent (SOCRadar, 2026-11-20).

    Its model API key was revoked on 2026-11-14, but a PowerShell beacon and a C# backdoor posing as a Windows Update service, persisted through scheduled tasks and a Run key, kept calling home until 2026-11-15, and stolen archives had gone out through Telegram (SOCRadar, 2026-11-20).

    ZATAZ reports that the BlackHatSect0r handle, whose toolchain SOCRadar says the agent runs, rents a jailbroken agent (ZATAZ, 2026-11-23) and offers a bank-phishing platform with templates for 81 banks in France, Belgium, Luxembourg and Switzerland, 28 of them Swiss including UBS, PostFinance and Raiffeisen; ZATAZ names no Swiss victim (ZATAZ, 2026-11-23).

    Exposure
    The gaps used were internet-facing analytics tools, storage-management interfaces at shared IT providers, unauthenticated API routes, sign-in flows that reveal whether an account exists and secrets readable from a web application's environment (SOCRadar, 2026-11-20).
    Detection
    Egress or proxy telemetry showing a server calling a model-provider API or the Telegram bot API without a business reason; on Windows, a Run key and scheduled tasks for a service posing as Windows Update, unexpected Defender exclusions and outbound TCP to port 8443; on PostgreSQL, triggers nobody created. SOCRadar's hunt window is 2026-11-05 to 2026-11-17, and revoking the model key did not remove deployed implants (SOCRadar, 2026-11-20).

    Triage: the Hermes Agent directory and its SOUL.md exist on every Hermes installation; they matter only when SOUL.md carries the jailbreak strings SOCRadar's rule matches (SOCRadar, 2026-11-20).

    Defender takeaway
    Patch Metabase and take analytics tools, storage-management interfaces and unauthenticated API routes off the internet, keep secrets out of runtime environments, and verify the controls that stopped the agent (TOTP, IP allow-listing, server-side validation) at the shared IT providers that hold municipal data (SOCRadar, 2026-11-20).

    Azure API Management Classic: a flaw let an unknown actor take secrets, named values and tokens from APIM instances; Norway's NSM names Equinor and Skagerak Energi among those hit and tells every APIM user to treat secrets as exposed and rotate them after Microsoft's 2026-11-19 mitigation

    Norway's National Security Authority (NSM) said on 2026-11-20, in a post updated on 2026-11-23, that an unknown actor has actively gone after access tokens, secrets and named values in Azure API Management (APIM), that Equinor and Skagerak Energi are among the organisations hit, and that the flaw also affects several sectors in Norway and beyond its borders (translated from Norwegian) (NSM, 2026-11-20). NSM says it is still uncertain how widely the flaw has been and is being exploited, and that it has no indication so far that compromises or attempts have affected deliveries at Norwegian organisations (translated from Norwegian) (NSM, 2026-11-20).

    Microsoft's customer notice, read by SecurityWeek, says Microsoft discovered the issue on 2026-11-18 and closed the access path the next day, and that an unauthorized party could have used it to reach secrets stored in Azure API Management Classic instances before Microsoft identified the issue; exposed data can include secrets stored as named values, client secrets for identity providers, subscription keys and tokens for APIM's direct management APIs, and instances on the v2 tiers are not affected (SecurityWeek, 2026-11-23). SecurityWeek adds that Microsoft noted Classic tiers that do not follow its documented security guidance are affected (SecurityWeek, 2026-11-23). Equinor reported its attack on 2026-11-17, said on 2026-11-19 that it did not appear to target Equinor specifically and on 2026-11-20 that the attack had been stopped (Equinor, 2026-11-20); Skagerak Energi reported a possible attempted attack on 2026-11-18 and said operations and production were not affected and there was no indication that information had left (Skagerak Energi, 2026-11-18). No source says how the flaw works, who the actor is or how many tenants lost secrets.

    NSM tells every APIM user to assume that secrets and named values are exposed and to rotate all tokens and secrets, to map what sits behind each instance to judge the potential scope, and to check whether the instance has been updated (translated from Norwegian) (NSM, 2026-11-20).

    Exposure
    NSM's guide reads the RuntimeVersion from the gateway's internal-status page: 0.52.x is patched from build 31936, 0.53.x from build 31938, lower numbers are still vulnerable, and patterns such as 0.53.4608.0 are v2 or Consumption tier and not vulnerable; an organisation whose instance is not updated is asked to contact the vendor, and one that sees signs of compromise to contact NSM (translated from Norwegian) (NSM, 2026-11-20).
    Detection
    An independent practitioner's hunting map, which is not a confirmed attack chain, points to the Azure Activity log for secret-list requests and configuration changes, APIM gateway logs for newly seen subscription identifiers and tracing requests, developer-portal audit logs to see whether an unused portal is in use, Entra service-principal sign-ins for use of the app credentials APIM held, Key Vault audit logs for reads of the secrets APIM references, and Microsoft Graph activity logs; calls to the retired direct Management API do not appear in the Activity log (Anders Kristiansen, 2026-11-21). Credentials lifted from APIM can be used against outside services, and the damage depends on each credential's permissions (SecurityWeek, 2026-11-23).
    Defender takeaway
    Patching is not the end: treat every APIM instance as having lost the secrets it held, rotate them all and then hunt for their use; the practitioner guide also advises switching off the retired direct Management API and closing an unused developer portal (Anders Kristiansen, 2026-11-21).

    Symantec: 41 likely AI-authored PowerShell modules ran under an IIS web shell at an African stock exchange for just over three minutes, hunting secrets in SYSVOL, shared folders, SharePoint, SCCM and TFS, testing them against financial APIs and returning the output as hex-encoded DNS lookups to a public out-of-band testing service

    Symantec's Threat Hunter Team found a toolkit on a stock-exchange web server in an African country: 41 PowerShell modules ran under a web shell inside the IIS worker process between 08:44 and 08:47 UTC on 2026-09-20, a new module every few seconds (Symantec, 2026-11-19). The modules profiled the host and its IIS sites and hunted for secrets in the domain's SYSVOL share (Group Policy Preferences password fields), shared policy folders, web roots and deployment directories (hard-coded passwords, AWS keys, connection strings in .xml, .json, .env and web.config files); they also searched SharePoint for the keywords aws, credential and password, queried SCCM for the machine a given user last logged on to, listed Team Foundation Server projects and probed a PostgreSQL instance and a SQL Server. Four modules tested a guessed password, a reused bearer token and several API keys against the exchange's investment API and a securities-depository gateway (Symantec, 2026-11-19).

    Every module hex-encoded its output into 50-character chunks and resolved each as a DNS name under unique subdomains of a single token on a public out-of-band testing service, so the data left as DNS lookups; Symantec calls this rarely seen, cannot see the collector and does not know whether any credential or key worked (Symantec, 2026-11-19). Its case for AI authorship is uniformity: the same error handling in every module, the DNS loop copied byte for byte into all 41, generic variable names and a deliberately invalid test credential; it calls no signal conclusive (Symantec, 2026-11-19).

    Symantec attributes six persistence implants on the same server to Witchetty (LookingFrog), a China-linked espionage group, with high confidence, the earliest evidence dating from April 2026, but does not attribute the toolkit to any group; it names three explanations: Witchetty with new tooling, a second operator using the same access, or an unrelated actor. The way in is not stated, a web shell under the IIS worker process suggests a vulnerability may have been exploited, and Symantec found no evidence of privilege escalation or data theft (Symantec, 2026-11-19).

    Exposure
    A Windows estate with an IIS server whose worker account can read secrets: Group Policy Preferences passwords in SYSVOL, credentials in web.config and deployment folders, and reachable SharePoint, SCCM and TFS servers (Symantec, 2026-11-19).
    Detection
    Repeated short-lived PowerShell jobs started within seconds with the IIS worker process as ancestor; DNS egress from a server-class host to long hex-looking labels under a public out-of-band testing service; reads of SYSVOL policy folders and of web.config and .env files by the web-tier account; SCCM, SharePoint and TFS queries from a web server. Symantec says the uniform scaffold and the copied DNS loop are what defenders can look for (Symantec, 2026-11-19).

    Triage: out-of-band testing lookups are normal from a vulnerability scanner or penetration-test host; the discriminator is a production web server issuing them from PowerShell children of the IIS worker process.

    Defender takeaway
    Hunt web-tier servers for PowerShell spawned by the worker process and for server DNS egress to out-of-band testing services; remove Group Policy Preferences passwords from SYSVOL, move secrets out of web roots and shared folders, rotate any found there, and keep the web-tier account away from SCCM, TFS and SharePoint (Symantec, 2026-11-19).

    Microsoft Entra Connect Health: an API flaw present from 2026-07-23 was exploited to read tenant metadata including administrator and technical-contact email addresses; Microsoft fixed it server-side on 2026-11-19 and warns of targeted phishing

    Microsoft told tenants through Azure Service Health, from 2026-11-20, that a vulnerability in the Microsoft Entra Connect Health API, introduced on 2026-07-23 and found on 2026-11-09, was exploited for unauthorized read-only access to tenant-level metadata (BleepingComputer, 2026-11-21). Connect Health is the cloud service that lets administrators monitor the health of their on-premises identity infrastructure through the Entra admin center (BleepingComputer, 2026-11-21). Microsoft deployed a server-side fix on 2026-11-19, concluded its investigation on 2026-11-20 and found no unauthorized configuration change, although the flaw could in principle also have changed Connect Health monitoring settings (BleepingComputer, 2026-11-21; Netzwoche, 2026-11-23).

    The exposed data are the email addresses of tenant technical contacts and administrator accounts, tenant IDs, display names, initial domain names, country and region codes, Entra licence tiers and directory-synchronisation status, Connect Health onboarding status, and an expired agent-registration certificate for an internal Microsoft service decommissioned in late 2024; Microsoft says passwords, password hashes, authentication tokens, valid cryptographic keys, on-premises server and Active Directory topology and Azure subscription data were not exposed (BleepingComputer, 2026-11-21).     Any tenant that received the Azure Service Health notification; Microsoft says the flaw needs no software update or other customer remediation (BleepingComputer, 2026-11-21).

    Defender takeaway
    Treat the exposed administrator and technical-contact addresses as targets of tailored phishing and social engineering, tell those people, and enforce phishing-resistant MFA on privileged accounts; there is nothing to patch (BleepingComputer, 2026-11-21).

    A BIG-IP on the 21.1, 17.5 or 17.1 branch (BSI's product tree lists builds before the hotfix builds) whose virtual servers use one of those iRule commands or APM policy agents (BSI CERT-Bund, 2026-11-23; The Hacker News, 2026-11-18).
    Detection
    TMM process terminations and restarts and core files in the BIG-IP system logs, tied to the virtual server that carries the affected iRule or policy, follow from the stated impact (traffic disrupted until TMM restarts); no source describes a successful code-execution chain or a post-exploitation artefact (The Hacker News, 2026-11-18).
    Defender takeaway
    An unauthenticated remote crash of the traffic plane, with possible code execution, can be reached only on the configurations above, so inventory those first and apply the engineering hotfix instead of waiting for a scheduled release; a system on a custom engineering hotfix needs a new one from F5 support (The Hacker News, 2026-11-18).

    NOTABLECVE-2026-108398 +1NATOB1

    Project Zero: clearing one COFF header flag makes .NET Framework 4 load an untrusted assembly past Windows code-integrity checks (CVE-2026-108398, fixed 2026-10-13); the same behaviour defeated VirtualBox's Windows process hardening (CVE-2026-87268) and is expected to remain a protected-process bypass

    James Forshaw of Google Project Zero published a write-up of a code-integrity bypass found re-examining VirtualBox's Windows process hardening (Project Zero, 2026-11-23). On .NET Framework 4 the runtime first maps an assembly as an image section; if that fails with a bad-format error it falls back to a flat, data-only mapping that .NET can still run, so protection code that checks the loaded image section never sees it. A check meant to stop the fallback when code integrity is enforced tests the Windows lockdown policy for inequality with the configuration-code-integrity value, which is exactly what Windows 11 S Mode returns (User Mode Code Integrity on, Dynamic Code Security off), so it passes. Clearing the executable-image flag in the COFF header of a managed assembly, one bit with no checksum fix-up, and loading it through a .NET Framework 4 command-line utility without administrator rights ran arbitrary code under User Mode Code Integrity; it only seems to work on .NET Framework v4 (Project Zero, 2026-11-23).

    Forshaw presented it at 44Con before reporting it in late September 2026, so Microsoft treated it as a zero day; CVE-2026-108398 was fixed in October 2026 by correcting the policy check (Project Zero, 2026-11-23). Microsoft rates it Important, not exploited (Microsoft MSRC, 2026-10-13).

    The same behaviour defeated VirtualBox's Windows process hardening (CVE-2026-87268): an AnyCPU .NET assembly made its image screening return the bad-format status, the flat fallback loaded the unmodified assembly, and a current-user COM registration brought it into a hardened process; VirtualBox fixed it by never returning that status and by adding a COM option that disables current-user hive lookups. Against protected processes, hijacking a COM object that WerSecureFault.exe loads gave code execution as a protected process light without administrator rights; Microsoft's servicing criteria place such bypasses out of scope and the policy fix does not change that, so Forshaw expects it to remain bypassable (Project Zero, 2026-11-23).

    Exposure
    Windows hosts that rely on App Control for Business or WDAC user-mode code integrity as an application-control boundary without Dynamic Code Security (Project Zero, 2026-11-23), and Windows hosts that run Oracle VM VirtualBox 7.2.16 or likely earlier builds (Oracle, 2026-09-15).
    Detection
    The post says protection code that checks the loaded image section does not see this load (Project Zero, 2026-11-23); from that and the shown method, look at process creation of the .NET assembly-registration utilities with an unregister option against a file in a user-writable path, current-user COM registrations for the .NET runtime, .NET assembly loads with no matching image load, and managed assemblies whose COFF header lacks the executable-image bit.

    Triage: developers and installers run the registration utilities legitimately for their own signed COM assemblies from build or Program Files paths; the discriminators are an unsigned or modified assembly, a user-writable path and a current-user COM registration on a host enforcing user-mode code integrity.

    Defender takeaway
    Confirm the October 2026 .NET Framework update (4.8.1 at build 4.8.9363.0, 4.8 at 4.8.4811.0, 4.6.2 to 4.7.2 at 4.7.4150.0) on every host that enforces user-mode code integrity (Microsoft MSRC, 2026-10-13) and do not treat protected process light as a boundary against local code that can run .NET Framework 4 assemblies; Dynamic Code Security blocks the behaviour but is off by default, disables loading assemblies from byte arrays and can break applications (Project Zero, 2026-11-23).
