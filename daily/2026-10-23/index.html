    MythicRatatoskr: ESET documents a Go backdoor that hides its command server inside the Yggdrasil mesh network, and a UAC-0099 to Sandworm access handoff that ended in a Group Policy wiper attack on a Ukrainian grain logistics firm

    ESET reports that on 2025-07-16 UAC-0099 gained access to a Ukrainian grain logistics company through a spearphishing attachment: a scheduled task ran a PowerShell payload, the MATCHBOIL downloader deployed the MATCHWOK backdoor, and the next day a previously undocumented Go backdoor, MythicRatatoskr, arrived, which ESET ties to that chain with high confidence because of the timing (ESET Research, 2026-10-22). Further copies reached other machines through an OpenSSH SFTP server, and a SOCKS5 server appeared on some of them (ESET Research, 2026-10-22). About two months later, on 2025-09-17, the SDelete utility was deployed through Active Directory Group Policy, which ESET calls standard Sandworm tradecraft and assesses with high confidence as Sandworm after UAC-0099 handed off the access; ESET could not say which group operated MythicRatatoskr, and it sets the pair beside the earlier Gamaredon and Turla collaboration (ESET Research, 2026-10-22).

    The backdoor is built on the user-space yggstack, so it needs no tunnel interface or privileges to join the Yggdrasil mesh, an encrypted IPv6 overlay in the 200::/7 range: it picks three peers at random from an embedded list of public peers and then speaks JSON over HTTPS on port 443 to a command server that has an address only inside the mesh, and some samples wait ten minutes before connecting (ESET Research, 2026-10-22). It runs as a Windows service with an updater-style name, and it exfiltrates files and screenshots over the mesh without staging them (ESET Research, 2026-10-22). ESET notes that hosting the command server in the mesh may prevent network security tools from detecting the outbound connections to it and that blocking the public peer addresses is a viable mitigation (ESET Research, 2026-10-22).

    Exposure
    Windows estates whose users can open email attachments from outside and whose egress to arbitrary internet peers is not filtered; there is no product vulnerability, and ESET has not seen the backdoor anywhere else (ESET Research, 2026-10-22).
    Detection
    In egress and DNS logs, connections to the public Yggdrasil peer addresses, since the mesh traffic looks like ordinary outbound connections and the peer list is the handle; in service-creation and process telemetry, a new Windows service with an updater-style name that runs a Go binary from a system or user folder, a scheduled task that runs a PowerShell payload from a temporary folder after an attachment is opened, and an OpenSSH SFTP server appearing on a workstation; and for the destructive stage, Group Policy objects that deploy SDelete or a similar wiper and mass file overwriting after a long quiet period (ESET Research, 2026-10-22).

    Triage: ESET notes that legitimate users adopt Yggdrasil for resilient connectivity, research and hobby networking (ESET Research, 2026-10-22), so a single mesh connection needs a business-owner check; a mesh peer connection together with a service named like an updater, as ESET found the backdoor's service to be (ESET Research, 2026-10-22), is the stronger combination.

    Defender takeaway
    Where the mesh has no business use, block egress to the public Yggdrasil peers and alert on Group Policy changes that deploy wiper-class tools; the observed victim is Ukrainian and ESET describes UAC-0099 as targeting Ukrainian governmental, financial and media organizations, so the lesson transfers as tradecraft, in particular that initial-access activity by one group preceded a destructive stage by another two months later (ESET Research, 2026-10-22).

    BlackX: Kaspersky finds a BlackLotus-style UEFI bootkit on fully patched Windows machines of Central Asian diplomatic bodies, because the Baton Drop fix does not revoke the old boot-manager certificate until an administrator triggers it

    Kaspersky GReAT reports that in early 2026 it found BlackX, a UEFI bootkit similar to BlackLotus, used against diplomatic agencies in Tajikistan, Uzbekistan and Turkmenistan after the attackers held administrator privileges: an installer takes an RC4-encrypted package and its key as command-line arguments and drops files to the system and UEFI partitions that exploit Baton Drop (CVE-2022-21894) to enrol attacker-controlled Machine Owner Keys, so arbitrary EFI files load despite Secure Boot (Kaspersky GReAT, 2026-10-22). Kaspersky ties the exploitation to Baton Drop alone; CVE-2023-24932, the flaw Microsoft's revocation guidance is titled for, appears in its post only as the one a UEFI component in ESET's FishMonger report might exploit (Kaspersky GReAT, 2026-10-22). The bootkit injects a kernel driver, signed with a certificate its issuer has since revoked, that disables process, thread and registry callbacks and ETW providers of security products; the user-mode payloads were a RAT that uses Google Drive, OneDrive or Yandex.Disk for command and control and a sideloaded loader (Kaspersky GReAT, 2026-10-22).

    The targeted machines were fully patched. Microsoft's fix revokes the Windows Production PCA 2011 certificate only when an administrator sets a Secure Boot registry flag and runs the Secure-Boot-Update scheduled task (Kaspersky GReAT, 2026-10-22); Microsoft's own article says the mitigations in the updates of 2024-07-09 and later are not enabled by default and the Enforcement Phase date is still to be announced (Microsoft Support, 2026-09-30), and Kaspersky says that phase has not been implemented and the certificate's expiry on 2026-10-19 does not stop the vulnerable binaries loading unless it is on the forbidden list (Kaspersky GReAT, 2026-10-22). Kaspersky attributes the campaign to APT41 with medium confidence, resting on the identifier "xdd" shared with a kernel implant in ESET's June 2026 FishMonger report, DLL sideloading and OLLVM (Kaspersky GReAT, 2026-10-22).

    Exposure
    Any Windows device that boots with Secure Boot, has the updates of 2024-07-09 or later and has not had the revocation steps applied; Microsoft's check is that the forbidden-list (DBX) variable contains Microsoft Windows Production PCA 2011, which a PowerShell test returns as True once the revocation is in (Microsoft Support, 2026-09-30).
    Detection
    The installer needs administrator rights, so the hunt starts with the administrator-level intrusion that precedes it; the behaviors Kaspersky describes are process creation of an executable from a program-data subfolder that takes an encrypted data file and a key as arguments, file writes to the EFI system partition by processes that are not servicing, kernel driver loads signed by an unfamiliar or revoked certificate, a signed executable renamed to look like an updater that loads a sideloaded DLL, and non-browser processes talking to consumer cloud storage (Kaspersky GReAT, 2026-10-22). Because the driver disables security-product callbacks and ETW providers, quiet host telemetry after a reboot on a machine that ran the installer is not evidence that nothing ran, although Kaspersky found that the driver's tampering routines, written for Kaspersky and Avast products, failed to interfere with Kaspersky products (Kaspersky GReAT, 2026-10-22).
    Defender takeaway
    A patched Windows fleet is not protected against this class until the revocation is applied, so decide which devices get Microsoft's procedure and in what order; Microsoft warns that the revocation cannot be reverted while Secure Boot is in use, that BitLocker recovery keys should be backed up first, and that recovery and install media must be updated (Microsoft Support, 2026-09-30).

    M365 token spray and replay: Huntress tracks a 10-week campaign that replays stolen post-MFA tokens from rented hosting within minutes, registers rogue Entra devices, wipes and re-registers MFA methods and hides mail with inbox rules of one to three characters or punctuation only

    Between 2026-07-14 and 2026-09-22 Huntress detected 497 Microsoft 365 sign-in events across 79 victim organizations that replayed stolen sign-in tokens instead of guessing passwords (Huntress, 2026-10-22). The tokens came from adversary-in-the-middle relays behind fake sign-in pages, from device-code phishing and from social engineering during a genuine sign-in; a relay passes the real login page and MFA prompt through and keeps the token Microsoft issues afterwards, so its holder does not face MFA again (Huntress, 2026-10-22). Replay followed within minutes, after 12 minutes on 2026-07-21 and four minutes on 2026-09-22, from one of six addresses in a single rented range used in turn, so blocking one address stops at most one phase (Huntress, 2026-10-22).

    A scripted replayer with the user agent node requests tokens with the Microsoft Office and Microsoft Authentication Broker client applications against Microsoft Graph, Exchange Online, SharePoint Online and the Device Registration Service and joins 48 rogue Entra devices named DESKTOP- plus exactly eight uppercase hexadecimal characters, where the Windows default is seven alphanumeric characters; a browser-session replayer uses current Chrome or Edge through the OfficeHome client (Huntress, 2026-10-22). What outlives a password reset is the persistence: in 19 organizations the victim's MFA methods were wiped and a new authenticator registered within three hours, the rogue devices stay in the directory until deleted, and hidden inbox rules with names of one to three characters or punctuation only, created from VPN or other rented addresses, moved mail to RSS Feeds, RSS Subscriptions or Conversation History or deleted it, one keyed on payroll and bank terms (Huntress, 2026-10-22). Conditional Access blocks reported as AADSTS53003 fire only after authentication has succeeded, so they signal a valid credential, and ranking tenants by failed attempts points responders at the wrong ones (Huntress, 2026-10-22).

    Exposure
    Any Entra tenant where users can sign in to Microsoft 365 from unmanaged networks and Conditional Access does not require MFA or block for all users, all cloud apps and all client app types unconditionally, or where the device-code flow is open; Huntress names no victim, sector or country (Huntress, 2026-10-22).
    Detection
    In Entra sign-in logs, OAuth2:Token and Cmsi:Cmsi requests from hosting infrastructure that use the Microsoft Office or Authentication Broker client with a node or bare Mozilla/5.0 user agent, above all those that touch user mailboxes or the Device Registration Service; in the Entra audit log, device registrations from hosting addresses with the DESKTOP-plus-eight-hex name shape and MFA methods deleted and re-added within minutes; in Exchange audit data, inbox rules with the short names described above, especially created through the REST API (Huntress, 2026-10-22).

    Triage: a node user agent with an Office client identifier can be legitimate automation, so Huntress focuses on sign-ins that touch user mailboxes or the Device Registration Service from hosting infrastructure, and it says the device-name pattern is rare but not unique to this campaign, so a device should be confirmed before it is deleted (Huntress, 2026-10-22).

    Defender takeaway
    Revoke sessions as well as resetting the password, because the access token lives about 90 minutes after a reset, then audit devices, MFA methods, inbox rules and newly consented enterprise applications; as controls, require MFA or block for all users, all cloud apps and all client app types unconditionally, restrict the device-code flow with authentication-flow policies, and disable user consent to new applications (Huntress, 2026-10-22).

The prerequisite is network access to the VCO web interface and a valid session on the VCO portal; the lowest role that suffices is Enterprise Read Only, the lowest built-in tenant role, the interface is exposed by default and no configuration prevents the exposure (Arista Networks, 2026-10-22).

    Affected are VCO 5.2.x before 5.2.3.18, 6.1.x before 6.1.3.10 and 6.4.x before 6.4.2.12, and end-of-support releases were not assessed; hosted and dedicated VCO were affected and are already patched, while VeloCloud Gateway and VeloCloud Edge are not affected (Arista Networks, 2026-10-22). Arista's recommended resolution is the upgrade, and for an unsupported release train it points customers to its support centre to discuss upgrade options (Arista Networks, 2026-10-22); its CSAF file records the CVSS 3.1 score and the same interim measures, and describes the flaw as "VeloCloud Orchestrator Remote Code Execution (VCO RCE)" where the advisory page names an SQL injection that grants operator privileges; Arista does not say how the two descriptions relate (Arista Networks CSAF, 2026-10-22).

    Exposure
    An on-premises VCO on one of the three trains above, reachable at its web interface by anyone who holds a portal login of any role, a customer-tenant account included; Arista's list is by train, so compare each Orchestrator against the three fixed releases (Arista Networks, 2026-10-22).
    Detection
    Web access logs of the VCO for requests with unusual URL-like path components, encoded characters, references to local or internal services and high request rates; outbound connections from the VCO host that the Orchestrator does not normally make; backdoor daemons and web shells on the host; and recent administrator activity for changes nobody made (Arista Networks, 2026-10-22). Arista asks operators to preserve the web, application, system and database logs and the file-system timestamps before remediation where feasible, and its advisory does not say that the upgrade removes a foothold that is already there (Arista Networks, 2026-10-22).

    Triage: a session authenticated as a low-privilege tenant account, Enterprise Read Only above all, that reaches operator-only or internal-only functions is the signal, because legitimate operators act from their own accounts; Arista lists attacker source addresses in its advisory (Arista Networks, 2026-10-22).

    Defender takeaway
    Upgrade the Orchestrator to a fixed release of its train now, restrict the web interface to administrative networks in the meantime, and on any Orchestrator that was reachable and unpatched keep the logs first and then check the host for backdoor daemons and web shells.

Horizon3 uses it to replace a health-check script that a cron job runs every 60 seconds, which gives code execution within a minute (Horizon3.ai, 2026-10-20; The Hacker News, 2026-10-20).     FortiSandbox appliances, virtual machines and PaaS instances on the affected ranges whose GUI an unauthenticated client can reach, and FortiSIEM 7.5.0 nodes where tcp port 27918 is reachable from outside the deployment (Fortinet PSIRT FG-IR-26-185, 2026-10-13; Fortinet PSIRT FG-IR-26-180, 2026-10-13).
    Detection
    Fortinet publishes no indicator or post-compromise check for either flaw (Fortinet PSIRT FG-IR-26-185, 2026-10-13; Fortinet PSIRT FG-IR-26-180, 2026-10-13). The behaviors to look for follow from the mechanisms: on FortiSandbox, administrator-level GUI actions that have no matching login event, and on FortiSIEM, connections to tcp port 27918 from addresses outside the deployment followed by new files or processes on the node. Horizon3 found no application logs that would reveal exploitation and advises inspecting the write and modification timestamps of a script that a cron job runs, such as the charting health-check script, and of other files of interest such as the license tool, for any that do not match the surrounding files (Horizon3.ai, 2026-10-20).

    Move FortiSandbox to 5.0.7 or 4.4.10 (PaaS 4.4 migrates) and FortiSIEM 7.5.0 to 7.5.1, treating the FortiSIEM upgrade or the port restriction as out of cycle now that a proof of concept is public; a FortiSandbox at 5.0.6 or 4.4.9 still needs this upgrade (Fortinet PSIRT FG-IR-26-185, 2026-10-13; Fortinet PSIRT FG-IR-26-180, 2026-10-13). Fortinet's only workaround is for FortiSIEM, restricting access on tcp port 27918 (Fortinet PSIRT FG-IR-26-180, 2026-10-13); it names none for FortiSandbox, where limiting GUI access to an administrator network is the usual precaution rather than a Fortinet instruction.
