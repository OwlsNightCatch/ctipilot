    HIGHCVE-2026-132825NATOA2

    Ruby 4.0.10, 3.4.13 and 3.3.14: seven memory-safety flaws in the regexp engine and string case conversion, three rated Critical by the project, with proofs of concept for code execution; Veria Labs says Rails and classic Sinatra are exposed by default and announces a public Rails exploit for 25 November 2026 (CVE-2026-132825, CVSS 3.1 7.4)

    The Ruby project released 4.0.10, 3.4.13 and 3.3.14 on 2026-11-18 to fix seven vulnerabilities in the regexp engine and in string case conversion, and says it is aware of proofs of concept that prove some of them can be used to trigger remote code execution (Ruby project, 2026-11-18). NCSC.ch lists three as Critical, a one-byte heap overflow in case conversion of strings in single-byte encodings such as ISO-8859-1 and Windows-1252, a double free in regexp compilation and a heap overflow from an integer overflow in regexp compilation, and the rest as High or Moderate (NCSC.ch, 2026-11-19); the project's advisory for the first confirms it can write one byte past the output buffer (Ruby project, 2026-11-18). Most regexp flaws need an application that compiles, matches or stringifies an attacker-controlled pattern, and one needs only a crafted subject string against a fixed case-insensitive backreference pattern; the case-conversion flaw needs attacker-controlled text passed to a case-changing method (NCSC.ch, 2026-11-19). Affected are Ruby 3.3.13 and earlier, 3.4.0 to 3.4.12 and 4.0.0 to 4.0.9, and Ruby 3.2 and earlier are end of life and unfixed (Ruby project, 2026-11-18).

    NCSC.ch and watchTowr say Rails and classic-style Sinatra are exposed to the case-conversion overflow in their default configuration, and watchTowr reports no exploitation as of 2026-11-19 (NCSC.ch, 2026-11-19; watchTowr, 2026-11-19). Veria Labs, which says it found the flaw independently and first demonstrated code execution, calls it Ruby2Shell, says it is reachable without authentication on Rails and classic Sinatra and that plain Rack and other frameworks are not exposed by default, and plans to publish a proof of concept for remote code execution on stock Rails on 25 November 2026, or later if major vendors have not shipped a fix (Veria Labs, 2026-11-20). Veria lists GitHub Enterprise Server 3.22.5 and earlier and Chatwoot 4.20.0 and earlier as having no fixed release, and GitLab (fixed in 19.6.1, 19.5.8 and 19.4.10), Mastodon, OpenProject and the Discourse base image as patched; the Ruby advisories name no product, so the vendors' own advisories decide for each (Veria Labs, 2026-11-20). CVE-2026-132825 names the case-conversion overflow and is scored CVSS 3.1 7.4 with a local attack vector and high complexity (ENISA EUVD, 2026-11-19); the Ruby announcement says CVE identifiers were requested and none was assigned at publication, so the other six flaws are known by GHSA id (Ruby project, 2026-11-18).

    Exposure
    Ruby 3.3, 3.4 and 4.0 below the fixed releases that run Rails or classic Sinatra, or any application that passes untrusted text to a case-changing method or compiles untrusted regexp patterns; the interpreter version is shown by ruby -v, and self-hosted products that bundle Ruby carry their own fix timeline (NCSC.ch, 2026-11-19).
    Detection
    Crashes, segmentation faults and abnormal restarts of Ruby application workers that coincide with requests carrying long single-byte-encoded text or unusual regexp parameters, and a shell or network tool spawned by a Ruby worker process; these follow from the memory-corruption mechanism, as no source gives detection guidance.
    Defender takeaway
    Update the interpreter, not the gems, rebuild container images and restart workers before the announced proof of concept; until then NCSC.ch's temporary measures are to avoid compiling regexps from untrusted input and, for the case-conversion flaw, to convert input to UTF-8 so the vulnerable path is not reached (NCSC.ch, 2026-11-19).

    HIGHCVE-2026-123890 +4exploitedNATOA2

    CVE-2026-123890, VMware vCenter Server: an unauthenticated authentication bypass in the Directory Service gives an administrator session; GTIG reports the suspected China-nexus actor ARMORY CASTLE exploited it from early September, Broadcom lists no workaround; fixed in 8.0 U3m, 9.0.2.0200 and 9.1.1.0200 (CVSS 3.1 9.8)

    Broadcom's advisory VMSA-2026-0009 of 2026-11-19 fixes CVE-2026-123890, an authentication bypass in the VMware Directory Service of vCenter: an actor with network access can bypass authentication and gain unauthorized access without credentials (CVSS 3.1 9.8) (Broadcom, 2026-11-19). Broadcom lists no workaround, calls the issue an emergency change and does not state exploitation (Broadcom, 2026-11-19). Broadcom credits Mandiant with the report (Broadcom, 2026-11-19), and Google Threat Intelligence Group and Mandiant say ARMORY CASTLE, a suspected PRC-nexus actor, exploited it in early September 2026 with its BONESAW utility, according to forensic evidence (GTIG, 2026-11-19). GTIG describes one intrusion that reached an internal vCenter from a Remote Support appliance compromised through the earlier BeyondTrust zero-day and names no victim sector or country (GTIG, 2026-11-19); BleepingComputer notes that Broadcom has not confirmed the exploitation (BleepingComputer, 2026-11-19).

    The flaw is a session-key disclosure over DCE/RPC in the rpc_srp_verifier service on TCP 2012 that yields an authenticated administrator@vsphere.local session; BONESAW then read the Directory Service database, extracted the SAML signing key and created an SSO administrator, SAWSNAKE forged administrator SAML assertions, and the actor switched SSH on through the appliance management API, took the master symmetric key and the PostgreSQL credential file, switched SSH off again, logged in to ESXi hosts, planted an authorized_keys entry and extracted the domain database, registry hives and DNS data from Windows guest virtual disks before copying an archive out over SCP (GTIG, 2026-11-19).

    Broadcom's response matrix names the fixes: vCenter 9.1 in 9.1.1.0200, 9.0 in 9.0.2.0200, 8.0 in 8.0 U3m, VMware Cloud Foundation 5.x in 5.2.5 through KB88287 and Telco Cloud through KB463116; vCenter 7.0 has no public fix, and extended-support customers contact Broadcom Support (Broadcom, 2026-11-19). The 8.0 U3m and 9.0.2.0200 updates block later upgrades to VCF 9.1.1 until 9.1.2 (Broadcom, 2026-11-19).

    Exposure
    VCenter 7.0, 8.0, 9.0 and 9.1 before the fixed builds; the only stated prerequisite is network access to vCenter, and GTIG's actor reached it from an internal Linux appliance, so exposure does not require an internet-facing vCenter (Broadcom, 2026-11-19; GTIG, 2026-11-19). The running build is in the vSphere Client Summary tab or in PowerCLI (Broadcom, 2026-11-19).
    Detection
    In the vCenter appliance management audit log, SSH switched on and then off again, a new local or SSO administrator, and reads of the Directory Service database, the master key and the PostgreSQL credential file; in network telemetry, sweeps of ports 2012, 5480 and 9080 from a Linux appliance that is not a management host; on ESXi, logins as vpxuser or root, a new authorized_keys entry and a hidden directory on a VMFS volume (GTIG, 2026-11-19). GTIG advises hardening the vCenter appliance beyond patching, and because BONESAW extracts the SAML signing key and the actor created accounts, the compromise check covers SSO and local administrators, signing material and ESXi keys from early September on (GTIG, 2026-11-19).

    Triage: SSH enablement through the management API alone does not identify this activity; in GTIG's case it followed internal port sweeps from a non-management appliance and was reversed after the credential reads (GTIG, 2026-11-19).

    Defender takeaway
    Treat the update as an emergency change and plan around vCenter 7.0, which has no public fix; until it is in, GTIG's hardening guidance lists dropping inbound TCP 2012 from non-allowlisted addresses, to be tested first because the port carries SSO traffic (GTIG, 2026-11-19; Broadcom, 2026-11-19).

    NOTABLECVE-2026-129289 +7NATOA2

    PHP 8.5.13, 8.4.28, 8.3.37 and 8.2.36: CVE-2026-129289 lets an unauthenticated request smuggle a second FastCGI request into PHP-FPM and run PHP code when the front end reuses FastCGI connections; the release also fixes the session flaw left open in October and follow-ups to an incomplete earlier fix (CVSS 4.0 9.2)

    The PHP project released 8.5.13, 8.4.28, 8.3.37, 8.2.36 and 8.6.0 on 2026-11-19, and the changelogs list up to 18 CVEs per branch (PHP, 2026-11-19). The most direct is CVE-2026-129289: when php://input was opened but not read to the end, PHP-FPM leaves the unread request bytes on a persistent FastCGI connection, so a malformed multipart body can place a second FastCGI request inside the first, and an unauthenticated attacker can bypass front-end routing and execute attacker-controlled PHP code with the privileges of the worker (PHP, 2026-11-19). It requires a front end that enables persistent backend connections and an application path that opens php://input without reading it fully; standard nginx and Apache configurations that close the FastCGI connection after each request are not affected by the demonstrated attack (PHP, 2026-11-19).

    Two session flaws close the item the October release left open (watchTowr, 2026-11-20): CVE-2026-115560, where upload-progress session data is written in one serializer format and read in another, and CVE-2026-126714, where an interrupted write by the default files handler leaves a mixed old and new session file; both end in object injection and need an object gadget chain in the application (PHP, 2026-11-19; PHP, 2026-11-19). The fix for the first disables upload progress by default (PHP, 2026-11-19). CVE-2026-129481, a use-after-free of a stale session filename after an interrupted session shutdown, is in PHP's words an incomplete fix for CVE-2026-109619 and affects PHP 8.3 and later, and CVE-2026-129182, for PHP 8.5 only, covers further scenarios after the 8.5.12 fix (PHP, 2026-11-19; PHP, 2026-11-19).

    CVE-2026-129474, PHP 8.5 only, is exposed on the built-in defaults, because fatal error backtraces are on in 8.5 and the default includes arguments, and php.ini-production, which sets zend.exception_ignore_args=1, or fatal_error_backtraces=0 prevents the attack; PHP confirmed code execution on 8.5 (PHP, 2026-11-19). CVE-2026-129496 needs a startup diagnostic written through a file-based error_log in a non-thread-safe build (PHP, 2026-11-19). CVE-2026-129291, an epoll use-after-free in PHP-FPM, gives root from a worker where catch_workers_output is on and the FPM master runs as root (PHP, 2026-11-19). NCSC.ch lists exploitation as unknown with no public proof of concept referenced, and watchTowr reports none as of 2026-11-20 (NCSC.ch, 2026-11-19; watchTowr, 2026-11-20).

    Exposure
    PHP 8.5 without php.ini-production settings is exposed to CVE-2026-129474 on the defaults, when an application path enters a magic method (PHP, 2026-11-19). For CVE-2026-129289, PHP-FPM servers whose front end keeps FastCGI backend connections open (nginx fastcgi_keep_conn on, Apache mod_proxy_fcgi enablereuse=on, HAProxy in FastCGI mode) and whose applications open php://input without consuming it, which the PHP advisory says some frameworks do; standard nginx and Apache setups are outside the demonstrated attack (PHP, 2026-11-19). The session flaws need an object gadget chain in the application, and the version is shown by php -v on the host or in the container image.
    Detection
    In web and proxy access logs, malformed multipart/form-data bodies sent to endpoints whose application opens php://input without consuming it, followed by PHP execution that no logged request explains; in process telemetry, a shell or network tool spawned by the PHP-FPM worker, which follows from worker-level code execution.
    Defender takeaway
    Move the PHP runtime, not the CMS or its plugins, to the fixed build of its branch and restart PHP-FPM; where that waits, turn FastCGI connection reuse off (PHP, 2026-11-19). PHP 8.1 hosts need a newer branch for CVE-2026-129291 (PHP, 2026-11-19).
