    Technical University of Munich: attackers captured the central-login passwords of everyone who signed in to the legacy myTUM portal, took a TUMonline system administrator's credentials and attacked the campus-management system; accounts with MFA were protected

    The Technical University of Munich says unknown persons attacked its myTUM portal and captured the passwords for the central login to TUM systems, among them login.tum.de and TUMonline, from all persons who had logged in to myTUM; among them were the access credentials of a system administrator for TUMonline, with which the attackers attacked the central campus-management system TUMonline, which TUM then took off the network (translated from German) (TUM, 2026-11-06). TUM says the attackers may have reached the account password, name, private address and date of birth of everyone affected, plus staff and student details, that the attackers' accesses within TUMonline were largely logged and that it currently assumes no further TUMonline data such as grades is affected, and that accounts with multi-factor authentication were protected in this attack (translated from German) (TUM, 2026-11-06). heise, quoting a TUM spokesperson, reports that the attackers entered through a legacy system and that whether data was exfiltrated is still being investigated, and adds that about 60,000 students and employees are concerned (translated from German) (heise online, 2026-11-06). Neither source states how the passwords were captured at myTUM.

    Exposure
    A public university or other public body that keeps a retired or secondary sign-in portal validating against its central directory, so that every password typed there is a credential for the primary identity and administration systems; TUM's accounts with MFA held, and the lesson transfers to Swiss cantonal and university portals.
    Defender takeaway
    Inventory legacy and secondary portals that accept the central directory password and retire them or put them behind MFA, require MFA on administrator accounts of campus and school-management systems, and check whether an administrator ever signed in to such a portal.

    NOTABLENATOB2

    Kaspersky GERT: two ESXi and Proxmox ransomware cases in which a monitoring server's reused root password and plaintext administrator notes, not a VM escape, gave the attackers the hypervisor

    In the first case, Kaspersky's investigation began with BlackNevas ransomware activity on a Windows system in a virtualised domain-controller segment, where the execution of the AnyDesk remote tool and the GMER binary was recorded (Kaspersky GERT, 2026-11-06). The environment used PRTG Network Monitor, whose deployment had broad access to the ESXi hosts, and the same root password was reused across several nodes; after obtaining access to the monitoring environment the attacker used the ESXi credential to connect over SSH to the hosts that shared the password (Kaspersky GERT, 2026-11-06). On the first host, a file was uploaded during a root SSH session and its first execution failed with "Execution of non-installed file prevented"; the actor then disabled the execInstalledOnly policy with esxcli and ran it, while on a second host in another subnet with the same password the binary ran and the logs were cleared (Kaspersky GERT, 2026-11-06).

    In the second case, a ransomware incident by The Gentlemen, the actor used information it had collected between initial access and visible impact: on a compromised system administrator's workstation it found Proxmox root credentials and access details in plain-text notes and logged in as root (Kaspersky GERT, 2026-11-06). It then activated the VNC web socket through the root account, which gave it control of the Proxmox environment, and used that access to download and run the ransomware in the cluster, encrypting the whole virtual environment (Kaspersky GERT, 2026-11-06). Kaspersky says a fully patched hypervisor can still be compromised through a shared password, an overprivileged monitoring account, an open SSH path or an administrator interface reachable from a general server network (Kaspersky GERT, 2026-11-06).

    Exposure
    A virtualisation estate where a monitoring, backup or management server stores or can use hypervisor root credentials, where one root password is shared across hosts, where SSH to ESXi is reachable from general server networks, or where administrators keep Proxmox or ESXi credentials in plain-text notes; PRTG, which supports storing VMware credentials at device or group level, is the product Kaspersky names (Kaspersky GERT, 2026-11-06).
    Detection
    On ESXi, root SSH logins from addresses that do not normally administer the hosts, a file upload followed by a failed execution of a non-installed file, a change to the execInstalledOnly setting and cleared logs; on Proxmox, root@pam requests to the VNC web socket used to reach other hosts, as the log records Kaspersky shows (Kaspersky GERT, 2026-11-06). Kaspersky advises alerting when execInstalledOnly, Secure Boot enforcement, Lockdown Mode, SSH, local accounts or remote logging settings change (Kaspersky GERT, 2026-11-06).
    Defender takeaway
    Give each monitoring platform its own least-privilege identity instead of ESXi root, replace stored root passwords with vault retrieval or limited tokens, administer ESXi through vCenter with Lockdown Mode and SSH stopped by default, and keep logs off the hosts so a compromised administrator cannot erase them (Kaspersky GERT, 2026-11-06).

    Acronis TRU on BOSSAI: one operator's mesh of 12 AI agents took patient-care records and dispatch case data from Taiwanese emergency services through a legacy open port, a public API and default root credentials, and failed wherever authentication was enforced

    Acronis TRU found an open attack workstation holding more than 90,000 files and describes BOSSAI as a mesh of 12 AI agents, nine active, driven by a changing roster of language models, with the operator acting as the bridge between agents and typing commands in Traditional Chinese (Acronis TRU, 2026-11-04). The agents that executed attacks ran almost exclusively on abliterated open-weight models run locally, after commercial models repeatedly refused offensive requests (Acronis TRU, 2026-11-04). In the 12 days TRU observed, the operator targeted government emergency services, banks and lenders, universities and military systems in 11 countries, with confirmed exfiltration or system access at roughly ten targets in three countries and about fifteen more attacked without confirmed compromise (Acronis TRU, 2026-11-04).

    The confirmed emergency-services harm is the part that matters here. A Taipei fire-department patient-care records platform exposed ECG readings, ambulance video and vital signs from 2018, accessible without credentials; a city's 119 dispatch system yielded case records with incident times, response types, status fields and street-level locations across seven districts from the system's API; and a fire-dispatch vendor's database administration panel opened with default root credentials, exposing 18 or more tables (Acronis TRU, 2026-11-04). In an emergency-management system the agents found a hardcoded AES-256 key in front-end JavaScript that exposed session-cookie contents, an administrator identity among them, and a partial server-side request forgery path, without confirming a full compromise (Acronis TRU, 2026-11-04). A brute-force run against a national fire agency's single sign-on portal gave no confirmed access, and the critical Apache flaw that the operator's vulnerability platform reported at a disaster-response centre was fabricated, because the port was filtered (Acronis TRU, 2026-11-04). TRU says the agents failed where authentication was enforced, where paywalls required valid sessions and where endpoints were properly filtered, and that obscurity no longer protects a system from agents that investigate hundreds of targets at once (Acronis TRU, 2026-11-04).

    Exposure
    Emergency-service, dispatch and public-safety systems that expose a record API or a legacy data port without authentication, leave default administrator credentials on a vendor's database panel, or ship secrets in front-end JavaScript; those are the weaknesses the agents turned into data, and TRU reports the patient-care and dispatch records as the gravest confirmed harm.
    Detection
    TRU names sqlmap, nmap and nikto among the most-used tools, so the traffic is ordinary scanner traffic in web access and authentication logs (an inference from the tool list): bursts of SQL-injection probing, repeated sign-in attempts against a single sign-on portal from one source, and logins to a database administration panel with a default account.
    Defender takeaway
    Swiss dispatch, patient-care and records systems of emergency services are the same target class, so check them for unauthenticated APIs and legacy ports, default root or administrator credentials on vendor panels, and keys or tokens in front-end code; the agents failed wherever authentication was enforced, so closing those gaps is what stops this tooling.

    CVE-2026-19868, SonicWall SonicOS SSLVPN: valid credentials for an alternate authentication method bypass SAML and the MFA it enforces; SonicWall investigated a report of exploitation and CISA lists it as exploited (CVSS 3.1 7.1)

    SonicWall's advisory SNWLID-2026-0014 of 2026-11-06 fixes seven SonicOS flaws on Gen7 and Gen8 firewalls, and one of them, CVE-2026-19868, is an authentication enforcement weakness in the SSLVPN service: a user with valid credentials for an alternate authentication method may bypass the SAML authentication controls, and successful exploitation may also bypass SAML-enforced multi-factor authentication (SonicWall PSIRT, 2026-11-06). SonicWall says the flaw only affects SSLVPN when SAML is enabled for SSLVPN logins, and scores it CVSS 3.1 7.1 as a use of single-factor authentication (CWE-308) (SonicWall PSIRT, 2026-11-06). The advisory says SonicWall PSIRT "has investigated a report indicating potential exploitation" and urges customers to upgrade (SonicWall PSIRT, 2026-11-06); its revision of 2026-11-09 adds an interim workaround for SAML deployments that cannot upgrade, to disable or delete every active LDAP, RADIUS and TACACS+ authentication server on the firewall (SonicWall PSIRT, 2026-11-09); CISA added the flaw to its Known Exploited Vulnerabilities catalog on 2026-11-06 "based on evidence of active exploitation" (CISA, 2026-11-06). SonicWall has not shared details about the reported exploitation (BleepingComputer, 2026-11-06).

    The advisory applies one table to all seven flaws: Gen7 hardware firewalls (TZ, NSa and NSsp) and Gen7 NSv up to and including 7.3.3-7015 are fixed in 7.3.4-7013 and higher, and Gen8 hardware firewalls (TZ and NSa) and Gen8 NSv up to and including 8.2.2-8015 are fixed in 8.2.3-8015 and higher (SonicWall PSIRT, 2026-11-06). It also fixes two management-interface flaws scored 8.8 that in specific conditions could potentially let a remote unauthenticated attacker perform unauthorized operations, and that need user interaction, a pre-authentication heap overflow in the SSL-VPN service that could cause a denial of service, and three lower-severity flaws; no source reports them exploited (SonicWall PSIRT, 2026-11-06).

    Exposure
    A Gen7 or Gen8 SonicWall firewall or NSv at or below the builds above with the SSL VPN enabled and SAML configured as a login method for SSLVPN; the running SonicOS build is the first check and the SAML setting for SSLVPN the second, the vendor's stated precondition (SonicWall PSIRT, 2026-11-06).
    Detection
    The advisory gives no indicators. From the stated mechanism, compare successful SSLVPN logins on the firewall with the identity provider's sign-in log: a VPN session with no matching SAML sign-in or MFA event, or a SAML-enrolled user who authenticated through another authentication method, is the signal. Patching does not evict an attacker who already holds a session or reuses the credentials, so review VPN sessions since SAML was enabled and reset the credentials of accounts that work through both authentication methods; once the workaround is applied, logins through the removed authentication methods should stop, and any that continue show the change did not take effect or that the session predates it.

    Triage: a legitimate SAML sign-in leaves an event at the identity provider; a login through the alternate path does not, which follows from the stated mechanism.

    Defender takeaway
    Upgrade every Gen7 and Gen8 firewall that serves SAML SSLVPN logins to 7.3.4-7013 or 8.2.3-8015 or later now, because the exploitation evidence is a vendor-investigated report plus CISA's listing; where a firewall cannot be upgraded today, disable or delete its LDAP, RADIUS and TACACS+ authentication servers as the advisory now says, and expect logins that rely on those servers to stop; then review VPN sessions for logins that skipped the identity provider.

    Oneconsult on the File System Access API: after two clicks a website holds read and write access to folders such as .vscode, .Azure, the public desktop and SMB shares in Chrome and Edge, enough for token theft and persistence without a process on the host

    Oneconsult analyses, from the Chromium source and tests on Windows 11 with Chrome and Edge 150.0.7871.101, what a website can reach through the File System Access API once a user selects a folder and grants permission: the handle stays valid as long as the tab is open and is obtained after just two user clicks (Oneconsult, 2026-11-02). Chrome rejects blocklisted paths, but a path that is not in its table and not an ancestor of a blocked path is allowed, and the kDontBlockChildren rule leaves the subfolders of listed directories selectable; Oneconsult confirmed .vscode, the Azure token cache, C:\Users\Public and SMB shares as accessible (Oneconsult, 2026-11-02).

    Oneconsult demonstrates these paths. A site can search a granted folder and take files such as cached Azure tokens and .env files. It can drop a fake VS Code extension into .vscode/extensions, which runs inside the normal code.exe process and is unaffected by Mark of the Web because Node.js does not check the Zone.Identifier stream. It can plant PowerShell profile and module backdoors, which work only with the Bypass or Unrestricted execution policy because the API stamps every written file with ZoneId=3 and RemoteSigned refuses such files. It can drop files on the public desktop, where they appear for all users and trigger a warning that a certain percentage of users acknowledge. And it can run an interactive file proxy through the still-open tab, where EDR sees only the browser reading and writing files (Oneconsult, 2026-11-02). A OneDrive Known Folder Move enabled while Chrome is running leaves a stale blocklist, so the redirected Desktop was writable; Oneconsult notes that the bypass has been reported to Google, which made the issue public, and that Google classed reading a single dragged file from a blocked folder as "not a security issue" (Oneconsult, 2026-11-02).

    Daniel Oz's July write-up of the same technique has a website edit a file the user already holds. He says the user-gesture requirement does not prevent phishing, only automatic picker invocation, and that signed or complex files may fail, be blocked or break in a way that prevents execution (Oz, 2026-07-05).

    Exposure
