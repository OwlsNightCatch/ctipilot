    01Active threats, incidents & disclosures1 item

    NOTABLEupdatedNATOB1

    GhostAction returns: stolen maintainer credentials push a fake security-audit workflow into the victims' own GitHub repositories, which now harvests credentials from the entire git history

    StepSecurity reports that on 2026-10-08 the GhostAction GitHub Actions credential-theft campaign used the accounts of two open-source maintainers to push a workflow disguised as a security improvement to 345 repositories in two automated sweeps, among them an Uber-owned repository that one maintainer could still write to (StepSecurity, 2026-10-09); Socket's independent analysis counts 346 (Socket, 2026-10-09). The operator holds a maintainer's GitHub credential, which StepSecurity assesses as most plausibly a personal access token leaked through infostealer logs or credential dumps, then commits a workflow titled to look like a security audit straight to the default branch under the victim's own identity, unsigned and without a pull request; that push runs it, and nothing in an audit log looks anomalous unless the content is read (StepSecurity, 2026-10-09). GitGuardian says the technique was later reused in the Shai-Hulud campaigns and remains at the core of the Mini Shai-Hulud malware family (GitGuardian, 2026-10-07).

    The newer payload sends the named Actions secrets and every cloud, AI-provider and SaaS credential pattern found in the working tree and the entire git history to a hardcoded address over plain HTTP, so no DNS lookup occurs (StepSecurity, 2026-10-09). StepSecurity saw the attacker's server acknowledge the request four seconds into the run at the Uber-owned repository (StepSecurity, 2026-10-09); neither it nor Socket has seen a malicious package release from the stolen credentials yet (Socket, 2026-10-09; StepSecurity, 2026-10-09). The wave was far larger than those first counts: Socket's update of 9 October reports more than 500 accounts committing the workflow to tens of thousands of repositories since 7 October (Socket, 2026-10-09), and GitGuardian's update of 13 October counts more than 30,000 repositories across 3,000 users and organisations between 8 and 12 October, reached by compromising about 1,900 GitHub accounts (GitGuardian, 2026-10-07).

    Exposure
    Any GitHub account whose token or session credential has leaked, and every repository it can write to; StepSecurity says a workflow posing as a security audit or an Actions security workflow that appeared in a repository you maintain since 2026-08-31 means treat it as a confirmed breach (StepSecurity, 2026-10-09).
    Detection
    Source-control audit logs: workflow files added straight to default branches without a pull request by a maintainer identity, unsigned commits landing in many repositories within minutes; an organisation-scoped code search with StepSecurity's published content-marker queries for security-themed workflow files (audit, check or Actions security); runner egress logs: an HTTP POST to a bare IP address with no preceding DNS lookup (StepSecurity, 2026-10-09). Removing the workflow does not undo the theft: StepSecurity says any secret ever committed to a repository must be treated as compromised, so treat each run as an exfiltration, scan the full history and rotate every credential found (StepSecurity, 2026-10-09); GitGuardian adds that the GitHub credential that allowed the injection must be revoked too, or someone else will reuse it (GitGuardian, 2026-10-07).

    Triage: the audit-log pattern separates this from a team adding a scanning workflow: no pull request, unsigned commits across many repositories, and a manual dispatch right after creation (StepSecurity, 2026-10-09).

    Defender takeaway
    Search the GitHub organisations your teams and suppliers administer for security-themed workflow files (audit, check or Actions security); on a hit revoke the committing credential and rotate everything in the repository's full history. StepSecurity saw requiring approval for workflow runs stop the exfiltration and names branch protection on .github/workflows so workflow changes need pull-request review (StepSecurity, 2026-10-09).
    Update20 Oct 2026 08:42 UTCrun 2026-10-20T0835Z-auditbodyevidencesourcing_notesummary

    GitGuardian updated its analysis on 2026-10-13 from its own dataset: between 8 and 12 October the campaign targeted more than 30,000 repositories across 3,000 users and organisations by compromising the GitHub accounts of about 1,900 users, and tried to extract 3,174 secrets from public repositories' CI, with the largest spike on 8 and 9 October (GitGuardian, 2026-10-07). Socket's update of 9 October, with more than 500 accounts and tens of thousands of repositories since 7 October, is of the same order (Socket, 2026-10-09). GitGuardian says GitHub started preventing the malicious workflow from running on 9 October, so the further waves it saw on 10 and 12 October, with the same payload, could not extract any secrets (GitGuardian, 2026-10-07); a workflow from those later waves still means the account that committed it is compromised. Part of the October victims had already been hit in the September 2025 and August 2026 waves, and GitGuardian assesses that the operator likely relies in part on secrets left unrotated since earlier campaigns (GitGuardian, 2026-10-07).

    02Trending vulnerabilities2 items

    HIGHCVE-2026-105133 +1exploitedupdatedNATOB1

    CVE-2026-105133 / CVE-2026-105134, AhsayCBS backup management console: an unauthenticated authentication-bypass and code-execution chain exploited since 7 October to drop webshells and a cryptominer; Ahsay says its earlier patches were incomplete and ships hotfixes 10.3.4.45 and 9.15.2.70 through its partner portal

    Huntress reports that from 2026-10-07 23:20 UTC attackers exploited two flaws in AhsayCBS, the management console of Ahsay's backup software that managed service providers and system integrators mainly use, to gain unauthenticated remote code execution and deploy webshells on exposed servers (Huntress, 2026-10-08). CVE-2026-105133, an improper-authentication flaw in the checkSysPwd function of the API, is used first to bypass authentication; CVE-2026-105134, in the /rps/api/json/UpdateReceivers.do endpoint of the Replication Receiver component, then gives code execution as NT AUTHORITY\SYSTEM, after which the attacker configured a malicious receiver and dropped a JSP webshell into the directory the application serves (Huntress, 2026-10-08). Horizon3's later source-level analysis traces the file write itself to the receiver's upload path, which a receiver created through that endpoint exposes (Horizon3.ai, 2026-10-14). BleepingComputer reports that the activity targeted at least five organizations on 7 October and that CVE-2026-105133 has a public exploit (BleepingComputer, 2026-10-09).

    Follow-on activity, per Huntress: commands spawned by the AhsayCBS service process fetch payloads over HTTP from cloud object storage into a Temp folder with curl and certutil; an XMRig Monero miner renamed to look like a Microsoft Edge binary runs as SYSTEM through a service that mimics the Edge updater and a renamed copy of the NSSM service manager, and reaches its mining pool on a non-standard port; and a PowerShell script that Huntress assesses as AI-assisted checks whether Task Manager is running, uses the host's local time to decide when to close it, and stops the miner while it is open (Huntress, 2026-10-08). The earlier patches did not close the flaws: public records had listed AhsayCBS up to 10.3.2 as affected (SecurityWeek, 2026-10-09), Huntress found on 2026-10-08 that 10.3.4 is also affected (Huntress, 2026-10-08), and Ahsay's release notes for 10.3.4 list no security fix (Ahsay, 2026-08-05).

    Exposure
    AhsayCBS servers (on Windows a service run from cbssvcX64.exe or cbssvcX86.exe; Horizon3 shows the same chain on the Linux build, where the service runs as root (Horizon3.ai, 2026-10-14)), whose management web interface is reachable from untrusted networks and that run a v7 to v10 build below the hotfixes v10.3.4.45 or v9.15.2.70, which includes v10.3.4.0 and v9.15.2.59 (Ahsay, 2026-10-12; Huntress, 2026-10-08).
    Detection
    Process-creation telemetry with parent lineage: children of the AhsayCBS service process outside its normal startup and maintenance commands, because commands from an uploaded JSP webshell appear as direct children of the service, and curl or certutil from that lineage writing into a Temp folder; service inventory: a service named like the Edge update service running an Edge-named binary from a Temp folder as SYSTEM; PowerShell script-block logs: a script that checks for Task Manager and stops or starts a service to match; command lines that name WinRing0 next to a URL; and new .jsp files in the application directory. Huntress published four Sigma rules (Huntress, 2026-10-08). Horizon3's source-level analysis adds checks on the server itself, where the service process is the CBS JVM on Linux: new .jsp files under webapps/rps, webapps/cbs or any served application directory, especially ones that answer 404 unless a specific parameter is supplied; replication receivers whose home directory sits under the install directory and that were created outside a change window (a "Created new receiver" entry in the system log); unexpected system administrator accounts and API logon entries for accounts nobody provisioned; and requests to the JSON .do endpoints or the receiver upload path that carry a FromServlet field or X-RSW-Request headers from untrusted sources (Horizon3.ai, 2026-10-14).

    Triage: AhsayCBS legitimately spawns its own startup and maintenance commands, so a child process alone is weak; the discriminators Huntress gives are a child of the service that downloads files into a Temp folder, and an Edge-named binary run as SYSTEM from a Temp folder under a service that mimics the Edge updater (Huntress, 2026-10-08).

    Defender takeaway
    Apply the hotfix v10.3.4.45 or v9.15.2.70 to every AhsayCBS server, including those on the earlier patches, and reboot it (Ahsay, 2026-10-12); ask your backup suppliers whether they run it, because the hotfixes sit behind a partner login, and until it is applied keep the management interface on trusted addresses or a VPN, since the exploit targets the externally reachable web application (Huntress, 2026-10-08); where an indicator of compromise turns up, re-image the host from a trusted backup, since Huntress says attackers hid secondary backdoors for extended persistence (Huntress, 2026-10-08).

    Ahsay now says its previous patches v9.15.2.59 and v10.3.4.0 "did not fully address" the two flaws, and tells partners to apply the AhsayCBS v10.3.4.45 hotfix on v10 and the v9.15.2.70 hotfix on v7, v8 and v9, both from the partner portal (a valid partner login is required), then to reboot the server (Ahsay, 2026-10-12). The announcement is dated 2026-10-12; Huntress, in an update of the same day to its report, dates the hotfix release to that day and says it independently verified that the v10.3.4.45 hotfix mitigates the initial entry point of the chain, which was still open on earlier v10 versions (Huntress, 2026-10-08).

    CISA added both flaws to its Known Exploited Vulnerabilities catalog on 2026-10-14 "based on evidence of active exploitation" (CISA, 2026-10-14). Bitdefender MDR reports three intrusions through the chain, the first two beginning around 7 to 8 October and a third identified on 14 October; in the first, attackers validated access through JSP webshells, staged PowerShell payloads, tried to stage payloads as command files in C:\Users\Public and tried to establish persistence; in the second they deployed JSP files, tried the same command-file staging, searched for stored credentials, elevated an account to SYSTEM and used obfuscated PowerShell to install and configure OpenSSH, which gives a way back that does not depend on the vulnerable web service, so patching alone does not end the incident; across its incidents the follow-on PowerShell scripts were staged on a subdomain of a public static-site hosting service; it attributes the activity to no named actor, and notes that the file names, tools and binaries differed from one incident to the next, so the dependable signal is how the server behaves after the exploit fires (Bitdefender, 2026-10-15).

    Improvement18 Oct 2026 03:34 UTCrun 2026-10-18T0256Z-intelsourcesevidenceactionsbody

    Horizon3.ai published a source-level analysis of both flaws on 2026-10-14, working from the Linux installer, and says its proof of concept for the chain, from authentication bypass to a webshell, is on its GitHub (Horizon3.ai, 2026-10-14). For CVE-2026-105133, every action of the JSON API extends a base class whose administrator password check is skipped when the request body carries a FromServlet flag that the caller sets, so the JSON API is reachable without credentials, and the AddSysUser action, which creates a system administrator, never consults the caller (Horizon3.ai, 2026-10-14). For CVE-2026-105134, an authentication-bypassed call creates a replication receiver whose home directory the attacker chooses; the system-folder denylist that screens that directory at creation is not applied to the upload path later built from two attacker-supplied headers, in which only the percent and colon characters are escaped, so a traversal sequence walks the write location into a served web application, and one upload of a .jsp file then runs as LocalSystem on Windows and as root on Linux (Horizon3.ai, 2026-10-14). Horizon3 says Ahsay released its hotfixes on 12 October 2026 (Horizon3.ai, 2026-10-14).

    ROUTINECVE-2026-84411updatedNATOA2

    CVE-2026-84411, MikroTik RouterOS: one unauthenticated request to the web management service can run code as root; fixed in 7.24 (v7 stable), 7.23.8 (v7 long-term) and 6.49.23 (v6 long-term) (CVSS 3.1 9.8)

    MikroTik's notice of 2026-10-06 describes an integer underflow in HTTP request body handling of the RouterOS web management service, the service behind WebFig on the www and www-ssl ports: a single specially crafted request sent without logging in could crash the service or let an attacker execute code on the router with full privileges, and MikroTik rates the flaw critical as CVE-2026-84411 (MikroTik, 2026-10-06). CISA's advisory ICSA-26-272-06 describes the same flaw as reachable before authentication, scores it CVSS 3.1 9.8 and records no known public exploitation reported to it (CISA, 2026-09-29). RouterOS versions before 7.24, v6 included, are affected on devices where the attacker can reach the web interface; 7.24 fixes the v7 stable channel (MikroTik, 2026-10-06), and MikroTik's changelogs list the fix in 7.23.8 for v7 long-term (dated 2026-10-08) and in 6.49.23 for v6 long-term (dated 2026-10-07), while its notice still shows both long-term releases as pending (MikroTik, 2026-10-08; MikroTik forum, 2026-10-09; MikroTik forum, 2026-10-09; MikroTik, 2026-10-06). BleepingComputer notes that hackers and botnet malware often target MikroTik flaws and recalls a recent CERT Polska warning of an exploit chain against devices with SSH exposed to the internet (BleepingComputer, 2026-09-30).

    Exposure
    A RouterOS device on a version before 7.24, v6 included, other than a long-term build that already carries the fix (7.23.8 on v7, 6.49.23 on v6), whose www or www-ssl service an attacker can reach; the services and their allowed addresses are listed under IP > Services (MikroTik, 2026-10-06). MikroTik says a device with default firewall rules is reachable only from the local network, so internet exposure means a device whose firewall or service settings let the web interface through (MikroTik, 2026-10-06).
    Detection
    MikroTik and CISA publish no indicators and neither reports exploitation. MikroTik says a single request could crash the service (MikroTik, 2026-10-06), so repeated restarts of the web service on a device reachable from untrusted networks are worth checking.
    Defender takeaway
    Upgrade each device to the fixed build for its channel: 7.24 or later on v7 stable, 7.23.8 on v7 long-term, 6.49.23 on v6 long-term (MikroTik, 2026-10-06; MikroTik, 2026-10-08; MikroTik forum, 2026-10-09; MikroTik forum, 2026-10-09). Where an upgrade has to wait, restrict the web services to trusted addresses or disable them and manage the router over WinBox, SSH or a VPN, as MikroTik advises, and do not open management ports to the internet (MikroTik, 2026-10-06). No source reports exploitation as of 2026-10-10, and the flaw is not in CISA's Known Exploited Vulnerabilities catalog (version 2026.10.08) (CISA KEV catalog, 2026-10-08).

    HIGHCVE-2026-81578 +2exploitedupdatedNATOB1

    CVE-2026-82078 / CVE-2026-81578, PaperCut NG/MF: an Apache Tapestry request-routing confusion chains an unauthenticated config rewrite to arbitrary code execution, exploited before a patch existed

    First published 2026-08-29 · open finding →

    Update10 Oct 2026 03:46 UTCrun 2026-10-10T0255Z-intelprioritysummaryimmediate_actiontagscvesactionssourcesevidencesourcing_notebody

    watchTowr published on 2026-10-09 how the emergency patches were bypassed in turn: the 28 August emergency build could still be taken without authentication through the Setup Wizard forms, and a new administrator-only Scan-to-Fax code-execution flaw, CVE-2026-82077, is fixed only in 26.0.5 and 25.0.13, not in the emergency builds. No source names exploitation of either, though PaperCut says Emergency Patch Release 3 closes off further attack vectors it has seen exploited. Earlier statements the cited sources do not support were corrected where they stood: the 2023 precedent, the university-customer statement, the emergency-patch chronology and the detection wording.

    watchTowr Labs published a write-up on 2026-10-09 that follows the emergency patches build by build (watchTowr, 2026-10-09).
