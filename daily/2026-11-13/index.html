    DarkLunnen: Group-IB's exposed operator directory shows mass exploitation of FortiOS CVE-2024-55591 that plants a 'service' super_admin account, a 4,725-target Swiss FortiGate scan list and restic access to an S3 backup repository at a 'Swiss domain'; Group-IB does not confirm any Swiss victim

    Group-IB reports that in late July 2026 it found an open directory on a Latvian server that held the operator's /root/ directory, 457 files of which 35 were recovered, and documents more than 14 months of operations against Europe by an operator it tracks as DarkLunnen; Group-IB links it to no known actor and does not establish nationality or state affiliation (Group-IB, 2026-11-11). The main campaign used a modified watchTowr proof of concept for FortiOS CVE-2024-55591, designed to create a backdoor super-admin account named service (Group-IB, 2026-11-11); the recovered results list about 600 devices in Turkey (hospitals, industry and municipalities), 16 in Ukraine, 14 in Azerbaijan and 1 in Algeria, and a stolen FortiGate configuration from a Romanian organisation carried the same account and yielded 10 cleartext VPN passwords (Group-IB, 2026-11-11).

    The Swiss content is thin. Group-IB recovered a list of 4,725 FortiGate scanning targets for Switzerland and says such lists identify scanning targets but do not confirm vulnerability or successful exploitation; a table of additional operations also lists restic commands with AWS credentials accessing an S3 repository at a Swiss domain in May and June 2025, with production snapshots enumerated, and the report names no organisation and says that for several operations the evidence is limited to recorded commands (Group-IB, 2026-11-11). Fortinet's advisory FG-IR-24-535 lists FortiOS 7.0.0 through 7.0.16 and FortiProxy 7.2.0 through 7.2.12 and 7.0.0 through 7.0.19 as affected, fixed in 7.0.17, 7.2.13 and 7.0.20, names FortiOS 7.2, 7.4, 7.6 and 6.4 as not affected and offers disabling the HTTP/HTTPS administrative interface as the workaround (Fortinet PSIRT, 2025-01-14).

    Exposure
    A FortiOS 7.0 device below 7.0.17, or a FortiProxy below its fixed release, whose HTTP/HTTPS administrative interface was ever reachable from the internet; a device exposed while vulnerable can carry an account that patching does not remove (Group-IB, 2026-11-11).
    Detection
    In FortiGate event logs, an administrator named service with the super_admin profile, any unexplained administrator or local user, and super_admin logins or account creation through the jsconsole interface, which Fortinet lists among its indicators; in VPN logs, logins with accounts whose secrets sat in an exposed configuration (Group-IB, 2026-11-11).
    Defender takeaway
    Hunt for the account on patched devices too, assume the configuration was read on a device that was exposed while vulnerable and rotate the VPN user passwords, administrator passwords, IPsec pre-shared keys and LDAP or RADIUS credentials it stored, review VPN logs and enforce MFA, and enable private data encryption, which is off by default (Group-IB, 2026-11-11); no source says that a Swiss organisation was compromised.

    NOTABLENATOB2

    Device-code phishing disguised as a Microsoft Teams meeting booking: Huntress traces an October intrusion from a spear-phish through a Microsoft Safe Links-wrapped Google share link to a scheduler page whose 'Booking Reference' is the device code, an in-browser decrypted kit that restarts the flow when MFA is required, and a token replayed through a residential proxy

    In mid-October a Huntress SOC saw an employee of a construction company receive a spear-phishing email from a typosquatted domain impersonating another company's senior vice president; the link in the mail was wrapped by Microsoft Safe Links and pointed to a Google share link that redirected server-side to the lure page, so the mail body held the Google link and not the lure domain, which Huntress says sidestepped URL reputation checks for email security (Huntress, 2026-11-12). The page posed as a Microsoft Teams meeting scheduler, and behind it the backend started a Microsoft device-code sign-in; the "Booking Reference" shown to the victim is the device code, which the victim enters in a genuine Microsoft sign-in window (Huntress, 2026-11-12).

    The kit is shipped as AES-256-GCM ciphertext that the browser decrypts, so that to an email scanner or crawler that does not run JavaScript the page is an encrypted blob; if Microsoft answers AADSTS50076 or interaction_required because MFA is required, the kit starts a new device-code session and restarts the flow (Huntress, 2026-11-12). After the victim finished, the attacker held a session token and the device-code login (Cmsi:Cmsi) was routed through a residential proxy; the compromised account had no MFA enrolled and was used from an unmanaged device, and Huntress contained the incident before it escalated (Huntress, 2026-11-12).

    Exposure
    A Microsoft 365 tenant that allows the device-code flow for users with no device that needs it, particularly accounts without MFA.
    Detection
    In Entra sign-in logs, a successful device-code authentication shown as Cmsi:Cmsi, programmatic user agents such as python-requests and node afterwards (often only in the non-interactive log), and a change of ASN and region inside the same session ID; in mail and proxy telemetry, a Google share link that redirects to a freshly registered lookalike domain (Huntress, 2026-11-12).

    Triage: Huntress treats a device-code prompt that follows a link, a booking request or another unexpected interaction as suspicious, and the captured session shows up as a replay from another ASN and region within one session (Huntress, 2026-11-12).

    Defender takeaway
    Restrict or monitor device-code authentication where it is not needed, enforce phishing-resistant MFA, and investigate unfamiliar device sign-ins from unmanaged devices, new regions or residential proxy networks (Huntress, 2026-11-12).

    NOTABLENATOB1

    WFX Phantom: stolen GitHub tokens push a CI secret stealer into repositories from 2026-11-10, steal Actions secrets, runner memory and cloud tokens, plant AWS and Azure persistence designed to outlast rotation and delete the workflow runs; StepSecurity counts more than 63,000 probe pull requests

    StepSecurity reports that from 2026-11-10 an attacker uses stolen GitHub tokens of real developer and bot accounts, as a developer would, not a bug in GitHub Actions, to push a CI secret stealer into repositories those tokens can write to (StepSecurity, 2026-11-12). It first opens a pull request titled "docs: dependency audit notes" from a branch named wfx-docs that only proves write access; StepSecurity counts more than 63,000 such probes by 2026-11-12 (StepSecurity, 2026-11-12), Aikido, which tracks the campaign as wfx-loot, counts 4,837 compromised accounts and at least 1,835 repositories where the payload ran, and Endor Labs counts 8,926 infected repositories (Aikido, 2026-11-12; Endor Labs, 2026-11-12); BleepingComputer reports that the compromised accounts included those of the US General Services Administration and the French government (BleepingComputer, 2026-11-12).

    Where the token's permissions and the repository's setup let it run, the attacker pushes a script of about 1,500 lines through an edit to an existing workflow or CI shell script, a new workflow on a short-lived branch or a hidden script that an npm hook runs, and the script collects every Actions secret, the job token, the memory of the runner worker process and credential files for the major clouds and registries, then uses the job's OIDC token to open AWS, GCP and Azure sessions (StepSecurity, 2026-11-12). It plants persistence meant to outlast rotation, a rewritten AWS role trust policy with new access keys and federated identity credentials on Azure applications, sends the archive over HTTP and from 2026-11-12 through a Telegram bot, and within about a minute pushes a revert commit and deletes the workflow run, leaving a gap in the run numbers that StepSecurity calls the most reliable sign the stealer ran (StepSecurity, 2026-11-12). How the tokens were obtained is not known: some probes came through the Fly.io GitHub App, and StepSecurity has no evidence of a breach of Fly.io (StepSecurity, 2026-11-12). BleepingComputer's report of Aikido's findings gives the same probe title and start date (BleepingComputer, 2026-11-12).

    Exposure
    Any account or bot with write access to repositories you own or build from whose token may be exposed (a personal access token, an OAuth grant, a GitHub App user token), and any build with cloud OIDC trust or long-lived secrets; bots that bypass branch protection raise the risk (StepSecurity, 2026-11-12).
    Detection
    In source-control data, pull requests titled "docs: dependency audit notes", branches named wfx-docs and commits since 2026-11-10 with the messages "ci: refresh build cache", "ci: restore", "ci: cleanup", "chore: add ci helper" or "chore: add dependency audit workflow", and in CI run history a gap in the run numbers right after one; in AWS and Azure audit logs, changes to role trust policies, newly created access keys and federated credentials named wfx-ci (StepSecurity, 2026-11-12).

    Triage: a probe pull request alone shows that the account that opened it is compromised, even if nothing else happened; the payload probably ran where a commit with one of those messages is paired with a deleted run (StepSecurity, 2026-11-12).

    Defender takeaway
    Treat the account behind any probe or payload commit as compromised and revoke its tokens; where the payload ran, rotation is not enough because the persistence is designed to outlast it, and Endor Labs says secrets rotated after the first wave were likely stolen again in 1,838 repositories (Endor Labs, 2026-11-12).

    The fixed builds are 14.1-73.57, 13.1-64.39, 14.1-73.58 FIPS and 13.1-37.293 for 13.1-FIPS and 13.1-NDcPP (Cloud Software Group, 2026-11-12), and 14.1-74.34 for the Console (Cloud Software Group, 2026-11-12); Secure Private Access Hybrid deployments must upgrade their NetScaler instances (Cloud Software Group, 2026-11-12). Neither bulletin states an exploitation status or a workaround. CERT-EU writes that Citrix reports no exploitation and no confirmed public proof of concept (CERT-EU, 2026-11-12), NCSC Switzerland lists the exploitation status as unknown (NCSC Switzerland, 2026-11-12), and none of the CVEs is in CISA's catalog. heise reports that Citrix will publish NetScaler security fixes monthly on a fixed date close to Patch Tuesday from now on, with out-of-cycle updates for urgent cases such as active exploitation (heise, 2026-11-12).

    Exposure
    Every customer-managed NetScaler ADC or Gateway below the fixed build of its branch is in scope for CVE-2026-120868 whatever its configuration; the other rows apply where the named feature is configured, which the bulletin tells you to find with configuration searches such as add vpn vserver, add authentication vserver or add authentication samlAction (Cloud Software Group, 2026-11-12).
    Detection
    No source states a detection method or a check for compromise. The stated impact is a crash or denial of service, so unexplained packet-engine restarts, core files or reboots after inbound traffic to a Gateway or AAA virtual server are the telemetry to review; this is an inference, not a source statement. Where a logout had occurred, /var/log/httperror.log can hold authentication material (one of the rows), so limit who can read that file (Cloud Software Group, 2026-11-12).
    Defender takeaway
    Upgrade internet-facing Gateway and AAA appliances first, then every other ADC, to the fixed build of the branch, because CVE-2026-120868 needs no feature (CERT-EU, 2026-11-12) and neither bulletin offers a workaround (Cloud Software Group, 2026-11-12; Cloud Software Group, 2026-11-12); keep NSIP and the Console IP on a management network.

    NOTABLENATOB2

    SignDrop: a public Windows local privilege escalation to SYSTEM that turns Microsoft's CLFS authentication mitigation against itself through Defender's signature-update RPC; proof of concept published 2026-11-10, no CVE and no patch, no exploitation reported

    Cyderes Howler Cell reports that the exploit was published on 2026-11-10 under a GitHub handle, the same day as November Patch Tuesday, with no coordinated disclosure, no CVE and no patch, and that its team reproduced a SYSTEM shell from a standard user session (Cyderes, 2026-11-12). The chain is a logic bug with no memory corruption: CLFS containers are created through Object Manager symbolic links, an oplock on a bait file confirms that Microsoft Defender has engaged, a call to Defender's signature-update RPC makes clfs.sys create its .cnpf authentication-signature file as SYSTEM at an attacker-chosen path, here hid.dll in the Common Files\microsoft shared\ink directory, a file that does not ship in that directory; the content is replaced with a payload DLL and a runas request makes consent.exe load it, which starts a SYSTEM conhost.exe on the user's desktop (Cyderes, 2026-11-12). Like every release of the same cluster it needs a foothold on the host first. It applies where the CLFS authentication Mode value, under HKLM\SYSTEM\CurrentControlSet\Services\CLFS\Authentication, is 0 or 1 (Cyderes, 2026-11-12).

    Cyderes says the feature ships enabled on current Windows versions and that the researcher tested Windows 11 26H2 and experimental builds of Windows 11 and Windows Server 2025; the researcher's estimate that 80% of Windows installations are vulnerable has no data behind it (Cyderes, 2026-11-12). The researcher adds that, because the privileged file creation appears to come from the antimalware engine's own process, the technique can be used against any antimalware engine's self-defense; that claim rests on his statement alone (BleepingComputer, 2026-11-12). No source reports exploitation, and Microsoft had not commented publicly as of 2026-11-11 (SecurityOnline, 2026-11-11).

    Exposure
    Any Windows host on which an attacker can already run code as a standard user and whose CLFS authentication Mode is 0 or 1; Cyderes tells defenders to read the Mode value on every host to size the population (Cyderes, 2026-11-12).
    Detection
    File-creation telemetry for hid.dll in the ink directory, which Cyderes counts, with the Defender signature-update RPC call, among its two highest-signal observables because the file does not ship in that directory; that RPC called from a process outside the Defender service tree; symbolic-link churn under \BaseNamedObjects\Restricted\ correlated with Defender RPC activity; consent.exe loading a DLL from the ink directory; and a SYSTEM conhost.exe on the interactive desktop right after a hid.dll write. The exploit deletes hid.dll afterwards, so keep file-creation and image-load telemetry rather than relying on a disk sweep (Cyderes, 2026-11-12).

    Triage: Cyderes calls a hid.dll creation in the ink directory and a Defender signature-update RPC from outside the Defender service tree rare enough in a typical estate to alert on rather than hunt, and the first is a successful write whatever the variant (Cyderes, 2026-11-12).

    Defender takeaway
    No patch exists, so inventory the Mode value, restrict untrusted local code execution with application and script control, and do not switch CLFS authentication off as a workaround, because that re-exposes the older memory-corruption attacks it blocks; Cyderes counts sixteen public releases from the same researcher in roughly thirty-one weeks, so expect more (Cyderes, 2026-11-12).
