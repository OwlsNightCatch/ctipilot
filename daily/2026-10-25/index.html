    Linux kernel ZDI-CAN-33367: a public local root exploit for an skb_zerocopy page-cache write that gets past the Dirty Frag fix, with no CVE and no mainline fix, among six reports Trend Micro's ZDI copied to public lists, two of them ksmbd flaws scored CVSS 9.0

ZDI-CAN-33367 matters most: skb_zerocopy() moves shared page-cache pages into a new socket buffer without the marker the Dirty Frag fix added, so IPsec ESP decrypts in place and an unprivileged local user writes attacker bytes into the cached copy of a read-only file, which gives root through a setuid binary or /etc/passwd; the public exploit needs unprivileged user namespaces and networking modules such as nlmon and act_pedit (Sysdig, 2026-10-24). TuxCare reproduced a root shell on AlmaLinux 8 to 10 (Dirty Frag fix installed), CloudLinux 9 and 10, Debian 12 and 13 and Ubuntu 24.04 and 26.04 (AppArmor user-namespace restriction bypassed) (Sysdig, 2026-10-24). A reviewed patch from the netdev list is now in the kernel's networking tree but not in mainline, and a kernel with only the fix for CVE-2026-90049, a bug in the same function, is not covered (Sysdig, 2026-10-24; TuxCare, 2026-10-27). AlmaLinux has put fixed kernels into production (4.18.0-553.178.1.el8_10, 5.14.0-687.60.1.el9_8, 6.12.0-211.69.1.el10_2), and TuxCare's rebootless patch is out for EL9 and EL10, with EL8 ready and Debian and Ubuntu in progress (AlmaLinux, 2026-10-28; TuxCare, 2026-10-27).

    Two reports concern ksmbd, the kernel's own SMB server, not Samba. ZDI-CAN-33774 is a pre-authentication race in the SMB1 or SMB2 handler choice: its public proof of concept leaks 28 bytes of kernel heap per attempt and can crash the kernel, ZDI labels it remote code execution, nothing public shows code execution, and a fix is queued in ksmbd-for-next (Sysdig, 2026-10-24; Phoronix, 2026-10-22). ZDI-CAN-33549 is an SMB Direct integer underflow that needs an RDMA interface, a writable share and an SMB Direct client, and its proof of concept crashes the kernel (Sysdig, 2026-10-24). ZDI scores both 9.0, and Red Hat Enterprise Linux does not include ksmbd by default (The Hacker News, 2026-10-22).

    Exposure
    A Linux host where a local user or workload can run code and unprivileged user namespaces are on (shared hosting, CI runners, container nodes, login nodes) on the distributions above. For ksmbd, look for the ksmbd module, the ksmbd.mountd daemon and a kernel-owned listener on TCP 445 (Sysdig, 2026-10-24).
    Detection
    The exploit is one unprivileged process that unshares into new user and network namespaces and writes sysctls, brings up an nlmon interface, installs XFRM state over netlink, adds an nftables NFQUEUE rule, attaches a tc pedit action with a redirect and then calls splice() into a socket on the loopback address; Sysdig says nothing legitimate does all of that from one unprivileged process, so syscall-level runtime telemetry sees it (Sysdig, 2026-10-24). The write lands in the page cache, not the file, so a disk-content integrity check does not show it.
    Defender takeaway
    Restrict unprivileged user namespaces where nothing depends on them (Sysdig says user.max_user_namespaces=0 should block the public exploit, untested by TuxCare, and breaks rootless containers and some build tooling), do not rely on Ubuntu's AppArmor restriction, set seccomp RuntimeDefault on Kubernetes pods and install the fixed kernel where your distribution has shipped it; unload ksmbd where unused and keep TCP 445 to trusted networks where it must stay (Sysdig, 2026-10-24).

    NTLM relay past required signing: SpecterOps and Blackfield re-authenticate a signed LDAP or SMB session with a relayed victim identity, and Microsoft fixed it in the September and October 2026 updates

    SpecterOps and Blackfield show that NTLM relay to a server that requires signing works again when the attacker first owns a signed session and then re-authenticates it with the victim's identity, so the session keeps the attacker's signing key. For LDAP, the attacker signs a session to a domain controller with valid credentials or, where accepted, an anonymous NTLM context, coerces a victim over SMB, and sends the victim's relayed authentication with a malicious LDAP modification in one SASL record signed with the attacker's key; the controller checks the signature once, switches to the victim's identity and runs the modification with the victim's rights (SpecterOps, 2026-10-23). The tested controller enforced LDAP signing and channel binding and the attack still worked over 389/TCP; the demonstration writes the resource-based constrained delegation attribute, and relaying a domain controller's machine account to another controller leads to DCSync and domain compromise (SpecterOps, 2026-10-23). Blackfield shows the SMB counterpart: a server keeps the original signing key on re-authentication without checking that the identity matches, so on any host that requires SMB signing, domain controllers included, a relayed privileged authentication yields a privileged session still signed with the low-privilege key, provided the attacker can capture or coerce that authentication (Blackfield, 2026-10-21).

    SpecterOps reported the LDAP flaw to Microsoft on 2026-10-06, received no response, and says the fix shipped in the 2026-10-13 cumulative update, KB5126646, while the SMB variant was patched quietly in September 2026 (KB5122882) (SpecterOps, 2026-10-23). KB5126646 is the October update for Windows Server 2025 and KB5122882 the September update for Windows Server 2022 (Microsoft, 2026-10-13; Microsoft, 2026-09-08), so each release needs its own cumulative update of the month. Blackfield found no CVE or KB note for the SMB change, says similar changes seem to have reached the other supported versions in the following weeks without having traced every build, and warns that one or two end-of-life versions may never receive it (Blackfield, 2026-10-21). Both publish tooling; neither reports use in attacks (SpecterOps, 2026-10-23; Blackfield, 2026-10-21).

    Exposure
    Windows Server domain controllers and SMB servers without the September 2026 (SMB) or 2026-10-13 (LDAP) cumulative update of their release; SpecterOps tested Server 2016 domain controllers and above and says every Server 2022 and 2025 domain controller it tested accepted the relay with LDAP signing required (SpecterOps, 2026-10-23). The LDAP variant needs a signed session the attacker controls, a victim coerced to authenticate over SMB and LDAP reachable on 389/TCP (SpecterOps, 2026-10-23).
    Detection
    Neither researcher publishes detection guidance. The demonstration ends in an LDAP modification of msDS-AllowedToActOnBehalfOfOtherIdentity on the victim's own computer object, and msDS-KeyCredentialLink (shadow credentials) is the other write (SpecterOps, 2026-10-23), so directory-service change auditing on computer objects for those two attributes is where it surfaces, attributed to the victim's own computer account while the connection comes from the attacker's host. Patching does not remove values a relay already wrote.
    Defender takeaway
    Confirm that every domain controller runs the 2026-10-13 cumulative update of its Windows release and every Windows server the September one, because required signing did not stop this relay before them. SpecterOps also advises enforcing LDAP signing and channel binding together, restricting LDAP on 389/TCP where possible and reducing NTLM; Blackfield says SMB signing stays necessary but is not sufficient (SpecterOps, 2026-10-23; Blackfield, 2026-10-21).
