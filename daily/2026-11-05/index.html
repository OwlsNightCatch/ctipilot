    Canton Vaud warns of a device-code phishing campaign against Microsoft 365 accounts running in French-speaking Switzerland, with several organisations already affected

    The canton of Vaud said on 2026-11-04 that a phishing campaign is currently running in French-speaking Switzerland and that several organisations have already been affected (translated from French) (Canton of Vaud, 2026-11-04). The messages can appear to come from a company or a known contact and invite the reader to view an invoice, open a document or verify information through a link; the campaign uses device-code phishing, which gets the victim to type a code on a genuine Microsoft authentication page and so gives the attackers fraudulent access to the Microsoft 365 account (Canton of Vaud, 2026-11-04). The links printed in the notice combine a company-style name and a portal word on a workers.dev subdomain whose second label starts with a cloud-storage word and an identifier, and the canton says other addresses can be used too (Canton of Vaud, 2026-11-04); workers.dev is the route assigned to every Cloudflare Worker (Cloudflare Docs, 2026-09-22). The notice names no actor, kit, count of organisations, sector or start date.

    Exposure
    Any Microsoft 365 tenant whose users can complete the device code flow, which Microsoft describes as meant for devices without local input such as shared devices or digital signage and as a high-risk method that phishing can use (Microsoft Learn, 2026-03-24).
    Detection
    Mail, web proxy and DNS telemetry for links to workers.dev subdomains of the structure above; in the Entra sign-in logs, device code events found with the authentication protocol filter (Microsoft Learn, 2026-03-24). Microsoft says protocol tracking persists through token refreshes, so later sign-ins in the same session can fall under an authentication-flows policy, and it records an original transfer method property in the activity details of the Conditional Access sign-in logs (Microsoft Learn, 2026-03-24).

    Triage: Microsoft documents device code sign-in for shared devices and signage; a device-code sign-in by a user who has no such device, soon after that user received a mailed link, falls outside that use (Microsoft Learn, 2026-03-24).

    Defender takeaway
    Where the tenant has no documented need for device code flow, Microsoft recommends blocking it with a Conditional Access policy, testing in report-only mode and auditing existing use first (Microsoft Learn, 2026-04-07). Tell users never to enter a Microsoft login code at a third party's request, and that anyone who has entered a code or validated an authentication request must call IT support at once, which is the canton's own instruction (Canton of Vaud, 2026-11-04).

    Sekoia: an APT29-linked watering hole serves n-day iOS and Android exploit chains through compromised sites, clone domains and a one-week compromise of the Plerdy tracker; CISA lists the Apple WebKit pointer-authentication bypass CVE-2024-27834 as exploited on 2026-11-04

    CISA added CVE-2024-27834, a WebKit flaw that lets an attacker with arbitrary read and write capability bypass Pointer Authentication and that Apple fixed on 2024-05-13, to its Known Exploited Vulnerabilities catalog on 2026-11-04, and names no victim or method (CISA KEV, 2026-11-04; Apple, 2024-05-13; Apple, 2024-05-13). The same day Sekoia reported a watering-hole campaign that it assesses with moderate to high confidence to be APT29 or one of its subgroups and in which that flaw is the pointer-authentication bypass of an iOS chain (Sekoia, 2026-11-04); the link between the listing and the campaign is the date alone. Sekoia retrieved three chains from the delivery host, which profiles the visitor and serves a platform-specific exploit without user interaction: an iOS 16.7 chain (CVE-2025-43529, then CVE-2024-27834) that steals the cookies of running apps; a DarkSword-based iOS chain that Sekoia's table labels iOS 18.5 (CVE-2025-43529 with CVE-2026-20700, then CVE-2025-14174 with CVE-2025-43510, then CVE-2025-43520) that harvests the phone; and an Android chain for Chrome 139 to 145 except 143 (CVE-2026-3910, then the Adreno driver flaw CVE-2025-27038) that takes Chrome cookies, saved logins, history and Wi-Fi configuration (Sekoia, 2026-11-04). The payloads exfiltrate data without establishing persistence, and Sekoia says none of the chains contains a zero-day or works against fully updated devices (Sekoia, 2026-11-04).

    Delivery used JavaScript injected into legitimate sites, among them a Ukrainian gas producer, a US chemical-industry trade association, a Bulgarian military-related site and an Australian clinic; reverse-proxy clones of high-profile sites; and a one-week compromise, 27 August to 3 September 2026, of the Plerdy SEO tracker script, which Sekoia says exposed hundreds or thousands of sites, mostly Ukrainian (Sekoia, 2026-11-04). Sekoia names no Swiss victim, counts no infected devices and says it is working with national CERTs on victim identification.

    Exposure
    IPhones and iPads below the builds that fix the six iOS flaws, and Android phones on Chrome before the fix of CVE-2026-3910 or an unpatched Adreno driver. Sekoia's iOS 16.7 chain filters for iOS 16.7 and 16.7.10, and the sources do not establish whether the later 16.7.x builds Apple lists for iPhone 8, 8 Plus, X, iPad 5th generation and the first-generation iPad Pro models, up to 16.7.16 of 2026-05-11, are exploitable (Sekoia, 2026-11-04; Apple, 2026-05-11).

    Fixes: iOS 26.2 and 18.7.3 close CVE-2025-43529 and CVE-2025-14174, iOS 26.1 and 18.7.2 close CVE-2025-43510 and CVE-2025-43520, iOS 26.3 closes CVE-2026-20700, and Chrome 146 closes CVE-2026-3910 (Apple, 2025-12-12; Google Threat Intelligence Group, 2026-03-18; Chrome Releases, 2026-03-12).

    Detection
    Sekoia names one on-device trace, a marker cookie that the iOS 16.7 chain's script sets as a replay guard so the exploit does not fire twice on a victim; it publishes some indicators and withholds several delivery and exfiltration hosts, so a visit to an injected site shows in web proxy and DNS telemetry from managed phones only against indicators obtained from Sekoia or a national CERT; the dependable check is the OS and Chrome version inventory (Sekoia, 2026-11-04).
    Defender takeaway
    Bring managed iOS devices to the newest release for each model and Android phones to current Chrome and the OEM patch level, because Sekoia says updated devices resist these chains and CISA lists every flaw they deliver as exploited (Sekoia, 2026-11-04; CISA KEV, 2026-11-04); the devices that cannot go past iOS 16.7.x are the open question.

    Sophos's own root-cause analysis of a developer-targeted intrusion: a fake job-interview repository's VS Code workspace settings ran BeaverTail and InvisibleFerret on a Mac whose endpoint agent had not reported since 11 June, and a third-party OAuth authorization outlived the session revocation

    On 2026-09-14 a Sophos employee cloned a public repository presented as a job-interview coding assignment and opened it as a workspace in VS Code; a weaponized workspace settings file replaced the editor's integrated terminal profile with a command that downloads and runs a remote script in a loop, delivery relied on the user opening the workspace as trusted, and no exploit or vulnerability was involved (Sophos RCA, 2026-10-20). Opening a terminal was enough: a shell script fetched a JavaScript component and a package manifest into a hidden directory in the user profile, a package-manager install ran, the JavaScript ran under Node.js and the final-stage backdoor lived in memory only, with no persistence found (Sophos RCA, 2026-10-20). SophosLabs identified the BeaverTail loader followed by the InvisibleFerret backdoor, able to steal browser-stored credentials, keychain data and SSH keys, and the JavaScript stage sent the process environment to an attacker web endpoint on a cloud application-hosting service (Sophos RCA, 2026-10-20).

    Two gaps lengthened the exposure. The Sophos Endpoint agent was installed but its core services were not running, so it enforced nothing and reported nothing; the device was last seen in Sophos Central on 2026-06-11, the cause is still under investigation, and SophosLabs says a working agent would have blocked the chain at the first dropped file (Sophos RCA, 2026-10-20). A third-party application authorization on the employee's source-code platform account survived the session revocation and password reset of 2026-09-15 and made 27 read requests against two internal repositories from an address new to the user until it was revoked on 2026-09-16; Sophos found no other host, no cloud activity and no customer impact (Sophos RCA, 2026-10-20). The analysis names no group; Sophos CTU says the technique matches the tradecraft of NICKEL ALLEY, which it describes as running the Contagious Interview campaign of fake companies, fake recruiters and malicious code repositories (Sophos blog, 2026-11-04).

    Exposure
    Developer workstations whose users clone and open repositories from outside parties, recruitment pretexts included, in an editor that trusts the workspace; and any managed device that is compliant in identity and device management but does not report to the endpoint console, as Sophos's fleet review found (Sophos RCA, 2026-10-20).
    Detection
    In macOS process lineage, the code editor's integrated terminal launching a download-and-run command that a cloned workspace's settings define, followed by a hidden directory in the user profile and a package-manager install run from it (Sophos RCA, 2026-10-20). In identity telemetry, a device that still signs in but does not report to the endpoint console is a coverage gap; a third-party authorization reading repositories from an address new to the user is the second signal (Sophos blog, 2026-11-04; Sophos RCA, 2026-10-20).

    Triage: a terminal profile normally launches a shell executable; this one launched a command that downloads and runs a remote script in a loop; it came from the settings of a freshly cloned repository (Sophos RCA, 2026-10-20).

    Defender takeaway
    Treat a coding assignment or repository from a recruiter or interviewer as untrusted code, because here the compromise needed only a trusted workspace and an opened terminal. Sophos's lasting controls are to require the endpoint agent for device compliance, to monitor for managed devices that stop reporting, and to revoke application authorizations as part of credential containment, not only sessions and passwords (Sophos RCA, 2026-10-20).

    A SEPPmail Secure Email Gateway before 15.1.1; the Home page of the administration interface shows the running version in the System section as "Firmware version" (SEPPmail, retrieved 2026-11-05).     03Research, reports & policy1 item

    NOTABLENATOB2

    SpecterOps: a Windows iSCSI Target Server set up without CHAP lets any host that knows the target and an authorised initiator name read the shared disks below file permissions, a Hyper-V domain controller's among them

    SpecterOps shows that the Windows iSCSI Target Server role, set up as a community cluster guide describes it with the optional CHAP step skipped, accepts a login from any host that knows the target host, the target name and an authorised initiator name (SpecterOps, 2026-11-04). The post says the role registers a service principal name on its computer account, so a directory query lists the target hosts, that initiator names are built from the host's DNS name and are therefore predictable, and that in the author's experience the service has no rate limiting or brute-force protection (SpecterOps, 2026-11-04). Access is below the file system, so NTFS permissions do not apply, and volume encryption such as BitLocker defeats it (SpecterOps, 2026-11-04). The worst case the post shows is a volume that holds a Hyper-V domain controller's virtual disk, from which the local credential stores and the directory database can be taken (SpecterOps, 2026-11-04). The author has not tested the technique in production and warns that it can cause outages, and the post cites no Microsoft response.

    Exposure
    Windows Server hosts that run the iSCSI Target Server role without CHAP, found by the service principal name the role registers and by a listener on TCP 3260 (SpecterOps, 2026-11-04; Pen Test Partners, 2016-05-18). The author's own research puts the common uses with clustered resources such as Hyper-V, SQL Server and Exchange database availability groups, followed by third-party backup products (SpecterOps, 2026-11-04).
    Detection
    The post names no telemetry. What the mechanism implies, not stated by the post: iSCSI traffic to TCP 3260 on a target host from a source that is not one of its cluster nodes, and a login that presents a listed initiator name from another source address, because the access list keys on initiator names that an impersonator can present (SpecterOps, 2026-11-04).
    Defender takeaway
    Enable CHAP on every iSCSI target, and isolate iSCSI traffic with segmentation and host-based firewalling, which the post calls arguably the most effective step; the post says IPsec mitigates network sniffing, and BitLocker or similar volume encryption makes the stolen disk unreadable (SpecterOps, 2026-11-04). Treat the disks of any domain controller that sat on an unprotected target as exposed.
