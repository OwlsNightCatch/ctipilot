    Tangerhütte (Saxony-Anhalt): the vendor of the municipal citizen-portal software says attackers exploited a zero-day in it, classifies the intrusion as AI-driven, and four other communes took their portals offline

    MDR AKTUELL reports on 2026-10-13 that the vendor of Tangerhütte's "digitales Rathaus" citizen portal says attackers found and exploited a vulnerability in its software that the vendor did not know of and for which no security update existed (MDR AKTUELL, 2026-10-13). The portal, an app-based service that went online in 2020, was taken offline in September, and MDR Sachsen-Anhalt reported on 2026-09-16 that the municipality said it had repelled an attack and gave no technical detail (MDR Sachsen-Anhalt, 2026-09-16). The software runs on systems that the state municipal IT provider KID operates for Tangerhütte; an IT employee noticed irregularities in the morning after the attack began at night, the server was isolated and cut from the internet, and the vendor analysed the secured logs on an offline notebook (MDR AKTUELL, 2026-10-13). Innocon told other affected communes, four of which also took their portals offline as a precaution although there was no sign of an attack on them, and says the attackers reached only test accounts and took no real data (MDR AKTUELL, 2026-10-13). Citizens could use the services only on paper for weeks (MDR AKTUELL, 2026-10-13).

    The vendor classifies the intrusion as AI-driven for two reasons: commands were executed faster than copy-and-paste would allow, and the follow-on steps were not prepared in advance but developed on the city's server during the attack, whereas human attackers normally upload their own code and do not change it (MDR AKTUELL, 2026-10-13). That is the vendor's reading of its own logs. The state criminal police are investigating data espionage and can neither confirm nor deny an AI attack, and two professors told MDR the reading is plausible without having seen the logs (MDR AKTUELL, 2026-10-13). No CVE, product version, fixed release or entry vector is named.

    Exposure
    Municipalities running Innocon's digitales Rathaus, which is used for Tangerhütte and at least four further communes that Innocon informed; whether any Swiss body runs it is not reported. The case matters to communal administrations as a supplier-built citizen portal hosted by a shared municipal IT provider, where the customer cannot patch an unknown flaw itself.
    Detection
    The vendor's two observations are the pattern to look for in a portal host's logs: commands issued faster than a person could type them, and follow-on scripts written and run on the host within the same session rather than uploaded once.
    Defender takeaway
    For a citizen portal built on a supplier's software, an exploited unknown flaw leaves isolation as the only lever, and this case shows what worked: isolate the server, copy the logs and analyse them offline, and have the supplier warn its other customers, four of which pulled their portals as a precaution.

    CRITICALCVE-2026-104935 +2exploitedupdatedNATOA1

    CVE-2026-104935, Ivanti Connect Secure: an authentication bypass chained to code execution is exploited as a zero-day, the root-escalation step was patched on 2026-10-29 and CISA lists all three chain flaws (CVSS 8.6)

    Ivanti disclosed CVE-2026-104935 in Connect Secure on 2026-10-13 and says it is aware of limited exploitation in the wild (Ivanti, 2026-10-13); Rapid7 describes it as an authentication bypass by spoofing that lets a remote unauthenticated attacker run commands, CVSS 8.6 (Rapid7, 2026-10-13), and CISA listed it in KEV the same day (CISA, 2026-10-13). Volexity tracks the operator as UTA0576 and dates exploitation of a fully patched 22.8R2.4 appliance to 2026-10-03 (Volexity, 2026-10-13).

    The chain has three steps. A request to the public login script welcome.cgi names a protected script in an X-DSCGI-PATH header, so the URL passes the authentication check and the header picks the destination. The upload script wu.cgi writes a file to disk before checking that it is a ZIP, and parallel requests run a Perl script before it is deleted. A root escalation then abuses the dsinvoked service's trust in the shared DSCache configuration store (Volexity, 2026-10-13). The first two steps are CVE-2026-104935 and the root step is CVE-2026-111357 (GitHub Advisory Database, 2026-10-15); Volexity's update banner says Ivanti patched it on 2026-10-29 (Volexity, 2026-10-13). CISA listed it and a third chain flaw, CVE-2026-118527, on 2026-10-30, says each can be chained with the other two, and describes CVE-2026-118527 as a predictable-identifier flaw that lets a remote authenticated attacker upload files with attacker-controlled content to a known location on disk (CISA KEV catalog, 2026-10-30). No source says which step of the chain that is, and it has no public CVE record or fixed build yet.

    The exploit leaves no web shell and patches library code in memory only, so Ivanti's Integrity Checker Tool, which looks for file changes, does not detect it, and Volexity found log entries removed. The operator then went after the Active Directory service account stored on the appliance: LDAP queries for LAPS passwords, BitLocker recovery keys and password attributes, password spraying, and packet capture of plaintext LDAP, HTTP Basic and NTLM traffic (Volexity, 2026-10-13).

    Exposure
    25.1.1.1 and prior, 25.1.2.2 and prior and 22.8R2.4 and prior are affected by CVE-2026-104935 and 22.7.x and below are not (Rapid7, 2026-10-13). The Canadian Cyber Centre's bulletin, updated 2026-10-30, lists every version before 25.1.1.3, 25.1.3.1 and 22.8R2.6 as affected (Canadian Centre for Cyber Security, 2026-10-13), which takes in 25.1.1.2 and 22.8R2.5, the builds of 2026-10-13; CISA's alert, updated the same day, says the three chain CVEs affect versions 25.1.1.2 and prior, 25.1.2.2 and prior and 22.8R2.5 and prior (CISA, 2026-10-13). Ivanti's advisory could not be read, so per-CVE fixed builds are unconfirmed.
    Detection
    The appliance's own logs were tampered with, so start upstream: web proxy, load balancer or WAF logs for many requests to welcome.cgi, above all with an X-DSCGI-PATH header or one whose script differs from the URL path. On domain controllers, look for LDAP queries from the appliance's service account for LAPS, BitLocker recovery and password attributes, and spraying from the appliance's address. Patching does not evict an attacker who is already in.
    Defender takeaway
    Upgrade to 25.1.1.3, 25.1.3.1 or 22.8R2.6 now, then treat every appliance that was exposed on an affected build as a compromise-assessment target and rotate what it could reach. Where compromise cannot be excluded, isolate the appliance and preserve its memory and logs before any reset, because CERT-FR knows of lateral movement using the LDAP and Active Directory secrets stored on it (CERT-FR, 2026-10-14).

    CVE-2026-96951, Windows Shell: a Mark of the Web bypass exploited as a zero-day, fixed in the 2026-10-13 cumulative updates and listed in CISA KEV (CVSS 8.8)

    Microsoft's 2026-10-13 release fixes CVE-2026-96951, a Windows Shell security feature bypass that Microsoft marks as exploited and not publicly disclosed (Microsoft Security Response Center, 2026-10-13); CISA added it to its Known Exploited Vulnerabilities catalog the same day, citing evidence of active exploitation (CISA, 2026-10-13). Microsoft says an attacker who exploits it could evade Mark of the Web defenses, by sending a crafted file by email or instant message or enticing the user to click a link or open an attachment (Microsoft Security Response Center, 2026-10-13). Microsoft's record gives the root cause as improper neutralization of special elements in a command (command injection, CWE-77) (Microsoft Security Response Center, 2026-10-13). Rapid7 describes the effect as Windows not showing the dialog that says it protected the PC, because the tag that triggers it is bypassed, calls this the second exploited Windows Shell zero-day this year, and says the flaw also affected Outlook.com, patched in a build several weeks ago (Rapid7, 2026-10-13). Rapid7 says Windows Server 2012 receives no patch while Server 2012 R2 does (Rapid7, 2026-10-13), and Microsoft's record lists no Windows Server 2012 product for this flaw (Microsoft Security Response Center, 2026-10-13).

    Exposure
    Windows 10, Windows 11 and Windows Server 2012 R2 through 2025 where users open files or links from mail, chat or the web; the fixed build per release is in the CVE record, and Rapid7 reports no patch for Windows Server 2012.
    Detection
    Microsoft, CISA and Rapid7 name no actor, payload or victims and no source describes the exploit's behavior, so this is a hunt hypothesis that follows from the mechanism: the failed control is the Mark of the Web tag, so there is no warning dialog for a user to report. Look at mail gateway, chat and endpoint file-origin telemetry for internet-origin files, archives and shortcuts that execute without the usual download warning, and at process lineage from explorer.exe into scripting interpreters and living-off-the-land binaries shortly after a mail or browser download.

    Triage: a file a user created or received from a trusted local source also carries no tag; the discriminator is an internet origin (mail, chat or web download) together with the absence of the tag on the opened item.

    Defender takeaway
    Install the October cumulative update now, ahead of the monthly cycle, on endpoints that open mail and web downloads first; because the tag is the control that failed, attachment blocking and mail-gateway detonation remain the compensating layer until the update is deployed, and Rapid7 reports no patch for Windows Server 2012.

CVE-2026-70279 is a cross-site scripting spoofing flaw (CVSS 9.3, also Exploitation More Likely): an attacker who persuades an administrator to click a crafted link could act with that administrator's privileges (Microsoft Security Response Center, 2026-10-13).     The fixed builds are Exchange Server Subscription Edition RTM 15.02.2562.056, 2019 CU15 15.02.1748.055, 2019 CU14 15.02.1544.050 and 2016 CU23 15.01.2507.077 (Microsoft Security Response Center, 2026-10-13). The 2016 and 2019 updates are available only to organisations enrolled in the Period 2 ESU program, and October 2026 is the last month those customers receive newly released updates (Microsoft Exchange Team, 2026-10-13). After October, updates ship for Subscription Edition only, Microsoft's announcements and CVEs stop mentioning 2016 and 2019, and Microsoft says that does not mean those versions are not vulnerable and that it will stop testing them for vulnerabilities (Microsoft Exchange Team, 2026-10-13); buying Period 2 ESU later only gets an organisation current through this release (Microsoft Exchange Team, 2026-10-13). Exchange Online customers are already protected (Microsoft Exchange Team, 2026-10-13).

    Exposure
    On-premises Exchange Subscription Edition, 2019 CU14 and CU15 and 2016 CU23 that receive external mail for CVE-2026-70571, and administrator sessions in the web interfaces for CVE-2026-70279.     Detection
    No source describes exploitation behavior. Microsoft says a successful attempt is not guaranteed, so, as an inference from the mechanism, a failed attempt would more likely appear as a crash than a shell: watch for crashes and application-log faults of the Exchange transport processes right after inbound mail from outside, and for unexpected child processes of those processes.
    Defender takeaway
    Install the October update on every Exchange server and management-tools machine, because Microsoft rates both flaws Exploitation More Likely. An organisation still on Exchange 2016 or 2019 without Period 2 ESU has no update for CVE-2026-70571 and no further updates after this one; the choices are enrolling, which ends at October's release, or moving to Subscription Edition. On an Exchange host that also takes the October Windows Server update, do not uninstall that update: Microsoft says the OWA failures, growing mail queues and lost DAG quorum that can follow are not caused by the Exchange security update, and its workaround is to set the Rpc registry value EpmapSavedContextCap to 65536 and reboot (Microsoft Exchange Team, 2026-10-17).
