    NOTABLENATOB2

    SoftwareOK: Q-Dir 12.83 to 12.85 and DesktopOK 12.82 and 12.85 installers from the vendor's official site carried a Python remote-access tool, ASEC says the update function may have been affected too, and reinstalling may not remove it

    AhnLab's ASEC reports that Q-Dir 12.83.0.0, 12.84.0.0 and 12.85.0.0 and DesktopOK 12.82.0.0 and 12.85.0.0 were replaced with tampered installers on SoftwareOK's official distribution path, and that the SHA-256 of some files downloaded from the official site did not match the value posted on its download page. ASEC says the evidence indicates malicious files were also generated during the update process of installed copies, a point it later hedges (users of the update function "may have been affected"), and that it has not identified how the files were replaced (ASEC, 2026-11-25).

    The tampered installer embeds the genuine, correctly signed Q-Dir or DesktopOK executable and runs it from the public user folder so the program appears to work. It then downloads the legitimate 7-Zip console extractor and a package holding a Python runtime and a remote-access tool, unpacks it under a Microsoft-looking folder in ProgramData and persists through a scheduled task, named to look like Edge, that runs the windowless Python interpreter. The tool runs shell commands and Python code, transfers files, takes screenshots and collects system information, and it compares running processes with a list of 1,206 security-product process names and sends the matches to its server. ASEC does not describe the server protocol, names no malware family or actor, and reads Chinese-language comments in the code only as a hint (ASEC, 2026-11-25).

    ASEC gives no distribution window. SoftwareOK's release pages date Q-Dir 12.83 to 4 November, 12.84 to 13 November and 12.85 to 21 November (SoftwareOK, 2026-11-21) and DesktopOK 12.82 to 28 October and 12.85 to 19 November (SoftwareOK, 2026-11-26), which bounds only when the listed versions could first have reached users, and its Q-Dir download page carries no notice about tampering as of 2026-11-27 (SoftwareOK, 2026-11-27).

    Exposure
    Any Windows endpoint on which the listed versions were installed or updated since 2026-10-28; ASEC adds that other versions installed or updated while the tampered files were distributed may be affected. The installed program is the genuine signed one, so a signature check on it passes; the check that finds the tampering is the installer's SHA-256 against the vendor page.
    Detection
    Software-inventory telemetry for the listed versions; in scheduled-task creation and process-creation telemetry, a task running a bundled Python interpreter from under ProgramData and an extractor tool started by an installer; and egress from that interpreter. After removal ASEC says to look for the Python environment, scheduled tasks, related files and external connections.
    Defender takeaway
    Treat every host that ran an affected installer or updater as compromised: isolate it, remove the tool and rotate the credentials used on it, because ASEC says uninstalling and reinstalling the utility may not remove the remote-access tool.

    02Trending vulnerabilities1 item

    NOTABLECVE-2026-99362NATOB2

    NFS2ROOT, CVE-2026-99362, Linux kernel NFS server (nfsd): an unauthenticated heap overflow over NFSv4.1 or 4.2 that OpenSec says it turned into a root shell with one TCP connection to port 2049 (CVSS 3.1 9.8); fixed upstream in 6.12.117, 6.18.61, 7.3.2 and 7.4-rc1, Ubuntu and RHEL 9 and 10 list no fixed kernel on 2026-11-27, exploit private, no exploitation reported

    CVE-2026-99362 is a heap out-of-bounds write in the Linux kernel's NFS server: nfsd4_sequence() narrows the reply buffer to the session's cached-reply limit before it accepts the slot sequence id, a client can negotiate that limit down so every slot has a zero-length buffer, and the server then caches a whole reply into a buffer with no room; the flaw has been present since Linux 3.16 (Linux kernel CVE team, 2026-11-19). The announcement lists fixes in 6.12.117, 6.18.61, 7.3.2 and 7.4-rc1 (Linux kernel CVE team, 2026-11-19); ENISA's record, last updated on 2026-11-23, adds 5.10.275, 5.15.226, 6.1.193 and 6.6.163 (ENISA EUVD, 2026-11-23).

    OpenSec, which reported it, says an unauthenticated client reaches a root shell with one TCP connection to port 2049 over NFSv4.1 or 4.2, shows this in its own recording and says its exploit stays private (OpenSec, 2026-11-25). watchTowr reports no exploitation in the wild as of 2026-11-26 (watchTowr, 2026-11-26), and the fix with its root-cause text has been public on the linux-nfs list since 2026-08-17 (linux-nfs, 2026-08-17).

    Distribution status as read on 2026-11-27: Debian trixie and the 6.12 backport kernel for bookworm are fixed, bookworm's default 6.1 kernel is not (Debian, 2026-11-27); Red Hat fixed RHEL 8 on 2026-11-26 (RHSA-2026:103817) while RHEL 9 and 10 are listed as affected with no fix (Red Hat, 2026-11-26); Ubuntu shows no fixed kernel on any release from 16.04 to 26.10 (Ubuntu, 2026-11-25).

    Exposure
    A host that serves NFS. Red Hat says default RHEL does not run nfsd, which limits the attack surface to systems configured to export NFSv4.1 or 4.2 shares (Red Hat, 2026-11-26). OpenSec's test is nfsd loaded, /proc/fs/nfsd/versions showing +4.1 or +4.2 and a listener on port 2049 on a non-loopback address, with a kernel older than the fixed one and no distribution backport (OpenSec, 2026-11-25). No source says whether an empty export list or client-address restrictions reduce the reach.
    Detection
    OpenSec says the traffic is valid NFS with no network signature and names kernel warnings from nfsd4_check_resp_size, oopses with nfsd4, svc or call_usermodehelper frames, shells spawned by kernel workers on a file server and bursts of short NFSv4.1 sessions from one source; no vendor confirms these (OpenSec, 2026-11-25). On a server that was reachable while unpatched, the kernel-worker-spawned shell is the compromise check.
    Defender takeaway
    On NFS servers, restrict TCP 2049 to trusted networks, the step OpenSec, watchTowr and Red Hat all name, or stop nfs-server where it is not needed (Red Hat, 2026-11-26); turning off NFSv4.1 and 4.2 is the researchers' mitigation and no vendor endorses it. Then install the first distribution kernel that lists the CVE and reboot. A host that does not run nfsd is outside the exposure the sources describe.

    Huntback's decoy captured the exploit chain for CVE-2026-115731 on 2026-11-19, two days after the KEV listing: a certificate request, a fetch of the signed certificate that tests for autosigning, and a report upload carrying a type definition, which it reads as a check for vulnerable servers. The hunt signal is a PUT to the certificate-request path from a non-agent address, a GET for the same name within seconds, then a PUT to the report path.

    Huntback, a research firm that runs decoy servers, captured the whole exploit chain on one Puppet Server decoy on the morning of 2026-11-19, in 1.47 seconds from one address (Huntback, 2026-11-20). The chain is a bare certificate request for a generated node name, which a CA that asks for a shared secret or other proof would refuse, a fetch of the signed certificate 1.4 seconds later without polling, which answers 200 only where the CA signs automatically, and a report upload whose wrapper is ordinary and whose event carries a type definition with a Ruby method annotation (Huntback, 2026-11-20). Huntback reads it as a check for vulnerable servers: the decoy signed the certificate, accepted the report with a 200 and returned no marker, and the same address had tried exploits for four other products in the previous ten days (Huntback, 2026-11-20). A scout from a different address had probed the status service and the CA paths about two and a half hours earlier without asking for a certificate. Huntback's advice is to list the signed certificates (puppetserver ca list --all) and account for every name, to refuse at a reverse proxy any report containing RubyMethod, since no agent sends a type definition in a report, and to keep TCP 8140 closed to networks that are not agents'; none of this is vendor guidance (Huntback, 2026-11-20). The capture is a single source and Huntback names no actor or victim.

    Update27 Nov 2026 04:54 UTCrun 2026-11-27T0355Z-intelsummaryentitiessourcesevidencesourcing_notebodyupdated_at

    Wiz shows that ARTEX writes a numeric intent ID from a per-installation counter it does not reset by default, and Cairn a per-project one, into AWS and Azure resource names, session names and comments, a pivot for hunting and linking activity; Wiz ties ARTEX-Harvester to more than a dozen organisations, Huntback's exposed console shows a Global Administrator takeover at a South Korean university, and DIVD's forensic report finds the same numbering in its own breach.

    Wiz Research shows how ARTEX and Cairn leak their intent numbering into victim logs. ARTEX draws intents, facts, findings, hints and digests from one counter per installation that is never reset by default, so intent numbers climb across runs and targets and consecutive ones are rare, and it puts the number in its working directory, its session name and its prompt; Cairn formats zero-padded counters per object type and resets them for every project (Wiz, 2026-11-25). The numbers surface wherever an API takes a name or comment: AWS role session names, SSM command comments, KMS key descriptions and aliases, security-group rule descriptions, Azure run-command, VM and app-registration names, and the error message of a denied call (Wiz, 2026-11-25). Wiz uses them to link activity across rotating residential-proxy addresses and victims, to separate installations and to read scope from a jump far larger than the activity in one victim's logs, and cautions that hits are tool markers and pacing clues, not operator fingerprints: unrelated installations collide in the same ranges and operators reset or parallelise (Wiz, 2026-11-25). Google's report of 2026-10-31 had already seen incremental numeric markers in ARTEX file names, account names, passwords and e-mail subjects without being able to explain them (GTIG and Mandiant, 2026-10-31).

    Wiz's account of ARTEX-Harvester ties it, at varying confidence, to activity at more than a dozen organisations between late October and mid-November, clustered by a distinctive boto3 build, the cross-victim intent counter and proxy-pool overlap, and warns that activity labelled ARTEX comes from multiple unrelated operators; these two posts do not mention Storm-0940 (Wiz, 2026-11-23).

    Huntback reads an exposed ARTEX console whose workspace holds a South Korean university, where the numbering also leaks onto the victim, with a local administrator account named after an intent number.
