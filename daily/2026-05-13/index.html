    Foxconn confirms a cyberattack on some North American factories after Nitrogen claims theft of 8 TB of customer project data

    Foxconn said some of its factories in North America suffered a cyberattack, that its cybersecurity team activated its response mechanism to keep production and delivery going and that the affected factories were resuming normal production; a spokesperson declined to say how many factories were hit (The Record, 2026-05-12), and Foxconn declined to confirm that any customer's information was taken (The Register, 2026-05-12). The Nitrogen ransomware gang took credit on Monday 2026-05-11 (The Record, 2026-05-12), claiming 8 TB of data comprising more than 11 million files, with confidential instructions, internal project documentation and technical drawings related to projects at Intel, Apple, Google, Dell and Nvidia, among others (The Register, 2026-05-12). Workers at the Mount Pleasant, Wisconsin campus reported a network collapse from Friday 2026-05-01, according to The Cybersec Guru as quoted by 9to5Mac, and AppleInsider reports that a Houston, Texas facility also appears to have been affected (9to5Mac, 2026-05-12). Nitrogen's ransomware is believed to have been created with a builder based on the defunct Conti ransomware, and Barracuda describes the group as first observed in 2023 (The Record, 2026-05-12); Coveware found that a coding mistake in Nitrogen's ESXi encryptor overwrites four bytes of the public key, so files are encrypted with a corrupted key that nobody, the attackers included, can decrypt (Coveware, 2026-02-02).

    Exposure
    Foxconn's customers, whose project documentation Nitrogen claims to hold, although Foxconn has not confirmed that any customer data was taken (The Register, 2026-05-12).
    Defender takeaway
    After a Nitrogen encryption of ESXi hosts, analyse the encrypted files against the specific encryptor sample before relying on a decryptor, since the encryptor Coveware examined leaves files without viable backups unrecoverable (Coveware, 2026-02-02); no access vector is public, so the incident changes no patching or detection decision.

    Exposure
    CVE-2026-41089 affects Windows Server 2012 through 2025 acting as a domain controller; the fixed builds are 10.0.14393.9140 (2016), 10.0.17763.8755 (2019), 10.0.20348.5074 (2022), 10.0.25398.2330 (2022 23H2) and 10.0.26100.32772 (2025) (CERT-EU, 2026-06-10); Windows Server 2012 and 2012 R2 are also affected (CERT-EU, 2026-06-10), and Krebs reports patches for every Windows Server version from 2012 onwards (Krebs on Security, 2026-05-12).

    HIGHCVE-2026-45185updatedNATOA1

    CVE-2026-45185 "Dead.Letter": Exim use-after-free in BDAT/CHUNKING on GnuTLS builds, fixed in 4.99.3

    The Exim maintainers published EXIM-Security-2026-05-01.1 (CVE-2026-45185, Critical, CVSS 9.8) on 2026-05-12 after a report from Federico Kirschbaum of XBOW on 2026-05-01: when a client sends a TLS close_notify alert before a BDAT body transfer is complete and follows it with a final byte in cleartext on the same TCP connection, Exim writes into a buffer already freed during the TLS teardown and corrupts the heap, and an attacker only needs to establish a TLS connection and use the CHUNKING (BDAT) extension (Exim advisory, 2026-05-12). Exim 4.97 up to and including 4.99.2 built with USE_GNUTLS=yes are affected, OpenSSL builds are not, and 4.99.3 fixes the flaw by resetting the input-processing stack when a TLS close notification arrives during a BDAT transfer; there is no known mitigation other than upgrading (Exim advisory, 2026-05-12). XBOW's write-up places the freed memory in Exim's TLS transfer buffer, into which the still-active BDAT receive wrapper's call to ungetc() writes a single newline, and notes that GnuTLS is the default TLS library on many Debian-based distributions, including Ubuntu (XBOW, 2026-05-12). During the disclosure window an LLM guided step by step by XBOW Native produced working exploits against non-PIE builds, first without ASLR and then with ASLR, the latter running its payload through Exim's ${run} expansion, which forks bash; against the default PIE build no full exploit was reported: the researcher's side got as far as leaking a stack address, while the LLM never got as far as a leak (XBOW, 2026-05-12).

    Exposure
    Exim 4.97 to 4.99.x built with GnuTLS that advertise STARTTLS and CHUNKING (oss-security, 2026-05-12); XBOW worked from Exim 4.97 as it ships in default Debian-based installations, including Ubuntu 24.04 LTS (XBOW, 2026-05-12).
    Detection
    Process lineage on mail servers: the Exim daemon forking a shell that opens an outbound TCP connection, the path XBOW's ASLR chain used to run its payload and return data outside the SMTP session (XBOW, 2026-05-12).
    Defender takeaway
    Upgrade GnuTLS-built Exim to 4.99.3; the maintainers know no other mitigation (Exim advisory, 2026-05-12). OpenSSL builds need no action.

    Mini Shai-Hulud hits TanStack: a pull_request_target Pwn Request, Actions cache poisoning and OIDC token theft from runner memory published 84 malicious @tanstack versions with valid provenance

    On 2026-05-11 between 19:20 and 19:26 UTC an attacker published 84 malicious versions across 42 @tanstack/* npm packages by chaining a pull_request_target "Pwn Request", GitHub Actions cache poisoning across the fork and base-repository trust boundary, and extraction of an OIDC token from the runner's memory; no npm token was stolen and the publish workflow itself was not modified (TanStack, 2026-05-11). StepSecurity, which detected the publishes, and Wiz attribute the wave to TeamPCP's Mini Shai-Hulud worm, which hit UiPath, Mistral AI and other npm packages the same day, though Wiz found a payload bug that leaves the malware non-functional in the @uipath and @mistralai packages (StepSecurity, 2026-05-11; Wiz, 2026-05-12). The worm's first wave had compromised four official SAP npm packages on 2026-04-29 through malicious preinstall scripts (The Register, 2026-04-30). The TanStack compromise is CVE-2026-45321, scored 9.6 (TanStack advisory, 2026-05-11), which CISA added to its Known Exploited Vulnerabilities catalog on 2026-05-27 with known ransomware campaign use (CISA KEV catalog, 2026-05-27).

    The chain, from TanStack's timeline (TanStack, 2026-05-11):

    1. Staging. On 2026-05-10 the attacker forked TanStack/router into a repository renamed to evade fork-list searches and committed a roughly 30,000-line bundled JavaScript payload under the history package, with a fabricated author identity and a commit message that suppressed CI on push; the post-mortem names two attacker GitHub accounts.
    2. Pwn Request. On 2026-05-11 at about 10:49 a pull request titled as a work-in-progress build simplification triggered the bundle-size and labeler workflows, both on pull_request_target, which needs no first-time-contributor approval. At 11:11 the benchmark job checked out the PR's merge ref and ran pnpm install and the bundle-size build, executing the payload.
    3. Cache poisoning. The payload wrote into the pnpm store under the key the release workflow computes, and the cache action's post-job save stored the 1.1 GB poisoned store in the base repository's cache scope; the job's read-only permissions: did not stop it, because cache writes use a runner-internal token. At 11:31 the attacker force-pushed the PR back to the main branch head, leaving a zero-file change, and closed it.
    4. Detonation. At 19:15 a re-run of the release workflow, and at 19:16 a fresh run triggered by a legitimate merge, restored the poisoned store. Attacker binaries run during the build located the Runner.Worker process, read its memory through /proc/<pid>/maps and /proc/<pid>/mem, took the OIDC token the runner mints in memory for a job with id-token: write, and posted the packages directly to the npm registry, using the same memory-dump script as the tj-actions/changed-files compromise of March 2025. Tests failed, so the workflow's own Publish Packages step was skipped.

    The packages carry valid SLSA provenance tied to TanStack's release workflow; provenance proves which pipeline built a package, not that the pipeline behaved, so a compromised build step yields a validly attested malicious package (StepSecurity, 2026-05-11).

    The payload. Installing an affected version resolves an optional dependency on a github: URL naming the TanStack repository, which GitHub serves from an orphan commit in the fork network; npm installs that commit's dependencies, including the Bun runtime, and runs its prepare lifecycle script, which executes a 2.3 MB obfuscated JavaScript file shipped at the tarball root and then exits with an error so npm silently discards the optional install (TanStack advisory, 2026-05-11). Behind three obfuscation layers, it queries the AWS instance metadata service with the IMDSv2 flow and the ECS credential endpoint, reads the local Vault agent, reads files from more than 100 hardcoded paths, and in CI pipes a memory-reading script to sudo python3 to pull every value the runner marks as secret (StepSecurity, 2026-05-11); NCSC-CH groups the paths as cloud credentials, SSH, Git, developer and AI tools, crypto wallets, VPN configurations, messaging apps, shell history and Kubernetes (NCSC-CH, 2026-05-12). It exfiltrates encrypted data through the Session messenger's file-upload network and through GitHub commits on branches named to look like Dependabot's, spreads by finding npm tokens that bypass two-factor checks, enumerating the maintainer's other packages and, in CI, exchanging the OIDC token for per-package publish tokens, and writes workflows disguised as CodeQL analysis that serialise all repository secrets (StepSecurity, 2026-05-11). Persistence is a Claude Code SessionStart hook, a VS Code folder-open task, and a LaunchAgent on macOS or systemd user service on Linux that checks the GitHub API every 60 seconds and deletes the user's home directory once the stolen token is revoked (NCSC-CH, 2026-05-12).

    Exposure
    Any developer machine or CI runner that ran npm install, pnpm install or yarn install against an affected version on 2026-05-11 (TanStack advisory, 2026-05-11). For maintainers, the same chain is open wherever a pull_request_target workflow checks out and builds fork code in a cache scope that a release job with id-token: write later restores (TanStack, 2026-05-11).
    Detection
    In package manifests and tarballs, an optional dependency on a github: URL pinned to a commit and a large JavaScript file at the package root that the files list does not declare; in runner process telemetry, the Bun runtime installed during npm install and python3 processes reading /proc/*/mem; in registry and repository history, two versions of one package published minutes apart and unexpected commits on Dependabot-style branches (StepSecurity, 2026-05-11). TanStack names publishes that do not come from the workflow's defined publish step as the signal to watch for (TanStack, 2026-05-11). On hosts, added Claude Code hooks, VS Code folder-open tasks and a token-monitoring LaunchAgent or systemd user service (NCSC-CH, 2026-05-12).
    Defender takeaway
    On any host that installed an affected version, isolate and image the machine before revoking any token, because revocation triggers the wipe (StepSecurity, 2026-05-11), then rotate the AWS, GCP, Kubernetes, Vault, GitHub, npm and SSH credentials reachable from it (TanStack, 2026-05-11). For repositories, never check out or build an untrusted pull request under pull_request_target (GitHub Security Lab, 2021-08-03); where a fork-reachable job needs a cache, use the separate restore action, which has no save step (actions/cache README); and treat npm audit signatures as proof of which pipeline built a package, not that it was clean (npm Docs; StepSecurity, 2026-05-11).
