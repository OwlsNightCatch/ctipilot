    NOTABLENATOB2

    1Password: an attacker used an employee's corporate GitHub account to push malicious code to backend services that downloaded administrative data about a subset of customers, and copied private-repository source code and reached the CI/CD system; vaults were not affected

    1Password disclosed on 2026-11-25 that on 2026-11-19 it began investigating indications that an attacker had gained access to an employee's corporate GitHub account (1Password, 2026-11-25). The attacker used the account to access source code and push malicious code to backend services, which downloaded administrative data about customers; the attacker also copied source code from private repositories and gained access to the CI/CD system, which holds infrastructure secrets, and 1Password rotated every credential that may have been exposed (1Password, 2026-11-25). It says the actor had stolen a token and that vault contents, the keys that protect them, account recovery keys and its apps and browser extensions were not affected (1Password, 2026-11-25).

    The records taken for a subset of users, whose size is not stated, are names and email addresses, account and user identifiers, account creation and last sign-in times, public keys, Secure Remote Password protocol parameters, tokens embedded in certain emailed invitation, SCIM Bridge and Hosted Provisioning, and account-recovery links, and non-secret internal metadata (1Password, 2026-11-25). Those tokens complete an invitation or recovery only together with an SSO sign-in or an emailed code, which 1Password has lengthened from six numeric digits to ten alphanumeric characters, and it says it found no evidence of account takeover with the exposed tokens; its advice to customers is caution about phishing that mentions invitations or account recovery, that it will never ask for the account password or Secret Key, keeping both safe, and reporting suspicious messages to its support address (1Password, 2026-11-25). BleepingComputer adds that the harvested name and email list is useful for such phishing (BleepingComputer, 2026-11-25).

    Exposure
    Any organisation with 1Password accounts, since users' names, sign-in addresses and identifiers were in the copied records, and especially one using SCIM provisioning or account recovery, because tokens in those emailed links were among the data; 1Password says it notified a small number of users with pending invitations or recoveries directly (1Password, 2026-11-25).
    Detection
    In the identity provider's and 1Password's administrator audit records, invitation, provisioning and account-recovery events since about 2026-11-19 that no administrator or user requested; in mail-gateway logs, inbound mail that imitates 1Password invitations or recovery messages with real tenant or user details; and user reports of recovery codes nobody asked for. These checks are analysis from the data classes the post lists, which publishes no indicator.

    Triage: a legitimate invitation or recovery message follows an administrator's or user's own action; one that arrives without it is the signal.

    Defender takeaway
    1Password's own advice covers phishing caution, never sharing the password or Secret Key and reporting suspicious messages, and BleepingComputer says it is not requiring customers to change their account passwords or Secret Keys (BleepingComputer, 2026-11-25); the action is to warn users about phishing that mentions invitations or account recovery and to watch for unrequested provisioning events. For your own pipelines the mechanism is one employee source-control identity that could push to backend services and reach CI/CD, so require review on the deploy path and alert on pushes and workflow changes made with employee tokens.

    NOTABLECVE-2026-130637 +10NATOA2

    SEPPmail Secure E-Mail Gateway before 15.1.2: an unauthenticated template injection on the GINA login page can read and take over any GINA account (CVE-2026-130637, vendor score 9.3) and ten more flaws are fixed in the 2026-11-24 patch release; no exploitation or workaround stated

    SEPPmail's revision history lists patch release 15.1.2 of 2026-11-24 with eleven security fixes, each marked as affecting versions before 15.1.2 (SEPPmail, 2026-11-24). The worst is CVE-2026-130637 (vendor score 9.3): request values reflected on the GINA login page were processed by the template engine, which could let an unauthenticated attacker read attributes of any GINA account and take it over, and the fix stops expanding request values as template placeholders. Two further rows score 9.2: CVE-2026-124840, where a session created by answering the security question was also accepted by the registration and settings workflows, so an attacker who knows the security answer could replace the password, and CVE-2026-124843, where a hard-coded fallback secret was used if the appliance's key material could not be loaded, which could let encrypted Large File Transfer attachments be decrypted outside the appliance (SEPPmail, 2026-11-24).

    The remaining rows are CVE-2026-124844 (8.7), unauthenticated GINA uploads that were never removed and could fill the disk; CVE-2026-124838 (8.5), a configuration-service socket open to every local user; CVE-2026-124842 (8.3), an unauthenticated GINA request that reset the password of a registered account without the security question; CVE-2026-124839 (7.7), a crafted GINA account address that reached a shell command in a maintenance script at start, with elevated privileges; and four rows at 6.9 to 6.3 covering unescaped LDAP filter values (CVE-2026-124841, CVE-2026-124836), a crafted DKIM signature that injects forged Authentication-Results later covered by the gateway's ARC seal (CVE-2026-124837) and a GINA domain lookup that falls back to the default domain settings (CVE-2026-124845) (SEPPmail, 2026-11-24). The page names no exploitation and no workaround, and does not say whether the 15.0 branch, whose last release is 15.0.7, is affected.

    Exposure
    A SEPPmail Secure E-Mail Gateway before 15.1.2 whose GINA web interface is reachable from outside; the revision history says release 15.1.0 added support for restricting the file types that external communication partners can upload through GINA, which shows external recipients use it (SEPPmail, 2026-11-24). The page does not state the CVSS vector of any score.
    Detection
    In GINA web access logs, login-page requests whose parameters carry template placeholder syntax, unauthenticated password-reset requests for accounts that are already registered, calls to the registration and settings workflows that follow a security-question recovery, and bursts of unauthenticated uploads; in the gateway's audit log, GINA password changes without the usual recovery sequence. The fixes do not undo an account already taken over, so review GINA password-change and sign-in history for the period before the update. These checks follow from the mechanisms the vendor names; the page publishes no indicator.

    Triage: an unauthenticated password reset on a GINA account that is not yet registered is legitimate, since the fix keeps it for unregistered accounts only; the same request taking effect on an already registered account without the security-question step is the abuse (SEPPmail, 2026-11-24).

    Defender takeaway
    Update every gateway on 15.1 to 15.1.2 and, for gateways on the 15.0 branch, ask SEPPmail whether these flaws apply, since the page does not say; where GINA is internet-facing, give the update priority within the regular cycle, because the template injection and the unauthenticated reset need no login, and review GINA account changes made before the update.

BSI had revised its advisory on 2026-11-24 (23:00 UTC) with the summary "CVE-2026-103406 is being exploited" (translated from German), without stating its basis (BSI, 2026-11-24). Juniper itself updated its bulletin JSA112183 on 2026-11-24 to say that at least one instance of malicious exploitation of CVE-2026-103406 has been reported to its security response team, as SecurityWeek quotes it (SecurityWeek, 2026-11-26), and NCSC Switzerland rates the flaw actively exploited (NCSC.ch, 2026-11-26). No source names an actor, a victim or the number of compromised systems, and the only first-exploitation date, ENISA's exploited-since field of 2026-11-25, follows the catalogue listing (ENISA EUVD, 2026-10-28).

    ENISA's record, which carries Juniper's description, narrows the flaw to the AutomatedProvisioner of Session Smart Conductor: an improper neutralization of special elements lets a remote attacker execute arbitrary commands as root via a specially crafted salt minion ID, scored CVSS 3.1 9.8 with network access, no privileges and no user interaction (ENISA EUVD, 2026-10-28). The affected ranges are Conductor before 7.0.5, from 7.1.0 before 7.1.7 and from 7.2.0 before 7.2.3, so 7.0.5, 7.1.7 and 7.2.3 are the first fixed releases (ENISA EUVD, 2026-10-28). The record references Juniper's bulletin JSA112183, which could not be read, and its CVE record was published on 2026-10-28. The same release fixes CVE-2026-103409 in the Session Smart Router, an unauthenticated flaw scored 9.8 that can be exploited only before the device is onboarded to Mist or a Conductor (ENISA EUVD, 2026-10-28).

    Exposure
    A Session Smart Conductor on a release below 7.0.5, 7.1.7 or 7.2.3 that a network attacker can reach; NCSC Switzerland names network access to the Conductor's provisioning service (the AutomatedProvisioner) as the prerequisite, with no authentication or user interaction, and no source gives the port or says whether it is on by default (NCSC.ch, 2026-11-26). CISA's catalogue record and NCSC.ch also name Session Smart Router, and SecurityWeek lists 7.2.3, 7.1.7 and 7.0.5 for both products (CISA KEV catalogue, 2026-11-25; SecurityWeek, 2026-11-26), so read the running release on each Conductor and each Router and compare it with the three fixed releases.
    Detection
    Process-creation events showing a shell or interpreter started as root by the Conductor's provisioning or salt services, minion or router registration events whose ID contains shell metacharacters or command-substitution syntax, and the Conductor's audit and configuration-change records; these follow from the mechanism ENISA relays, and no source publishes an indicator. Upgrading does not remove an attacker who is already in, so a Conductor that was reachable before the upgrade needs a check for accounts, router registrations and configuration pushed from it that nobody made; NCSC Switzerland's check is the fleet list, for router names the team did not create (NCSC.ch, 2026-11-26).
    Defender takeaway
    Upgrade every Conductor to a fixed release now rather than at the next cycle, since Juniper, CISA and BSI report exploitation of an unauthenticated root command injection; until then, NCSC Switzerland advises keeping the Conductor's management and provisioning interfaces off untrusted network segments (NCSC.ch, 2026-11-26), because the flaw needs only network access.

    NOTABLENATOB2

    Okta Threat Intelligence: AI agents register on Auth0 tenants and Okta organizations with disposable addresses from the mail.tm service, whose single rotating mailbox domain makes blocklists very likely stop matching within weeks; ARTEX, Cairn, CyberStrikeAI and pentestcode each picked it at run time

    Okta Threat Intelligence reports that since June 2026, and at scale through October and November, AI agents have registered accounts with disposable email addresses on Auth0 tenants and Okta organizations that allow public self-service registration, activity Okta calls almost certainly malicious and that customers often reported alongside attacks on their applications (Okta, 2026-11-23). The addresses mostly belong to the mail.tm family, a free receive-only service whose API needs no account or key and lets a script create a mailbox, obtain a token and poll for one-time codes (Okta, 2026-11-23). In tests by the P0 Labs team of Permiso, which Okta acquired on 2026-08-26 (Okta, 2026-07-30), the ARTEX, Cairn, CyberStrikeAI and pentestcode frameworks each picked mail.tm at run time, and in a data set containing attacker tooling mail.tm appeared on 80 percent of the attacker hosts where disposable email was found (Okta, 2026-11-23).

    mail.tm exposes only one active mailbox domain at a time and replaces it periodically, so a blocklist built from earlier domains will very likely stop matching within weeks; Okta's Auth0 telemetry shows sign-ups tracking the domain the API currently returns, and the attackers' domain changed around 2026-10-30 when the API response did. Agents also used mailinator, guerrillamail and emailnator, and at one target an agent moved to another provider when blocked, which Okta reads as agents treating disposable mail as an interchangeable capability. Okta says the use always occurred within a short window of other agentic reconnaissance and intrusion attempts against the same entities (Okta, 2026-11-23). Bot detection and CAPTCHA generally stopped the October mail.tm sign-ups before email verification, but Okta warns agents can solve challenges and commonly register by calling the Auth0 Authentication API directly, which can skip protections applied in Universal Login (Okta, 2026-11-23).

    Exposure
    An Auth0 tenant or Okta organization that allows public self-service registration. For workforce users Okta says self-service registration is a prerequisite for many of the attacks it describes and should be disabled or restricted (Okta, 2026-11-23).
    Detection
    In identity-provider registration telemetry, sign-up events whose email domain belongs to a disposable provider's currently active mailbox domain, kept current by polling the provider's public domain endpoint instead of a static list, as Okta advises (Okta, 2026-11-23).

    Triage: the discriminator Okta supports is context: a disposable-domain sign-up read alongside other agentic reconnaissance or intrusion attempts against the same entities, not the domain alone (Okta, 2026-11-23).

    Defender takeaway
    On Auth0, block sign-ups through the API while allowing Universal Login and block disposable domains with Actions; on Okta Workforce Identity, disable or restrict self-service registration. Treat a disposable-domain sign-up as a prompt to look for other agentic activity against the same estate, since Okta says it gives a heads-up to look for successful intrusion attempts, and do not rely on CAPTCHA alone (Okta, 2026-11-23).

    PolinRider: a North Korea-linked loader reaches developers through force-pushed forged commits in at least 7,609 GitHub repositories, hijacked npm releases and a fake employer's take-home test, and reads its server address from an Ethereum wallet

    First published 2026-11-15 · open finding →

    Update26 Nov 2026 05:07 UTCrun 2026-11-26T0356Z-intelsummarytechniquessourcessourcing_noteactionsbodyupdated_at

    SafeDep found a Python variant of the loader in 375 public repositories, hidden in a utils package or conftest.py, and StepSecurity traced force-pushed pull-request commits that ran in CircuitVerse's release workflows and published 40 infected installers, with the loader padded by tabs; StepSecurity counts 576 infected repositories of 622 fetched.

    SafeDep reports that PolinRider now plants a Python loader in GitHub repositories, hidden in a small utils package or in conftest.py with five import lines added to a start file, and found it in 375 public repositories under 260 accounts on 2026-11-24; no PyPI or npm package carries it, and because it uses only the standard library a scan of requirements files or a lockfile does not show it (SafeDep, 2026-11-24). When Python imports the file, the loader reads the input data of the newest transaction an Ethereum wallet sent to itself, writes it as JavaScript to a temporary file and runs node on it; the next stage is written to the standard input of a detached interactive node process, so it is absent from the process command line, and the node child starts from python or pytest. pytest runs the loader through conftest.py every time, and fixing an import error for the missing utils package also starts it. SafeDep did not contact the command server, so later stages are unobserved, and the stealer behavior it describes comes from the September chain. Its remedy is to delete the planted package, import lines and conftest.py loader, then clean the machines that push to the repository and replace their GitHub tokens and SSH keys (SafeDep, 2026-11-24).

    StepSecurity reports that the loader reached open-source projects through commits force-pushed on 2026-10-19 into pull requests that were still open, from one GitHub account, at AsyncAPI Generator, CircuitVerse and Open Food Facts; the malicious commits reuse a clean commit's message and date but are unsigned and carry a different committer name, and none of the merged pull requests contains the loader (StepSecurity, 2026-11-26).
