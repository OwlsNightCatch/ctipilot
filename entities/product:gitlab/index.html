    What each entry about GitLab tells a defender to do, newest first.

    2026-11-14NOTABLEGitLab critical patch: a merge request can reach a Git heap overflow on Gitaly; update to 19.5.4, 19.4.6 or 19.3.8

    Defender takeaway

    Upgrade self-managed GitLab to a fixed release and, for a self-compiled install, rebuild both the Git in Gitaly and the Git at git.bin_path or move the distribution Git to 2.56.1 or later (GitLab, 2026-11-10); until then limit who can create projects and sign up, and on a hit treat the instance and every repository on that Gitaly node as compromised (GitLab, 2026-11-12). Servers that cannot upgrade yet can set conflict-marker-size=7 in each repository's info/attributes or turn off the merge checks for untrusted repositories (The Hacker News, 2026-11-11). Update Git on runners and workstations and avoid recursive clones of untrusted repositories until it is done.

    Exposure · detection
    Exposure

    A self-managed GitLab CE or EE in the affected ranges that lets users create projects and merge requests, or any Git older than the fixed releases on a workstation, CI runner or service that clones or merges untrusted repositories; applications that bundle Git need their own update (GitLab, 2026-11-10; GitHub Blog, 2026-11-10).

    Detection

    GitLab's rule fires when the error field of a Gitaly event contains merge-tree: signal: followed by anything other than killed or terminated, and a .gitattributes in the target branch that sets an unusually large conflict-marker-size supports a true positive; GitLab says a working attempt is silent, a clean result does not prove the flaw was not used, the rules rest on error wording captured on 19.4.1 only, and many installs do not ship the Gitaly and Sidekiq logs (GitLab, 2026-11-12). On build hosts, hook scripts or shells spawned by git during a recursive clone are the behavior CVE-2026-111760 produces.

    2026-10-21NOTABLEeMudhra: eight ECDSA CA keys guessable, eight RSA CAs revoked; Windows drops the rest 2026-11-16; update clients

    Defender takeaway

    Update trust bundles and toolchains on every non-browser client, rebuild container images that embed an old bundle, and do not rely on revocation or CT for those clients; website operators with certificates chaining to emSign ECC Root CA - G3 need one from another hierarchy now (Google, 2026-10-20), and so does anything issued under emSign Root CA - G1 after 2026-11-16, because Chrome 153 and higher will not trust such a certificate by default when its earliest SCT is later (Google, 2026-11-04). On Macs, update to macOS 27.2.1, 26.7.3 or 15.8.3, which block them in the command-line tools; where that is not possible, remove emSign ECC Root CA - G3 from that file as Apple describes (removing AAA Certificate Services as well is optional and can stop tools that read only that file from verifying some unaffected sites) (Apple, 2026-11-10). From 2026-11-16 Microsoft removes the remaining eMudhra roots from Windows, Edge and WebView2, so a certificate under emSign Root CA - G1 stops validating there too (Microsoft, 2026-11-10). Certificates from the eight revoked RSA G2B and G2C issuers are revoked and eMudhra says its subscribers were migrated, so check inventories for any holder still on them.

    Exposure · triage · detection
    Exposure

    Any software that keeps its own CA bundle or does not check revocation keeps trusting the intermediates until updated; Python 3.15.2, 3.14.10, 3.13.18, 3.12.16 and 3.11.18 carry a built-in denylist (Python Insider, 2026-10-26); Apple says the curl, git, python3, ruby, perl and openssl that ship with macOS or the Xcode command-line tools read /etc/ssl/cert.pem, check neither Apple's block nor revocation and keep trusting them until macOS 27.2.1, 26.7.3 or 15.8.3 (Apple, 2026-11-10). SonicOS firewalls with Client DPI-SSL enabled re-signed the chains with their own DPI-SSL CA, so client browsers could not reject a forged one, until SonicOS 7.3.4-7015 (Gen7) and 8.2.3-8015 (Gen8) (SonicWall, 2026-11-10; SonicWall advisory data, 2026-11-10).

    Triage

    A site that still chains to emSign ECC Root CA - G3 failing in Chrome after 2026-10-27, or a certificate that chains to one of the seven certificates Microsoft removed failing in Windows or Edge once the change reaches the device, is the announced root removal, not an attack (Google, 2026-10-20; Microsoft, 2026-10-26).

    Detection

    EMudhra says it found no evidence that the intermediates were used to issue end-user certificates (BleepingComputer, 2026-10-20), so a server certificate chain seen in TLS session metadata, proxy or EDR network telemetry that contains one of the eight intermediates or their Sectigo cross-signs, which the tracker lists, is worth treating as a possible forged certificate (Dennis Jackson, 2026-10-20). CT monitoring will not show one, because Google found no certificate chaining to the six TLS intermediates logged before it blocked them (Google, 2026-10-20).

    2026-10-13HIGHexploitedGitLab's CVSS 10.0 CI regex RCE is now on CISA KEV; the public PoC needs push access to a public project

    Defender takeaway

    Upgrade to 19.4.2, 19.3.5 or 19.2.8 now (GitLab, 2026-10-12), or better to 19.5.1, 19.4.3, 19.3.6 or 19.2.9, or on older branches the backports 19.1.9, 19.0.10 and 18.11.13, the builds of 2026-10-21 that also fix a second CVSS 10 regular-expression compiler flaw, CVE-2026-110264 (GitLab, 2026-10-21), internet-facing instances first as CERT-EU advises (CERT-EU, 2026-10-12), then instances where new users can self-register and create projects, which removes the push-access constraint Rapid7 found (Rapid7, 2026-10-13); the fix is a set of patches to the Ruby that GitLab bundles in its own packages and images, so an installation with its own Ruby, from source or in a self-built image, needs Ruby 3.3.13, 3.4.12 or 4.0.9 as well, and Alpine's GitLab on 19.3.6 with standard Ruby stayed vulnerable (Alpine Linux, 2026-10-28). CISA lists the flaw as exploited and NCSC Switzerland reports active exploitation, so an instance reachable on an affected version needs a compromise assessment as well as the upgrade; Rapid7's interim controls (restrict anonymous access to public projects and stop untrusted users creating or writing to public projects) reduce exposure only to the path it demonstrated (Rapid7, 2026-10-13).

    Exposure · triage · detection
    Exposure

    Self-managed GitLab CE or EE on 19.2.x below 19.2.8, 19.3.x below 19.3.5 or 19.4.x below 19.4.2; GitLab's table for this flaw starts at 19.2 (GitLab, 2026-10-12), but the sibling CVE-2026-110264 reaches every version from 7.0 (GitLab, 2026-10-21). The Ruby project says the underlying engine bugs are reached by any application that compiles a regular expression from attacker-controlled input (Ruby, 2026-10-23). Rapid7 found the conditions: an attacker must first commit a malicious CI/CD configuration file and a repository path containing UTF-8 characters to a branch in a public project, which an ordinary account can do by creating a public project where the instance allows it (Rapid7, 2026-10-13), and on instances where new users can self-register and create projects that constraint is removed (Rapid7, 2026-10-13). An instance with open sign-up, or with public projects that untrusted users can write to, is the case to prioritise.

    Triage

    Ordinary CI jobs run shells under the runners; only a shell spawned by the GitLab application server processes themselves matches this flaw, not one started inside a runner job.

    Detection

    GitLab's release page lists six detections for exploitation attempts on self-managed instances (GitLab, 2026-10-12). Alpine saw the attack as crashes of GitLab worker processes after crafted CI configurations from a newly registered account, with 502 errors and failed CI jobs, and notes that a successful exploit would leave no crash and no trace in the web logs (Alpine Linux, 2026-10-28); in process-creation telemetry, shells, interpreters or network tools started as children of the GitLab application server processes are the sign of success, and a server where that turns up needs its CI/CD variables, runner registration tokens and deploy keys treated as exposed.

    2026-10-22NOTABLEGitLab's critical patch fixes an unauthenticated CVSS 10.0 RCE in Org-mode rendering; no exploitation reported

    Defender takeaway

    Upgrade to the fixed build of the instance's line now, internet-reachable instances and those with public projects first; an instance that moved to 19.4.2, 19.3.5 or 19.2.8 for the earlier flaws is not yet fixed for this one (GitLab, 2026-10-21). For other Ruby applications that compile attacker-controlled patterns, Ruby recommends upgrading to 4.0.9, 3.4.12 or 3.3.13 or later, or avoiding compiling such patterns, and says neither Regexp.timeout nor a pattern-length limit reliably protects; Ruby has not requested CVE identifiers of its own for now and tells operators to track the issues under GitLab's identifiers (Ruby, 2026-10-23).

    Exposure · triage · detection
    Exposure

    Self-managed GitLab CE and EE on the versions above; the vulnerable path is reached when GitLab renders a .org file, so an instance with public projects, or one where untrusted users can create them, is the exposed shape, and until patching GitLab advises reducing public visibility (GitLab security, 2026-10-21). A Ruby application outside GitLab is exposed to the same bug when it compiles a regular expression from a string an attacker controls, through Regexp.new, Regexp.union, Regexp.compile or interpolation into a regexp literal; applications that only use patterns written by their own developers are not affected (Ruby, 2026-10-23).

    Triage

    A reader of documentation .org files renders each file once and quickly, while an attack produces a burst of timeouts from one client over a few minutes (GitLab security, 2026-10-21); a worker crash with no accompanying render burst from one client is more likely a benign parser bug than an attack (GitLab security, 2026-10-21).

    Detection

    GitLab's two detections key on, first, five or more render timeouts from the Org-mode renderer on .org files from one client within 30 minutes in the Rails exceptions log, with the request that actually crashes a worker visible only as a 502 on the .org blob route in the Workhorse log, and second, a native Ruby crash report in the Puma error log whose backtrace runs through org-ruby or Onigmo frames (GitLab security, 2026-10-21). In repository content, scan each suspect checkout for .org files with an oversized TODO-keyword line, and in the Rails request log look for editor preview requests whose file_path ends in .org while the URL names another file type, which forces the Org renderer (GitLab security, 2026-10-21). A successful exploit is quiet and does not reliably crash, so the absence of a hit never clears an instance (GitLab security, 2026-10-21). On an exposed, unpatched instance, hunt for unexpected child processes of Puma, new files owned by git in the temporary directory, outbound connections and changed crontabs or SSH keys for the git user, and treat the secrets, CI/CD variables, runner tokens and access tokens the git user can read as at risk (GitLab security, 2026-10-21).

GitLab's detection page says any user who can create a project and open a merge request reaches the flaw, which gives command execution as the git operating-system user and read and write access to every repository on that Gitaly node (GitLab, 2026-11-12).

    Git 2.56.1 and the backports 2.55.1, 2.54.1, 2.53.1, 2.52.1, 2.51.3 and 2.50.2 of 2026-11-10 fix the same flaw and five others (GitHub Blog, 2026-11-10). The one that matters on workstations and CI runners is CVE-2026-111760: a long path that passes validation is written as .git and replaces a freshly cloned submodule's .git file with a symlink to a directory that holds attacker hooks or configuration, which GitHub says can execute attacker-controlled code during a recursive clone (oss-security, 2026-11-11; GitHub Blog, 2026-11-10). The maintainers believe it is only triggerable with --recurse-submodules and note that such a repository fails fsck, which does not protect downstream users, since an innocuous-looking .gitmodules pointing at it suffices (oss-security, 2026-11-11). GitHub Enterprise Server fixes are in 3.19.15, 3.20.11, 3.21.9 and 3.22.4, and GitHub is coordinating releases of GitHub Desktop and the Copilot app with patched Git (GitHub Blog, 2026-11-10); Git for Windows 2.56.1.windows.1 addresses the issue (Git for Windows, 2026-11-10). No source reports exploitation; GitLab documents a lab reproduction in which opening one merge request left a crash entry within a second and a half (GitLab, 2026-11-12).

    Exposure
    A self-managed GitLab CE or EE in the affected ranges that lets users create projects and merge requests, or any Git older than the fixed releases on a workstation, CI runner or service that clones or merges untrusted repositories; applications that bundle Git need their own update (GitLab, 2026-11-10; GitHub Blog, 2026-11-10).
    Detection
    GitLab's rule fires when the error field of a Gitaly event contains merge-tree: signal: followed by anything other than killed or terminated, and a .gitattributes in the target branch that sets an unusually large conflict-marker-size supports a true positive; GitLab says a working attempt is silent, a clean result does not prove the flaw was not used, the rules rest on error wording captured on 19.4.1 only, and many installs do not ship the Gitaly and Sidekiq logs (GitLab, 2026-11-12). On build hosts, hook scripts or shells spawned by git during a recursive clone are the behavior CVE-2026-111760 produces.
    Defender takeaway
    Upgrade self-managed GitLab to a fixed release and, for a self-compiled install, rebuild both the Git in Gitaly and the Git at git.bin_path or move the distribution Git to 2.56.1 or later (GitLab, 2026-11-10); until then limit who can create projects and sign up, and on a hit treat the instance and every repository on that Gitaly node as compromised (GitLab, 2026-11-12). Servers that cannot upgrade yet can set conflict-marker-size=7 in each repository's info/attributes or turn off the merge checks for untrusted repositories (The Hacker News, 2026-11-11). Update Git on runners and workstations and avoid recursive clones of untrusted repositories until it is done.

    eMudhra: the private keys of eight ECDSA intermediate CA certificates were trivially recoverable, so anyone could forge trusted HTTPS certificates, and eight RSA intermediates were revoked on 2026-11-07 for key handling eMudhra cannot show compliant; browsers block them, clients with their own trust store or no revocation checking need an update (CVE-2026-111943 in Go)

    On 2026-10-17 a researcher reported to the Chrome Root Program, and Mozilla received a report the same day, that the private keys of eight eMudhra subordinate CA certificates were compromised: the keys were so weak that anyone could forge trusted HTTPS certificates to impersonate any website against clients that have not removed trust in those CAs; Google describes the cause as insufficient randomness (Google, 2026-10-20; Mozilla, 2026-10-20). BleepingComputer, citing Mozilla's incident report, says all eight were P-384 keys generated in April 2025 with values below 256, so testing 256 numbers recovers a key (BleepingComputer, 2026-10-20). eMudhra's incident report of 2026-11-10 says the keys were generated correctly on its hardware module at a ceremony on 2025-04-30 and then passed through a custom Python wrap/unwrap script that truncated the eight ECDSA private values; the keys of eight RSA-4096 issuers (G2B and G2C) stayed intact but were handled in that script's process memory, so eMudhra cannot show compliance with its certification practice statement, and it revoked them on 2026-11-07 with the reason cessationOfOperation after having said on 2026-10-19 that they were not impacted; its G2C issuers had issued end-entity certificates, the last on 2026-11-03, and no source says any RSA key leaked (eMudhra, Mozilla bug 2083449, 2026-11-10; eMudhra, Mozilla bug 2083449, 2026-10-19; BleepingComputer, 2026-11-11). The tracker says it is not known whether attackers used the flaw against other clients (Dennis Jackson, 2026-10-20).

    Chrome blocked the intermediates on 2026-10-17, Firefox through OneCRL the same day, Microsoft platforms on 2026-10-20 and Apple products on 2026-10-22, and eMudhra revoked all eight (Dennis Jackson, 2026-10-20; BleepingComputer, 2026-10-20). Microsoft went further: an out-of-band Windows update of 2026-10-26 removes seven certificates, six eMudhra G3 roots and an AAA Certificate Services cross-sign, from the Windows trust list, and the same seven left the Edge trust list on 2026-10-27 (Microsoft, 2026-10-26). Google removed the root that signed them, emSign ECC Root CA - G3, from the Chrome Root Store, with the removal expected to reach devices on 2026-10-27 (Google, 2026-10-20). Go 1.27.3 and 1.26.10 filter chains that contain the intermediates in crypto/x509, tracked as CVE-2026-111943 (Go team, 2026-10-20), and GitLab's release of 2026-10-29 removes trust for the eight intermediates in self-managed CE and EE, with Runner 19.5.1 and the AI Gateway updated separately (GitLab, 2026-10-29).

    Any software that keeps its own CA bundle or does not check revocation keeps trusting the intermediates until updated; Python 3.15.2, 3.14.10, 3.13.18, 3.12.16 and 3.11.18 carry a built-in denylist (Python Insider, 2026-10-26); Apple says the curl, git, python3, ruby, perl and openssl that ship with macOS or the Xcode command-line tools read /etc/ssl/cert.pem, check neither Apple's block nor revocation and keep trusting them until macOS 27.2.1, 26.7.3 or 15.8.3 (Apple, 2026-11-10).     EMudhra says it found no evidence that the intermediates were used to issue end-user certificates (BleepingComputer, 2026-10-20), so a server certificate chain seen in TLS session metadata, proxy or EDR network telemetry that contains one of the eight intermediates or their Sectigo cross-signs, which the tracker lists, is worth treating as a possible forged certificate (Dennis Jackson, 2026-10-20). CT monitoring will not show one, because Google found no certificate chaining to the six TLS intermediates logged before it blocked them (Google, 2026-10-20).

On Macs, update to macOS 27.2.1, 26.7.3 or 15.8.3, which block them in the command-line tools; where that is not possible, remove emSign ECC Root CA - G3 from that file as Apple describes (removing AAA Certificate Services as well is optional and can stop tools that read only that file from verifying some unaffected sites) (Apple, 2026-11-10).     HIGHCVE-2026-97229exploitedupdatedNATOA2

    CVE-2026-97229, GitLab CE/EE: an integer overflow in the CI/CD regular-expression compiler allows code execution on self-managed servers; exploited, fixed in 19.4.2, 19.3.5 and 19.2.8 (CVSS 10.0)

    GitLab's critical patch release of 2026-10-12 (19.4.2, 19.3.5 and 19.2.8) fixes CVE-2026-97229, an integer overflow in the CI/CD regular-expression compiler that, "under certain conditions", could allow an unauthenticated user to execute arbitrary code on the GitLab server through a specially crafted regular expression in a CI/CD configuration; GitLab scores it CVSS 3.1 10.0 with no privileges required (GitLab, 2026-10-12). Affected are self-managed CE and EE from 19.2 before 19.2.8, 19.3 before 19.3.5 and 19.4 before 19.4.2. The 19.4.1 release of 2026-09-23 fixed two related flaws in the same component (GitLab, 2026-09-23) but is still affected (GitLab, 2026-10-12). Rapid7 reproduced the code execution on 19.4.1 and published a proof of concept on 2026-10-13 (Rapid7, 2026-10-13); CISA added the flaw to its Known Exploited Vulnerabilities catalog on 2026-10-29 on evidence of active exploitation (CISA, 2026-10-29), and NCSC Switzerland updated its advisory the same day to active exploitation, citing Alpine Linux (NCSC Switzerland, 2026-10-29). Alpine says a newly registered account sent crafted CI configurations to its GitLab 19.3.4 on 2026-10-20 and 21, crashing worker processes eight times, four of them partway through the exploit; it found no evidence that code ran, could not rule it out and rebuilt the instance (Alpine Linux, 2026-10-28).

    Exposure
    Self-managed GitLab CE or EE on 19.2.x below 19.2.8, 19.3.x below 19.3.5 or 19.4.x below 19.4.2; GitLab's table for this flaw starts at 19.2 (GitLab, 2026-10-12), but the sibling CVE-2026-110264 reaches every version from 7.0 (GitLab, 2026-10-21). The Ruby project says the underlying engine bugs are reached by any application that compiles a regular expression from attacker-controlled input (Ruby, 2026-10-23). Rapid7 found the conditions: an attacker must first commit a malicious CI/CD configuration file and a repository path containing UTF-8 characters to a branch in a public project, which an ordinary account can do by creating a public project where the instance allows it (Rapid7, 2026-10-13), and on instances where new users can self-register and create projects that constraint is removed (Rapid7, 2026-10-13). An instance with open sign-up, or with public projects that untrusted users can write to, is the case to prioritise.
    Detection
    GitLab's release page lists six detections for exploitation attempts on self-managed instances (GitLab, 2026-10-12). Alpine saw the attack as crashes of GitLab worker processes after crafted CI configurations from a newly registered account, with 502 errors and failed CI jobs, and notes that a successful exploit would leave no crash and no trace in the web logs (Alpine Linux, 2026-10-28); in process-creation telemetry, shells, interpreters or network tools started as children of the GitLab application server processes are the sign of success, and a server where that turns up needs its CI/CD variables, runner registration tokens and deploy keys treated as exposed.

    Triage: ordinary CI jobs run shells under the runners; only a shell spawned by the GitLab application server processes themselves matches this flaw, not one started inside a runner job.

    Defender takeaway
    Upgrade to 19.4.2, 19.3.5 or 19.2.8 now (GitLab, 2026-10-12), or better to 19.5.1, 19.4.3, 19.3.6 or 19.2.9, or on older branches the backports 19.1.9, 19.0.10 and 18.11.13, the builds of 2026-10-21 that also fix a second CVSS 10 regular-expression compiler flaw, CVE-2026-110264 (GitLab, 2026-10-21), internet-facing instances first as CERT-EU advises (CERT-EU, 2026-10-12), then instances where new users can self-register and create projects, which removes the push-access constraint Rapid7 found (Rapid7, 2026-10-13); the fix is a set of patches to the Ruby that GitLab bundles in its own packages and images, so an installation with its own Ruby, from source or in a self-built image, needs Ruby 3.3.13, 3.4.12 or 4.0.9 as well, and Alpine's GitLab on 19.3.6 with standard Ruby stayed vulnerable (Alpine Linux, 2026-10-28). CISA lists the flaw as exploited and NCSC Switzerland reports active exploitation, so an instance reachable on an affected version needs a compromise assessment as well as the upgrade; Rapid7's interim controls (restrict anonymous access to public projects and stop untrusted users creating or writing to public projects) reduce exposure only to the path it demonstrated (Rapid7, 2026-10-13).
