    2026-10-21NOTABLEEight eMudhra CA keys were guessable; Windows drops seven certificates, and Java, Python, Go and GitLab need updates

    Defender takeaway

    Update trust bundles and toolchains on every non-browser client, rebuild container images that embed an old bundle, and do not rely on revocation or CT for those clients; website operators with certificates chaining to emSign ECC Root CA - G3 need one from another hierarchy now, Chrome's removal of that root having been due to reach devices on 2026-10-27 (Google, 2026-10-20), and Windows devices that do not receive automatic certificate-trust updates need the updated Disallowed Certificate Trust List and the trust-list changes, including Microsoft's out-of-band update of 2026-10-26 (Microsoft, 2026-10-26). A Java runtime updated in the past few days needs the update of 2026-10-24 (OpenJDK, 2026-10-24), and an ACME client will not replace a certificate under that root outside its renewal window unless it supports ACME Renewal Information, so trigger the renewal by hand (The Hacker News, 2026-10-22).

    Exposure · triage · detection
    Exposure

    Any software that keeps its own CA bundle or does not check revocation keeps trusting the intermediates until updated; Python 3.15.2, 3.14.10, 3.13.18, 3.12.16 and 3.11.18 carry a built-in denylist (Python Insider, 2026-10-26), and the tracker lists fixed versions for pip (26.2.2), certifi, rustls-webpki, the curl CA bundle and distribution packages and lists Bottlerocket, HarmonyOS, certbot, containerd, Godot and LibreOffice as still pending; its update of 28 October says the git, curl and python3 that ship with macOS still trust them (Dennis Jackson, 2026-10-28). A client's state is read with the tracker's test hosts: a certificate error means the client does not trust the intermediates (Dennis Jackson, 2026-10-20).

    Triage

    A site that still chains to emSign ECC Root CA - G3 failing in Chrome after 2026-10-27, or a certificate that chains to one of the seven certificates Microsoft removed failing in Windows or Edge once the change reaches the device, is the announced root removal, not an attack (Google, 2026-10-20; Microsoft, 2026-10-26).

    Detection

    EMudhra says it found no evidence that the intermediates were used to issue end-user certificates (BleepingComputer, 2026-10-20), so a server certificate chain seen in TLS session metadata, proxy or EDR network telemetry that contains one of the eight intermediates or their Sectigo cross-signs, which the tracker lists, is worth treating as a possible forged certificate (Dennis Jackson, 2026-10-20). CT monitoring will not show one, because Google found no certificate chaining to the six TLS intermediates logged before it blocked them (Google, 2026-10-20).

    2026-10-13HIGHexploitedGitLab's CVSS 10.0 CI regex RCE is now on CISA KEV; the public PoC needs push access to a public project

    Defender takeaway

    Upgrade to 19.4.2, 19.3.5 or 19.2.8 now (GitLab, 2026-10-12), or better to 19.5.1, 19.4.3, 19.3.6 or 19.2.9, or on older branches the backports 19.1.9, 19.0.10 and 18.11.13, the builds of 2026-10-21 that also fix a second CVSS 10 regular-expression compiler flaw, CVE-2026-110264 (GitLab, 2026-10-21), internet-facing instances first as CERT-EU advises (CERT-EU, 2026-10-12), then instances where new users can self-register and create projects, which removes the push-access constraint Rapid7 found (Rapid7, 2026-10-13); the fix is a set of patches to the Ruby that GitLab bundles in its own packages and images, so an installation with its own Ruby, from source or in a self-built image, needs Ruby 3.3.13, 3.4.12 or 4.0.9 as well, and Alpine's GitLab on 19.3.6 with standard Ruby stayed vulnerable (Alpine Linux, 2026-10-28). CISA lists the flaw as exploited and NCSC Switzerland reports active exploitation, so an instance reachable on an affected version needs a compromise assessment as well as the upgrade; Rapid7's interim controls (restrict anonymous access to public projects and stop untrusted users creating or writing to public projects) reduce exposure only to the path it demonstrated (Rapid7, 2026-10-13).

    Exposure · triage · detection
    Exposure

    Self-managed GitLab CE or EE on 19.2.x below 19.2.8, 19.3.x below 19.3.5 or 19.4.x below 19.4.2; GitLab's table for this flaw starts at 19.2 (GitLab, 2026-10-12), but the sibling CVE-2026-110264 reaches every version from 7.0 (GitLab, 2026-10-21). The Ruby project says the underlying engine bugs are reached by any application that compiles a regular expression from attacker-controlled input (Ruby, 2026-10-23). Rapid7 found the conditions: an attacker must first commit a malicious CI/CD configuration file and a repository path containing UTF-8 characters to a branch in a public project, which an ordinary account can do by creating a public project where the instance allows it (Rapid7, 2026-10-13), and on instances where new users can self-register and create projects that constraint is removed (Rapid7, 2026-10-13). An instance with open sign-up, or with public projects that untrusted users can write to, is the case to prioritise.

    Triage

    Ordinary CI jobs run shells under the runners; only a shell spawned by the GitLab application server processes themselves matches this flaw, not one started inside a runner job.

    Detection

    GitLab's release page lists six detections for exploitation attempts on self-managed instances (GitLab, 2026-10-12). Alpine saw the attack as crashes of GitLab worker processes after crafted CI configurations from a newly registered account, with 502 errors and failed CI jobs, and notes that a successful exploit would leave no crash and no trace in the web logs (Alpine Linux, 2026-10-28); in process-creation telemetry, shells, interpreters or network tools started as children of the GitLab application server processes are the sign of success, and a server where that turns up needs its CI/CD variables, runner registration tokens and deploy keys treated as exposed.

    2026-10-22NOTABLEGitLab's critical patch fixes an unauthenticated CVSS 10.0 RCE in Org-mode rendering; no exploitation reported

    Defender takeaway

    Upgrade to the fixed build of the instance's line now, internet-reachable instances and those with public projects first; an instance that moved to 19.4.2, 19.3.5 or 19.2.8 for the earlier flaws is not yet fixed for this one (GitLab, 2026-10-21). For other Ruby applications that compile attacker-controlled patterns, Ruby recommends upgrading to 4.0.9, 3.4.12 or 3.3.13 or later, or avoiding compiling such patterns, and says neither Regexp.timeout nor a pattern-length limit reliably protects; Ruby has not requested CVE identifiers of its own for now and tells operators to track the issues under GitLab's identifiers (Ruby, 2026-10-23).

    Exposure · triage · detection
    Exposure

    Self-managed GitLab CE and EE on the versions above; the vulnerable path is reached when GitLab renders a .org file, so an instance with public projects, or one where untrusted users can create them, is the exposed shape, and until patching GitLab advises reducing public visibility (GitLab security, 2026-10-21). A Ruby application outside GitLab is exposed to the same bug when it compiles a regular expression from a string an attacker controls, through Regexp.new, Regexp.union, Regexp.compile or interpolation into a regexp literal; applications that only use patterns written by their own developers are not affected (Ruby, 2026-10-23).

    Triage

    A reader of documentation .org files renders each file once and quickly, while an attack produces a burst of timeouts from one client over a few minutes (GitLab security, 2026-10-21); a worker crash with no accompanying render burst from one client is more likely a benign parser bug than an attack (GitLab security, 2026-10-21).

    Detection

    GitLab's two detections key on, first, five or more render timeouts from the Org-mode renderer on .org files from one client within 30 minutes in the Rails exceptions log, with the request that actually crashes a worker visible only as a 502 on the .org blob route in the Workhorse log, and second, a native Ruby crash report in the Puma error log whose backtrace runs through org-ruby or Onigmo frames (GitLab security, 2026-10-21). In repository content, scan each suspect checkout for .org files with an oversized TODO-keyword line, and in the Rails request log look for editor preview requests whose file_path ends in .org while the URL names another file type, which forces the Org renderer (GitLab security, 2026-10-21). A successful exploit is quiet and does not reliably crash, so the absence of a hit never clears an instance (GitLab security, 2026-10-21). On an exposed, unpatched instance, hunt for unexpected child processes of Puma, new files owned by git in the temporary directory, outbound connections and changed crontabs or SSH keys for the git user, and treat the secrets, CI/CD variables, runner tokens and access tokens the git user can read as at risk (GitLab security, 2026-10-21).

    NOTABLECVE-2026-91403 +2updatedNATOA1

    eMudhra: the private keys of eight intermediate CA certificates were trivially recoverable, so anyone could forge trusted HTTPS certificates; browsers block them, clients with their own trust store or no revocation checking need an update (CVE-2026-111943 in Go)

    On 2026-10-17 a researcher reported to the Chrome Root Program, and Mozilla received a report the same day, that the private keys of eight eMudhra subordinate CA certificates were compromised: the keys were generated with insufficient randomness, which lets anyone forge trusted HTTPS certificates to impersonate any website against clients that have not removed trust in those CAs (Google, 2026-10-20; Mozilla, 2026-10-20). BleepingComputer, citing Mozilla's incident report, says all eight were P-384 keys generated in April 2025 with values below 256, so testing 256 numbers recovers a key, and that eMudhra blames a key-generation script error and found no evidence of end-user certificates (BleepingComputer, 2026-10-20). Google reports that no certificates chaining to the six TLS intermediates were logged to Certificate Transparency before it blocked them, so CT-enforcing clients such as Chrome could not have been attacked (Google, 2026-10-20); the tracker says it is not known whether attackers used the flaw against other clients (Dennis Jackson, 2026-10-20).

    Chrome blocked the intermediates on 2026-10-17, Firefox through OneCRL the same day, Microsoft platforms on 2026-10-20 and Apple devices on 2026-10-22, and eMudhra revoked all eight (Dennis Jackson, 2026-10-20; BleepingComputer, 2026-10-20). Microsoft went further: an out-of-band Windows update of 2026-10-26 removes seven certificates, six eMudhra G3 roots and an AAA Certificate Services cross-sign, from the Windows trust list, and the same seven left the Edge trust list on 2026-10-27 (Microsoft, 2026-10-26). Google removed the root that signed them, emSign ECC Root CA - G3, from the Chrome Root Store, with the removal expected to reach devices on 2026-10-27, after which some legitimate certificates chaining to it will stop working in Chrome (Google, 2026-10-20). Go 1.27.3 and 1.26.10 filter chains that contain the intermediates in crypto/x509, tracked as CVE-2026-111943 (Go team, 2026-10-20), and GitLab's release of 2026-10-29 removes trust for the eight intermediates in self-managed CE and EE, with GitLab Runner 19.5.1 and the AI Gateway needing separate updates (GitLab, 2026-10-29).

    Oracle's Security Alert of 2026-10-21 for CVE-2026-91403 (CVSS 3.1 9.1, component JSSE, remotely exploitable without authentication through the component's APIs) provided Java updates that distrust the impacted eMudhra intermediate CA certificates (Oracle, 2026-10-21), and a second Security Alert of 2026-10-24, CVE-2026-114820 (CVSS 3.1 9.1, same component and exposure), provides updates that remove the impacted root CA certificates and, from its revision of 2026-10-30, also covers the Java component of Oracle Database Server (not client-only installations), Autonomous Health Framework and OPatch (Oracle, 2026-10-30). OpenJDK's guidance tells users of a standalone runtime to act immediately even if they updated in the past few days, preferably by installing an update whose release note names JDK-8395690 and CVE-2026-114820 (OpenJDK, 2026-10-24). If no update is available, OpenJDK gives two alternatives: delete the aliases emsignrootcag1, emsignrootcag2, emsigneccrootcag3 and comodoaaaca from the runtime's cacerts keystore and restart it, repeating for each installation, or enable revocation checking with -Dcom.sun.net.ssl.checkRevocation=true and -Dcom.sun.security.enableCRLDP=true on the application's java command line (OpenJDK, 2026-10-24). OpenJDK packages from Red Hat, Oracle Linux, Fedora, Arch Linux and Gentoo most likely use the operating system's certificates; Debian, Devuan and Ubuntu need a manual workaround because updating ca-certificates and ca-certificates-java does not refresh the keystore (as superuser, remove /etc/ssl/certs/java/cacerts and run update-ca-certificates --fresh) (OpenJDK, 2026-10-24).

    Exposure
    Any software that keeps its own CA bundle or does not check revocation keeps trusting the intermediates until updated; Python 3.15.2, 3.14.10, 3.13.18, 3.12.16 and 3.11.18 carry a built-in denylist (Python Insider, 2026-10-26), and the tracker lists fixed versions for pip (26.2.2), certifi, rustls-webpki, the curl CA bundle and distribution packages and lists Bottlerocket, HarmonyOS, certbot, containerd, Godot and LibreOffice as still pending; its update of 28 October says the git, curl and python3 that ship with macOS still trust them (Dennis Jackson, 2026-10-28). A client's state is read with the tracker's test hosts: a certificate error means the client does not trust the intermediates (Dennis Jackson, 2026-10-20).
    Detection
    EMudhra says it found no evidence that the intermediates were used to issue end-user certificates (BleepingComputer, 2026-10-20), so a server certificate chain seen in TLS session metadata, proxy or EDR network telemetry that contains one of the eight intermediates or their Sectigo cross-signs, which the tracker lists, is worth treating as a possible forged certificate (Dennis Jackson, 2026-10-20). CT monitoring will not show one, because Google found no certificate chaining to the six TLS intermediates logged before it blocked them (Google, 2026-10-20).

    Triage: a site that still chains to emSign ECC Root CA - G3 failing in Chrome after 2026-10-27, or a certificate that chains to one of the seven certificates Microsoft removed failing in Windows or Edge once the change reaches the device, is the announced root removal, not an attack (Google, 2026-10-20; Microsoft, 2026-10-26).

    Defender takeaway
    Update trust bundles and toolchains on every non-browser client, rebuild container images that embed an old bundle, and do not rely on revocation or CT for those clients; website operators with certificates chaining to emSign ECC Root CA - G3 need one from another hierarchy now, Chrome's removal of that root having been due to reach devices on 2026-10-27 (Google, 2026-10-20), and Windows devices that do not receive automatic certificate-trust updates need the updated Disallowed Certificate Trust List and the trust-list changes, including Microsoft's out-of-band update of 2026-10-26 (Microsoft, 2026-10-26). A Java runtime updated in the past few days needs the update of 2026-10-24 (OpenJDK, 2026-10-24), and an ACME client will not replace a certificate under that root outside its renewal window unless it supports ACME Renewal Information, so trigger the renewal by hand (The Hacker News, 2026-10-22).

    Detection
    GitLab's release page lists six detections for exploitation attempts on self-managed instances (GitLab, 2026-10-12).     Triage: ordinary CI jobs run shells under the runners; only a shell spawned by the GitLab application server processes themselves matches this flaw, not one started inside a runner job.

    NOTABLECVE-2026-110264updatedNATOA2

    CVE-2026-110264, GitLab CE/EE: an unauthenticated code-execution flaw in the Org-mode renderer's regular-expression handling, fixed in 19.5.1, 19.4.3 and 19.3.6 and backported to four older lines (CVSS 10.0)

    GitLab's ad-hoc critical patch release of 2026-10-21 fixes CVE-2026-110264 (CVSS 3.1 10.0), an integer overflow while compiling a specially crafted regular expression that could let an unauthenticated user execute code on the GitLab server (GitLab, 2026-10-21). GitLab's detection write-ups place the flaw in the rendering of Org-mode files: the org-ruby gem builds a regular expression from a custom TODO keyword in a .org file, a keyword with more than 32,767 repeats makes the Onigmo engine write out of bounds when it matches, and with heap grooming that becomes command execution as the git user (GitLab security, 2026-10-21). The attack needs no authentication, only one public project that can hold the .org payload (GitLab security, 2026-10-21). Affected are all versions from 7.0 before 18.11.13, 19.0 before 19.0.10, 19.1 before 19.1.9, 19.2 before 19.2.9, 19.3 before 19.3.6, 19.4 before 19.4.3 and 19.5 before 19.5.1; GitLab.com is already patched, and GitLab Dedicated tenants on 19.3.5-internal0, 19.4.2-internal0 or later need no action (GitLab, 2026-10-21). The builds 19.4.2, 19.3.5 and 19.2.8 from GitLab's earlier regular-expression fixes do not contain this fix (GitLab security, 2026-10-21). GitLab does not state that the flaw is exploited, and its patch notes and detection pages mention no public proof of concept (GitLab, 2026-10-21). The bug is in Ruby's Onigmo regular-expression engine: the Ruby project released 4.0.9, 3.4.12 and 3.3.13 on 2026-10-23 with the fix, the release of 4.0.8 lacks the fix for this flaw, and GitLab fixed its own servers by patching the Ruby it ships (Ruby, 2026-10-23).

    Exposure
    Self-managed GitLab CE and EE on the versions above; the vulnerable path is reached when GitLab renders a .org file, so an instance with public projects, or one where untrusted users can create them, is the exposed shape, and until patching GitLab advises reducing public visibility (GitLab security, 2026-10-21). A Ruby application outside GitLab is exposed to the same bug when it compiles a regular expression from a string an attacker controls, through Regexp.new, Regexp.union, Regexp.compile or interpolation into a regexp literal; applications that only use patterns written by their own developers are not affected (Ruby, 2026-10-23).
    Detection
    GitLab's two detections key on, first, five or more render timeouts from the Org-mode renderer on .org files from one client within 30 minutes in the Rails exceptions log, with the request that actually crashes a worker visible only as a 502 on the .org blob route in the Workhorse log, and second, a native Ruby crash report in the Puma error log whose backtrace runs through org-ruby or Onigmo frames (GitLab security, 2026-10-21). In repository content, scan each suspect checkout for .org files with an oversized TODO-keyword line, and in the Rails request log look for editor preview requests whose file_path ends in .org while the URL names another file type, which forces the Org renderer (GitLab security, 2026-10-21). A successful exploit is quiet and does not reliably crash, so the absence of a hit never clears an instance (GitLab security, 2026-10-21). On an exposed, unpatched instance, hunt for unexpected child processes of Puma, new files owned by git in the temporary directory, outbound connections and changed crontabs or SSH keys for the git user, and treat the secrets, CI/CD variables, runner tokens and access tokens the git user can read as at risk (GitLab security, 2026-10-21).

    Triage: a reader of documentation .org files renders each file once and quickly, while an attack produces a burst of timeouts from one client over a few minutes (GitLab security, 2026-10-21); a worker crash with no accompanying render burst from one client is more likely a benign parser bug than an attack (GitLab security, 2026-10-21).

    Defender takeaway
    Upgrade to the fixed build of the instance's line now, internet-reachable instances and those with public projects first; an instance that moved to 19.4.2, 19.3.5 or 19.2.8 for the earlier flaws is not yet fixed for this one (GitLab, 2026-10-21). For other Ruby applications that compile attacker-controlled patterns, Ruby recommends upgrading to 4.0.9, 3.4.12 or 3.3.13 or later, or avoiding compiling such patterns, and says neither Regexp.timeout nor a pattern-length limit reliably protects; Ruby has not requested CVE identifiers of its own for now and tells operators to track the issues under GitLab's identifiers (Ruby, 2026-10-23).
