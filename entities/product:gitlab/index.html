    2026-10-22NOTABLEGitLab's critical patch fixes an unauthenticated CVSS 10.0 RCE in Org-mode rendering; no exploitation reported

    Defender takeaway

    Upgrade to the fixed build of the instance's line now, internet-reachable instances and those with public projects first; an instance that moved to 19.4.2, 19.3.5 or 19.2.8 for the earlier flaws is not yet fixed for this one (GitLab, 2026-10-21). For other Ruby applications that compile attacker-controlled patterns, Ruby recommends upgrading to 4.0.9, 3.4.12 or 3.3.13 or later, or avoiding compiling such patterns, and says neither Regexp.timeout nor a pattern-length limit reliably protects; Ruby has not requested CVE identifiers of its own for now and tells operators to track the issues under GitLab's identifiers (Ruby, 2026-10-23).

    Exposure · triage · detection
    Exposure

    Self-managed GitLab CE and EE on the versions above; the vulnerable path is reached when GitLab renders a .org file, so an instance with public projects, or one where untrusted users can create them, is the exposed shape, and until patching GitLab advises reducing public visibility (GitLab security, 2026-10-21). A Ruby application outside GitLab is exposed to the same bug when it compiles a regular expression from a string an attacker controls, through Regexp.new, Regexp.union, Regexp.compile or interpolation into a regexp literal; applications that only use patterns written by their own developers are not affected (Ruby, 2026-10-23).

    Triage

    A reader of documentation .org files renders each file once and quickly, while an attack produces a burst of timeouts from one client over a few minutes (GitLab security, 2026-10-21); a worker crash with no accompanying render burst from one client is more likely a benign parser bug than an attack (GitLab security, 2026-10-21).

    Detection

    GitLab's two detections key on, first, five or more render timeouts from the Org-mode renderer on .org files from one client within 30 minutes in the Rails exceptions log, with the request that actually crashes a worker visible only as a 502 on the .org blob route in the Workhorse log, and second, a native Ruby crash report in the Puma error log whose backtrace runs through org-ruby or Onigmo frames (GitLab security, 2026-10-21). In repository content, scan each suspect checkout for .org files with an oversized TODO-keyword line, and in the Rails request log look for editor preview requests whose file_path ends in .org while the URL names another file type, which forces the Org renderer (GitLab security, 2026-10-21). A successful exploit is quiet and does not reliably crash, so the absence of a hit never clears an instance (GitLab security, 2026-10-21). On an exposed, unpatched instance, hunt for unexpected child processes of Puma, new files owned by git in the temporary directory, outbound connections and changed crontabs or SSH keys for the git user, and treat the secrets, CI/CD variables, runner tokens and access tokens the git user can read as at risk (GitLab security, 2026-10-21).

    2026-10-13HIGHGitLab's CVSS 10.0 CI regex flaw now has a public PoC; the demonstrated path needs push access to a public project

    Defender takeaway

    Upgrade to 19.4.2, 19.3.5 or 19.2.8 now, starting with internet-facing instances as CERT-EU advises (CERT-EU, 2026-10-12); GitLab's release page lists no workaround as of 2026-10-13 (GitLab, 2026-10-12), Rapid7's interim controls (restrict anonymous access to public projects and stop untrusted users creating or writing to public projects) reduce exposure only to the path it demonstrated and do not fix the compiler flaw (Rapid7, 2026-10-13), and the proof of concept is tuned to one build while its author says analysis of additional reachable paths is ongoing (Rapid7 proof-of-concept README, 2026-10-13), so an instance that cannot be upgraded this week should be kept off untrusted networks; on a single-node instance the upgrade causes downtime, because migrations must finish before GitLab can start, so schedule the window now (GitLab, 2026-10-12).

    Exposure · triage · detection
    Exposure

    Self-managed GitLab CE or EE on 19.2.x below 19.2.8, 19.3.x below 19.3.5 or 19.4.x below 19.4.2; GitLab's table starts at 19.2 and lists no earlier branch (GitLab, 2026-10-12). NCSC Switzerland states the prerequisites as network access to the instance and delivery of a crafted regular expression through CI/CD configuration (NCSC Switzerland, 2026-10-12); Rapid7 found the conditions: an attacker must first commit a malicious CI/CD configuration file and a repository path containing UTF-8 characters to a branch in a public project, which an ordinary account can do by creating a public project where the instance allows it (Rapid7, 2026-10-13), and on instances where new users can self-register and create projects that constraint is removed (Rapid7, 2026-10-13). An instance with open sign-up, or with public projects that untrusted users can write to, is the case to prioritise.

    Triage

    Ordinary CI jobs run shells under the runners; only a shell spawned by the GitLab application server processes themselves matches this flaw, not one started inside a runner job; an anonymous CI lint request is ordinary on its own, and the signal is one aimed at a project that a newly created or little-used account has just pushed a CI configuration to.

    Detection

    GitLab and NCSC publish no indicators, so this is a hunt for the mechanism: in process-creation telemetry, shells, interpreters or network tools started as children of the GitLab application server processes, and in GitLab's audit and application logs, recently created or changed CI/CD configurations that carry unusual regular expressions, from accounts or addresses that have not used the instance before. Rapid7's proof of concept delivers the code through the public CI lint API without credentials, after pushing to a public project (Rapid7 proof-of-concept README, 2026-10-13): look for unauthenticated GET requests to /api/v4/projects/:id/ci/lint against a project that an account has just pushed to, and for application worker crashes that follow them, which the README says end the request with HTTP 502 while the worker is replaced (Rapid7 proof-of-concept README, 2026-10-13). A server where that turns up needs its CI/CD variables, runner registration tokens and deploy keys treated as exposed.

    Defender takeaway

    Triage
    Triage

GitLab has also published three detections for exploitation attempts: reads of gitlab.yml, inclusion through the metadata.path parameter, and file-path enumeration (GitLab, 2026-09-10).

    Detection

    Authentication logs across the Exchange interfaces for failed sign-ins spread over many accounts from one source, mailbox reads by connected applications nobody registered, a SoftEther client presented as conhost.exe or dllhost.exe in process and service-installation telemetry, directory-replication requests that reach a domain controller from a host that is not one, and web access logs for traversal, command-injection and enumeration attempts (FBI IC3, AA26-281A, 2026-10-08).

    2026-10-07NOTABLECloudSEK: a Gentlemen affiliate reached victims through stolen GitLab CI/CD secrets and drove attacks over MCP

    Defender takeaway

    Treat CI/CD variable stores and git history as credential stores: keep secrets in a dedicated secrets manager, mask and protect every variable, rotate tokens and audit history for removed secrets, because the actor recovered credentials from commits that no longer appeared on the current branch; never bind an MCP server beyond loopback and treat its command-execution tool as privileged with an audit trail (CloudSEK, 2026-10-05).

    Exposure · triage · detection
    Exposure

    GitLab instances whose CI/CD variables or git history hold tokens, keys and database credentials, including secrets removed from the current branch but still in history, GitLab instances that run pipelines for more than one organisation, APIs that fetch user-supplied URLs without validation, and MCP servers reachable beyond strict loopback (CloudSEK, 2026-10-05).

    Triage

    Legitimate backup jobs also mirror object storage to remote destinations, so the discriminator is the destination and the source host, not the copy command itself (CloudSEK, 2026-10-05).

    Detection

    CI/CD and repository audit logs for variable reads from unexpected addresses, service-account token use outside the normal runner infrastructure, and README or issue changes made with a pipeline token from an unusual source; object-storage and database logs for bulk mirroring or dumps to hosts outside the backup estate; MCP initialisation requests from clients outside an allowlist; and a PostgreSQL process killed and its data directory deleted after a large read (CloudSEK, 2026-10-05).

    2026-08-19HIGHexploitedGitLab breaks its own release cadence for a pre-auth flaw whose impact is destruction, not disclosure

    Defender takeaway

    The hunt is unusually cheap and worth running even on an instance you believe was patched on day one, because the exploitation window opened before most change windows close. watchTowr's guidance is to search web logs for requests containing @gl_introduced and to look for signs of probes or attempted exploitation (SecurityWeek, 2026-08-20), a literal string search against access logs for the GraphQL API path, needing no new tooling. The impact class is what changes the follow-up: this flaw modifies and deletes public projects and user data rather than exfiltrating it, so a successful attack does not leave the usual outbound-transfer trace and may look like an operator error or a bad merge rather than an intrusion. That makes backup and integrity comparison, not egress review, the way to answer whether anything happened.

    Triage
    Triage

    GraphQL is how GitLab's own web UI and integrations talk to the server, so request volume to that endpoint is uninformative on its own; the discriminator is a state-changing outcome (a deleted or altered project, a modified user record) appearing in the audit log with no corresponding authenticated actor, and for the CSRF flaw, mutations arriving as GET rather than POST, which normal clients do not do.

    NOTABLECVE-2026-110264updatedNATOA2

    CVE-2026-110264, GitLab CE/EE: an unauthenticated code-execution flaw in the Org-mode renderer's regular-expression handling, fixed in 19.5.1, 19.4.3 and 19.3.6 and backported to four older lines (CVSS 10.0)

    GitLab's ad-hoc critical patch release of 2026-10-21 fixes CVE-2026-110264 (CVSS 3.1 10.0), an integer overflow while compiling a specially crafted regular expression that could let an unauthenticated user execute code on the GitLab server (GitLab, 2026-10-21). GitLab's detection write-ups place the flaw in the rendering of Org-mode files: the org-ruby gem builds a regular expression from a custom TODO keyword in a .org file, a keyword with more than 32,767 repeats makes the Onigmo engine write out of bounds when it matches, and with heap grooming that becomes command execution as the git user (GitLab security, 2026-10-21). The attack needs no authentication, only one public project that can hold the .org payload (GitLab security, 2026-10-21). Affected are all versions from 7.0 before 18.11.13, 19.0 before 19.0.10, 19.1 before 19.1.9, 19.2 before 19.2.9, 19.3 before 19.3.6, 19.4 before 19.4.3 and 19.5 before 19.5.1; GitLab.com is already patched, and GitLab Dedicated tenants on 19.3.5-internal0, 19.4.2-internal0 or later need no action (GitLab, 2026-10-21). The builds 19.4.2, 19.3.5 and 19.2.8 from GitLab's earlier regular-expression fixes do not contain this fix (GitLab security, 2026-10-21). GitLab does not state that the flaw is exploited, and its patch notes and detection pages mention no public proof of concept (GitLab, 2026-10-21). The bug is in Ruby's Onigmo regular-expression engine: the Ruby project released 4.0.9, 3.4.12 and 3.3.13 on 2026-10-23 with the fix, the release of 4.0.8 lacks the fix for this flaw, and GitLab fixed its own servers by patching the Ruby it ships (Ruby, 2026-10-23).

    Exposure
    Self-managed GitLab CE and EE on the versions above; the vulnerable path is reached when GitLab renders a .org file, so an instance with public projects, or one where untrusted users can create them, is the exposed shape, and until patching GitLab advises reducing public visibility (GitLab security, 2026-10-21). A Ruby application outside GitLab is exposed to the same bug when it compiles a regular expression from a string an attacker controls, through Regexp.new, Regexp.union, Regexp.compile or interpolation into a regexp literal; applications that only use patterns written by their own developers are not affected (Ruby, 2026-10-23).
    Detection
    GitLab's two detections key on, first, five or more render timeouts from the Org-mode renderer on .org files from one client within 30 minutes in the Rails exceptions log, with the request that actually crashes a worker visible only as a 502 on the .org blob route in the Workhorse log, and second, a native Ruby crash report in the Puma error log whose backtrace runs through org-ruby or Onigmo frames (GitLab security, 2026-10-21). In repository content, scan each suspect checkout for .org files with an oversized TODO-keyword line, and in the Rails request log look for editor preview requests whose file_path ends in .org while the URL names another file type, which forces the Org renderer (GitLab security, 2026-10-21). A successful exploit is quiet and does not reliably crash, so the absence of a hit never clears an instance (GitLab security, 2026-10-21). On an exposed, unpatched instance, hunt for unexpected child processes of Puma, new files owned by git in the temporary directory, outbound connections and changed crontabs or SSH keys for the git user, and treat the secrets, CI/CD variables, runner tokens and access tokens the git user can read as at risk (GitLab security, 2026-10-21).

    Triage: a reader of documentation .org files renders each file once and quickly, while an attack produces a burst of timeouts from one client over a few minutes (GitLab security, 2026-10-21); a worker crash with no accompanying render burst from one client is more likely a benign parser bug than an attack (GitLab security, 2026-10-21).

    Defender takeaway
    Upgrade to the fixed build of the instance's line now, internet-reachable instances and those with public projects first; an instance that moved to 19.4.2, 19.3.5 or 19.2.8 for the earlier flaws is not yet fixed for this one (GitLab, 2026-10-21). For other Ruby applications that compile attacker-controlled patterns, Ruby recommends upgrading to 4.0.9, 3.4.12 or 3.3.13 or later, or avoiding compiling such patterns, and says neither Regexp.timeout nor a pattern-length limit reliably protects; Ruby has not requested CVE identifiers of its own for now and tells operators to track the issues under GitLab's identifiers (Ruby, 2026-10-23).

    HIGHCVE-2026-97229updatedNATOA2

    CVE-2026-97229, GitLab CE/EE: an integer overflow in the CI/CD regular-expression compiler allows code execution on self-managed servers and now has a public proof of concept; fixed in 19.4.2, 19.3.5 and 19.2.8, and 19.4.1 does not close it (CVSS 10.0)

    GitLab's critical patch release of 2026-10-12 (19.4.2, 19.3.5 and 19.2.8) fixes CVE-2026-97229, an integer overflow in the CI/CD regular-expression compiler that, "under certain conditions", could allow an unauthenticated user to execute arbitrary code on the GitLab server through a specially crafted regular expression in a CI/CD configuration; GitLab scores it CVSS 3.1 10.0 with no privileges required (GitLab, 2026-10-12). Affected are self-managed CE and EE from 19.2 before 19.2.8, 19.3 before 19.3.5 and 19.4 before 19.4.2; GitLab.com already runs the patched version and Dedicated customers need no action (GitLab, 2026-10-12). CERT-EU and BleepingComputer give 19.3.4 as the 19.3 fix, but GitLab's page names 19.3.5 and says 19.3.4 had a merge-request page bug, so the GitLab figure governs (CERT-EU, 2026-10-12; BleepingComputer, 2026-10-12). The 19.4.1 release of 2026-09-23 fixed two flaws from the same reporter in the same component, a double free in the regular-expression parser and an integer overflow in the compiler, both rated for an authenticated user (GitLab, 2026-09-23); CVE-2026-97229 is rated without that requirement, and 19.4.1 is still affected. NCSC Switzerland and CERT-EU both published advisories on 2026-10-12 (NCSC Switzerland, 2026-10-12; CERT-EU, 2026-10-12); NCSC lists the exploitation status as unknown (NCSC Switzerland, 2026-10-12); Rapid7 reproduced the code execution on 19.4.1, published a proof of concept, and reports no confirmed exploitation in the wild (Rapid7, 2026-10-13). GitLab publishes the issue detail for a security fix 90 days after the release that carries it (GitLab, 2026-10-12).

    Exposure
    Self-managed GitLab CE or EE on 19.2.x below 19.2.8, 19.3.x below 19.3.5 or 19.4.x below 19.4.2; GitLab's table starts at 19.2 and lists no earlier branch (GitLab, 2026-10-12). NCSC Switzerland states the prerequisites as network access to the instance and delivery of a crafted regular expression through CI/CD configuration (NCSC Switzerland, 2026-10-12); Rapid7 found the conditions: an attacker must first commit a malicious CI/CD configuration file and a repository path containing UTF-8 characters to a branch in a public project, which an ordinary account can do by creating a public project where the instance allows it (Rapid7, 2026-10-13), and on instances where new users can self-register and create projects that constraint is removed (Rapid7, 2026-10-13). An instance with open sign-up, or with public projects that untrusted users can write to, is the case to prioritise.
    Detection
    GitLab and NCSC publish no indicators, so this is a hunt for the mechanism: in process-creation telemetry, shells, interpreters or network tools started as children of the GitLab application server processes, and in GitLab's audit and application logs, recently created or changed CI/CD configurations that carry unusual regular expressions, from accounts or addresses that have not used the instance before. Rapid7's proof of concept delivers the code through the public CI lint API without credentials, after pushing to a public project (Rapid7 proof-of-concept README, 2026-10-13): look for unauthenticated GET requests to /api/v4/projects/:id/ci/lint against a project that an account has just pushed to, and for application worker crashes that follow them, which the README says end the request with HTTP 502 while the worker is replaced (Rapid7 proof-of-concept README, 2026-10-13). A server where that turns up needs its CI/CD variables, runner registration tokens and deploy keys treated as exposed.

    Triage: ordinary CI jobs run shells under the runners; only a shell spawned by the GitLab application server processes themselves matches this flaw, not one started inside a runner job; an anonymous CI lint request is ordinary on its own, and the signal is one aimed at a project that a newly created or little-used account has just pushed a CI configuration to.

    Defender takeaway
    Upgrade to 19.4.2, 19.3.5 or 19.2.8 now, starting with internet-facing instances as CERT-EU advises (CERT-EU, 2026-10-12); GitLab's release page lists no workaround as of 2026-10-13 (GitLab, 2026-10-12), Rapid7's interim controls (restrict anonymous access to public projects and stop untrusted users creating or writing to public projects) reduce exposure only to the path it demonstrated and do not fix the compiler flaw (Rapid7, 2026-10-13), and the proof of concept is tuned to one build while its author says analysis of additional reachable paths is ongoing (Rapid7 proof-of-concept README, 2026-10-13), so an instance that cannot be upgraded this week should be kept off untrusted networks; on a single-node instance the upgrade causes downtime, because migrations must finish before GitLab can start, so schedule the window now (GitLab, 2026-10-12).

    HIGHCVE-2026-85706 +2exploitedupdatedNATOA1

    CVE-2026-85706, GitLab CE/EE: unauthenticated path traversal in the repository commits API reads arbitrary server files, and honeypots recorded probes by the day after the patch (CVSS 10.0)

    GitLab's own patch-release notes name the root cause plainly: "improper path confinement and missing authentication enforcement in the repository commits API" let an unauthenticated caller read arbitrary files from the server (GitLab, 2026-09-10). The vulnerability, CVE-2026-85706 (CVSS 10.0, scope-changed, no privileges or user interaction required), affects every self-managed CE/EE release from 18.7 up to 19.1.8, 19.2.6 and 19.3.2, the versions GitLab shipped on 2026-09-10, with backports to 19.0.9 and 18.11.12 following on 2026-09-23; GitLab.com was already running the patched version, and GitLab Dedicated customers need no action. watchTowr warns that the readable files can include configuration files, secrets or other sensitive server-side data, and that GitLab instances often hold source code, credentials and CI/CD configuration data (watchTowr, 2026-09-11); in analyst judgement, that is what turns a file-read primitive into a foothold on the CI/CD and source-control plane GitLab manages. The flaw was reported through GitLab's HackerOne bug-bounty program by researcher s3ntago (GitLab, 2026-09-10).

    watchTowr reproduced the vulnerability and validated exposure across client environments, and by 2026-09-11 its Attacker Eye honeypot network was already recording behavioral probes for the vulnerability, which watchTowr reads as attackers having already built an exploit (watchTowr, 2026-09-11). CISA added the CVE to its Known Exploited Vulnerabilities catalog on 2026-09-11 (CISA KEV, catalogue version 2026.09.11), and NCSC Switzerland's own advisory, published earlier that same day, still recorded exploitation status as "unknown", which shows how fast the status moved within a single day (NCSC Switzerland, 2026-09-11). The same release also fixed CVE-2026-87719 (CVSS 9.9), an insecure GraphQL-subscription deserialization issue that lets an authenticated user with Duo Chat access obtain Advanced Search configurations and credentials (GitLab, 2026-09-10); it is not KEV-listed, and NCSC Switzerland's advisory has since recorded it as exploited too (see the 2026-09-16 update below), though on materially thinner evidence than CVE-2026-85706's own KEV listing and honeypot corroboration.

GitLab has also published three detections for exploitation attempts: reads of gitlab.yml, inclusion through the metadata.path parameter, and file-path enumeration (GitLab, 2026-09-10).
