    NOTABLENATOB2

    Okta Threat Intelligence: AI agents register on Auth0 tenants and Okta organizations with disposable addresses from the mail.tm service, whose single rotating mailbox domain makes blocklists very likely stop matching within weeks; ARTEX, Cairn, CyberStrikeAI and pentestcode each picked it at run time

    Okta Threat Intelligence reports that since June 2026, and at scale through October and November, AI agents have registered accounts with disposable email addresses on Auth0 tenants and Okta organizations that allow public self-service registration, activity Okta calls almost certainly malicious and that customers often reported alongside attacks on their applications (Okta, 2026-11-23). The addresses mostly belong to the mail.tm family, a free receive-only service whose API needs no account or key and lets a script create a mailbox, obtain a token and poll for one-time codes (Okta, 2026-11-23). In tests by the P0 Labs team of Permiso, which Okta acquired on 2026-08-26 (Okta, 2026-07-30), the ARTEX, Cairn, CyberStrikeAI and pentestcode frameworks each picked mail.tm at run time, and in a data set containing attacker tooling mail.tm appeared on 80 percent of the attacker hosts where disposable email was found (Okta, 2026-11-23).

    mail.tm exposes only one active mailbox domain at a time and replaces it periodically, so a blocklist built from earlier domains will very likely stop matching within weeks; Okta's Auth0 telemetry shows sign-ups tracking the domain the API currently returns, and the attackers' domain changed around 2026-10-30 when the API response did. Agents also used mailinator, guerrillamail and emailnator, and at one target an agent moved to another provider when blocked, which Okta reads as agents treating disposable mail as an interchangeable capability. Okta says the use always occurred within a short window of other agentic reconnaissance and intrusion attempts against the same entities (Okta, 2026-11-23). Bot detection and CAPTCHA generally stopped the October mail.tm sign-ups before email verification, but Okta warns agents can solve challenges and commonly register by calling the Auth0 Authentication API directly, which can skip protections applied in Universal Login (Okta, 2026-11-23).

    Exposure
    An Auth0 tenant or Okta organization that allows public self-service registration. For workforce users Okta says self-service registration is a prerequisite for many of the attacks it describes and should be disabled or restricted (Okta, 2026-11-23).
    Detection
    In identity-provider registration telemetry, sign-up events whose email domain belongs to a disposable provider's currently active mailbox domain, kept current by polling the provider's public domain endpoint instead of a static list, as Okta advises (Okta, 2026-11-23).

    Triage: the discriminator Okta supports is context: a disposable-domain sign-up read alongside other agentic reconnaissance or intrusion attempts against the same entities, not the domain alone (Okta, 2026-11-23).

    Defender takeaway
    On Auth0, block sign-ups through the API while allowing Universal Login and block disposable domains with Actions; on Okta Workforce Identity, disable or restrict self-service registration. Treat a disposable-domain sign-up as a prompt to look for other agentic activity against the same estate, since Okta says it gives a heads-up to look for successful intrusion attempts, and do not rely on CAPTCHA alone (Okta, 2026-11-23).

    Unit 42: more than ten campaigns in July to September 2026 ran autonomous AI agents from web-shell footholds on vulnerable web applications, with a command-gap median of 1.4 seconds, ===[Title]=== script headers and 40 to 100 unique Base64 payloads per session

    Unit 42 tracked more than ten global campaigns between July and September 2026 in which different attackers deployed autonomous AI agents, against sectors including government, logistics, manufacturing, agriculture and education. Every campaign began with a web shell deployed through a vulnerable web application, typically supplied by the human operator, after which the agent did reconnaissance, credential harvesting, privilege escalation and lateral movement; Unit 42 names no product, CVE or flaw class for the entry vectors and says the novelty was speed and efficiency, not technique (Unit 42, 2026-11-24).

    The traces: a median gap of 1.4 seconds between commands once an agent took over, against 23.9 seconds in the human phase of a subset of attacks; about 800 unique commands in 140 minutes in one case; section headers such as ===[Title]=== in shell commands and scripts in every campaign and step-by-step reasoning notes in more than half; 40 to 100 unique, target-tailored Base64 payloads per session; and no compiled implants, the arsenal being in most cases simple single-use scripts such as PHP web shells, PowerShell WMI backdoors and Python credential harvesters. The agents probed defences: the same find command ran on six endpoints excluding three security vendors, and one agent applied strace to the Microsoft Defender for Endpoint daemon (Unit 42, 2026-11-24).

    The Copy Fail exploit recurred across several organisations; in a different attack sequence an agent tried the public PwnKit and CVE-2024-1086 binaries, then wrote custom C on the target and rewrote the exploit in Python, and Unit 42 saw agents try five techniques in sequence when earlier ones failed. In one AWS case it switched to IMDSv2 token acquisition after IMDSv1 was blocked and enumerated 20 services across eight regions; in another it pushed web shells to more than 40 locations on a Windows IIS server within 26 minutes, and Unit 42 describes another agent that found a vendor's GitLab credentials on a victim's web server and tried to brute-force access to that GitLab instance, exploiting no GitLab flaw (Unit 42, 2026-11-24).

    Unit 42 found no behavioural marker tying the activity to a model or framework; a command-and-control address in one campaign also hosted a CyberStrikeAI instance, from which it infers the orchestration platform (Unit 42, 2026-11-24). ReliaQuest saw a credential-gated CyberStrikeAI login page on a staging host and could not determine whether the tool played a part (ReliaQuest, 2026-10-07).

    NOTABLENATOB2

    CyberStrikeAI turned on AWS: Elastic reads one server's 16 days across eight identities in four accounts, 56 user-data reads in 141 milliseconds, and why six detections each rated medium or low and only the source address tied them together

    Between 2026-09-30 and 2026-10-16 one server serving a CyberStrikeAI web interface used the credentials of eight AWS identities (five IAM users and three EC2 instance roles) across four accounts and generated 78 alerts, the first case Elastic has seen of this tooling turned on AWS (Elastic Security Labs, 2026-11-13). It started by validating identities: GetCallerIdentity on four IAM users in three accounts within 51 minutes, three of the calls in the same second (Elastic Security Labs, 2026-11-13). An instance role then read a secret, made one user-data request and fired 56 more in 141 milliseconds, spacing Elastic says fits tooling working through a prepared list of instance IDs (Elastic Security Labs, 2026-11-13). On 2026-10-02 another instance role read an encrypted Systems Manager parameter and issued a SendCommand 29 seconds later, which Elastic calls the highest-risk activity; the audit log does not show the command or its outcome (Elastic Security Labs, 2026-11-13). After 14 quiet days the server returned and revalidated credentials, including a user in a fourth account (Elastic Security Labs, 2026-11-13). Elastic does not know how the credentials were obtained and infers that the instance-role sessions, used from an outside address, were taken from the instances, for example through SSRF or host compromise (Elastic Security Labs, 2026-11-13). Team Cymru counted 21 unique addresses running CyberStrikeAI between 2026-01-20 and 2026-02-26 (Team Cymru, 2026-03-02).

    Exposure
    AWS accounts where IAM user keys or instance-role credentials can leave the account and the principals may read EC2 user data or Secrets Manager values or send Systems Manager commands; secrets in user data are readable by any such principal and Elastic says to treat them as exposed (Elastic Security Labs, 2026-11-13).
