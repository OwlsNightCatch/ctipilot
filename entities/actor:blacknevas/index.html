    Defender insights

    What each entry about BlackNevas tells a defender to do, newest first.

    2026-11-14NOTABLEKaspersky: BlackNevas used vCenter Host Profiles to enable SSH on ESXi, destroyed backups first, then wiped datastores

    Defender takeaway

    Treat the vCenter appliances as the control plane to protect: alert on Host Profile changes to TSM-SSH outside change windows and on SSH from vCenter to ESXi that follows them, review VMware-looking services on the appliances against a trusted list, and keep backup-platform credentials and administration separate from the systems that can reach vCenter, because the backup environment was destroyed before the hosts (Kaspersky GERT, 2026-11-13).

    Exposure · triage · detection
    Exposure

    A vCenter and ESXi estate where accounts from systems outside the virtualisation layer can reach the vCenter appliances and where Host Profile remediation can change the SSH service state; the article names no version (Kaspersky GERT, 2026-11-13).

    Triage

    Each Host Profile step is legitimate alone, so the distinguishing context is authorisation, timing, source account, change window and whether the desired state weakens security; a VMware-looking service is not malicious by default, since custom integrations exist, but one absent from the trusted list is a high-confidence anomaly, and chmod +x is ambiguous alone while execution of a newly staged executable from /tmp is itself a strong indicator (Kaspersky GERT, 2026-11-13).

    Detection

    In vCenter events and tasks and in vpxa.log and vobd.log, Host Profile remediation that changes TSM or TSM-SSH from policy-disabled to running outside an approved change window, which Kaspersky rates critical when an SSH session from vCenter or another management appliance to the same host follows within 15 minutes; on the vCenter appliance, a new VMware-looking systemd unit absent from the organisation's list of trusted services; in ESXi shell logs, execution of a newly staged executable under /tmp followed by access to /vmfs; and preserved hostprofiletrace.log (Kaspersky GERT, 2026-11-13). ESXi logs sit in a ramdisk that is cleared at reboot, so Kaspersky says not to begin by rebooting a host (Kaspersky GERT, 2026-11-13).

    2026-11-07NOTABLEKaspersky: ESXi and Proxmox ransomware ran on a monitoring server's root password and admin notes, no VM escape

    Defender takeaway

    Give each monitoring platform its own least-privilege identity instead of ESXi root, replace stored root passwords with vault retrieval or limited tokens, administer ESXi through vCenter with Lockdown Mode and SSH stopped by default, and keep logs off the hosts so a compromised administrator cannot erase them (Kaspersky GERT, 2026-11-06).

    Exposure · detection
    Exposure

    A virtualisation estate where a monitoring, backup or management server stores or can use hypervisor root credentials, where one root password is shared across hosts, where SSH to ESXi is reachable from general server networks, or where administrators keep Proxmox or ESXi credentials in plain-text notes; PRTG, which supports storing VMware credentials at device or group level, is the product Kaspersky names (Kaspersky GERT, 2026-11-06).

    Detection

    On ESXi, root SSH logins from addresses that do not normally administer the hosts, a file upload followed by a failed execution of a non-installed file, a change to the execInstalledOnly setting and cleared logs; on Proxmox, root@pam requests to the VNC web socket used to reach other hosts, as the log records Kaspersky shows (Kaspersky GERT, 2026-11-06). Kaspersky advises alerting when execInstalledOnly, Secure Boot enforcement, Lockdown Mode, SSH, local accounts or remote logging settings change (Kaspersky GERT, 2026-11-06).

    NOTABLENATOB2

    Kaspersky GERT BlackNevas case: credentials from systems outside the virtualisation layer reach both vCenter appliances, a remote-access agent and a VMware-lookalike tunnel service persist, vCenter Host Profile remediation switches SSH on across the ESXi hosts, backups are destroyed first and a wipe of the datastores detonates over ten days, with no vulnerability exploited

    Kaspersky GERT describes an engagement in which an adversary destroyed an organisation's virtualisation estate over ten days: four ESXi hosts, every virtual machine on them, both vCenter Server Appliances and all connected backup infrastructure (Kaspersky GERT, 2026-11-13). No virtualisation-layer vulnerability was exploited: credentials obtained from non-virtualisation systems inside the perimeter reached the appliances, and every action against ESXi ran through legitimate VMware management interfaces (Kaspersky GERT, 2026-11-13). The activity is attributed to BlackNevas through the ransom notes (Kaspersky GERT, 2026-11-13).

    The attackers logged in as root over SSH to the vCenter appliance that manages virtualisation disaster recovery, fetched and deployed MeshAgent with a shell script 43 seconds later, and about four hours later returned through MeshAgent to install the Ligolo-ng tunnel as a persistent systemd unit whose name, description and Restart=always imitate appliance housekeeping (Kaspersky GERT, 2026-11-13). They then used vCenter Host Profiles to change the TSM-SSH service state: eleven minutes after the first configuration read SSH was enabled on the target ESXi hosts, and direct SSH to the hosts then came from the vCenter appliance address (Kaspersky GERT, 2026-11-13). Payloads went to ESXi over SFTP, a self-test of the executable ran about three hours before the final detonation, and about the first 2 KB of the virtual disk files were overwritten (Kaspersky GERT, 2026-11-13). The backup environment fell first: the attacker extracted stored credentials after gaining administrative execution on the backup infrastructure, disabled antivirus there days earlier, then stopped backup services and encrypted the recovery infrastructure, all before ESXi detonation (Kaspersky GERT, 2026-11-13).

    Exposure
    A vCenter and ESXi estate where accounts from systems outside the virtualisation layer can reach the vCenter appliances and where Host Profile remediation can change the SSH service state; the article names no version (Kaspersky GERT, 2026-11-13).
    Detection
    In vCenter events and tasks and in vpxa.log and vobd.log, Host Profile remediation that changes TSM or TSM-SSH from policy-disabled to running outside an approved change window, which Kaspersky rates critical when an SSH session from vCenter or another management appliance to the same host follows within 15 minutes; on the vCenter appliance, a new VMware-looking systemd unit absent from the organisation's list of trusted services; in ESXi shell logs, execution of a newly staged executable under /tmp followed by access to /vmfs; and preserved hostprofiletrace.log (Kaspersky GERT, 2026-11-13). ESXi logs sit in a ramdisk that is cleared at reboot, so Kaspersky says not to begin by rebooting a host (Kaspersky GERT, 2026-11-13).

    Triage: each Host Profile step is legitimate alone, so the distinguishing context is authorisation, timing, source account, change window and whether the desired state weakens security; a VMware-looking service is not malicious by default, since custom integrations exist, but one absent from the trusted list is a high-confidence anomaly, and chmod +x is ambiguous alone while execution of a newly staged executable from /tmp is itself a strong indicator (Kaspersky GERT, 2026-11-13).

    Defender takeaway
    Treat the vCenter appliances as the control plane to protect: alert on Host Profile changes to TSM-SSH outside change windows and on SSH from vCenter to ESXi that follows them, review VMware-looking services on the appliances against a trusted list, and keep backup-platform credentials and administration separate from the systems that can reach vCenter, because the backup environment was destroyed before the hosts (Kaspersky GERT, 2026-11-13).

    NOTABLENATOB2

    Kaspersky GERT: two ESXi and Proxmox ransomware cases in which a monitoring server's reused root password and plaintext administrator notes, not a VM escape, gave the attackers the hypervisor

    In the first case, Kaspersky's investigation began with BlackNevas ransomware activity on a Windows system in a virtualised domain-controller segment, where the execution of the AnyDesk remote tool and the GMER binary was recorded (Kaspersky GERT, 2026-11-06). The environment used PRTG Network Monitor, whose deployment had broad access to the ESXi hosts, and the same root password was reused across several nodes; after obtaining access to the monitoring environment the attacker used the ESXi credential to connect over SSH to the hosts that shared the password (Kaspersky GERT, 2026-11-06). On the first host, a file was uploaded during a root SSH session and its first execution failed with "Execution of non-installed file prevented"; the actor then disabled the execInstalledOnly policy with esxcli and ran it, while on a second host in another subnet with the same password the binary ran and the logs were cleared (Kaspersky GERT, 2026-11-06).

    In the second case, a ransomware incident by The Gentlemen, the actor used information it had collected between initial access and visible impact: on a compromised system administrator's workstation it found Proxmox root credentials and access details in plain-text notes and logged in as root (Kaspersky GERT, 2026-11-06). It then activated the VNC web socket through the root account, which gave it control of the Proxmox environment, and used that access to download and run the ransomware in the cluster, encrypting the whole virtual environment (Kaspersky GERT, 2026-11-06). Kaspersky says a fully patched hypervisor can still be compromised through a shared password, an overprivileged monitoring account, an open SSH path or an administrator interface reachable from a general server network (Kaspersky GERT, 2026-11-06).

    Exposure
    A virtualisation estate where a monitoring, backup or management server stores or can use hypervisor root credentials, where one root password is shared across hosts, where SSH to ESXi is reachable from general server networks, or where administrators keep Proxmox or ESXi credentials in plain-text notes; PRTG, which supports storing VMware credentials at device or group level, is the product Kaspersky names (Kaspersky GERT, 2026-11-06).
    Detection
    On ESXi, root SSH logins from addresses that do not normally administer the hosts, a file upload followed by a failed execution of a non-installed file, a change to the execInstalledOnly setting and cleared logs; on Proxmox, root@pam requests to the VNC web socket used to reach other hosts, as the log records Kaspersky shows (Kaspersky GERT, 2026-11-06). Kaspersky advises alerting when execInstalledOnly, Secure Boot enforcement, Lockdown Mode, SSH, local accounts or remote logging settings change (Kaspersky GERT, 2026-11-06).
    Defender takeaway
    Give each monitoring platform its own least-privilege identity instead of ESXi root, replace stored root passwords with vault retrieval or limited tokens, administer ESXi through vCenter with Lockdown Mode and SSH stopped by default, and keep logs off the hosts so a compromised administrator cannot erase them (Kaspersky GERT, 2026-11-06).
