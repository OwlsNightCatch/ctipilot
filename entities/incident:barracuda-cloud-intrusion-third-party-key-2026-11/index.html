    Barracuda cloud intrusion through a vendor-held access key (November 2026)

    incident · incident:barracuda-cloud-intrusion-third-party-key-2026-11 single-source-victim

    Barracuda says an attacker used a valid cloud access key it had issued to an AI-sector vendor and not retired, found when that vendor's development environment was compromised in October, to work across about ten cloud accounts, a data analytics system, a source-code token and Kubernetes clusters between 2026-11-01 04:33 and 2026-11-02 23:31 UTC; credentials Barracuda Managed XDR uses to collect data from customers' connected systems were within reach and notified customers must recreate them (Barracuda, 2026-11-10 to 2026-11-13). Barracuda calls the activity consistent with ARTEX and names no actor.

    Defender takeaway

    A notified customer revokes and recreates its integration credentials and reviews connected-system activity since 2026-11-01 (Barracuda Trust Center, 2026-11-13). Barracuda's own lesson is to remove standing credentials, especially long-lived keys held by third parties (Barracuda Blog, 2026-11-11), and to expire vendor credentials when an engagement ends (Barracuda Trust Center, 2026-11-13).

    Exposure · detection
    Exposure

    A system the attacker reached stores the credentials Barracuda Managed XDR uses to collect data from customers' connected systems such as Microsoft 365, Google Workspace and endpoint security platforms; only organisations using the API integration for Managed XDR Cloud or Monitored Endpoint are affected, and Barracuda notified those with potentially affected credentials (Barracuda Trust Center, 2026-11-13). Logging in that environment was not detailed enough to rule out access to the credentials (Barracuda Blog, 2026-11-11). Relevant as a supplier incident for any organisation whose monitoring runs on Managed XDR, and as a worked example of ARTEX-style cloud tradecraft.

    Detection

    In cloud control-plane audit logs, a long-lived key used by a non-vendor address, secret-store reads followed by use of those secrets in other accounts, resources named with the letter i followed by digits and no hyphen, short-lived branches in a handful of repositories that trigger a workflow, and container deployments that mount the node's file system (Barracuda Trust Center, 2026-11-13; Barracuda Blog, 2026-11-11).

    Entries about Barracuda cloud intrusion through a vendor-held access key (November 2026) (1)

    2026-11-18 · view entry permalink →

    NOTABLENATOA2

    Barracuda's own account of a 44-hour intrusion into its cloud: a key given to an AI vendor and never retired, found in that vendor's compromised development environment, led an intruder across about ten cloud accounts to Kubernetes; notified Managed XDR customers must recreate their integration credentials

    Barracuda says the attacker did not break in but used a valid cloud access key that Barracuda had issued to a third-party vendor, a company working in AI, for an earlier project and had not retired when the work ended (Barracuda Blog, 2026-11-11). The key had been stored in a configuration file in the vendor's GitHub repository, which was exposed when the vendor's development environment was compromised (Barracuda Trust Center, 2026-11-13). The first call with the key came on 2026-11-01 at 04:33 UTC; within minutes the attacker was mapping what the key reached and reading stored secrets such as AWS access keys and Azure service principal secrets, and each secret opened the next system, from cloud accounts to a data analytics system, to a source-code access token and on to Kubernetes clusters (Barracuda Blog, 2026-11-11). In just under four hours on 2026-11-02 it pushed short-lived branches to a handful of repositories to trigger a build workflow written to print the build system's secrets into the job log, encoded so that log masking would not hide them, and its last recorded activity was at 23:31 UTC, about 10 cloud accounts and 44 hours after the start (Barracuda Blog, 2026-11-11).

    In a Kubernetes cluster the attacker deployed a container that mounted the underlying server's file system read-only, enough to harvest that server's credentials, and tried to create a new administrative cloud identity, which was blocked (Barracuda Blog, 2026-11-11). On servers where it had a shell, its commands searched for environment variables named WALLET, MNEMONIC, SEED and PRIV, Ethereum keystore files, extended private keys, seed phrase files and Kubernetes secrets with wallet-related names, and Barracuda calls the activity consistent with a financially motivated actor seeking cryptocurrency and reusable credentials (Barracuda Trust Center, 2026-11-13). Barracuda says the resource names, the sequence of activity and the credential and wallet hunting routines match ARTEX, which many groups use, so the match shows how the attacker operated, not who it was (Barracuda Blog, 2026-11-11).

    Exposure
    A system the attacker reached stores the credentials Barracuda Managed XDR uses to collect data from customers' connected systems such as Microsoft 365, Google Workspace and endpoint security platforms; only organisations using the API integration for Managed XDR Cloud or Monitored Endpoint are affected, and Barracuda notified those with potentially affected credentials (Barracuda Trust Center, 2026-11-13). Logging in that environment was not detailed enough to rule out access to the credentials (Barracuda Blog, 2026-11-11). Relevant as a supplier incident for any organisation whose monitoring runs on Managed XDR, and as a worked example of ARTEX-style cloud tradecraft.
    Detection
    In cloud control-plane audit logs, a long-lived key used by a non-vendor address, secret-store reads followed by use of those secrets in other accounts, resources named with the letter i followed by digits and no hyphen, short-lived branches in a handful of repositories that trigger a workflow, and container deployments that mount the node's file system (Barracuda Trust Center, 2026-11-13; Barracuda Blog, 2026-11-11).
    Defender takeaway
    A notified customer revokes and recreates its integration credentials and reviews connected-system activity since 2026-11-01 (Barracuda Trust Center, 2026-11-13). Barracuda's own lesson is to remove standing credentials, especially long-lived keys held by third parties (Barracuda Blog, 2026-11-11), and to expire vendor credentials when an engagement ends (Barracuda Trust Center, 2026-11-13).
