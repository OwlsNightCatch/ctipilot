    2026-10-22NOTABLEGitLab's critical patch fixes an unauthenticated CVSS 10.0 RCE in Org-mode rendering; no exploitation reported

    Defender takeaway

    Upgrade to the fixed build of the instance's line now, internet-reachable instances and those with public projects first; an instance that moved to 19.4.2, 19.3.5 or 19.2.8 for the earlier flaws is not yet fixed for this one (GitLab, 2026-10-21). For other Ruby applications that compile attacker-controlled patterns, Ruby recommends upgrading to 4.0.9, 3.4.12 or 3.3.13 or later, or avoiding compiling such patterns, and says neither Regexp.timeout nor a pattern-length limit reliably protects; Ruby has not requested CVE identifiers of its own for now and tells operators to track the issues under GitLab's identifiers (Ruby, 2026-10-23).

    Exposure · triage · detection
    Exposure

    Self-managed GitLab CE and EE on the versions above; the vulnerable path is reached when GitLab renders a .org file, so an instance with public projects, or one where untrusted users can create them, is the exposed shape, and until patching GitLab advises reducing public visibility (GitLab security, 2026-10-21). A Ruby application outside GitLab is exposed to the same bug when it compiles a regular expression from a string an attacker controls, through Regexp.new, Regexp.union, Regexp.compile or interpolation into a regexp literal; applications that only use patterns written by their own developers are not affected (Ruby, 2026-10-23).

    Triage

    A reader of documentation .org files renders each file once and quickly, while an attack produces a burst of timeouts from one client over a few minutes (GitLab security, 2026-10-21); a worker crash with no accompanying render burst from one client is more likely a benign parser bug than an attack (GitLab security, 2026-10-21).

    Detection

    GitLab's two detections key on, first, five or more render timeouts from the Org-mode renderer on .org files from one client within 30 minutes in the Rails exceptions log, with the request that actually crashes a worker visible only as a 502 on the .org blob route in the Workhorse log, and second, a native Ruby crash report in the Puma error log whose backtrace runs through org-ruby or Onigmo frames (GitLab security, 2026-10-21). In repository content, scan each suspect checkout for .org files with an oversized TODO-keyword line, and in the Rails request log look for editor preview requests whose file_path ends in .org while the URL names another file type, which forces the Org renderer (GitLab security, 2026-10-21). A successful exploit is quiet and does not reliably crash, so the absence of a hit never clears an instance (GitLab security, 2026-10-21). On an exposed, unpatched instance, hunt for unexpected child processes of Puma, new files owned by git in the temporary directory, outbound connections and changed crontabs or SSH keys for the git user, and treat the secrets, CI/CD variables, runner tokens and access tokens the git user can read as at risk (GitLab security, 2026-10-21).

    NOTABLECVE-2026-110264updatedNATOA2

    CVE-2026-110264, GitLab CE/EE: an unauthenticated code-execution flaw in the Org-mode renderer's regular-expression handling, fixed in 19.5.1, 19.4.3 and 19.3.6 and backported to four older lines (CVSS 10.0)

    GitLab's ad-hoc critical patch release of 2026-10-21 fixes CVE-2026-110264 (CVSS 3.1 10.0), an integer overflow while compiling a specially crafted regular expression that could let an unauthenticated user execute code on the GitLab server (GitLab, 2026-10-21). GitLab's detection write-ups place the flaw in the rendering of Org-mode files: the org-ruby gem builds a regular expression from a custom TODO keyword in a .org file, a keyword with more than 32,767 repeats makes the Onigmo engine write out of bounds when it matches, and with heap grooming that becomes command execution as the git user (GitLab security, 2026-10-21). The attack needs no authentication, only one public project that can hold the .org payload (GitLab security, 2026-10-21). Affected are all versions from 7.0 before 18.11.13, 19.0 before 19.0.10, 19.1 before 19.1.9, 19.2 before 19.2.9, 19.3 before 19.3.6, 19.4 before 19.4.3 and 19.5 before 19.5.1; GitLab.com is already patched, and GitLab Dedicated tenants on 19.3.5-internal0, 19.4.2-internal0 or later need no action (GitLab, 2026-10-21). The builds 19.4.2, 19.3.5 and 19.2.8 from GitLab's earlier regular-expression fixes do not contain this fix (GitLab security, 2026-10-21). GitLab does not state that the flaw is exploited, and its patch notes and detection pages mention no public proof of concept (GitLab, 2026-10-21). The bug is in Ruby's Onigmo regular-expression engine: the Ruby project released 4.0.9, 3.4.12 and 3.3.13 on 2026-10-23 with the fix, the release of 4.0.8 lacks the fix for this flaw, and GitLab fixed its own servers by patching the Ruby it ships (Ruby, 2026-10-23).

    The Ruby project published an advisory on 2026-10-23 and released Ruby 4.0.9, 3.4.12 and 3.3.13 with fixes for the bugs in its Onigmo regular-expression engine behind four GitLab flaws: CVE-2026-89078 (a double free when parsing a pattern fails after an alternation), CVE-2026-93577 and CVE-2026-97229 (an integer overflow in the size of a compiled pattern) and CVE-2026-110264 (an overflow of internal IDs in a pattern with many repeats) (Ruby, 2026-10-23). Ruby's table gives the first release of each series that carries each fix: the fix for CVE-2026-110264 first appears in 4.0.9, so 4.0.8 is not enough, and 3.4.12 and 3.3.13 carry all of them; GitLab fixed its own servers by patching the Ruby it ships (Ruby, 2026-10-23).

    The advisory widens the exposure beyond GitLab to any Ruby application that compiles a regular expression from a string an attacker controls, says Regexp.timeout does not protect against these bugs and that limiting pattern length does not reliably protect, and says Ruby has not requested CVE identifiers of its own and that operators should track the issues under GitLab's identifiers (Ruby, 2026-10-23).

    NOTABLENATOC2

    GitLab CE/EE RCE via the Jupyter-notebook diff renderer and two ~5-year-old Oj Ruby-parser memory-corruption bugs, public PoC, silent patch, no CVE

    depthfirst disclosed (2026-07-24) a remote-code-execution chain against default self-managed GitLab CE/EE, reached through GitLab's in-tree ipynbdiff gem, which calls Oj::Parser.usual.parse (the native-C implementation of the Oj Ruby JSON parser) whenever a commit diff contains a .ipynb (Jupyter notebook) file (depthfirst, 2026-07-24). Two Oj memory-safety bugs that had survived in the parser for nearly five years (introduced 2021-08-08, first shipped in Oj 3.13.0, and reachable in GitLab from 15.2.0 once notebook validation switched to Oj in July 2022) are combined: an unchecked 16-bit key-length narrowing truncates an oversized object key and causes GitLab's notebook-diff output to print a live heap pointer (used to defeat ASLR and locate libc/libruby), and an unchecked nesting-stack overflow in Oj::Parser.usual.parse supplies a write primitive that redirects a parser callback to system(). The whole chain needs no elevated access, in depthfirst's words, "A normal authenticated user able to create or push to a project and view the resulting commit diff could commit an .ipynb file" (depthfirst, 2026-07-24), no admin rights, no CI/runner access, no victim interaction, by committing two crafted notebooks and requesting the commit diff (GET /<project>/-/commit/<sha>/diffs_stream).

    The affected range is GitLab CE/EE 15.2.0–18.10.7, 18.11.0–18.11.4 and 19.0.0–19.0.1; GitLab shipped the fixed Oj (3.17.3) in its 10 June 2026 releases 18.10.8, 18.11.5 and 19.0.2 (The Hacker News, 2026-07-25). The operationally important detail is that GitLab did not record the fix in its security-fix table and no CVE was assigned to the GitLab chain, so any operator that tracks GitLab patching against the vendor's security-advisory feed missed it for the 44 days between the silent 10 June bump and the 2026-07-24 PoC publication; GitLab.com and Dedicated instances were already patched, but self-managed operators must act. A separate set of nine Oj advisories (covering the dumper, loader, SAJ callback and document APIs, each with its own CVE) came out of the same depthfirst review and are also fixed in Oj 3.17.3. No in-the-wild exploitation is reported; this is a disclosed researcher PoC.

    Detection
    In GitLab web/application-access telemetry (Rails/Workhorse request logs), the exploit's own mechanics surface as .../-/commit/<sha>/diffs_stream requests correlated with recently-pushed .ipynb files carrying implausible JSON field lengths, object keys near the 65,535-byte boundary that only make sense as a deliberate truncation trigger; the attacker must push two purpose-built notebooks and then request their diff in sequence. In host process telemetry, a shell interpreter forked from the GitLab Puma/Rails worker (parent image puma / bundle exec puma) would reflect the system() redirection this chain achieves. Triage: routine data-science notebook review produces diffs_stream requests too; the discriminators are the anomalous multi-kilobyte JSON key lengths in the pushed notebook and the parent-of-shell being the Puma worker, neither of which appears in legitimate notebook diffing. Because the chain needs only ordinary push access, tightening project push-access grants is a meaningful interim control for instances that cannot upgrade immediately, but there is no vendor workaround short of the patch.
