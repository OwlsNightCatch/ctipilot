    Defender insights

    What each entry about VMware ESXi tells a defender to do, newest first.

    2026-11-14NOTABLEKaspersky: BlackNevas used vCenter Host Profiles to enable SSH on ESXi, destroyed backups first, then wiped datastores

    Defender takeaway

    Treat the vCenter appliances as the control plane to protect: alert on Host Profile changes to TSM-SSH outside change windows and on SSH from vCenter to ESXi that follows them, review VMware-looking services on the appliances against a trusted list, and keep backup-platform credentials and administration separate from the systems that can reach vCenter, because the backup environment was destroyed before the hosts (Kaspersky GERT, 2026-11-13).

    Exposure · triage · detection
    Exposure

    A vCenter and ESXi estate where accounts from systems outside the virtualisation layer can reach the vCenter appliances and where Host Profile remediation can change the SSH service state; the article names no version (Kaspersky GERT, 2026-11-13).

    Triage

    Each Host Profile step is legitimate alone, so the distinguishing context is authorisation, timing, source account, change window and whether the desired state weakens security; a VMware-looking service is not malicious by default, since custom integrations exist, but one absent from the trusted list is a high-confidence anomaly, and chmod +x is ambiguous alone while execution of a newly staged executable from /tmp is itself a strong indicator (Kaspersky GERT, 2026-11-13).

    Detection

    In vCenter events and tasks and in vpxa.log and vobd.log, Host Profile remediation that changes TSM or TSM-SSH from policy-disabled to running outside an approved change window, which Kaspersky rates critical when an SSH session from vCenter or another management appliance to the same host follows within 15 minutes; on the vCenter appliance, a new VMware-looking systemd unit absent from the organisation's list of trusted services; in ESXi shell logs, execution of a newly staged executable under /tmp followed by access to /vmfs; and preserved hostprofiletrace.log (Kaspersky GERT, 2026-11-13). ESXi logs sit in a ramdisk that is cleared at reboot, so Kaspersky says not to begin by rebooting a host (Kaspersky GERT, 2026-11-13).

    2026-11-11NOTABLEInsikt: GhostFrame implant re-disables ESXi execInstalledOnly every five seconds and steals guest credentials

    Defender takeaway

    Treat a VPN-appliance compromise as a possible hypervisor compromise and check the ESXi persistence files and the execInstalledOnly state before declaring the incident closed; restrict ESXi and vCenter management to dedicated administration hosts.

    Exposure · triage · detection
    Exposure

    ESXi hosts whose root credentials, SSH or shell, or vCenter are reachable after an edge compromise; no ESXi vulnerability is involved, so patching ESXi does not address it, and an estate that runs both a SonicWall, Palo Alto Networks or Fortinet VPN appliance and ESXi without isolated hypervisor management is in the pattern Insikt describes.

    Triage

    Administrators legitimately edit local.sh, create snapshots and use VNC; the discriminators are a firewall-off and execInstalledOnly loop, a binary under /opt named vmhostd where the genuine daemon is vmware-hostd, and snapshot-file reads by a non-backup account.

    Detection

    In ESXi file-integrity and shell-audit telemetry, changes to local.sh, a process masquerading as the host daemon or an unexpected executable under /opt, and repeated firewall-off and execInstalledOnly resets; in network telemetry, six near-simultaneous SYNs from the hypervisor management address to one destination on those ports, and any outbound command-style traffic from a hypervisor at all; in vCenter and ESXi logs, snapshot creation or deletion, VNC enablement and power-state changes outside change windows; in datastore telemetry, reads of VM memory-snapshot and virtual-disk files by an identity that is not the backup service.

    2026-11-07NOTABLEKaspersky: ESXi and Proxmox ransomware ran on a monitoring server's root password and admin notes, no VM escape

    Defender takeaway

    Give each monitoring platform its own least-privilege identity instead of ESXi root, replace stored root passwords with vault retrieval or limited tokens, administer ESXi through vCenter with Lockdown Mode and SSH stopped by default, and keep logs off the hosts so a compromised administrator cannot erase them (Kaspersky GERT, 2026-11-06).

    Exposure · detection
    Exposure

    A virtualisation estate where a monitoring, backup or management server stores or can use hypervisor root credentials, where one root password is shared across hosts, where SSH to ESXi is reachable from general server networks, or where administrators keep Proxmox or ESXi credentials in plain-text notes; PRTG, which supports storing VMware credentials at device or group level, is the product Kaspersky names (Kaspersky GERT, 2026-11-06).

    Detection

    On ESXi, root SSH logins from addresses that do not normally administer the hosts, a file upload followed by a failed execution of a non-installed file, a change to the execInstalledOnly setting and cleared logs; on Proxmox, root@pam requests to the VNC web socket used to reach other hosts, as the log records Kaspersky shows (Kaspersky GERT, 2026-11-06). Kaspersky advises alerting when execInstalledOnly, Secure Boot enforcement, Lockdown Mode, SSH, local accounts or remote logging settings change (Kaspersky GERT, 2026-11-06).

    2026-11-06NOTABLEQilin's October build spreads through vCenter and ESXi, reboots into Safe Mode and prints notes on office printers

    Exposure

    2026-09-29NOTABLEKaspersky GERT: a Group Policy Object was the whole ransomware on Windows, in a channel most EDR tools do not inspect

    Defender takeaway

    Review GPO-write/modify permissions at the domain root and any OU covering a meaningful share of the estate, since the Windows-side technique requires only that access, not code execution rights on any endpoint; make the directory-service and SYSVOL telemetry in the Detection line a primary detection surface, because on Windows this attack leaves no malicious binary or process for endpoint detection to find (Kaspersky Securelist, 2026-09-21). The GPO technique is domain/Active-Directory-architecture-generic and directly transferable to any Windows AD environment, including a government AD estate managing distributed desktop fleets through central Group Policy; ESXi/Linux hosts in the same estate still need standard ransomware-binary detection and exfiltration monitoring, since the GPO-only technique does not extend to them.

    Triage · detection
    Triage

    For the Windows-side GPO attack, the discriminator is Group Policy content and change history, not endpoint behavior, since no encryption or binary execution occurs on those hosts. Kaspersky calls a gPLink change at the domain root by a non-standard account one of the most telling indicators of this attack class (Kaspersky Securelist, 2026-09-21). In this incident one new domain-root GPO combined ransom-note file drops, a ransom logon banner, a ransom wallpaper and lock screen and disablement of the local Administrator account, and a second domain-root GPO disabled Windows Firewall (Kaspersky Securelist, 2026-09-21). That combination, not an Administrator-account or firewall setting on its own, separates the attack from routine policy work. On ESXi/Linux hosts, the discriminator is the ordinary one for ransomware: an actual PAYLOAD binary execution.

    Detection

    Kaspersky's telemetry for this class starts with directory-service change auditing on every domain controller (Advanced Audit Policy, DS Access, Audit Directory Service Changes). Event 5137 flags a new groupPolicyContainer object, whose creator should be an authorized GPO administrator. Event 5136 flags changes to gPLink on the domain root or sensitive OUs and to a GPO's extension-name, file-system-path or version attributes, and event 5141 flags GPO deletions (Kaspersky Securelist, 2026-09-21). Kaspersky adds file-integrity monitoring of the SYSVOL Policies folder for unexpected image, text or script files, ScheduledTasks.xml, and modified registry.pol or GptTmpl.inf files not created by replication. A GPO whose SYSVOL content changes without a matching 5136 event can indicate direct template editing that bypasses the Group Policy Management Console, though misconfigured auditing can cause the same gap (Kaspersky Securelist, 2026-09-21). On endpoints, the Group Policy Operational log records policy application, and a sudden domain-wide change to the applied policy set is a strong post-detonation signal (Kaspersky Securelist, 2026-09-21).

    Kaspersky GERT describes an engagement in which an adversary destroyed an organisation's virtualisation estate over ten days: four ESXi hosts, every virtual machine on them, both vCenter Server Appliances and all connected backup infrastructure (Kaspersky GERT, 2026-11-13). No virtualisation-layer vulnerability was exploited: credentials obtained from non-virtualisation systems inside the perimeter reached the appliances, and every action against ESXi ran through legitimate VMware management interfaces (Kaspersky GERT, 2026-11-13). The activity is attributed to BlackNevas through the ransom notes (Kaspersky GERT, 2026-11-13).

    The attackers logged in as root over SSH to the vCenter appliance that manages virtualisation disaster recovery, fetched and deployed MeshAgent with a shell script 43 seconds later, and about four hours later returned through MeshAgent to install the Ligolo-ng tunnel as a persistent systemd unit whose name, description and Restart=always imitate appliance housekeeping (Kaspersky GERT, 2026-11-13). Payloads went to ESXi over SFTP, a self-test of the executable ran about three hours before the final detonation, and about the first 2 KB of the virtual disk files were overwritten (Kaspersky GERT, 2026-11-13).     Exposure
    A vCenter and ESXi estate where accounts from systems outside the virtualisation layer can reach the vCenter appliances and where Host Profile remediation can change the SSH service state; the article names no version (Kaspersky GERT, 2026-11-13).
    Detection
    In vCenter events and tasks and in vpxa.log and vobd.log, Host Profile remediation that changes TSM or TSM-SSH from policy-disabled to running outside an approved change window, which Kaspersky rates critical when an SSH session from vCenter or another management appliance to the same host follows within 15 minutes; on the vCenter appliance, a new VMware-looking systemd unit absent from the organisation's list of trusted services; in ESXi shell logs, execution of a newly staged executable under /tmp followed by access to /vmfs; and preserved hostprofiletrace.log (Kaspersky GERT, 2026-11-13). ESXi logs sit in a ramdisk that is cleared at reboot, so Kaspersky says not to begin by rebooting a host (Kaspersky GERT, 2026-11-13).

    Triage: each Host Profile step is legitimate alone, so the distinguishing context is authorisation, timing, source account, change window and whether the desired state weakens security; a VMware-looking service is not malicious by default, since custom integrations exist, but one absent from the trusted list is a high-confidence anomaly, and chmod +x is ambiguous alone while execution of a newly staged executable from /tmp is itself a strong indicator (Kaspersky GERT, 2026-11-13).

    Defender takeaway
    Treat the vCenter appliances as the control plane to protect: alert on Host Profile changes to TSM-SSH outside change windows and on SSH from vCenter to ESXi that follows them, review VMware-looking services on the appliances against a trusted list, and keep backup-platform credentials and administration separate from the systems that can reach vCenter, because the backup environment was destroyed before the hosts (Kaspersky GERT, 2026-11-13).

    GhostFrame: Recorded Future's Insikt Group finds an ESXi post-exploitation framework (vmhostd-core implant, VM control panel, VMkatz credential theft) used by TAG-218, whose activity overlaps Settra ransomware and which targeted SonicWall, Palo Alto Networks and Fortinet VPN appliances in the US and Europe

    Insikt Group describes GhostFrame, a previously undocumented command-and-control and post-exploitation framework for compromised VMware ESXi hosts, which it saw used by TAG-218, a group "whose operations overlap with Settra ransomware" (Recorded Future, 2026-11-10). Operators must already hold root on the host: the implant, an ELF named vmhostd-core generated from a web operator panel, does not exploit a vulnerability to gain access (Recorded Future, 2026-11-10). It copies itself to /opt/vmhostd-core, edits the ESXi boot script /etc/rc.local.d/local.sh and runs /sbin/auto-backup.sh to keep the change across reboots, masquerades as vmhostd (resembling VMware's vmware-hostd), and about every five seconds disables the ESXi firewall and the execInstalledOnly control that restricts execution of unsigned binaries, so an administrator who re-enables them is undone (Recorded Future, 2026-11-10). Its command channel opens simultaneous TCP connections to one address on ports 53, 2222, 3389, 4444, 8443 and 9443, keeps the first that succeeds and retries after a random delay of 5 to 12 seconds, which Insikt notes is a network detection opportunity; the implant is mainly an in-memory shellcode loader with a reverse-shell fallback.

    From the hypervisor the panel can list registered VMs, change power state, create or delete snapshots, enable VNC on a guest, run a SOCKS5 proxy for pivoting, intercept ESXi logins, and run the open-source VMkatz against VM memory snapshots, virtual disks or whole datastores to recover NTLM hashes, Kerberos tickets, SAM and LSA secrets and NTDS.dit data without running anything inside the guest (Recorded Future, 2026-11-10). Insikt ties TAG-218's victim-facing servers to VPN-appliance targeting across the US and Europe between late August and October 2026, "predominantly SonicWall, Palo Alto Networks, and Fortinet devices", and says four of those organisations later appeared on the Settra leak site; it assesses that other financially motivated actors are highly likely to adopt the framework, which is an assessment, not an observation (Recorded Future, 2026-11-10). Unit 42 independently reports that after CVE-2026-0257 exploitation attackers pivot from the VPN gateway directly to the virtualization layer (Palo Alto Networks Unit 42, 2026-10-20).

    Exposure
    ESXi hosts whose root credentials, SSH or shell, or vCenter are reachable after an edge compromise; no ESXi vulnerability is involved, so patching ESXi does not address it, and an estate that runs both a SonicWall, Palo Alto Networks or Fortinet VPN appliance and ESXi without isolated hypervisor management is in the pattern Insikt describes.
    Detection
    In ESXi file-integrity and shell-audit telemetry, changes to local.sh, a process masquerading as the host daemon or an unexpected executable under /opt, and repeated firewall-off and execInstalledOnly resets; in network telemetry, six near-simultaneous SYNs from the hypervisor management address to one destination on those ports, and any outbound command-style traffic from a hypervisor at all; in vCenter and ESXi logs, snapshot creation or deletion, VNC enablement and power-state changes outside change windows; in datastore telemetry, reads of VM memory-snapshot and virtual-disk files by an identity that is not the backup service.

    Triage: administrators legitimately edit local.sh, create snapshots and use VNC; the discriminators are a firewall-off and execInstalledOnly loop, a binary under /opt named vmhostd where the genuine daemon is vmware-hostd, and snapshot-file reads by a non-backup account.

    Defender takeaway
    Treat a VPN-appliance compromise as a possible hypervisor compromise and check the ESXi persistence files and the execInstalledOnly state before declaring the incident closed; restrict ESXi and vCenter management to dedicated administration hosts.

    Kaspersky GERT: two ESXi and Proxmox ransomware cases in which a monitoring server's reused root password and plaintext administrator notes, not a VM escape, gave the attackers the hypervisor

    In the first case, Kaspersky's investigation began with BlackNevas ransomware activity on a Windows system in a virtualised domain-controller segment, where the execution of the AnyDesk remote tool and the GMER binary was recorded (Kaspersky GERT, 2026-11-06). On the first host, a file was uploaded during a root SSH session and its first execution failed with "Execution of non-installed file prevented"; the actor then disabled the execInstalledOnly policy with esxcli and ran it, while on a second host in another subnet with the same password the binary ran and the logs were cleared (Kaspersky GERT, 2026-11-06).

    In the second case, a ransomware incident by The Gentlemen, the actor used information it had collected between initial access and visible impact: on a compromised system administrator's workstation it found Proxmox root credentials and access details in plain-text notes and logged in as root (Kaspersky GERT, 2026-11-06). It then activated the VNC web socket through the root account, which gave it control of the Proxmox environment, and used that access to download and run the ransomware in the cluster, encrypting the whole virtual environment (Kaspersky GERT, 2026-11-06). Kaspersky says a fully patched hypervisor can still be compromised through a shared password, an overprivileged monitoring account, an open SSH path or an administrator interface reachable from a general server network (Kaspersky GERT, 2026-11-06).

    Exposure
    A virtualisation estate where a monitoring, backup or management server stores or can use hypervisor root credentials, where one root password is shared across hosts, where SSH to ESXi is reachable from general server networks, or where administrators keep Proxmox or ESXi credentials in plain-text notes; PRTG, which supports storing VMware credentials at device or group level, is the product Kaspersky names (Kaspersky GERT, 2026-11-06).

    On ESXi, root SSH logins from addresses that do not normally administer the hosts, a file upload followed by a failed execution of a non-installed file, a change to the execInstalledOnly setting and cleared logs; on Proxmox, root@pam requests to the VNC web socket used to reach other hosts, as the log records Kaspersky shows (Kaspersky GERT, 2026-11-06). Kaspersky advises alerting when execInstalledOnly, Secure Boot enforcement, Lockdown Mode, SSH, local accounts or remote logging settings change (Kaspersky GERT, 2026-11-06).

    Give each monitoring platform its own least-privilege identity instead of ESXi root, replace stored root passwords with vault retrieval or limited tokens, administer ESXi through vCenter with Lockdown Mode and SSH stopped by default, and keep logs off the hosts so a compromised administrator cannot erase them (Kaspersky GERT, 2026-11-06).
