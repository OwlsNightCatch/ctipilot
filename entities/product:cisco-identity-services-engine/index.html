    Exposure · triage · detection
    Exposure

    Any software that keeps its own CA bundle or does not check revocation keeps trusting the intermediates until updated; Python 3.15.2, 3.14.10, 3.13.18, 3.12.16 and 3.11.18 carry a built-in denylist (Python Insider, 2026-10-26); Apple says the curl, git, python3, ruby, perl and openssl that ship with macOS or the Xcode command-line tools read /etc/ssl/cert.pem, check neither Apple's block nor revocation and keep trusting them until macOS 27.2.1, 26.7.3 or 15.8.3 (Apple, 2026-11-10). SonicOS firewalls with Client DPI-SSL enabled re-signed the chains with their own DPI-SSL CA, so client browsers could not reject a forged one, until SonicOS 7.3.4-7015 (Gen7) and 8.2.3-8015 (Gen8) (SonicWall, 2026-11-10; SonicWall advisory data, 2026-11-10).

    Triage

    A site that still chains to emSign ECC Root CA - G3 failing in Chrome after 2026-10-27, or a certificate that chains to one of the seven certificates Microsoft removed failing in Windows or Edge once the change reaches the device, is the announced root removal, not an attack (Google, 2026-10-20; Microsoft, 2026-10-26).

    Detection

    EMudhra says it found no evidence that the intermediates were used to issue end-user certificates (BleepingComputer, 2026-10-20), so a server certificate chain seen in TLS session metadata, proxy or EDR network telemetry that contains one of the eight intermediates or their Sectigo cross-signs, which the tracker lists, is worth treating as a possible forged certificate (Dennis Jackson, 2026-10-20). CT monitoring will not show one, because Google found no certificate chaining to the six TLS intermediates logged before it blocked them (Google, 2026-10-20).

    Triage
    Triage

    A legitimate administrative session against the ISE API originates from an authenticated, known management source; the discriminator here is that exploitation reaches the API without any authentication at all, so any successful request against the affected endpoint from outside expected management-plane sources is itself the signal, and because a root-level attacker can edit or delete access.log entries, an apparently clean on-box log is not evidence of an intact device. Cisco's guidance is to corroborate against firewall and network logs external to the ISE node for uploads initiated from the device to external IP addresses or downloads from malicious IP addresses.

    eMudhra: the private keys of eight ECDSA intermediate CA certificates were trivially recoverable, so anyone could forge trusted HTTPS certificates, and eight RSA intermediates were revoked on 2026-11-07 for key handling eMudhra cannot show compliant; browsers block them, clients with their own trust store or no revocation checking need an update (CVE-2026-111943 in Go)

    On 2026-10-17 a researcher reported to the Chrome Root Program, and Mozilla received a report the same day, that the private keys of eight eMudhra subordinate CA certificates were compromised: the keys were so weak that anyone could forge trusted HTTPS certificates to impersonate any website against clients that have not removed trust in those CAs; Google describes the cause as insufficient randomness (Google, 2026-10-20; Mozilla, 2026-10-20). BleepingComputer, citing Mozilla's incident report, says all eight were P-384 keys generated in April 2025 with values below 256, so testing 256 numbers recovers a key (BleepingComputer, 2026-10-20). eMudhra's incident report of 2026-11-10 says the keys were generated correctly on its hardware module at a ceremony on 2025-04-30 and then passed through a custom Python wrap/unwrap script that truncated the eight ECDSA private values; the keys of eight RSA-4096 issuers (G2B and G2C) stayed intact but were handled in that script's process memory, so eMudhra cannot show compliance with its certification practice statement, and it revoked them on 2026-11-07 with the reason cessationOfOperation after having said on 2026-10-19 that they were not impacted; its G2C issuers had issued end-entity certificates, the last on 2026-11-03, and no source says any RSA key leaked (eMudhra, Mozilla bug 2083449, 2026-11-10; eMudhra, Mozilla bug 2083449, 2026-10-19; BleepingComputer, 2026-11-11). The tracker says it is not known whether attackers used the flaw against other clients (Dennis Jackson, 2026-10-20).

    Chrome blocked the intermediates on 2026-10-17, Firefox through OneCRL the same day, Microsoft platforms on 2026-10-20 and Apple products on 2026-10-22, and eMudhra revoked all eight (Dennis Jackson, 2026-10-20; BleepingComputer, 2026-10-20). Microsoft went further: an out-of-band Windows update of 2026-10-26 removes seven certificates, six eMudhra G3 roots and an AAA Certificate Services cross-sign, from the Windows trust list, and the same seven left the Edge trust list on 2026-10-27 (Microsoft, 2026-10-26). Google removed the root that signed them, emSign ECC Root CA - G3, from the Chrome Root Store, with the removal expected to reach devices on 2026-10-27 (Google, 2026-10-20). Go 1.27.3 and 1.26.10 filter chains that contain the intermediates in crypto/x509, tracked as CVE-2026-111943 (Go team, 2026-10-20), and GitLab's release of 2026-10-29 removes trust for the eight intermediates in self-managed CE and EE, with Runner 19.5.1 and the AI Gateway updated separately (GitLab, 2026-10-29).

OpenJDK's guidance tells users of a standalone runtime to act immediately even if they updated in the past few days (OpenJDK, 2026-10-24).

    CRITICALCVE-2026-76460 +3exploitedupdatedNATOA1

    CVE-2026-76460 (+ CVE-2026-76423), Cisco Identity Services Engine: unauthenticated API authentication bypass to root, found during a Cisco TAC support case, no workaround beyond ACLs (CVSS 10.0)

    Cisco disclosed CVE-2026-76460 (CVSS 3.1 10.0, AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H) on 2026-09-16: an unauthenticated, remote attacker can bypass authentication on an API endpoint of Cisco Identity Services Engine (ISE) and ISE Passive Identity Connector (ISE-PIC) due to insufficient authentication control, affecting ISE and ISE-PIC releases before the fixed patch levels "regardless of device configuration" (Cisco PSIRT, 2026-09-16). Cisco states the flaw was found during the resolution of a Cisco TAC support case and that it is aware of active exploitation (Cisco PSIRT, 2026-09-16); a successful exploit bypasses the web-based management interface and, per Cisco's own advisory, "threat actors may obtain command execution with root privileges" (Cisco PSIRT, 2026-09-16). There is no workaround; the only mitigation is restricting management-plane access via infrastructure ACLs. Fixed releases are 3.1 Patch 12, 3.2 Patch 11, 3.3 Patch 12, 3.4 Patch 7 and 3.5 Patch 4; Cisco ISE 3.0 has reached End of Software Maintenance and must migrate to a supported, fixed release (Cisco PSIRT, 2026-09-16). CISA added the flaw to its Known Exploited Vulnerabilities catalog the same day (CISA, 2026-09-16; CISA KEV JSON feed, 2026-09-16).

    This CVE was part of a bundled disclosure of 15 distinct Cisco ISE advisories the same day (Cisco PSIRT, 2026-09-16). A sibling flaw, CVE-2026-76423 (CVSS 10.0, also unauthenticated and affecting ISE and ISE-PIC before the same fixed patch levels "regardless of device configuration"), removes the same authentication boundary via a separate API endpoint, letting an attacker read or modify ISE configuration and identity data with administrative privileges; Cisco states it is "not aware of any public announcements or malicious use" of this second flaw as of disclosure, but it shares the same fixed-release schedule (Cisco PSIRT, 2026-09-16).

    Defender takeaway
    Patch every ISE/ISE-PIC node and restrict management-plane reachability via ACLs immediately: there is no other mitigation, and Cisco's own guidance is to distrust the appliance's own logs for ruling out compromise once root access is possible. Cisco supplies a concrete first check: review each node's access.log (or a decrypted debug-log bundle at ./ise/logs/apigateway/access.log.*.gz) for suspicious usernames on the API endpoint; Cisco's non-exhaustive example filters the output of show logging application ise-kong/access.log for the suspicious username (Cisco PSIRT, 2026-09-16). If malicious activity is suspected, Cisco strongly recommends re-imaging the affected nodes and restoring from configuration backup if needed (Cisco PSIRT, 2026-09-16).

    Triage: a legitimate administrative session against the ISE API originates from an authenticated, known management source; the discriminator here is that exploitation reaches the API without any authentication at all, so any successful request against the affected endpoint from outside expected management-plane sources is itself the signal, and because a root-level attacker can edit or delete access.log entries, an apparently clean on-box log is not evidence of an intact device. Cisco's guidance is to corroborate against firewall and network logs external to the ISE node for uploads initiated from the device to external IP addresses or downloads from malicious IP addresses.

    Cisco ISE CVE-2026-20181 / CVE-2026-20190: administrator-level command execution to root and an unauthenticated disclosure of hashed credentials, two independent flaws

    Cisco's advisory of 2026-06-17 covers two independent flaws in Identity Services Engine and ISE-PIC; Cisco states that exploiting one is not required to exploit the other (Cisco PSIRT).
