    CVE-2026-93616, Check Point Security Management: pre-authentication path traversal to arbitrary script execution, exploited as a zero-day, with attacks observed on 2026-07-23 (CVSS 9.8)

    Check Point discloses a pre-authentication directory-traversal and file-upload vulnerability that lets an unauthenticated attacker upload and execute arbitrary scripts on the Check Point Management Server (Check Point Support, sk1000171, 2026-09-22), which in Check Point Research's words "allows an attacker to execute a script from an arbitrary path and load an arbitrary Java class" (Check Point Research, 2026-09-22). It affects Security Management Server, Multi-Domain Security Management Server, Log Server, Multi-Domain Log Server and SmartEvent; Smart-1 Cloud already carries the fix, and Security Gateway appliances and Spark Firewall are not affected. Check Point states it identified "a handful of pinpointed attacks" exploiting this as a zero-day on 2026-07-23 (Check Point Research, 2026-09-22), roughly two months before the 2026-09-22 disclosure and fix. Affected versions: R82.20 (all takes), R82.10 Jumbo Hotfix Take 44 or lower, R82 Take 126 or lower, R81.20 Take 166 or lower, R81.10 Take 190 or lower (end-of-support), and the end-of-support R80/R80.10–R80.40/R81 lines. Fixed in the R82.20 Security Hotfix, or Jumbo Hotfix Accumulator R82.10 Take 45+ / R82 Take 127+ / R81.20 Take 170+ / R81.10 Take 192+; Check Point published no fix for the end-of-support trains older than R81.10, and upgrading is the only remediation for them (Bishop Fox, 2026-10-01). Check Point states plainly "because of the nature of the fix, a LivePatch is not be available for this issue" (Check Point Support, sk1000171, 2026-09-22); the September LivePatch (Take 28/29) that addressed the unrelated CVE-2026-91843 flaw does not cover this vulnerability (The Hacker News, 2026-09-22). CISA added it to KEV the same day (CISA KEV, catalogue version 2026.09.22). This is a distinct, unrelated flaw from CVE-2026-85102 (a separate Check Point Security Gateway/Spark VPN certificate-validation RCE, disclosed 2026-09-09, with exploitation attempts reported from 2026-09-12 (Check Point Research, 2026-09-22)), with different components and no CVE overlap.

    Detection concept, per Check Point's own two independent indicators of compromise (Check Point Support, sk1000171, 2026-09-22): first, a pre-authentication login attempt whose username field is anomalously long (over 1,000 characters) in the management-process log, occurring at the same timestamp as a management-process core dump, indicates a crash consistent with exploitation attempt; second, a resource-loading error referencing a file path containing parent-directory-reference sequences in the same log, which Bishop Fox says fires only when an upgrade-tools load fails and not on the route it published (see the 2026-10-04 update below). Triage: the first indicator is diagnostic only as its own correlated pair: an anomalously long username alone is not, and Bishop Fox attributes that crash signature to the separate CVE-2026-91843, not to this traversal (Bishop Fox, 2026-10-01). The second indicator, a traversal-pattern sequence inside the resource-loading error path, signals an attempt on the upgrade-service route when it appears, but its absence says little (Bishop Fox, 2026-10-01). Hardening: because no LivePatch exists, restrict network reachability to the management web service (Check Point names TCP/19009 specifically) to trusted administrative IP ranges via the platform's Trusted Clients or implied-rule mechanism, which Bishop Fox calls Check Point's primary mitigation (Bishop Fox, 2026-10-01).

    Defender takeaway
    Treat any affected server that was internet-reachable on TCP/19009 before 2026-09-22 as a potential compromise-assessment target, not just a patch target: Check Point observed attacks on 2026-07-23, about two months before the fix, so an unpatched, exposed server could have been compromised well before disclosure. On a server that was exposed and unpatched, also plan credential and certificate rotation, since execution runs as root inside the process that holds the policy and the internal certificate authority (Bishop Fox, 2026-10-01).
    Update04 Oct 2026 05:12 UTCrun 2026-10-04T0405Z-inteltitlesummaryimmediate_actiontagstechniquescvessourcesevidencesourcing_noteactionsbody

    Bishop Fox published on 2026-10-01 a lab reproduction of an unauthenticated root code-execution chain on unpatched R81.10 and R82.10 management servers, run end to end over TCP 19009 (Bishop Fox, 2026-10-01). The chain mints a session by presenting the server's own internal certificate name, which the server accepts from a caller-supplied string without checking that a certificate was presented, then uses the file service to write a file anywhere as root; overwriting a stock scheduled-task file makes the system's cron daemon run the attacker's command as root with no further request, and the output is read back over the same session (Bishop Fox, 2026-10-01). Bishop Fox confirmed two further routes from the same write to code execution and says closing any one leaves the others standing (Bishop Fox, 2026-10-01). The post describes the chain but links only a patch-state scanner, not the exploit script.

    Bishop Fox reads the hotfix as closing three defects while the advisory names two: the forged login, the unbounded file write and the upgrade-service parameter validation, with either of the first two alone breaking the chain; this is its comparison of the shipped code, not a Check Point statement (Bishop Fox, 2026-10-01). Its scanner reads patch state from outside with one benign request to the management port and, per its README, does not detect prior compromise (Bishop Fox, 2026-10-01).

    Bishop Fox says Check Point's second indicator fires only when an upgrade-tools load fails and is never reached by this route, so it leaves neither the error line nor the parent-directory sequence, and that a genuine upgrade can trip it; it calls the first indicator, an over-long username next to a core dump, the crash signature of the separate CVE-2026-91843 and not evidence of this traversal (Bishop Fox, 2026-10-01). An exposed, unpatched server with neither log sign is therefore not shown to be clean. Its hunting advice is file-integrity monitoring of scheduled-task directories, startup and SSH key paths, the normally empty upgrade-tools directory, the CPM configuration files and anything new in the output-staging directory, paired with execution telemetry, cron reload events and an alert on the management Java process spawning a shell, because a scheduled hash check can miss stock files restored byte for byte (Bishop Fox, 2026-10-01). It also notes that the Trusted Clients restriction is a permissions setting that emits an implied rule, so a rule-base audit alone can miss it (Bishop Fox, 2026-10-01).

    HIGHCVE-2026-91843updatedNATOA2

    CVE-2026-91843, Check Point Security Management / Multi-Domain Security Management / Log Server: unauthenticated stack overflow in the login process reaches root RCE (CVSS 9.8)

    Check Point disclosed CVE-2026-91843 (CVSS 9.8) on 2026-09-16: a stack overflow in the unauthenticated login process to Check Point Security Management Server, Multi-Domain Security Management Server, Log Server and Multi-Domain Log Server lets an attacker who reaches the login interface run arbitrary code remotely as root (Check Point PSIRT, 2026-09-16). Check Point's attack indicator is a failed administrator login for an over-long username (Check Point PSIRT, 2026-09-16). Neither Check Point's advisory nor CERT-FR reports observed exploitation (Check Point PSIRT, 2026-09-16 · CERT-FR CERTFR-2026-AVI-1193, 2026-09-17).

    Check Point ships the fix as a LivePatch: administrators with automatic updates enabled per sk175504 are already protected, and cplp list in Expert mode should show the CVE-2026-91843 patch armed on R82.20, R82.10, R82 and R81.20 (Check Point PSIRT, 2026-09-16). The fix is also in the Jumbo Hotfix Accumulator for R82.10 from Take 45, R82 from Take 127, R81.20 from Take 170 and the end-of-support R81.10 from Take 192, while Check Point lists no fix for R80.x and R81 (Check Point PSIRT, 2026-09-16). Check Point's mitigation is to limit Trusted Clients (GUI clients) to trusted IP addresses or subnets and never to use "Any" as the client type (Check Point PSIRT, 2026-09-16). The flaw needs no credentials and yields root (Check Point PSIRT, 2026-09-16), so the absence of exploitation reports does not lower the urgency.

    Detection
    In SmartConsole, search Audit and Admin login logs for the message "Administrator failed to log in: Username too long" (Check Point PSIRT, 2026-09-16). Check Point's advisory for the related, exploited CVE-2026-93616 also tells administrators to search cpm.elg for login requests with usernames over 1,000 characters and to check for an FWM or MDS core dump at the same time (Check Point Support, sk1000171, 2026-09-20).

    Triage: Check Point's advisory for CVE-2026-93616 treats a login with a username over 1,000 characters that coincides with an FWM or MDS core dump as a potential attempt to exploit that flaw (Check Point Support, sk1000171, 2026-09-20). For CVE-2026-91843, Check Point gives only the "Username too long" login failure as its attack indicator (Check Point PSIRT, 2026-09-16).

    Defender takeaway
    Apply the fix to every Security Management, Multi-Domain Security Management, Log Server and Multi-Domain Log Server now, preferably through a Jumbo Hotfix take that also closes CVE-2026-93616 (Check Point Support, sk1000171, 2026-09-20), and independently verify that no Trusted Client/GUI access reaches the login interface from outside the management network.
