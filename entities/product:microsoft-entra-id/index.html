    Defender insights

    What each entry about Microsoft Entra ID tells a defender to do, newest first.

    2026-10-23NOTABLEHuntress: stolen post-MFA M365 tokens replayed within minutes; a password reset leaves planted devices and MFA methods

    Defender takeaway

    Revoke sessions as well as resetting the password, because the access token lives about 90 minutes after a reset, then audit devices, MFA methods, inbox rules and newly consented enterprise applications; as controls, require MFA or block for all users, all cloud apps and all client app types unconditionally, restrict the device-code flow with authentication-flow policies, and disable user consent to new applications (Huntress, 2026-10-22).

    Exposure · triage · detection
    Exposure

    Any Entra tenant where users can sign in to Microsoft 365 from unmanaged networks and Conditional Access does not require MFA or block for all users, all cloud apps and all client app types unconditionally, or where the device-code flow is open; Huntress names no victim, sector or country (Huntress, 2026-10-22).

    Triage

    A node user agent with an Office client identifier can be legitimate automation, so Huntress focuses on sign-ins that touch user mailboxes or the Device Registration Service from hosting infrastructure, and it says the device-name pattern is rare but not unique to this campaign, so a device should be confirmed before it is deleted (Huntress, 2026-10-22).

    Detection

    In Entra sign-in logs, OAuth2:Token and Cmsi:Cmsi requests from hosting infrastructure that use the Microsoft Office or Authentication Broker client with a node or bare Mozilla/5.0 user agent, above all those that touch user mailboxes or the Device Registration Service; in the Entra audit log, device registrations from hosting addresses with the DESKTOP-plus-eight-hex name shape and MFA methods deleted and re-added within minutes; in Exchange audit data, inbox rules with the short names described above, especially created through the REST API (Huntress, 2026-10-22).

    2026-10-18HIGHexploitedConnectWise SkyKick app credential used in 162+ Microsoft 365 tenants; disabling it does not undo planted access

    Defender takeaway

    Where any ConnectWise or SkyKick app is consented, disable it by client ID without deleting it, keep it disabled until ConnectWise gives restoration instructions, and review credentials, roles, owners, consents and Conditional Access exclusions since 13 October (ConnectWise, 2026-10-19; Huntress, 2026-10-16). An MSP should review its own management and security tools first, since a foothold there can reach its customers, but the review covers every application, because Huntress saw secrets planted on apparently random ones (Huntress, 2026-10-16). ConnectWise cannot independently determine whether a given partner or customer tenant was affected, so the answer for a tenant has to come from its own sign-in and audit logs (ConnectWise, 2026-10-19).

    Exposure · triage · detection
    Exposure

    Every Entra tenant, including each customer tenant an MSP manages, in which a ConnectWise or SkyKick Cloud Backup or Cloud Management app was ever consented, dormant connections included; ConnectWise lists seven application client IDs, among them Cloud Backup (506e08f9-6e9a-4da4-942b-a099a03644ae), and says to match on client ID (ConnectWise, 2026-10-19). Todyl says to find every SkyKick and ConnectWise app in a tenant, inherited ones included, and that all SkyKick apps are published from one vendor tenant (named ConnectWise S-K LLC, ID 3f9cd7a0-127a-4ed4-bf06-2f830d5616b7); SpecterOps hunts for apps owned by that tenant and notes that older tenants may list them under SkyKick names (Todyl, 2026-10-15; SpecterOps, 2026-10-17).

    Triage

    The vendor's apps sign in from Azure addresses with a .NET SDK user agent, while the credential additions used a Python user agent; Python and curl are common in administration, so Huntress says the combination of actor, operation and user agent is the signal (Huntress, 2026-10-16). Role self-assignments carrying the vendor's own user agent are not proven benign, since Huntress has not confirmed vendor automation (Huntress, 2026-10-16).

    Detection

    Entra service-principal sign-in logs for these apps from any address outside Microsoft and Azure ranges, which misses the credential additions, made from private Azure space (Huntress, 2026-10-16); the sweep of sign-ins itself, which Sophos saw come from a single virtual private server in strictly ascending tenant-ID order with Python HTTP-library user agents (Sophos, 2026-10-19); directory audit events Add member to role, Update application and Add service principal credentials initiated by a ConnectWise or SkyKick app (Huntress, 2026-10-16); Graph activity logs (Entra ID P1 or P2, not retroactive) for per-request source addresses (Todyl, 2026-10-15); and mailbox forwarding, inbox and transport rule and delegation changes (ConnectWise, 2026-10-19). Huntress notes that Microsoft Graph directory reads leave no audit record, so a clean audit log does not rule out reads of the directory (Huntress, 2026-10-16). Disabling the apps does not remove credentials, roles or consents already planted, and revoking user sessions does not end this access (ConnectWise, 2026-10-19; Todyl, 2026-10-15). Disabling an app stops new tokens only: a token issued before the disable stays valid for up to 90 minutes (Todyl, 2026-10-15; SpecterOps, 2026-10-17), and ConnectWise says that after its own certificate revocation previously issued tokens may remain usable until they expire (ConnectWise, 2026-10-19). The service-principal sign-in log records an application's authentication (ConnectWise, 2026-10-19), while per-request use of a token appears in the Graph activity logs named above (Todyl, 2026-10-15), so the review of that period belongs there. Microsoft asks tenants to review service-principal sign-ins from at least 2026-10-15, and from 2026-10-01 where records exist, and to search by application ID rather than display name (Microsoft, 2026-10-21). Any alerting a tenant took from ConnectWise SaaS Security is out of service while that service is suspended (ConnectWise, 2026-10-19).

    2026-10-22NOTABLEMicrosoft: Storm-0940 runs the ARTEX agent framework at machine speed; Expel adds an Okta self-registration technique

    Defender takeaway

    Expel's reading is that the framework adds speed, not a new vulnerability, so the levers are the identity controls it runs into: least privilege on multi-tenant application permissions and consent grants, alerting on credential additions and privileged role assignments by applications, and a review of self-registered Okta accounts since 2026-10-13 (Microsoft, 2026-10-21; Expel, 2026-10-21).

    Exposure · triage · detection
    Exposure

    Any tenant that relies on password sign-in or grants OAuth consent to applications, and any Okta org with self-service registration enabled; not using ConnectWise does not exclude exposure (Expel, 2026-10-21).

    Triage

    Python and curl user agents match common legitimate automation, so Expel treats them as supporting evidence only, and a Python user agent on an application that normally calls Microsoft Graph with a .NET SDK is the anomaly (Expel, 2026-10-21).

    Detection

    In the authentication logs of every identity provider in use, bursts of failed logons and lockouts spread over many accounts; in the Okta system log, newly self-registered accounts that enrol Okta Verify and start single sign-on within minutes; and in the Entra audit log, credentials or certificates added to applications that nobody on your team created and any application that assigns itself a directory role (Microsoft, 2026-10-21; Expel, 2026-10-21). A clean audit log is not proof of no access, because Microsoft Graph directory reads leave no Entra audit record (Expel, 2026-10-21). In web access logs of an application exposed to the same actor, Wiz points to source-map and OpenAPI downloads followed minutes later by calls to internal routes that appear only in those files, and to sign-in telemetry showing a new user agent for each burst of attempts at a one-second cadence (Wiz, 2026-10-22).

    2026-09-27NOTABLEHuntress: attacker JavaScript in a signed Windows AppX host drives Microsoft's own OAuth broker, so a genuine login yields MFA-surviving refresh tokens

    Defender takeaway

    The prerequisite toggle is the whole control surface, so audit where Developer Mode and enterprise sideloading are enabled and remove them where they are not needed; treat developer workstations, build runners and cloud VMs as the population that most likely carries them. Where a token is suspected stolen, a password reset is not a remedy: revoke the user's refresh tokens explicitly, because the stolen token keeps working from any network until revocation, a revocation event, or Continuous Access Evaluation ends it.

    Triage · detection
    Triage

    MSAppHost/3.0 reaching Microsoft-owned infrastructure is ordinary AppX behaviour and not a finding; the same user agent reaching an origin outside Microsoft is what has no benign explanation. Likewise, an Office sign-in from a managed device is unremarkable on its own, so the discriminator is the pairing: a successful Office-client-ID sign-in on a host that also produced outbound EdgeHTML-engine traffic to a non-Microsoft origin in the same window.

    Detection

    Endpoint and identity telemetry come up empty by design here, because the process is Microsoft-signed, the endpoint is Microsoft's, and the client ID is Microsoft Office's. The network leg is what separates the two. Every AppX web host renders through the legacy EdgeHTML engine, which announces itself in the user agent as MSAppHost/3.0 paired with Edge/18; Chromium-based Edge retired EdgeHTML years ago, so "No modern browser produces that string" (Huntress, 2026-09-23). Proxy and egress logs carrying that user agent to any destination outside Microsoft-owned infrastructure are the signal, and because the rule keys on the shared rendering engine rather than a host binary name, it covers the whole class. On the endpoint, package-registration events for AppX packages that no software-distribution system deployed are the complementary tell, as is the state of the Developer Mode registry value across the fleet. In Entra ID sign-in logs the record looks like a routine Office desktop sign-in with no risk flags, and the one field that differs is the user agent Microsoft itself records for the authentication leg, MSAuthHost on the Trident engine rather than MSAppHost/3.0, which is a reason to correlate the identity and network sides rather than to rely on either alone.

    2026-09-24NOTABLEA public tool bulk-enumerates Entra ID accounts and their MFA methods through Microsoft's own password-reset portal

    Defender takeaway

    Scoping SSPR to a specific security group rather than tenant-wide limits method disclosure to the accounts inside the group and to administrators, but it does not stop existence enumeration, and it exposes the registered methods, or the empty method list, of every in-scope account (LevelBlue SpiderLabs, 2026-09-23). Remove alternate-email-OTP and security-question options from the permitted SSPR methods, and enforce phishing-resistant MFA on every privileged role: Microsoft enforces SSPR on admin accounts and this cannot be disabled, so a stronger factor on those accounts is the control that raises the cost of exploiting what the technique reveals (LevelBlue SpiderLabs, 2026-09-23).

    Triage · detection
    Triage

    A genuine user forgetting a password generates one SSPR lookup that is normally followed by a completed reset; a burst of lookups against many usernames with no completions is the anomalous pattern the volume/velocity discriminator is built on, not the existence of lookups themselves (LevelBlue SpiderLabs, 2026-09-23).

    Detection

    Entra ID / Azure AD self-service-password-reset audit events are the telemetry class, specifically SSPR activity records with status failures such as "user is not member of the password reset users group", and bulk enumeration attempts: many requests in a short window across varied usernames with no subsequent completed reset (LevelBlue SpiderLabs, 2026-09-23).

    2026-09-08HIGHCloudSEK gained admin access to the panel and found custom code specifically written to defeat the one MFA class that structurally resists this attack

    Defender takeaway

    Any Microsoft 365 or Entra ID tenant, and any managed IT-service provider holding privileged access to one, is directly in scope; phishing-resistant FIDO2/WebAuthn is the only MFA class this operation cannot structurally defeat, so its deployment should be prioritized over TOTP, push or SMS wherever administrative or high-value accounts are concerned, paired with Conditional Access policies keyed to device-compliance state rather than geolocation, since geo-matched residential proxies defeat the latter.

    Triage
    Triage

    The vendor-neutral tell is a session-cookie-authenticated action with no matching interactive MFA challenge in the same session lineage, or a token-issuance event immediately followed by activity from a network location or device-compliance state inconsistent with the device that originally enrolled; a legitimate user re-using a cached session from a known device does not produce this mismatch, which is what separates the AiTM replay from ordinary session persistence.

    M365 token spray and replay: Huntress tracks a 10-week campaign that replays stolen post-MFA tokens from rented hosting within minutes, registers rogue Entra devices, wipes and re-registers MFA methods and hides mail with inbox rules of one to three characters or punctuation only

    Between 2026-07-14 and 2026-09-22 Huntress detected 497 Microsoft 365 sign-in events across 79 victim organizations that replayed stolen sign-in tokens instead of guessing passwords (Huntress, 2026-10-22). The tokens came from adversary-in-the-middle relays behind fake sign-in pages, from device-code phishing and from social engineering during a genuine sign-in; a relay passes the real login page and MFA prompt through and keeps the token Microsoft issues afterwards, so its holder does not face MFA again (Huntress, 2026-10-22). Replay followed within minutes, after 12 minutes on 2026-07-21 and four minutes on 2026-09-22, from one of six addresses in a single rented range used in turn, so blocking one address stops at most one phase (Huntress, 2026-10-22).

    A scripted replayer with the user agent node requests tokens with the Microsoft Office and Microsoft Authentication Broker client applications against Microsoft Graph, Exchange Online, SharePoint Online and the Device Registration Service and joins 48 rogue Entra devices named DESKTOP- plus exactly eight uppercase hexadecimal characters, where the Windows default is seven alphanumeric characters; a browser-session replayer uses current Chrome or Edge through the OfficeHome client (Huntress, 2026-10-22). What outlives a password reset is the persistence: in 19 organizations the victim's MFA methods were wiped and a new authenticator registered within three hours, the rogue devices stay in the directory until deleted, and hidden inbox rules with names of one to three characters or punctuation only, created from VPN or other rented addresses, moved mail to RSS Feeds, RSS Subscriptions or Conversation History or deleted it, one keyed on payroll and bank terms (Huntress, 2026-10-22). Conditional Access blocks reported as AADSTS53003 fire only after authentication has succeeded, so they signal a valid credential, and ranking tenants by failed attempts points responders at the wrong ones (Huntress, 2026-10-22).

    Exposure
    Any Entra tenant where users can sign in to Microsoft 365 from unmanaged networks and Conditional Access does not require MFA or block for all users, all cloud apps and all client app types unconditionally, or where the device-code flow is open; Huntress names no victim, sector or country (Huntress, 2026-10-22).
    Detection
    In Entra sign-in logs, OAuth2:Token and Cmsi:Cmsi requests from hosting infrastructure that use the Microsoft Office or Authentication Broker client with a node or bare Mozilla/5.0 user agent, above all those that touch user mailboxes or the Device Registration Service; in the Entra audit log, device registrations from hosting addresses with the DESKTOP-plus-eight-hex name shape and MFA methods deleted and re-added within minutes; in Exchange audit data, inbox rules with the short names described above, especially created through the REST API (Huntress, 2026-10-22).
