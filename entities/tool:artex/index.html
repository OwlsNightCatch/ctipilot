    2026-10-02HIGHexploitedZammad 6.5.5 emergency-fixes the exploited session-leak RCE on 6.5; 7.2.3 now supersedes 7.2.2 (root escalation)

    Defender takeaway

    Upgrade to Zammad 7.2.3, which supersedes 7.2.2 as a critical security update (Zammad, 2026-11-11), after saving the logs: 7.2.2 fixed the root escalation on DEB and RPM installs (Zammad advisory GHSA-p97w-927q-8vxq, 2026-10-08), 6.5 and older receive no regular security fixes (Zammad, 2026-10-01), with 6.5.5 as an emergency fix for the code-execution flaw on 6.5 only where upgrading is not yet possible (Zammad, 2026-10-15), and 7.2.0 is affected by the advisories published on 2026-10-06 (Zammad advisory records, 2026-10-06); treat any internet-reachable instance on 6.3.0 to 6.5.4 since 2026-09-21 as possibly compromised, including the ticket data and anything the host can reach, since NCSC-NL says an attacker can take over the system, read, change or delete data and use it for further attacks (NCSC-NL, 2026-09-30), and treat a DEB or RPM host where code ran as the zammad account as possibly root-compromised, since the upgrade does not undo an escalation already made; keep restricting access to the underlying server to trusted administrators, as Zammad advises (Zammad, 2026-10-05), and keep Zammad behind authentication or off the internet; the forensic report asks for deny-by-default segmentation even inside one VLAN and for TLS on database links, because its intruder moved from Zammad to Jira and Confluence in the same VLAN (DIVD CSIRT, 2026-11-24).

    Exposure · detection
    Exposure

    Self-hosted Zammad. The code-execution flaw needs a version from 6.3.0 to 6.5.4 per DIVD and NCSC-NL (DIVD CSIRT, 2026-10-01; NCSC-NL, 2026-09-30), and Zammad says only 6.5 and older are exploitable and 7.0 and later are not affected (Zammad, 2026-10-01); the root escalation was reported by DIVD as present in every version from 1.5.0 (DIVD CSIRT, 2026-10-01), while Zammad's advisory of 2026-10-08 limits it to installations from the DEB and RPM packages (packager.io), says every released packaged version was affected and says installations from source or the official container images were not (Zammad advisory GHSA-p97w-927q-8vxq, 2026-10-08); Zammad assesses it as a local privilege escalation that needs prior access to the server (Zammad, 2026-10-05), so it matters as the second stage after the code-execution flaw or any other foothold as the zammad user. Zammad says SaaS customers need take no action for 7.2.1 because their instances are already patched (Zammad, 2026-10-06), and the 27 advisories of 2026-10-06 list affected versions up to 7.2.0 (Zammad advisory records, 2026-10-06); the two critical ones concern the public sign-up form and accounts with multi-factor authentication configured that never completed email verification (Zammad advisory GHSA-79wh-8g2f-xj2c, 2026-10-06; Zammad advisory GHSA-f3qr-94c2-7mx2, 2026-10-06).

    Detection

    Web and application logs on the Zammad host. DIVD links a log-check script for the code-execution flaw that searches the Zammad application and nginx logs for error lines carrying session material, a cookie value or a client list, and says to look for unfamiliar processes and files as well (DIVD CSIRT, 2026-10-01; DIVD log-check script, 2026-10-01). Horizon3's public exploit shows the flaw from the attacker's side: a single request to the /ws WebSocket endpoint makes the server return an error carrying every active user's session cookies, so those error log lines are the trace, and an administrator session obtained that way can install a package through the admin interface that writes a template over the password-reset email view, so unexpected packages and overridden view templates in the application directory are the follow-on artifact (Horizon3, 2026-10-07). The forensic report adds traces: a mail-view template override or a file written through the package-upload endpoint, a setuid copy of bash, a root-run systemd loop and cron entries that run text files dropped in the web-served directory, ARP-cache changes on the application servers, and remember-me tokens in the Confluence and Jira databases that no login issued (DIVD CSIRT, 2026-11-24). Updating to 7.2.2 closes the escalation but does not show whether it was already used: Zammad's advisory says an attacker holding a foothold as the zammad account could have reached root within seconds (Zammad advisory GHSA-p97w-927q-8vxq, 2026-10-08), so on any host where code ran as that account, look for new root-owned files, services and processes as well. More generally, updating does not show whether an instance was already compromised: NCSC-NL asks operators to copy application and network logs before installing the update so the second flaw's use can be investigated later (NCSC-NL, 2026-09-30).

    2026-10-22NOTABLEFBI: various actors run ARTEX against many sectors, government included; Microsoft now names six users

    Defender takeaway

    Expel's reading is that the framework adds speed, not a new vulnerability, so the levers are identity controls: least privilege on multi-tenant application permissions and consent grants, alerting on credential additions and privileged role assignments by applications, and a review of self-registered Okta accounts since 2026-10-13 (Microsoft, 2026-10-21; Expel, 2026-10-21).

    Exposure · triage · detection
    Exposure

    Microsoft 365 tenants with applications already granted access, whose abuse ARTEX sped up (Microsoft, 2026-10-21); Entra and Okta sign-in, which the sprays target (Wiz, 2026-10-22); and any Okta org with self-service registration enabled, where not using ConnectWise does not exclude exposure (Expel, 2026-10-21).

    Triage

    Python and curl user agents match common legitimate automation, so Expel treats them as supporting evidence only, and on the two ConnectWise applications Huntress reviewed, which call Graph with a .NET SDK, a Python user agent is the anomaly (Expel, 2026-10-21).

    Detection

    In every identity provider's authentication logs, bursts of failed logons and lockouts spread over many accounts; in the Okta system log, newly self-registered accounts that enrol Okta Verify and start single sign-on within minutes; and in the Entra audit log, credentials or certificates added to applications that nobody on your team created and any application that assigns itself a directory role (Microsoft, 2026-10-21; Expel, 2026-10-21). A clean audit log is not proof of no access, because Microsoft Graph directory reads leave no Entra audit record (Expel, 2026-10-21). In web access logs, Wiz points to source-map and OpenAPI downloads followed minutes later by calls to internal routes found only in those files, and in sign-in telemetry to a new user agent per burst at a one-second cadence (Wiz, 2026-10-22). Wiz also reports that ARTEX and Cairn write a numeric intent ID into names the agent creates (ARTEX i<N>, a per-installation counter unreset by default; Cairn i001, reset per project), visible in AWS role session names, SSM comments, tags and Azure resource names; pair it with an anchor (Wiz, 2026-11-25).

    Exposure

    Detection

    In cloud control-plane audit logs, a long-lived key used by a non-vendor address, secret-store reads followed by use of those secrets in other accounts, resources named with the letter i followed by digits and no hyphen, short-lived branches in a handful of repositories that trigger a workflow, and container deployments that mount the node's file system (Barracuda Trust Center, 2026-11-13; Barracuda Blog, 2026-11-11).

    2026-11-15NOTABLEARTEX in AWS: CloudWatch log searches for secrets, Cognito self-sign-up for credentials; hunt CloudTrail for both

    Defender takeaway

    Check which Cognito user pools allow open self-registration and what their identity pools' authenticated roles can read, rotate long-term IAM keys found in code or logs, and hunt CloudTrail for the sequences above; a narrow authenticated role is what stopped the Cognito path in the case Datadog describes.

    Exposure · triage · detection
    Exposure

    AWS accounts with long-term IAM access keys that may have leaked, applications whose public Cognito user pools allow self-registration with identity pools that vend AWS credentials to authenticated users, and S3 buckets that serve web front ends without authentication.

    Triage

    FilterLogEvents is a routine call for log tooling and engineers; the discriminator is a long-term user key searching log text for credentials, internal addresses or company names at a constant page limit, from an address that key does not normally use.

    Detection

    In CloudTrail and S3 access logs, anonymous read bursts that include requests for placeholder-named objects; FilterLogEvents calls with a fixed limit of 1,000 from a long-term user key; Cognito SignUp spikes with PreSignUp failures, followed by CognitoIdentityCredentials sessions issuing broad read-only discovery calls that end in access-denied errors; and instance-role credentials used from an address outside AWS, which Datadog lists among the unusual patterns to hunt (Datadog Security Labs, 2026-11-09).

    ARTEX: Microsoft reports Storm-0940, a China-state aligned actor, running an open-source multi-agent LLM penetration-testing framework against hundreds of organizations, with privileged cloud access in under three hours in some cases, and Expel sees the same infrastructure abuse Okta self-service registration

    Microsoft Threat Intelligence reports that as early as September 2026 Storm-0940, a China-state aligned actor active since 2021, used the agentic penetration-testing framework ARTEX to automate attacks on hundreds of organizations across many industries, government and military among them; ARTEX is an open-source multi-agent LLM system that runs a penetration test from reconnaissance to exfiltration with little human involvement (Microsoft, 2026-10-21). Microsoft says ARTEX accelerated the abuse of compromised applications already granted access to Microsoft 365 tenants, and most targeting failed, yet several cases went from first targeting to privileged cloud access in under three hours (Microsoft, 2026-10-21).

    Expel saw Storm-0940 infrastructure scan a customer and, from 2026-10-13, abuse its Okta self-service registration with no ConnectWise application involved: the attacker created five accounts, enrolled Okta Verify on three of them about a minute after activation and ran a password spray that Okta ThreatInsight blocked (Expel, 2026-10-21). Expel says the shared source address is its only link to Storm-0940, and the activity alone does not prove ARTEX was used (Expel, 2026-10-21). CrowdStrike saw another actor use ARTEX against South Korean financial institutions from late September; Recorded Future tracks it as TAG-217 (CrowdStrike, 2026-10-07; Recorded Future, 2026-10-16).

    Wiz tracked an actor using ARTEX-associated tooling, overlapping with Storm-0940, against IT and software vendors in October 2026, focused on identity providers and Microsoft 365 integrations; most attempts failed and none of the techniques is novel (Wiz, 2026-10-22).

    Exposure
    Microsoft 365 tenants with applications already granted access, whose abuse ARTEX sped up (Microsoft, 2026-10-21); Entra and Okta sign-in, which the sprays target (Wiz, 2026-10-22); and any Okta org with self-service registration enabled, where not using ConnectWise does not exclude exposure (Expel, 2026-10-21).
    Detection
    In every identity provider's authentication logs, bursts of failed logons and lockouts spread over many accounts; in the Okta system log, newly self-registered accounts that enrol Okta Verify and start single sign-on within minutes; and in the Entra audit log, credentials or certificates added to applications that nobody on your team created and any application that assigns itself a directory role (Microsoft, 2026-10-21; Expel, 2026-10-21). A clean audit log is not proof of no access, because Microsoft Graph directory reads leave no Entra audit record (Expel, 2026-10-21). In web access logs, Wiz points to source-map and OpenAPI downloads followed minutes later by calls to internal routes found only in those files, and in sign-in telemetry to a new user agent per burst at a one-second cadence (Wiz, 2026-10-22). Wiz also reports that ARTEX and Cairn write a numeric intent ID into names the agent creates (ARTEX i<N>, a per-installation counter unreset by default; Cairn i001, reset per project), visible in AWS role session names, SSM comments, tags and Azure resource names; pair it with an anchor (Wiz, 2026-11-25).

    Triage: Python and curl user agents match common legitimate automation, so Expel treats them as supporting evidence only, and on the two ConnectWise applications Huntress reviewed, which call Graph with a .NET SDK, a Python user agent is the anomaly (Expel, 2026-10-21).

    Defender takeaway
    Expel's reading is that the framework adds speed, not a new vulnerability, so the levers are identity controls: least privilege on multi-tenant application permissions and consent grants, alerting on credential additions and privileged role assignments by applications, and a review of self-registered Okta accounts since 2026-10-13 (Microsoft, 2026-10-21; Expel, 2026-10-21).

    Okta Threat Intelligence: AI agents register on Auth0 tenants and Okta organizations with disposable addresses from the mail.tm service, whose single rotating mailbox domain makes blocklists very likely stop matching within weeks; ARTEX, Cairn, CyberStrikeAI and pentestcode each picked it at run time

    Okta Threat Intelligence reports that since June 2026, and at scale through October and November, AI agents have registered accounts with disposable email addresses on Auth0 tenants and Okta organizations that allow public self-service registration, activity Okta calls almost certainly malicious and that customers often reported alongside attacks on their applications (Okta, 2026-11-23). The addresses mostly belong to the mail.tm family, a free receive-only service whose API needs no account or key and lets a script create a mailbox, obtain a token and poll for one-time codes (Okta, 2026-11-23). In tests by the P0 Labs team of Permiso, which Okta acquired on 2026-08-26 (Okta, 2026-07-30), the ARTEX, Cairn, CyberStrikeAI and pentestcode frameworks each picked mail.tm at run time, and in a data set containing attacker tooling mail.tm appeared on 80 percent of the attacker hosts where disposable email was found (Okta, 2026-11-23).

    mail.tm exposes only one active mailbox domain at a time and replaces it periodically, so a blocklist built from earlier domains will very likely stop matching within weeks; Okta's Auth0 telemetry shows sign-ups tracking the domain the API currently returns, and the attackers' domain changed around 2026-10-30 when the API response did. Agents also used mailinator, guerrillamail and emailnator, and at one target an agent moved to another provider when blocked, which Okta reads as agents treating disposable mail as an interchangeable capability. Okta says the use always occurred within a short window of other agentic reconnaissance and intrusion attempts against the same entities (Okta, 2026-11-23). Bot detection and CAPTCHA generally stopped the October mail.tm sign-ups before email verification, but Okta warns agents can solve challenges and commonly register by calling the Auth0 Authentication API directly, which can skip protections applied in Universal Login (Okta, 2026-11-23).

    Exposure
    An Auth0 tenant or Okta organization that allows public self-service registration. For workforce users Okta says self-service registration is a prerequisite for many of the attacks it describes and should be disabled or restricted (Okta, 2026-11-23).
    Detection
    In identity-provider registration telemetry, sign-up events whose email domain belongs to a disposable provider's currently active mailbox domain, kept current by polling the provider's public domain endpoint instead of a static list, as Okta advises (Okta, 2026-11-23).

    Triage: the discriminator Okta supports is context: a disposable-domain sign-up read alongside other agentic reconnaissance or intrusion attempts against the same entities, not the domain alone (Okta, 2026-11-23).

    Defender takeaway
    On Auth0, block sign-ups through the API while allowing Universal Login and block disposable domains with Actions; on Okta Workforce Identity, disable or restrict self-service registration. Treat a disposable-domain sign-up as a prompt to look for other agentic activity against the same estate, since Okta says it gives a heads-up to look for successful intrusion attempts, and do not rely on CAPTCHA alone (Okta, 2026-11-23).
