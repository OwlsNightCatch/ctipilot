    2026-10-29NOTABLESafeDep and JFrog: the testmetest npm worm now runs on import, so --ignore-scripts does not stop it; 42 repos armed

    Defender takeaway

    An install that ran with scripts disabled is not clean once the package has been imported; for an affected host SafeDep's order is to disconnect it, remove persistence first, rotate all credentials, check the accounts for the repositories and commits above and reinstall the operating system (SafeDep, 2026-10-27). Because the wiper is triggered by the token's revocation, the host is isolated and cleaned before the GitHub token is revoked.

    Exposure · detection
    Exposure

    Any developer endpoint, build agent or CI runner that installed or imported one of the operator's packages, and any GitHub or GitLab account whose token such a host held (SafeDep, 2026-10-27).

    Detection

    In package metadata, a binding.gyp whose sources field runs node in a package with no C or C++ sources, a postinstall that requires a .node file and discards errors beside a large high-entropy file, and prebuilt addons with no native source; on endpoints and CI runners, a node process that downloads or finds and runs the Bun runtime and a child node process started from a temporary path named after its process ID; in GitHub and GitLab audit logs, a new public repository in a developer's own account with a generic project description, commits with a fixed automated-sync message, commits that add AI-assistant configuration files (.claude, .cursor, .gemini, .vscode tasks, CLAUDE.md or AGENTS.md), an injected CI job that requests OIDC tokens, and unexpected patch releases of your own packages (SafeDep, 2026-10-27).

    2026-05-20HIGHThe compromised actions-cool GitHub Actions were re-enabled in September with malicious tags and ran the payload again

    Defender takeaway

    Treat any workflow run that used either action by tag on 2026-05-18 to 05-19 or from 2026-09-16 to 09-25 as a secrets exposure: rotate every secret the workflow could read, review what its GitHub token was allowed to do, audit the repository for commits from 2026-09-16 onward, and remove the actions or pin them to a full commit SHA verified to predate 2026-05-18 (Socket, 2026-09-24). Disabling a repository leaves its tags untouched, so a later re-enable reactivates the compromise without any change to your own workflow file; SHA pinning removes that dependency (Socket, 2026-09-24). Runner egress control is the layer that still holds when a compromised action runs: StepSecurity added the exfiltration domain to Harden-Runner's global block list, which blocks outbound connections to it even in audit mode, so that "even if a compromised action somehow runs, the credentials cannot leave the runner" (StepSecurity, 2026-05-18).

    Exposure · triage · detection
    Exposure

    Any workflow that referenced either action by a version tag pulled the malicious code on its next run after the tags moved; "Only workflows pinned to a known-good full commit SHA are unaffected" (StepSecurity, 2026-05-18). That happened on 2026-05-18 to 05-19 and again from 2026-09-16 until the second disable by 2026-09-25, and for issues-helper alone GitHub's dependency graph lists about 15,000 dependent repositories (Socket, 2026-09-24).

    Triage

    An issue-housekeeping action has no reason to install a separate JavaScript runtime or run a multi-minute script; a scheduled workflow that switches from failing in seconds to running for minutes without any change to its own code means the tagged action became downloadable again (Socket, 2026-09-24).

    Detection

    On the runner, the Bun runtime appearing under /home/runner/.bun/bin/bun, a python3 child process reading /proc/<Runner.Worker PID>/mem, gh auth token and sudo python3 executions, tr and grep pipelines filtering for secret-flagged values, and an outbound HTTPS connection to a domain outside the workflow's normal destinations (StepSecurity, 2026-05-18). In workflow definitions, an action reference that resolves to a commit matching no legitimate tag or branch head of the action's repository is the signature of this attack (StepSecurity, 2026-05-18). In workflow run history, runs of either action that start succeeding after a stretch of job-setup failures, or whose duration jumps from seconds to minutes, with runner logs showing Bun being set up for the action (Socket, 2026-09-24); in repository history, commits from 2026-09-16 onward that nobody can account for (Socket, 2026-09-24), in particular added Claude Code or VS Code hook configuration (The Hacker News, 2026-09-25).

    2026-05-28HIGHexploitedNx Console / TanStack / DAEMON Tools supply-chain cascade lands three CISA KEV entries

    Defender takeaway

    One stolen developer credential became a public release because any core contributor could publish Nx Console without a second human's approval (Nx postmortem, 2026-05-21). For a host that installed 18.95.0, the postmortem says to treat anything reachable from it as exposed and to rotate every credential that was on disk or could have been minted during the exposure window. Its lesson for any pipeline that can publish to a public registry is to require approval gating (Nx postmortem, 2026-05-21).

    Exposure · detection
    Exposure

    For Nx Console, only 18.95.0 is affected, in VS Code and forks such as Cursor. Earlier and later versions are not, and 18.100.0 is the fixed release (Nx postmortem, 2026-05-21). The Visual Studio Marketplace reports 28 installs of 18.95.0 and Open VSX 41 downloads from 21 unique IPs, while Nx's own analytics count about 6,000 activations of that version, so Nx says anyone who had the extension with auto-update enabled between 12:30 and 13:09 UTC on 2026-05-18 should assume compromise (Nx postmortem, 2026-05-21). The 2.2 million installs are the extension's overall count, not those of the malicious version (Help Net Security, 2026-05-21). For DAEMON Tools Lite, the trojanised builds are 12.5.0.2421 to 12.5.0.2434, in circulation from 2026-04-08 (Kaspersky, 2026-05-05). Disc Soft says only the free 12.5.1 release was affected, not the paid Lite, Ultra or Pro products, and that 12.6 is clean (Disc Soft Limited, 2026-05-06). For the upstream TanStack compromise (CVE-2026-45321), TanStack says any developer or CI environment that ran an npm, pnpm or yarn install against an affected @tanstack/* version on 2026-05-11 should be considered compromised, with every credential the install process could reach rotated and cloud audit logs reviewed for activity from those hosts (GHSA-g7cv-rxg3-hmpx, 2026-05-11).

    Detection

    Inventory installed editor extensions on developer hosts for Nx Console at exactly version 18.95.0 (the postmortem's check lists extensions with their versions and filters on angular-console) (Nx postmortem, 2026-05-21). On hosts that ran it, look for the payload's persistence: a Python backdoor under the user profile with staging and state files in temporary directories, a LaunchAgent on macOS, attempted /etc/sudoers changes on Linux, and a Bun runtime installed under the user profile on Windows (Nx postmortem, 2026-05-21). Updating to 18.100.0 is only the first remediation step: the advisory also says to kill the backdoor processes, which actively try to exfiltrate credentials, and to delete the persistence artifacts, so check patched hosts as well (GHSA-c9j4-9m59-847w, 2026-05-18). For DAEMON Tools Lite: hunt for DTHelper.exe or DTShellHlp.exe invocations with parent-process or file-modify timestamps inside the 2026-04-08 → 2026-05-05 window and a hash that does not match the post-12.6 reference set (compare against the indicators Kaspersky links from its write-up (Kaspersky, 2026-05-05)). For TanStack: a pinned @tanstack/* version is malicious if its published manifest carries an optionalDependencies entry for the fictitious @tanstack/setup package, with an undeclared obfuscated JavaScript payload of about 2.3 MB at the package root, and the CI pipelines to audit are those that ran an install against @tanstack/* between 19:20 and 19:30 UTC that day (GHSA-g7cv-rxg3-hmpx, 2026-05-11).

    2026-05-15NOTABLETeamPCP open-sourced its Shai-Hulud framework; Datadog maps its theft, persistence and npm-poisoning code

    Defender takeaway

    Before revoking any GitHub token on a suspect host, disable the token-monitoring daemon, then rotate credentials; yank any package version that gained an unexpected preinstall script (Datadog Security Labs, 2026-05-13).

    Exposure · detection
    Exposure

    CI/CD pipelines, developer workstations and cloud environments open to the documented techniques, in particular Runner.Worker memory extraction, instance and container metadata collection and IDE hook persistence; with the code public, other actors can reuse the playbook (Datadog Security Labs, 2026-05-13).

    Detection

    On hosts, a gh-token-monitor LaunchAgent or systemd user service, and Claude Code SessionStart hooks or VS Code folderOpen tasks that run a setup.mjs loader; in repositories, commits on any branch under a spoofed claude identity that add these hook and loader files; under stolen tokens, new public repositories with Dune-themed names; in npm, unexpected patch releases of your packages that add a preinstall script; in GitHub Actions, a disguised workflow that dumps the repository's secrets, followed by deleted workflow runs and branches (Datadog Security Labs, 2026-05-13).

    2026-05-13NOTABLEexploitedA Pwn Request, cache poisoning and runner-memory OIDC theft let attackers publish 84 malicious TanStack npm versions

    Defender takeaway

    On any host that installed an affected version, isolate and image the machine before revoking any token, because revocation triggers the wipe (StepSecurity, 2026-05-11), then rotate the AWS, GCP, Kubernetes, Vault, GitHub, npm and SSH credentials reachable from it (TanStack, 2026-05-11). For repositories, never check out or build an untrusted pull request under pull_request_target (GitHub Security Lab, 2021-08-03); where a fork-reachable job needs a cache, use the separate restore action, which has no save step (actions/cache README); and treat npm audit signatures as proof of which pipeline built a package, not that it was clean (npm Docs; StepSecurity, 2026-05-11).

    Exposure · detection
    Exposure

    Any developer machine or CI runner that ran npm install, pnpm install or yarn install against an affected version on 2026-05-11 (TanStack advisory, 2026-05-11). For maintainers, the same chain is open wherever a pull_request_target workflow checks out and builds fork code in a cache scope that a release job with id-token: write later restores (TanStack, 2026-05-11).

    Detection

    In package manifests and tarballs, an optional dependency on a github: URL pinned to a commit and a large JavaScript file at the package root that the files list does not declare; in runner process telemetry, the Bun runtime installed during npm install and python3 processes reading /proc/*/mem; in registry and repository history, two versions of one package published minutes apart and unexpected commits on Dependabot-style branches (StepSecurity, 2026-05-11). TanStack names publishes that do not come from the workflow's defined publish step as the signal to watch for (TanStack, 2026-05-11). On hosts, added Claude Code hooks, VS Code folder-open tasks and a token-monitoring LaunchAgent or systemd user service (NCSC-CH, 2026-05-12).

The recommended shift is from attestation-verification to build-pipeline integrity, monitor GitHub Actions runner process trees for unexpected outbound network from within a build, alert on actions/upload-artifact shipping signed-but-anomalous binaries, and cross-check published package checksums against CI logs via independent transparency ledgers (e.g. Sigstore Rekor). EU/Swiss public-sector teams running npm-based automation or Red Hat tooling should audit CI/CD pipeline definitions for unexpected workflow-step insertions.
