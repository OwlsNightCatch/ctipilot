    2026-08-17HIGHAkira reboots a SonicWall-VPN victim into Safe Mode to strip EDR, and starves its own encryptor

    Defender takeaway

    The whole chain from first VPN logon to attempted detonation ran in under five hours, and the data theft succeeded regardless of the encryption failure, so an environment that survives this on encryption alone has still lost its Active Directory inventory and its file shares. The detection weight sits on boot-configuration telemetry rather than on the endpoint agent, precisely because the agent is what the technique removes: Huntress recommends alerting on msconfig.exe and bcdedit activity, on Kernel-Boot event 27 with a SAFEBOOT load option, on Kernel-General event 12 with BootMode=2, on third-party security services stopping (System event 7036), and on tooling being added to the Safe Mode minimal-service registry list (Huntress, 2026-08-12). Those events survive the reboot in the local log and reach a SIEM if VPN and Windows logs are already being shipped, which is also what makes the two-hour gap between the successful spray and the first hands-on action usable. Coverage is the other half: Huntress records that in this environment "the agent was on a fraction of the machines the attacker enumerated; unmonitored hosts are where preparation happens undetected" (Huntress, 2026-08-12).

    Triage
    Triage

    Safe Mode with Networking is a legitimate diagnostic boot mode, so a lone Safe Mode boot is not the signal and IT-driven troubleshooting will generate them. The discriminators are what surrounds it: a SafeBoot Minimal or Network registry write naming a remote-access tool rather than a core Windows driver, a boot-configuration change made from an interactive session that traces back to an external VPN logon minutes earlier, and third-party security services stopping without a corresponding maintenance window. A genuine support-driven Safe Mode boot carries none of those, and the registry write in particular has no benign reason to name a remote-support binary.

    Triage

    Where no CLI-based VPN client is authorized or typical, any sess="CLI" event is a high-fidelity indicator; where scripted VPN authentication is legitimate, ReliaQuest says to baseline it and tune on volume, source IP and timing (ReliaQuest, 2026-05-19).

    HIGHNATOB2

    Akira blinds EDR by rebooting a victim host into Safe Mode with Networking, the operator's first observed use of the technique, and the stripped-down boot starved its own encryptor

    An Akira affiliate took a compromised Windows host into Safe Mode with Networking to strip its endpoint defences, which Huntress reports is the first time it has observed this operator using the technique; Snatch and AvosLocker have abused Safe Mode for years, but not Akira (Huntress, 2026-08-12). Everything around that step is the operator's familiar chain. From roughly 03:45 UTC on 4 August the SonicWall logged a burst of failed logins against multiple usernames from several external addresses, and about seven minutes later one succeeded against an SSL VPN with no multi-factor authentication in front of it; nearly two hours passed before any hands-on-keyboard activity (Huntress, 2026-08-12). The operator then reached the domain controller over RDP, spawned an elevated command shell, and ran full-property Get-ADUser and Get-ADComputer exports to files under C:\ProgramData; prefixed with $formatenumerationlimit = -1 so PowerShell's default four-item truncation would not clip multi-valued attributes such as group membership. Collection followed on an application server: WinRAR was installed mid-intrusion and used to recursively archive mapped file shares with the same flag string Huntress has documented in earlier SonicWall-entry Akira cases, and the archives went out to cloud object storage.

    The evasion itself is three cheap steps. AnyDesk was installed as a service to carry both hands-on control and payload delivery; because third-party services do not start in Safe Mode (including the attacker's own) the operator first wrote that service into the Safe Mode allow-list with a single reg.exe add against HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Network, then ran msconfig.exe at 06:29:21 UTC and forced the reboot. The host came back with Kernel-Boot event 27 recording a SAFEBOOT:NETWORK load option and Kernel-General event 12 recording BootMode = 2. Windows Defender logged event 3002 seconds into the boot, and Huntress states plainly that "For the entire Safe Mode window, the host had no working EDR, and AV was blinded" (Huntress, 2026-08-12).

    What the operator did not anticipate is that the same stripped-down environment starved the ransomware. The encryptor launched at 06:34:29 UTC, and within about two minutes the host logged System event 26 for virtual-memory exhaustion and a cascade of PowerShell stack failures; it never encrypted. A scheduled Defender scan identified the binary at 07:43:50 UTC but its cleanup routine failed repeatedly because real-time protection was down, and quarantine only succeeded at 08:12:28 UTC, after the attacker rebooted back to normal operation at 08:10:38 UTC and thereby restored the very protection they had removed (Huntress, 2026-08-12). Huntress calls that "a lucky side effect of the attacker's own mistake in these circumstances, not a defence you can plan around", and notes that a host with more memory or a larger page file, or a retooled encryptor with a lighter footprint, could carry the same play to completion (Huntress, 2026-08-12).

    Defender takeaway
    The whole chain from first VPN logon to attempted detonation ran in under five hours, and the data theft succeeded regardless of the encryption failure, so an environment that survives this on encryption alone has still lost its Active Directory inventory and its file shares. The detection weight sits on boot-configuration telemetry rather than on the endpoint agent, precisely because the agent is what the technique removes: Huntress recommends alerting on msconfig.exe and bcdedit activity, on Kernel-Boot event 27 with a SAFEBOOT load option, on Kernel-General event 12 with BootMode=2, on third-party security services stopping (System event 7036), and on tooling being added to the Safe Mode minimal-service registry list (Huntress, 2026-08-12). Those events survive the reboot in the local log and reach a SIEM if VPN and Windows logs are already being shipped, which is also what makes the two-hour gap between the successful spray and the first hands-on action usable. Coverage is the other half: Huntress records that in this environment "the agent was on a fraction of the machines the attacker enumerated; unmonitored hosts are where preparation happens undetected" (Huntress, 2026-08-12).

    Triage: Safe Mode with Networking is a legitimate diagnostic boot mode, so a lone Safe Mode boot is not the signal and IT-driven troubleshooting will generate them.     NOTABLECVE-2024-12802exploitedupdatedNATOB2

    SonicWall Gen6 SSL-VPN: patched-firmware appliances still open to the CVE-2024-12802 MFA bypass without manual LDAP remediation, exploited February to March 2026 by a suspected access broker

    SonicWall's SNWLID-2025-0001 describes CVE-2024-12802 (CWE-305, CVSS 6.5): when SSL-VPN authenticates against Microsoft Active Directory, UPN and SAM account names are handled separately, so MFA can be configured independently for each and an attacker can bypass it through the alternative account name (SonicWall SNWLID-2025-0001); in practice an attacker with valid credentials authenticates without the MFA step (BleepingComputer, 2026-05-20). On Gen6 the fixed firmware does not remove the vulnerable LDAP configuration, so six manual steps are needed: delete the LDAP configuration that uses userPrincipalName, remove cached LDAP users, remove the SSL VPN user domain, reboot, recreate the LDAP configuration without userPrincipalName and take a fresh backup (BleepingComputer, 2026-05-20); Gen7 firmware version 7.2.0-7015 and Gen8 firmware version 8.0.1-8017 build those steps in (SonicWall SNWLID-2025-0001). ReliaQuest responded to intrusions between February and March 2026 on Gen6 devices that looked patched and assesses with medium confidence that they are the first in-the-wild exploitation; the attacker brute-forced VPN accounts with an automated tool, in one case after only 13 attempts, and reached a file server within 30 minutes (ReliaQuest, 2026-05-19), connected to it over RDP with a shared local administrator password, and tried to deploy a Cobalt Strike beacon and a vulnerable driver to disable endpoint protection, both blocked by EDR (BleepingComputer, 2026-05-20). ReliaQuest describes the tools as consistent with actors in the ransomware ecosystem and the logouts and later re-entries with other accounts as initial access broker activity (ReliaQuest, 2026-05-19); the researchers could not attribute the attacks, though the activity resembled the Akira ransomware group's (Cybersecurity Dive, 2026-05-19).

    Exposure
    SonicWall Gen6 firewalls and NSv appliances running SSL-VPN with LDAP authentication against Active Directory where the LDAP configuration used userPrincipalName, even on the fixed firmware, until all six remediation steps are done; affected builds are firmware version 6.5.4.15-117n and older and NSv firmware version 6.5.4.4-44v-21-2457 and older (SonicWall SNWLID-2025-0001) (BleepingComputer, 2026-05-20). Gen6 reached end-of-life on 2026-04-16 (Cybersecurity Dive, 2026-05-19).
