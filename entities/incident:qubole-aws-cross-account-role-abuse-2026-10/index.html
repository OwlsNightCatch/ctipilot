    Defender takeaway

    Inventory third-party trust relationships, delete the roles of ended integrations, narrow each trusted principal to the vendor's specific principal and add a source-address or endpoint condition, which Wiz says alone would have blocked every observed assumption; after an incident, revoke the issued role sessions and rotate every secret, parameter, Lambda variable and identity-provider credential the role could read.

    Exposure · triage · detection
    Exposure

    Any AWS account holding an IAM role whose trust policy lets a Qubole account, or any other vendor account, assume it, including roles left from integrations that ended; the roles' trust policies and last-used data show them, and Wiz publishes the vendor account identifier, the two principals and the attacker address ranges for a CloudTrail hunt back to 2026-10-01 (Wiz, 2026-11-09).

    Triage

    Legitimate vendor traffic comes from the vendor's own AWS infrastructure; the correct External ID does not discriminate, because it is logged in plaintext and often stored by the vendor, while a vendor role assumed from a consumer VPN or a hosting provider the vendor has never used is the high-signal case.

    Detection

    In cloud control-plane audit logs, AssumeRole events into integration roles whose calling identity is the vendor account but whose source address is not AWS infrastructure, and session names with a consistent attacker-chosen prefix; GetCallerIdentity calls from many keys within seconds and Entra ID or Okta sign-ins by service principals or clients right after, as the actor validates credentials; ListSecrets, GetSecretValue, Parameter Store and Lambda configuration reads in bursts. Object reads are absent from CloudTrail management events, so S3 data events or server access logs must be on, and Wiz says missing logs left responders unable to see what was read (Wiz, 2026-11-09).

    Entries about Qubole cross-account AWS role abuse (October 2026) (1)

    2026-11-11 · view entry permalink →

    NOTABLENATOB1

    Qubole: an attacker used IAM credentials from a vendor-associated AWS account to assume dormant cross-account integration roles in dozens of customer accounts, then harvested secrets and validated Entra ID and Okta client credentials (Wiz and Sentra, 14 to 26 October)

    Wiz, working with Sentra and Mandiant, observed a threat actor using IAM credentials from an AWS account associated with Qubole, a big-data platform, between 2026-10-14 and 2026-10-26 (Wiz, 2026-11-09). The actor used two Qubole IAM users to call sts:AssumeRole on the cross-account integration roles that customers had created to trust Qubole's account; "every AssumeRole request we attributed to the threat actor included an External ID, and every one succeeded", most of the roles were otherwise not in use, and the traffic came from a rented hosting server and commercial VPN exits, not the AWS infrastructure where legitimate platform traffic originates (Wiz, 2026-11-09; Sentra, 2026-11-09).

    Inside each account the actor enumerated resources, read Lambda function configuration, Secrets Manager and Systems Manager Parameter Store, ran TruffleHog to test AWS access keys, Entra ID service-principal client secrets and Okta client credentials it found, and then downloaded S3 data opportunistically, in some cases whole buckets in one session (Wiz, 2026-11-09). Wiz found no tie to other reported activity and judges the targeting opportunistic; how the Qubole IAM users were compromised is not stated. Sentra writes that dozens of Qubole customers were impacted, and BleepingComputer could not find a public Qubole announcement (Sentra, 2026-11-09; BleepingComputer, 2026-11-10). No Swiss or public-sector victim is named, but the exposure is shared by any account that gave a data or analytics vendor a cross-account role and left it in place.

    Exposure
    Any AWS account holding an IAM role whose trust policy lets a Qubole account, or any other vendor account, assume it, including roles left from integrations that ended; the roles' trust policies and last-used data show them, and Wiz publishes the vendor account identifier, the two principals and the attacker address ranges for a CloudTrail hunt back to 2026-10-01 (Wiz, 2026-11-09).
    Detection
    In cloud control-plane audit logs, AssumeRole events into integration roles whose calling identity is the vendor account but whose source address is not AWS infrastructure, and session names with a consistent attacker-chosen prefix; GetCallerIdentity calls from many keys within seconds and Entra ID or Okta sign-ins by service principals or clients right after, as the actor validates credentials; ListSecrets, GetSecretValue, Parameter Store and Lambda configuration reads in bursts. Object reads are absent from CloudTrail management events, so S3 data events or server access logs must be on, and Wiz says missing logs left responders unable to see what was read (Wiz, 2026-11-09).

    Triage: legitimate vendor traffic comes from the vendor's own AWS infrastructure; the correct External ID does not discriminate, because it is logged in plaintext and often stored by the vendor, while a vendor role assumed from a consumer VPN or a hosting provider the vendor has never used is the high-signal case.

    Defender takeaway
    Inventory third-party trust relationships, delete the roles of ended integrations, narrow each trusted principal to the vendor's specific principal and add a source-address or endpoint condition, which Wiz says alone would have blocked every observed assumption; after an incident, revoke the issued role sessions and rotate every secret, parameter, Lambda variable and identity-provider credential the role could read.
