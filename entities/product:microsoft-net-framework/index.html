    NOTABLECVE-2026-108398 +1NATOB1

    Project Zero: clearing one COFF header flag makes .NET Framework 4 load an untrusted assembly past Windows code-integrity checks (CVE-2026-108398, fixed 2026-10-13); the same behaviour defeated VirtualBox's Windows process hardening (CVE-2026-87268) and is expected to remain a protected-process bypass

    James Forshaw of Google Project Zero published a write-up of a code-integrity bypass found re-examining VirtualBox's Windows process hardening (Project Zero, 2026-11-23). On .NET Framework 4 the runtime first maps an assembly as an image section; if that fails with a bad-format error it falls back to a flat, data-only mapping that .NET can still run, so protection code that checks the loaded image section never sees it. A check meant to stop the fallback when code integrity is enforced tests the Windows lockdown policy for inequality with the configuration-code-integrity value, which is exactly what Windows 11 S Mode returns (User Mode Code Integrity on, Dynamic Code Security off), so it passes. Clearing the executable-image flag in the COFF header of a managed assembly, one bit with no checksum fix-up, and loading it through a .NET Framework 4 command-line utility without administrator rights ran arbitrary code under User Mode Code Integrity; it only seems to work on .NET Framework v4 (Project Zero, 2026-11-23).

    Forshaw presented it at 44Con before reporting it in late September 2026, so Microsoft treated it as a zero day; CVE-2026-108398 was fixed in October 2026 by correcting the policy check (Project Zero, 2026-11-23). Microsoft rates it Important, not exploited (Microsoft MSRC, 2026-10-13).

    The same behaviour defeated VirtualBox's Windows process hardening (CVE-2026-87268): an AnyCPU .NET assembly made its image screening return the bad-format status, the flat fallback loaded the unmodified assembly, and a current-user COM registration brought it into a hardened process; VirtualBox fixed it by never returning that status and by adding a COM option that disables current-user hive lookups. Against protected processes, hijacking a COM object that WerSecureFault.exe loads gave code execution as a protected process light without administrator rights; Microsoft's servicing criteria place such bypasses out of scope and the policy fix does not change that, so Forshaw expects it to remain bypassable (Project Zero, 2026-11-23).

    Exposure
    Windows hosts that rely on App Control for Business or WDAC user-mode code integrity as an application-control boundary without Dynamic Code Security (Project Zero, 2026-11-23), and Windows hosts that run Oracle VM VirtualBox 7.2.16 or likely earlier builds (Oracle, 2026-09-15).
    Detection
    The post says protection code that checks the loaded image section does not see this load (Project Zero, 2026-11-23); from that and the shown method, look at process creation of the .NET assembly-registration utilities with an unregister option against a file in a user-writable path, current-user COM registrations for the .NET runtime, .NET assembly loads with no matching image load, and managed assemblies whose COFF header lacks the executable-image bit.

    Triage: developers and installers run the registration utilities legitimately for their own signed COM assemblies from build or Program Files paths; the discriminators are an unsigned or modified assembly, a user-writable path and a current-user COM registration on a host enforcing user-mode code integrity.

    Defender takeaway
    Confirm the October 2026 .NET Framework update (4.8.1 at build 4.8.9363.0, 4.8 at 4.8.4811.0, 4.6.2 to 4.7.2 at 4.7.4150.0) on every host that enforces user-mode code integrity (Microsoft MSRC, 2026-10-13) and do not treat protected process light as a boundary against local code that can run .NET Framework 4 assemblies; Dynamic Code Security blocks the behaviour but is off by default, disables loading assemblies from byte arrays and can break applications (Project Zero, 2026-11-23).

    NOTABLENATOB2

    CL-STA-1178 (Blinder Tunnel): an Iranian-nexus recruitment lure delivers a Visual Studio project that runs code when it is opened, then hijacks the .NET AppDomainManager, disables ETW and takes tasking from GitHub

    Unit 42 tracks an Iranian state-aligned cluster as CL-STA-1178 and names its March 2026 campaign against an individual in Iraqi critical infrastructure "Blinder Tunnel"; the infrastructure was staged from November 2025, and the same actor ran conflict-themed Google Drive credential phishing against an Israeli entity in May and June 2026 (Unit 42, 2026-10-06). A recruiter persona impersonating the Dubai Airports IT department sent a decoy career-portal installer and then a weaponised C# Visual Studio project as an at-home coding test (Unit 42, 2026-10-06). When a developer opens a project, Visual Studio runs a design-time build in the background, and the project file overrides one of the targets that step runs, so the payload executes at project load, before any compile; it copies binaries into a folder under the user profile and launches one of them (Unit 42, 2026-10-06).

    The launched binary is a renamed, signed Microsoft Visual Studio hosting process. A configuration file beside it replaces the .NET application's default app-domain manager with a malicious one and sets the ETW enable flag to false, which Unit 42 says could impair detection, and the loader, ShelbyLoader V2, then arrives through DLL sideloading (Unit 42, 2026-10-06). The loader persists through a current-user startup registry value, authenticates to the GitHub API with a hard-coded personal access token for tasking, and falls back to encrypted routing data in comments on GitHub issues; a follow-on module hooks the PowerShell engine inside the hijacked process, so commands run without starting powershell.exe, and a second loader, Blackwood, runs the open-source Chisel tunnelling tool in memory to give a reverse SOCKS proxy into the victim's network (Unit 42, 2026-10-06). GitHub removed the malicious infrastructure Unit 42 identified, and Unit 42 is not aware of any breach of Dubai Airports (Unit 42, 2026-10-06).

    Exposure
    Developers and IT staff who open third-party Visual Studio projects, such as recruiter coding tests or contractor repositories, on workstations that can reach the GitHub API; no Swiss or European target is reported (Unit 42, 2026-10-06).
    Detection
    Process-creation lineage showing Visual Studio or the build engine copying executables into a user-profile folder and launching one at project open; a renamed, signed Microsoft host binary with a sidecar configuration file that names an app-domain manager or turns ETW off; binaries that load unknown or non-standard DLLs outside system directories, which Unit 42 advises monitoring; non-browser, non-git processes calling the GitHub API with a token or searching issues; and the PowerShell engine loaded into a process that is not a PowerShell host (Unit 42, 2026-10-06).

    Triage: developers legitimately build projects and call GitHub, so the discriminators are that execution starts at project open rather than at a build the developer chose to run, a DLL beside a renamed signed host binary that does not belong to it, and a configuration file that changes ETW or app-domain settings.

    Defender takeaway
    Treat a recruiter-supplied or third-party Visual Studio project as untrusted code before it is ever built, since Unit 42 reports execution at project load, and watch for the sideload and configuration-file signals above on developer workstations; Unit 42's own advice is to secure developer environments and monitor anomalous cloud-platform traffic (Unit 42, 2026-10-06).
