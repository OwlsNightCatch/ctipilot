    Defender takeaway

    Update trust bundles and toolchains on every non-browser client, rebuild container images that embed an old bundle, and do not rely on revocation or CT for those clients; website operators with certificates chaining to emSign ECC Root CA - G3 must install a certificate from another hierarchy before 2026-10-27 (Google, 2026-10-20).     Exposure · triage · detection
    Exposure

    Any software that keeps its own CA bundle or does not check revocation keeps trusting the intermediates until updated; the tracker lists fixed versions for Python (3.15.1, 3.14.9 and 3.13.17, and pip 26.2.2), Python certifi, rustls-webpki, the curl CA bundle, the Composer ca-bundle, Erlang certifi and several distributions' ca-certificates packages, shows Node.js, Bun and FreeBSD as fixed, and lists Bottlerocket, Godot, LibreOffice and RHEL 7 as still pending (Dennis Jackson, 2026-10-20). The tracker adds that macOS blocks the intermediates but its built-in curl reads /etc/ssl/cert.pem without a revocation check and the file was not updated (Dennis Jackson, 2026-10-20). A client's state is read with the tracker's test hosts: a certificate error means the client does not trust the intermediates (Dennis Jackson, 2026-10-20).

    Triage

    A site that still chains to emSign ECC Root CA - G3 failing in Chrome after 2026-10-27 is the announced root removal, not an attack (Google, 2026-10-20).

    Detection

    EMudhra says it found no evidence that the intermediates were used to issue end-user certificates (BleepingComputer, 2026-10-20), so a server certificate chain seen in TLS session metadata, proxy or EDR network telemetry that contains one of the eight intermediates or their Sectigo cross-signs, which the tracker lists, is worth treating as a possible forged certificate (Dennis Jackson, 2026-10-20). Google reports that no certificates chaining to the six TLS intermediates were logged to Certificate Transparency before it blocked them, so CT monitoring will not show one (Google, 2026-10-20).

    Detection

    NOTABLECVE-2026-91403 +2updatedNATOA1

    eMudhra: the private keys of eight intermediate CA certificates were trivially recoverable, so anyone could forge trusted HTTPS certificates; browsers block them, clients with their own trust store or no revocation checking need an update (CVE-2026-111943 in Go)

    On 2026-10-17 a researcher reported to the Chrome Root Program, and Mozilla received a report the same day, that the private keys of eight eMudhra subordinate CA certificates were compromised: the keys were generated with insufficient randomness, which lets anyone forge trusted HTTPS certificates to impersonate any website against clients that have not removed trust in those CAs (Google, 2026-10-20; Mozilla, 2026-10-20). BleepingComputer, citing Mozilla's incident report, says all eight were P-384 keys generated in April 2025 with values below 256, so testing 256 numbers recovers a key, and that eMudhra blames a key-generation script error and found no evidence of end-user certificates (BleepingComputer, 2026-10-20). Google reports that no certificates chaining to the six TLS intermediates were logged to Certificate Transparency before it blocked them, so CT-enforcing clients such as Chrome could not have been attacked (Google, 2026-10-20); the tracker adds that many clients outside browsers do not enforce CT and that it is not known whether attackers used the flaw against them (Dennis Jackson, 2026-10-20).

    Chrome blocked the intermediates on 2026-10-17, Firefox through OneCRL the same day, Microsoft platforms on 2026-10-20 and Apple devices on 2026-10-22, and eMudhra revoked all eight (Dennis Jackson, 2026-10-20; BleepingComputer, 2026-10-20). Google removed the root that signed them, emSign ECC Root CA - G3, from the Chrome Root Store, with the removal expected to reach devices on 2026-10-27, after which some legitimate certificates chaining to it will stop working in Chrome (Google, 2026-10-20); Mozilla removes the signing root from NSS 3.131.1 to protect applications that use its trust store without OneCRL (Mozilla, 2026-10-20). Go 1.27.3 and 1.26.10 filter chains that contain the intermediates in crypto/x509, tracked as CVE-2026-111943 (Go team, 2026-10-20).

    Standalone OpenJDK runtimes, unlike operating-system packages, carry their own keystore (OpenJDK, 2026-10-24). Oracle's Security Alert of 2026-10-21 for CVE-2026-91403 (CVSS 3.1 9.1, component JSSE, remotely exploitable without authentication through the component's APIs, for example a web service that supplies data to them) provided Java updates that distrust the impacted eMudhra intermediate CA certificates (Oracle, 2026-10-21), and a second Security Alert of 2026-10-24, CVE-2026-114820 (CVSS 3.1 9.1, same component and exposure), provides updates that remove the impacted root CA certificates and lists Oracle Java SE 8u511-b32, 11.0.33.0.2, 17.0.21.0.2, 21.0.13.0.2, 25.0.5.0.2 and 27.0.1.0.2 as affected (Oracle, 2026-10-24). The OpenJDK advisory of 2026-10-24 lists 27.0.1.0.2, 25.0.5.0.2, 21.0.13.0.2, 17.0.21.0.2, 11.0.32.1 and 8u504 and earlier as affected (OpenJDK, 2026-10-24), and OpenJDK's guidance tells users of a standalone runtime to act immediately even if they updated in the past few days, preferably by installing an update whose release note names JDK-8395690 and CVE-2026-114820 (OpenJDK, 2026-10-24). If no update is available, OpenJDK gives two alternatives: delete the aliases emsignrootcag1, emsignrootcag2, emsigneccrootcag3 and comodoaaaca from the runtime's cacerts keystore and restart it, or enable revocation checking with -Dcom.sun.net.ssl.checkRevocation=true and -Dcom.sun.security.enableCRLDP=true for TLS clients and use jarsigner -verify -revcheck -strict for signed JARs on JDK 17 and later; the step is repeated for every installed runtime (OpenJDK, 2026-10-24). OpenJDK packages from Arch Linux, Fedora, Gentoo, Oracle Linux and Red Hat Enterprise Linux most likely use the operating system's certificates, so updating those is likely sufficient; Debian and its derivatives, Devuan and Ubuntu among them, need a manual workaround because updating ca-certificates and ca-certificates-java does not refresh the keystore (as superuser, remove /etc/ssl/certs/java/cacerts and run update-ca-certificates --fresh), and the FreeBSD and Homebrew packages need an updated package (OpenJDK, 2026-10-24). NCSC.ch published an advisory on 2026-10-22 and lists the exploitation status as unknown (NCSC.ch, 2026-10-22).

    Exposure
    Any software that keeps its own CA bundle or does not check revocation keeps trusting the intermediates until updated; the tracker lists fixed versions for Python (3.15.1, 3.14.9 and 3.13.17, and pip 26.2.2), Python certifi, rustls-webpki, the curl CA bundle, the Composer ca-bundle, Erlang certifi and several distributions' ca-certificates packages, shows Node.js, Bun and FreeBSD as fixed, and lists Bottlerocket, Godot, LibreOffice and RHEL 7 as still pending (Dennis Jackson, 2026-10-20). The tracker adds that macOS blocks the intermediates but its built-in curl reads /etc/ssl/cert.pem without a revocation check and the file was not updated (Dennis Jackson, 2026-10-20). A client's state is read with the tracker's test hosts: a certificate error means the client does not trust the intermediates (Dennis Jackson, 2026-10-20).
    Detection
    EMudhra says it found no evidence that the intermediates were used to issue end-user certificates (BleepingComputer, 2026-10-20), so a server certificate chain seen in TLS session metadata, proxy or EDR network telemetry that contains one of the eight intermediates or their Sectigo cross-signs, which the tracker lists, is worth treating as a possible forged certificate (Dennis Jackson, 2026-10-20). Google reports that no certificates chaining to the six TLS intermediates were logged to Certificate Transparency before it blocked them, so CT monitoring will not show one (Google, 2026-10-20).

    Triage: a site that still chains to emSign ECC Root CA - G3 failing in Chrome after 2026-10-27 is the announced root removal, not an attack (Google, 2026-10-20).

    HIGHCVE-2026-20316exploitedupdatedNATOA2

    CVE-2026-20316: Cisco Secure Firewall Management Center ships a static low-privilege account in its web interface, and Cisco confirms active exploitation

    Cisco Secure Firewall Management Center is the management server for a Cisco firewall estate. CVE-2026-20316 places a vendor-embedded static password for a low-privileged account inside that server's web interface: Cisco states the flaw "is due to the presence of static user credentials for a low-privileged account" and that "an attacker could exploit this vulnerability by using the account to log in to an affected system" (Cisco PSIRT, 2026-07-29). Because the credential ships with the software, there is no attacker-side prerequisite beyond reaching the interface: the account exists on every affected release, so an attacker needs a network path and nothing else.

    The exploitation status is what moves this out of the routine patch cycle. Cisco PSIRT states that "in July 2026, the Cisco PSIRT became aware of active exploitation of this vulnerability" (Cisco PSIRT, 2026-07-29). CISA added the flaw to its Known Exploited Vulnerabilities catalog on 2026-07-29 (CISA KEV catalog, 2026-07-29).

    Read the score and the rating together rather than separately. The CVSS 3.1 base score is 5.3 (AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N) because the exposed account is low-privileged and the direct impact is confidentiality-only, but Cisco overrode that judgement in its own advisory: "Cisco has assigned this security advisory a Security Impact Rating (SIR) of High rather than Medium as the score indicates. The reason is that this vulnerability can be used with other Cisco Secure FMC Software vulnerabilities to elevate privileges" (Cisco PSIRT, 2026-07-29). Treating this as a medium-severity information disclosure and scheduling it accordingly is the wrong read: it is a pre-authenticated foothold on a security-management server, and its value to an attacker is as the first link in a chain.

    Affected releases are 7.0 and earlier, 7.2, 7.4, 7.6, 7.7 and 10.0, regardless of how the device is configured, with 7.0.10 as the fix for 7.0 and earlier (Cisco PSIRT, revised 2026-09-16), and Cisco explicitly states no workaround exists (Cisco PSIRT, 2026-07-29). Cloud-Delivered FMC, Firewall Device Manager, Secure Firewall ASA, Secure Firewall Threat Defense and Security Cloud Control are listed as not affected (Cisco PSIRT, 2026-07-29), so the exposure is specifically the on-premises management centre.

    Detection
    Cisco does not name the static account, so the check to run is the forensic self-check it publishes: in expert mode, search the system messages logs for package_info entries naming /var/tmp/license.tmp, which indicate the flaw may have been exploited on that device. Cisco's example is a sudo log line in which the web-server user runs package_info.pl as root against that file (Cisco PSIRT, revised 2026-09-16). Hardening beyond the fix is reachability: Cisco notes that if the FMC management interface has no public internet access, the attack surface is reduced (Cisco PSIRT, revised 2026-09-16).
    Defender takeaway
    Patch, then check for compromise. Cisco states its hot fix files are "for preventing future exploitation only and may not address existing compromise", the advisory does not say the hardening releases that replace them remove an existing compromise, and Cisco sends any device with indicators to TAC (Cisco PSIRT, revised 2026-09-16). The upgrade alone only closes the door behind whoever may already have walked through it, so a hit on Cisco's log check is a compromise case, not a patch ticket.

    HIGHCVE-2026-20079 +2exploitedupdatedNATOA1

    CVE-2026-20079, Cisco Secure Firewall Management Center: unauthenticated authentication bypass to root, unpatched for five months and only exploitable in a post-boot window (CVSS 10.0)

    Cisco Secure Firewall Management Center is the box that holds the policy, the rules and the credentials for a firewall fleet, and CVE-2026-20079 gives an unauthenticated caller root on it. Cisco describes the flaw as "due to an improper system process that is created at boot time", reachable by sending crafted HTTP requests, and scores it CVSS 3.1 10.0 (CWE-288) against Secure FMC Software and Cisco Security Cloud Control Firewall Management "regardless of device configuration" (Cisco PSIRT, 2026-08-03). What makes this worth acting on now rather than in March is the timeline: the advisory went out on 2026-03-04 with no fix and no workaround, and the per-train hot fixes plus the first compromise-check guidance only arrived with advisory version 2.0 on 2026-07-31, and Cisco has revised that check three times since, v2.1 and v2.2 the same day and v2.3 on 2026-08-03. For roughly five months the only available response was exposure reduction. Those hot fixes are no longer the remediation: revision 2.6 of 2026-09-16 replaced them with the September hardening releases (see the correction below).

    The mechanics explain why exposure is narrower than a CVSS 10.0 suggests, and why the detection guidance matters more than usual. VulnCheck built a working exploit and published the chain on 2026-03-26: a startup process leaves a partial csm_processes session in the sfsnort.sessions database, and if nobody authenticates after boot that session persists and can be upgraded using the hardcoded machine-user credential report:snortrules, yielding the sf_action_id request token; an arbitrary file write through the validateLicense bulk AJAX endpoint on sajaxintf.cgi drops a Cisco-format Makeself script to /var/tmp/license.tmp, and calling pjb.cgi with SF::UI::DataObjectLibrary::upgradeReadinessCall makes the appliance process that file as an upgrade package, executing it as root (VulnCheck, 2026-03-26). VulnCheck also found the precondition is fragile (dashboard interaction by a real administrator, cloud-managed session activity, or a periodic cleanup all clear the injected session) so in its assessment the realistic exploitation window is shortly after a reboot, or on appliances nobody logs into. That same source counts roughly 300 internet-facing FMC instances on Censys and between 600 and 700 on FOFA.

    Cisco's advisory, as first published on 2026-08-03, said it had seen no public announcements or malicious use of this CVE (Cisco PSIRT, 2026-08-03); CISA's KEV addition on 2026-09-09 (see the update below) now confirms active exploitation Cisco itself had not observed, and Cisco's own advisory has since been revised to say the same thing. The reason to treat it as out-of-band even before that KEV listing sat on the same web interface: the separate static low-privilege credential flaw CVE-2026-20316 is CISA KEV-listed with exploitation Cisco says has been ongoing since July 2026 (covered here on 2026-07-30), and in that advisory Cisco raises the Security Impact Rating to High specifically because "this vulnerability can be used with other Cisco Secure FMC Software vulnerabilities to elevate privileges" (Cisco PSIRT, 2026-08-03). An attacker already using the exploited flaw for low-privilege read access is one documented step from the root path this CVE opens.

    Detection, and the discriminator: both advisories key compromise assessment on the same artifact, a package_info.pl invocation against /var/tmp/license.tmp in /var/log/messages*, run as root via sudo from the www account. Legitimate FMC upgrades and licensing operations do run package_info.pl, so the file path is the signal rather than the command: a genuine upgrade references a package under Cisco's own upgrade directories, not a temporary file in /var/tmp. Because the injected session only survives while no administrator has authenticated, correlate any unauthenticated web-UI activity against appliance boot and uptime records, a request sequence reaching CGI endpoints with no preceding interactive login, minutes after a reboot, is the shape here. Hardening beyond the fixed release is exposure reduction; Cisco notes that "If the FMC management interface does not have public internet access, the attack surface that is associated with this vulnerability is reduced", and low-touch appliances that nobody logs into are precisely the ones that stay exploitable longest.

    Update13 Sep 2026 04:37 UTCrun 2026-09-13T0409Z-intelentitiestechniquestagsevidencesourcesbody

    Cisco Talos confirmed active exploitation by three distinct post-compromise clusters (Cisco Talos, 2026-09-09). UAT-12197 exploited this CVE alone, planting a JSP web shell in the CSM Tomcat webroot and a JAR-based command executor used to query the FMC's internal user database for credentials (Cisco Talos, 2026-09-09). UAT-11823 exploited both this CVE and CVE-2026-20316 together; Talos states the cluster "overlaps in tooling with the Sandworm APT actor" (Cisco Talos, 2026-09-09), replacing the appliance's license.tmp file with a malicious root-executed package before deploying a variant of Cyclops Blink, the modular implant the US and UK previously attributed to Sandworm. UAT-11988 entered via CVE-2026-20316's static credential alone and, after AD/MySQL credential harvesting, tunnel-based lateral movement and disabling security tooling, deployed ransomware whose subsequent actions Talos found "were consistent with those of Qilin ransomware affiliates" (Cisco Talos, 2026-09-09). Cisco's own advisory was separately revised (v2.5, 2026-09-09) to confirm it became aware of active exploitation of this vulnerability in August 2026 (Cisco PSIRT, 2026-09-09), and Cisco has scheduled a further comprehensive Secure FMC/ASA/FTD hardening release for 2026-09-16 (Cisco PSIRT advance notification, 2026-09-09).

    A JSP file appearing in the CSM Tomcat webroot, or a JAR-based executor querying the FMC's own user database, is UAT-12197's signature; a Cyclops Blink deployment resolves its command-and-control address over DNS-over-HTTPS rather than a hardcoded address, so DoH lookups from the FMC management-plane process are a discriminator; and a SOCKS5 proxy or reverse-SSH tunnel originating from the FMC and forwarding LDAP, LDAPS, Kerberos, SMB or NetBIOS/WinRM traffic toward the internal directory is UAT-11988's lateral-movement signature, worth treating as an active-compromise indicator whether or not ransomware has yet deployed.
