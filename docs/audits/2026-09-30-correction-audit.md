# CTI quality audit, 2026-09-30 (operator-directed correction run)

**Mandate.** The second half of the operator-directed whole-setup review of 2026-09-29: after the v4.17 machinery shipped, correct the published content the review had found wrong, and go on fixing whatever else turned up. The review's reviewer lists covered the 2026-09-16 to 2026-09-29 entries, every entry whose exploitation status a later record had changed, every banned citation in the store and the defanged indicators the review found. This pass then looked beyond the audits' usual trailing window for the first time. Run record: [`runs/2026-09-30/2026-09-30T0639Z-audit.md`](../../runs/2026-09-30/2026-09-30T0639Z-audit.md). Prompt v4.19, shipped in this commit.

**Method.** One research sub-agent (`cti-research`, R1) searched for a citable replacement for each of the 36 banned citations, found one for 26 and none for 10, and re-checked the fact each replacement carried against the fetched page. Where no replacement exists, the fact was removed or is carried by another cited source. Every other correction was made in the main context against a primary fetched in this run: vendor advisories (Fortinet, Check Point, Arista, Ivanti, IBM, LiteSpeed, Cisco), national authorities (ABW, CERT-FR, NCSC-CH, BACS), the CISA KEV catalog feed and the news reports the entries cite. Each entry received one changelog record for this fire. A site sub-agent (listed in the run record's `sub_agents`) finished the 4.17 site work. Verification: the Phase 5.7 loop over the claim ledger of every changed entry, this report and the run record (see the run record's verification block).

---

## Verdict

**75 entries received a changelog record, 7 legacy entries were fully re-verified, and 3 duplicate entries were folded into their survivor.** The window's newer entries were mostly sound in their facts and weak in their upkeep: their main text went stale after later records, they led with US federal KEV deadlines, and they narrated the pipeline to the reader. The older half of the store is a different problem. 478 of 966 entries came from the v2 daily briefs before verification existed, only 3 of them had been touched by an audit before 2026-09-30, and the handful opened in this run carried claims their sources do not make. That is the finding that matters most, and v4.19 turns it into a finite repair queue.

## Findings: systemic and operational

1. **The legacy corpus was never verified.** 478 entries carried `migrated_from: briefs/...` before this run folded three of them (475 after), and before 2026-09-30 only 3 of them had ever received a record from an audit (the parallel 2026-09-30T0634Z audit corrected four more that day). The ones opened here held fabricated specifics (attributions, victims, statistics, package versions). Root cause: the weekly audit re-verifies only its trailing window, so nothing ever reached back. Fix: `tools/legacy_review.py`, `state/legacy_review.json` and quality-audit Phase 0 step 6b (a batch of about 20 per audit, oldest first). Seven reviewed here, 468 of the 475 pending.
2. **Duplicates survived the v4.0 migration.** 48 of 54 CVE-sharing entry pairs carried no link (no `references`, `merged_from` or `update_of` in either direction), 24 legacy "UPDATE (originally covered ...)" entries were never folded, and two CVE-2026-50751 twins disagreed about which CVE was exploited. Root cause: the migration keyed on `update_of`, which these entries never had. Fix: `tools/fold_entries.py`, list-valued `merged_from`, redirect support in the build, a `silent-edit` exception for folded ids, and quality-audit Phase 3 item 13.
3. **Touching a legacy entry pulls it under current gates.** Every legacy entry corrected here also needed a rating and an ATT&CK mapping. That is by design and is now documented in the legacy memory note, so the next audit budgets for it.
4. **The changelog-fields check was stricter than its purpose.** Removing inline ATT&CK ids, defanged indicators or citation groups counted as reader-facing rewrites. The word allowance now ignores those, and still catches rewritten claims.
5. **Touched entries carried far more unsupported text than the corrections targeted.** Verification iteration 1 read the 75 changed entries whole and raised 150 truth findings (F1, F3, F4, F13, F14) and 87 editorial or advisory ones, most of them in older text this run had not written: invented mitigations (CVE-2026-46300), actor links an entry never sourced, headline overstatements (TraderTraitor, NightEagle), detection discriminators with no source behind them, and one error this run introduced itself (the ShinyHunters correction claimed an FBI confirmation the sources do not contain). Every finding was checked against its page and fixed through the entry's record. Root cause: the verifier loop only ever read what a fire changed, so older text in a living entry was never re-read after publication. The legacy queue covers the migrated half, and the audit's whole-entry truth passes cover the window, but September entries outside any audit window had the same defect class.
6. **The site sub-agent widened the landing alarm to seven days.** That contradicted the 2026-09-29 directive for a very short alarm (six rows that week). Reverted, the seven-day span stays in `data/alerts.json` for notification hooks.
