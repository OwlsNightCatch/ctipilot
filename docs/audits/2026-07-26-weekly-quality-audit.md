- **Novelty, quote fidelity and date precision (7).** CVE-2026-8496 framed as "newly disclosed"/"previously-unknown" when it was published 2026-05-13 and patched in SOGo 5.12.8 on 2026-05-12, though `event_date` correctly records the in-window anchor (`ta458-roundpress-…`); autonomy overstated against a source narrating operator-prompted escalation (`gpt56-autonomous-…`); a paraphrase presented inside quotation marks as a Kaspersky quote (`weekly-w29-state-nexus-edr-blinding-…`); an `evidence[]` quote spliced from a GHSA lead-in plus its first bullet rather than a contiguous substring (`moodle-local-o365-…`); a same-day convergence claim where the two events are ~15 days apart (`stiftung-autismuslink-…`); an exploitation-onset date a day later than the source's (`servicenow-…`); an exploitation prerequisite understated against Exodus's stated precondition (`cve-2026-2291-dnsmasq-…`).

**Root cause — one mechanism, and a natural experiment that proves it.** The attribution group and much of the scope group are the same failure: composing from a set of sources and then attaching a citation to a sentence rather than checking, clause by clause, which page carries which fact. The v3.26 weekly fix ran exactly this experiment last week. It had two limbs: (a) citation dates must come from the source's own publication metadata, and (b) every fact must be cited to the specific source that states it. Limb (a) is mechanically checkable and **worked completely** — 0 of 52 W29 citation dates wrong, against 12 of 15 W28 entries drifting by 1–8 days. Limb (b) is a judgement call and **did not move at all** — 4 attribution defects in W29 against 4 in W28. The lesson is that prose exhortation does not fix this and mechanisation does, so v3.29 mechanises limb (b) on both sides: at composition (one citation per clause, never chain two vulnerabilities under one identifier) and at verification (a mandatory per-citation adjacency sweep, explicitly not a sample). The `fixed: "not stated in advisory"` case has its own contributing cause — the CSAF-remediation rule existed in `.claude/memory/csaf-msrc-transcription.md` but not in the prompt, so it was not in context at compose time; v3.29 moves it into Phase 2.

## Findings — systemic / operational

1. **A source-lifecycle rule was dead on arrival — 11 candidates long past the promotion bar.** `sources/sources.json` documents "candidate → active after 3 contributing runs", but nothing counted contributing runs, and a stateless per-fire agent cannot remember earlier fires. Result: `proofpoint` (cited by published entries from **11** distinct runs, 5 citations in this window alone), `sysdig` (7), `socradar` (6), `mysites-guru` (5), `swisscybersecurity-net` (5), `jamf-threat-labs` (4), `onapsis` (4), `reliaquest` (4), `searchlight-cyber` (4), `netzwoche` (3) and `ox-security` (3) all sat at `candidate` — which excludes them from `active_ids` and therefore from the slices the fires actually build. Fixed both ways: `tools/run_summary.py` now emits `sources.promotion_due[]` (counting distinct `run_id`s among entries whose `sources[]` cite each candidate's host), v3.29 makes acting on it a Phase 0 duty, and all 11 are promoted in this commit.
2. **The previous audit's own new source was never fetched — the same gap it was added to close.** `wordpress-org-news` was added on 07-18 specifically because WordPress core releases had no discovery path (the cause of that audit's WP2Shell miss). Eight runs later its `last_successful_fetch` is still `null` and no run record mentions it. **Root cause:** the Phase 0 allocation rule described the staleness rotation for `tier: standard` without ever saying `status: candidate` records participate, and the digest's convenient `active_ids` list excludes them — so a newly added candidate is structurally unreachable, making the promotion bar it must clear unattainable. v3.29 states that candidates rotate and that a `null` `last_successful_fetch` sorts oldest, so a source added last run tops the next slice. This is a **fix that did not take**, and its root cause is now fixed rather than the symptom.
3. **Reachability ≠ readability, with a concrete recipe divergence.** `cisa-advisories` probes green in `state/source_health.json` (200/`bridge-ok`, 07-26T07:10Z) while the 07-25 and 07-26 fires both logged HTTP 403 on it. Cause, stated more narrowly than this audit first put it: the record's `url` field is the HTML listing that Akamai 403s for every UA, and the sweeping agents led with it — even though the working feed URL was **already** on the record as `rss_url`, and the record's own 2026-07-10 note already said to prefer it ("Prefer the RSS feed over the page URL for enumeration"). The health probe passes because it uses that feed recipe. So this is not a missing-recipe problem but an ignored-recipe one, and the fix shipped here is a note that says so in the imperative rather than a new field. Two further recipe corrections shipped: `ncsc-uk`'s 07-13 note calling its feed path unresolved is stale (the combined feed resolved cleanly this run), and `ccb-belgium` moves to `fetch_method: jina` (WebFetch and the generic bridge return only cookie-consent boilerplate; the reader returns the full dated listing).
