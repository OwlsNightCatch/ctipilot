## Verdict

**46 of the 54 entries with activity in the window verified clean against freshly fetched primaries.** Two factual errors, six imprecisions, and no hallucinated source, broken link, IOC leak or unrated entry anywhere in the window. Every one of the previous audit's ten corrections and improvements held on re-verification, and both defects truth pass D found were pre-existing errors that fire never touched.

The honest state of the pipeline is that soundness is in good shape and completeness is not. The two factual errors both matter operationally: a MikroTik entry told defenders to patch to releases that CERT Polska now says carried an incomplete fix, and a Linux kernel entry annotated a network-reachable flaw with a local attack vector that no authority assigns and that contradicted the entry's own analysis. Both are corrected. Against that, this audit's independent research re-sweep recovered **eighteen** publishable research-blog items the week's seven fires never saw, on top of an incomplete Oracle patch-release entry and four incident items. That is the largest completeness gap any recent audit has measured, and its cause is not judgement: the source rotation the previous audit repaired was still putting only 51 of 115 research sources in front of a research sub-agent all week, because the v4.11 fix stopped consecutive fires repeating each other without making the underlying ranking advance. The rotation now ranks on a cursor that an attempt advances, which reaches 112 of those 115 in seven fires. The soundness numbers should be read in that light: what the fires published was almost all true, and there was a great deal they were never given the chance to see.

## Findings — systemic and operational

### 1. The v4.11 rotation fix worked, and left a three-slice carousel behind it

This is the previous audit's headline fix, measured in production. It did what it promised. Mean consecutive-fire source-slice overlap on S3 fell to **8 %**; `talos`, `sentinellabs`, `huntress` and `kaspersky-securelist` — the four publishers the 2026-09-20 audit found allocated to *no fire at all* — were all swept, and `huntress` produced a published entry (`2026-09-21/huntress-vss-abuse-detection-correlation-ntds-shadow-copy`). Distinct S3 sources across the seven fires rose from roughly 14 to **54**. Watch item 3 (rotation-fix effectiveness) is resolved.

It also exposed the half of the cause it did not reach. Subtracting the previous two fires' attempts stops consecutive fires repeating each other; it does not make the underlying *ranking* advance, and the ranking was the cause. `last_successful_fetch` still moves only when a source is fetched **and used**, and used counts in this window ran 1 to 6 per fire, so the oldest-first order stayed frozen and each fire simply took the next slice down. Fire N+3 then saw the same head again:

| Domain | slice overlap, lag 1 | lag 2 | **lag 3** | distinct sources, 7 fires |
|---|---|---|---|---|
| S1 vulnerabilities | 53 % | 55 % | **82 %** | 54 |
| S2 incidents / region | 59 % | 61 % | **92 %** | 55 |
| S3 research | 8 % | 9 % | **85 %** | 54 |
| S4 breaches | 22 % | 25 % | **51 %** | 37 |

The rotation had become a three-slice carousel. Over the seven fires **51 of 115** research sources appeared in a research sub-agent's slice across the seven fires; the other 64 never did, and **22 of the 115 were given to no sub-agent at all** (sources carry several categories, so some were swept by another domain's slice). Among the 22: `msft-ti`, `checkpoint-research`, `eset`, `crowdstrike`, `citizen-lab`, `ahnlab-asec`, `team-cymru`, `symantec-broadcom`, `tenable-research`.

**Root cause:** the rotation was ranking on a field that is deliberately not a rotation clock. **Fix shipped:** rank on a rotation cursor, `max(last_successful_fetch, last_attempted)`, so an *attempt* advances a source's place in the queue while `last_successful_fetch` stays what it always was, a content-health signal. `last_attempted` is derived from the `sources_attempted` lists already on every intel run record, so there is no new field in `sources.json` and no per-fire bookkeeping step to forget — the `kev-window.txt` lesson applied before the fact. Simulated over the next seven fires against the live store, the cursor reaches **112 of 115** research sources with **zero** consecutive overlap.

### 2. A run record no standards-compliant YAML parser can read sat in the store since May, invisible to every gate run

`runs/2026-05-14/2026-05-14-e05c6e6e.md` carries a double-quoted scalar containing a Windows path (`C:\ProgramData\USOShared\`). `\U` is a YAML escape sequence, so PyYAML rejects the whole document; this repo's own deliberately lenient stdlib parser reads it correctly, which is why the site builds and the record renders normally.

**Root cause:** the `frontmatter-yaml` portability check has always covered the fire's own run record in **run scope**, but under `--all` it walked entries only. A record that no fire would ever re-gate was therefore checked exactly once, by the fire that wrote it, before the check existed. **Fix shipped:** `--all` now walks run records too. It fires on exactly one record of 196 — the check is confirming a clean store, not opening a backlog.

The record itself is immutable, so the warning is acknowledged rather than fixed. Whether a pure re-quoting that provably preserves every parsed value should count as an edit to an immutable record is a judgement the audit should not make alone; it is recommendation 1.
