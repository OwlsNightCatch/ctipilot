    Kaspersky GERT BlackNevas case: credentials from systems outside the virtualisation layer reach both vCenter appliances, a remote-access agent and a VMware-lookalike tunnel service persist, vCenter Host Profile remediation switches SSH on across the ESXi hosts, backups are destroyed first and a wipe of the datastores detonates over ten days, with no vulnerability exploited

    Kaspersky GERT describes a ten-day engagement in which an adversary, identified as BlackNevas from its ransom notes, used credentials taken from systems outside the virtualisation layer to reach both vCenter appliances, persisted on one with a remote-access agent and a tunnel installed as a VMware-lookalike systemd service, then used vCenter Host Profile remediation to switch SSH on across four ESXi hosts, destroyed the backup environment first and detonated a wiper-capable locker that took every virtual machine. Kaspersky states no initial access vector, victim sector or country, and no virtualisation-layer vulnerability was exploited.

    GitLab shipped an ad-hoc critical patch release on 2026-11-10 for CVE-2026-105437, a heap overflow in Git that, per GitLab, any user who can create a project and open a merge request reaches, and that can run commands as the git user with access to every repository on that Gitaly node. Git 2.56.1 and its backports fix the same flaw and five others, among them CVE-2026-111760, code execution when a malicious repository is cloned with --recurse-submodules; no source reports exploitation.

Red Hat fixed both in Quay 3.9.28, 3.10.28, 3.12.24, 3.14.10, 3.15.9, 3.16.7, 3.17.7 and 3.18.3, lists Quay 5 and the mirror registry for Red Hat OpenShift 2 as affected with no fix, and NCSC Switzerland lists exploitation as unknown.

    CyberStrikeAI turned on AWS: Elastic reads one server's 16 days across eight identities in four accounts, 56 user-data reads in 141 milliseconds, and why six detections each rated medium or low and only the source address tied them together

    Elastic Security Labs reports that between 2026-09-30 and 2026-10-16 one server running the open-source CyberStrikeAI platform used the credentials of eight AWS identities (five IAM users, three EC2 instance roles) across four accounts, reading secrets and EC2 user data and, in one case, issuing a Systems Manager command.
