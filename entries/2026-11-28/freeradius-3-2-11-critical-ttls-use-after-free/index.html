    FreeRADIUS before 3.0.29 and 3.2.11: a Critical use-after-free in the default-enabled EAP-TTLS module can be started by an unauthenticated user and code execution may be possible; 21 issues fixed in all, among them TEAP bugs that return Access-Accept to an unauthenticated peer; no exploitation stated and no proof of concept for the Critical flaw

    FreeRADIUS 3.2.11, 3.0.29: Critical unauthenticated use-after-free in default EAP-TTLS, TEAP bypasses; upgrade

    first published 2026-11-28 04:57 UTC

    Analysis

    FreeRADIUS announced 3.0.29 and 3.2.11 on its security page of 2026-11-25 (GitHub release pages: 2026-11-26), fixing various overflows and memory leaks, and recommends that everyone on earlier versions upgrade (FreeRADIUS, 2026-11-25). The page lists 21 issues: one Critical, eight High, five Medium and seven Low (FreeRADIUS, 2026-11-25). The Critical issue is a use-after-free in the TTLS module, which the project says is enabled in the default configuration: an unauthenticated user could start an EAP-TTLS session and send invalid inner-tunnel data, and with heap shaping an attacker can cause a write of a heap pointer to a chosen address, so code execution may be possible (FreeRADIUS, 2026-11-25). The page states no exploitation and no proof of concept for this flaw, mentions a proof of concept that Ada Logics wrote for two High EAP-FAST issues, and says a system whose affected module is not enabled is not vulnerable to that module's issues (FreeRADIUS, 2026-11-25).

    The High issues in DHCP, EAP-FAST, EAP-SIM and TEAP are in modules the project says are not enabled by default, among them an unauthenticated out-of-bounds write in the DHCP option encoder (FreeRADIUS, 2026-11-25). Three Medium TEAP issues let an unauthenticated peer that starts a TEAP session obtain an Access-Accept, through skipped Basic-Password checks, a Crypto-Binding check missing in production builds and an unexpected Crypto-Binding TLV; their fixes are listed on 3.2.x only, and TEAP is off by default (FreeRADIUS, 2026-11-25). CERT-FR restated the release on 2026-11-27, saying some of the flaws allow remote code execution, remote denial of service and a breach of data confidentiality (translated from French) (CERT-FR, 2026-11-27). The project page lists no CVE ids; ENISA's database lists CVE-2026-127030, an EAP-FAST session-ticket stack overflow, and CVE-2026-127029, an EAP-SIM identity-length stack overflow, both published on 2026-11-12 and scored CVSS 3.1 7.5 for availability impact only (ENISA EUVD, 2026-11-12; ENISA EUVD, 2026-11-12).

    Exposure
    FreeRADIUS before 3.0.29 or 3.2.11 with the TTLS module enabled, as it is in the default configuration, for the Critical flaw; the project says EAP-TLS, TTLS and PEAP are enabled by default, and it states no default for the EAP-MSCHAPv2 module of a High issue, which a PEAP-only site should check; the issues in TEAP, EAP-FAST, EAP-SIM and DHCP apply only where those modules are enabled (FreeRADIUS, 2026-11-25). The project's standing advice on the same page, from its earlier 2026-06-01 announcement, is to keep the RADIUS server on a management VLAN and off the internet (FreeRADIUS, 2026-11-25).
    Detection
    Radiusd crashes and restarts, as service-manager events or core dumps, that follow EAP-TTLS handshakes, and on servers with TEAP enabled, Access-Accept replies for TEAP sessions with no completed inner authentication in the authentication detail log; both follow from the mechanisms the project describes, which publishes no indicator. A heap-corruption attack may leave only a crash, so review radiusd restarts in the days before the upgrade.
    Defender takeaway
    Upgrade to 3.2.11, or to 3.0.29 on a 3.0 server and then migrate, because the release notes call 3.0.29 the planned last 3.0 release and tell everyone to move to 3.2.11 or later (FreeRADIUS 3.0.29, 2026-11-26); check which EAP methods the server enables and switch off those in use by nobody, and keep the listener reachable only from network access servers and proxies. The Critical flaw sits in a method that is on by default, though no exploitation is stated.
