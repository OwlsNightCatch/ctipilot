    OptimJack: poisoned scripts served by Optimizely, Kissmetrics, StorifyMe and minute-ly route iPhones to exploit-kit stages, the Optimizely files also carry a crypto clipper and card skimmer, and the University of Basel site loaded a poisoned StorifyMe widget on 2026-11-14

    OptimJack: Optimizely names the exploited signup-flow flaw; Report URI counts 178 organisations, Zscaler 450+ domains

    first published 2026-11-17 04:38 UTCupdated 2026-11-22 14:54 UTC

    Defender actions

    • List every page of your organisation's sites, and of the agencies that build them, that has loaded Optimizely project JavaScript since 2026-11-16, or Kissmetrics i.js, a StorifyMe widget or the minute-ly loader since 2026-11-13, capture the bytes the browser receives and compare them with the provider's own project content (a search for the loader's host name misses the variant that hides it in base64), and where a file carries the injected loader remove it, keep the response bytes as evidence and treat the payment, login and form pages that loaded an affected Optimizely file as exposed to card and session theft.
    • If your organisation or an agency building its sites has an Optimizely Web Experimentation account, audit every Project JavaScript field for code nobody wrote and rotate the API tokens, session tokens and integration keys tied to it, because the attacker impersonated users on targeted accounts to edit that field.
    • For every page that loaded an Optimizely snippet on 2026-11-16, review the card and cryptocurrency transactions made on it during Optimizely's exposure window (07:51 to 22:24 UTC; Report URI saw the first injection at 04:21 UTC) and keep the web server, CDN, WAF and payment logs that cover the day, because Optimizely says the script was meant to take card details typed into a site's own forms and cryptocurrency transfers.

    Analysis

    Per Ohey, from 2026-11-13 the scripts served by Kissmetrics and StorifyMe gained a few lines that load a small router script for iPhones, and minute-ly's loader was replaced outright (Ohey, 2026-11-17). Optimizely's customer project files followed on 2026-11-16, when Report URI saw its first injection at 04:21 UTC and counted 188 infected snippets of 178 organisations, a floor (Report URI, 2026-11-16). Optimizely says an unauthorized party exploited a flaw in its Web Experimentation account signup flow on 2026-11-16 to impersonate users on targeted customer accounts and insert malicious JavaScript into their projects, that it closed the vulnerability within three hours of detection, that this was not a credentials breach and that fewer than 5% of its customers were affected (Optimizely, 2026-11-18); Zscaler ThreatLabz counts more than 450 unique domains and more than 3,000 URLs serving the script (Zscaler ThreatLabz, 2026-11-18). Hudson Rock names 21 web properties, among them BBC, Zoom, HSBC UAE and the University of Basel (Hudson Rock, 2026-11-16). The Basel capture of 2026-11-14 recorded a poisoned StorifyMe web component (Hudson Rock, 2026-11-16). How the Kissmetrics, StorifyMe and minute-ly files were altered, who operates the campaign and how many visitors loaded them are unknown (Hudson Rock, 2026-11-16).

    The financial theft sits in the Optimizely files: Ohey says that on 2026-11-16 they switched to a script that swaps copied wallet addresses and skims card numbers in every browser and adds the router only on iPhones and iPads (Ohey, 2026-11-17). Hudson Rock describes the stealer as skimming card number, expiry and CVV from form and fetch POST bodies, and a conditional path that sends readable cookies with a page image only after a recorded wallet address matches (Hudson Rock, 2026-11-16). In Hudson Rock's reading the router sends iOS 13 to 17 to a Coruna-associated entry and iOS 18 to 25 to a DarkSword-labelled one (Hudson Rock, 2026-11-16), and Ohey states that DarkSword attacks iPhones running iOS 18.4 to 18.7.2 through Safari (Ohey, 2026-11-17); Hudson Rock calls them delivery observations, not demonstrated compromises (Hudson Rock, 2026-11-16).

    Exposure
    Any page that loads an Optimizely project snippet, whether from cdn.optimizely.com or from the customer's own host name (Report URI, 2026-11-16), Kissmetrics i.js, a StorifyMe widget or web component, or the minute-ly loader; Hudson Rock's advice is to verify what visitors actually receive (Hudson Rock, 2026-11-16).
    Detection
    Web proxy and DNS telemetry for a vendor script that causes a further script load from a host unrelated to the vendor, payment-form POST bodies sent to an unfamiliar host, and response-body diffs of served third-party bundles; Content-Security-Policy script-src violation reports naming unknown hosts, which Amirul Cyber says stopped the payload on two affected sites (Amirul Cyber, 2026-11-16). After removal, review the provider-side project change history, API credentials and integrations, because the poisoned output does not show how the attacker got in (Hudson Rock, 2026-11-16); Zscaler advises customers to review recent changes, user activity, account creation events and administrative access in the Optimizely account (Zscaler ThreatLabz, 2026-11-18).
    Defender takeaway
    Inventory third-party scripts on public, payment and e-government pages now and verify what each serves; a DNS or network block alone does not remove the poisoned trusted script (Hudson Rock, 2026-11-16), so keep the evidence, remove the file and set an allow-listed script-src policy.

    Updates5

    Update18 Nov 2026 04:57 UTC

    Optimizely says an unauthorized party exploited a vulnerability in Experimentation and used it to add malicious JavaScript to some customer projects, that it has fixed the vulnerability and removed the injected code, and that it secured affected user accounts; that post named no flaw class, CVE or count, and the status entry's later post of 2026-11-18 is described below (Optimizely, 2026-11-18). The status entry covers the Optimizely files only; how the Kissmetrics, StorifyMe and minute-ly scripts were reached is still unknown.

    Report URI's timeline adds that the card skimmer was added to the clipper at 13:43 UTC on 2026-11-16, that a mass clean-up ran between about 20:40 and 21:10 UTC, and that a snippet cleaned and then re-infected shows the writer still had access at that point (Report URI, 2026-11-16). Contradiction on dates: Ohey puts the change to the Optimizely project files at 2026-11-13 together with the Kissmetrics and StorifyMe scripts (Ohey, 2026-11-17), while Report URI's first Optimizely injection is at 04:21 UTC on 2026-11-16; Report URI's logged first-hand record is the better dated one, and the earlier wave through Kissmetrics, StorifyMe and Minute Media is not in the 178 (Report URI, 2026-11-16).

    The injected loader came in three forms: a plain script tag, the same address hidden in base64 and decoded with atob(), which a search for the host name misses, and a full inline copy that runs through eval (Report URI, 2026-11-16). Cards entered in hosted payment iframes were out of the skimmer's reach, while cards typed into a site's own form fields were not (Report URI, 2026-11-16).

    Update19 Nov 2026 05:06 UTC

    Optimizely's status entry now says that on 2026-11-16 an unauthorized third party exploited a flaw in the Optimizely Web Experimentation account signup flow to impersonate users on targeted customer accounts and insert malicious JavaScript into their projects, that it detected the activity the same day, blocked delivery and closed the vulnerability within three hours of detection, that this was not a credentials breach, that the incident was limited to Web Experimentation and that fewer than 5% of its customers were affected; it gives no CVE and no absolute count (Optimizely, 2026-11-18). Zscaler ThreatLabz says the flaw let the attacker edit the project JavaScript field and counts more than 450 unique domains and more than 3,000 URLs serving the malicious script, without stating its vantage point or time window, so the figure is not reconciled with Report URI's 178 organisations (Zscaler ThreatLabz, 2026-11-18). It advises customers to review recent changes, user activity, account creation events and administrative access, to audit all Project JavaScript fields for unauthorized or unexpected code and to rotate the API tokens, session tokens and integration keys associated with Optimizely (Zscaler ThreatLabz, 2026-11-18).

    Update22 Nov 2026 14:54 UTC

    Report URI's update of 2026-11-17 says all infected Optimizely files were clean from 23:11 UTC on 2026-11-16 and stayed clean, and that the main payload and data-collection server was put on a registrar hold (clientHold) at 00:37 UTC on 2026-11-17 and no longer resolves (Report URI, 2026-11-16), which bounds the browser exposure from Optimizely-served pages to 2026-11-16. Ohey reports that the iPhone exploit router is a rental service: its operator rents it by channel code, renters get a console that lists each phone's wallets, keystores, Keychain, messages and photos, Ohey holds 31 renter codes in use since 2026-08-31, and the vendor attack ran on the operator's own channel (Ohey, 2026-11-19). The vendor scripts loaded the router from an address of a seller of hidden backlinks on hacked sites; registrars took that loader down on 17 and 18 November, while nine router hosts still answered on the evening of 18 November (Ohey, 2026-11-19).

    Improvement24 Nov 2026 04:29 UTC

    Optimizely's customer incident report, shortened on 2026-11-20 with a link to the full version in its customer portal, says the first malicious code was written at 07:51 UTC on 2026-11-16, detected at 13:34 UTC, the vulnerability closed at 16:10 UTC and the injected code removed from all affected projects by 22:24 UTC, and tells customers the exposure window is 07:51 to 22:24 UTC (Optimizely, 2026-11-20); Report URI logged its first injection earlier, at 04:21 UTC (Report URI, 2026-11-16), and the two accounts are not reconciled. Optimizely says the attacker acted as administrator users without their credentials, so no customer password was stolen, that only Web Experimentation was involved, that the script was meant to take card details typed into the site's own forms and cryptocurrency transfers, and that cards entered in hosted payment iframes such as Stripe or Adyen were not reachable (Optimizely, 2026-11-20).

    The vendor's early advice of 2026-11-16 to switch the snippet off has been withdrawn, and re-enabling it is stated to be safe (Optimizely, 2026-11-20). Its customer actions are to confirm which pages ran the snippet in the window, review Content-Security-Policy violation reports and outbound requests to unfamiliar domains, review card and cryptocurrency transactions, keep web server, CDN, WAF, CSP-report and payment logs that cover 2026-11-16, assess legal notification duties, check that a strong Content-Security-Policy is in place, and remove the snippet from payment or crypto pages that run no experiments (Optimizely, 2026-11-20). Report URI counted 68 of the affected sites with no policy, 50 with a policy that still allowed the payload and the data theft, and 24 (15 percent) with one that fully blocked the payload (Krebs on Security, 2026-11-17).

    Improvement25 Nov 2026 04:47 UTC

    CISA added CVE-2026-132224, an external control of critical state data vulnerability in Optimizely Web Experimentation, to the Known Exploited Vulnerabilities catalog on 2026-11-24, on evidence of active exploitation (CISA, 2026-11-24); the catalogue record points to Optimizely's incident page (CISA, 2026-11-24). Optimizely says it closed the vulnerability exploited on 2026-11-16 in its hosted service (Optimizely, 2026-11-18); the customer actions above are unchanged.
