    eMudhra: the private keys of eight intermediate CA certificates were trivially recoverable, so anyone could forge trusted HTTPS certificates; browsers block them, clients with their own trust store or no revocation checking need an update (CVE-2026-111943 in Go)

    Eight eMudhra CA keys were guessable; browsers are protected, Go, Java, Python, Rust and curl stacks need updates

    first published 2026-10-21 03:43 UTCupdated 2026-10-23 03:43 UTC

    Defender actions

    • Update the trust store or toolchain of every non-browser TLS client that keeps its own CA bundle or does not check revocation (every standalone Java runtime through Oracle's alert for CVE-2026-91403 or the OpenJDK update, or until then replace its blocked.certs file, blacklisted.certs on Java 8, with the vendor's version or enable revocation checking, while distribution OpenJDK packages need only the updated operating-system certificates; Go 1.27.3 or 1.26.10, Python certifi 2026.10.19, rustls-webpki 0.103.16, webpki-roots 1.0.10, the curl CA bundle of 2026-10-20, the distribution ca-certificates package, container base images) and rebuild images that embed an older bundle, then confirm with curl against the tracker's test host that the client now rejects the certificate; replace before 2026-10-27 every TLS certificate your organisation holds that chains to emSign ECC Root CA - G3.

    Analysis

    On 2026-10-17 a researcher reported to the Chrome Root Program, and Mozilla received a report the same day, that the private keys of eight eMudhra subordinate CA certificates were compromised: the keys were generated with insufficient randomness, which lets anyone forge trusted HTTPS certificates to impersonate any website against clients that have not removed trust in those CAs (Google, 2026-10-20; Mozilla, 2026-10-20). BleepingComputer, citing Mozilla's incident report, says all eight were P-384 keys generated in April 2025 with values below 256, so testing 256 numbers recovers a key, and that eMudhra blames a key-generation script error and found no evidence of end-user certificates (BleepingComputer, 2026-10-20). Google reports that no certificates chaining to the six TLS intermediates were logged to Certificate Transparency before it blocked them, so CT-enforcing clients such as Chrome could not have been attacked (Google, 2026-10-20); the tracker adds that many clients outside browsers do not enforce CT and that it is not known whether attackers used the flaw against them (Dennis Jackson, 2026-10-20).

    Chrome blocked the intermediates on 2026-10-17, Firefox through OneCRL the same day, Microsoft platforms on 2026-10-20 and Apple devices on 2026-10-22, and eMudhra revoked all eight (Dennis Jackson, 2026-10-20; BleepingComputer, 2026-10-20). Google removed the root that signed them, emSign ECC Root CA - G3, from the Chrome Root Store, with the removal expected to reach devices on 2026-10-27, after which some legitimate certificates chaining to it will stop working in Chrome (Google, 2026-10-20); Mozilla removes the signing root from NSS 3.131.1 to protect applications that use its trust store without OneCRL (Mozilla, 2026-10-20). Go 1.27.3 and 1.26.10 filter chains that contain the intermediates in crypto/x509, tracked as CVE-2026-111943 (Go team, 2026-10-20).

    Standalone Java runtimes keep their own trust store (OpenJDK, 2026-10-21). Oracle's Security Alert of 2026-10-21 for CVE-2026-91403 (CVSS 3.1 9.1, component JSSE, remotely exploitable without authentication through the component's APIs, for example a web service that supplies data to them) provides Java updates that distrust the impacted eMudhra intermediate CA certificates (Oracle, 2026-10-21), and the OpenJDK advisory of the same day says a standalone OpenJDK runtime likely contains the compromised certificates and should be updated as soon as possible (OpenJDK, 2026-10-21). If a runtime cannot be updated, OpenJDK gives two alternatives: replace the runtime's blocked.certs file (blacklisted.certs on Java 8) with the vendor's version, or enable revocation checking with -Dcom.sun.net.ssl.checkRevocation=true and -Dcom.sun.security.enableCRLDP=true for TLS clients, and use jarsigner -verify -revcheck -strict for signed JARs on JDK 17 and later; the step is repeated for every installed runtime (OpenJDK, 2026-10-21). OpenJDK packages from Arch Linux, Debian, Devuan, Fedora, Gentoo, Oracle Linux, Red Hat Enterprise Linux and Ubuntu use the operating system's certificates, so updating those suffices, which is not true of the FreeBSD and Homebrew packages (OpenJDK, 2026-10-21). NCSC.ch published an advisory on 2026-10-22 and lists the exploitation status as unknown (NCSC.ch, 2026-10-22).

    Exposure
    Any software that keeps its own CA bundle or does not check revocation keeps trusting the intermediates until updated; the tracker lists fixed versions for Java, Python certifi, rustls-webpki, the curl CA bundle and several distributions' ca-certificates packages, and shows Node.js, Bun and FreeBSD as fixed and the Composer ca-bundle, Erlang certifi, Bottlerocket and Godot as still pending (Dennis Jackson, 2026-10-20). The tracker adds that macOS blocks the intermediates but its built-in curl reads /etc/ssl/cert.pem without a revocation check and the file was not updated (Dennis Jackson, 2026-10-20). A client's state is read with the tracker's test hosts: a certificate error means the client does not trust the intermediates (Dennis Jackson, 2026-10-20).
    Detection
    EMudhra says it found no evidence that the intermediates were used to issue end-user certificates (BleepingComputer, 2026-10-20), so a server certificate chain seen in TLS session metadata, proxy or EDR network telemetry that contains one of the eight intermediates or their Sectigo cross-signs, which the tracker lists, is worth treating as a possible forged certificate (Dennis Jackson, 2026-10-20). Google reports that no certificates chaining to the six TLS intermediates were logged to Certificate Transparency before it blocked them, so CT monitoring will not show one (Google, 2026-10-20).

    Triage: a site that still chains to emSign ECC Root CA - G3 failing in Chrome after 2026-10-27 is the announced root removal, not an attack (Google, 2026-10-20).

    Defender takeaway
    Update trust bundles and toolchains on every non-browser client, rebuild container images that embed an old bundle, and do not rely on revocation or CT for those clients; website operators with certificates chaining to emSign ECC Root CA - G3 must install a certificate from another hierarchy before 2026-10-27 (Google, 2026-10-20).

    Update23 Oct 2026 03:43 UTC

    On 2026-10-21 Oracle issued Security Alert CVE-2026-91403 and the OpenJDK project an advisory for the same event, which reaches Java runtimes as well; Oracle says it also applies to sandboxed Java Web Start and applet clients (Oracle, 2026-10-21). Affected are Oracle Java SE 8u511, 8u511-perf, 11.0.33, 17.0.21, 21.0.13, 25.0.5 and 27.0.1, GraalVM for JDK 17.0.21 and 21.0.13 and GraalVM Enterprise Edition 21.3.20, and OpenJDK lists 27.0.1, 25.0.5, 21.0.13, 17.0.21, 11.0.32.1 and 8u504 and earlier (Oracle, 2026-10-21; OpenJDK, 2026-10-21). The tracker lists the fixed Java builds as 27.0.1.0.2, 25.0.5.0.2, 21.0.13.0.2, 17.0.21.0.2, 11.0.33.0.2 and 8u511 (Dennis Jackson, 2026-10-20), so compare the full build string, not the release number, against the affected list; the tracker's 8u511 as fixed sits against Oracle's 8u511 as affected, and the sources do not reconcile the two. NCSC.ch's advisory of 2026-10-22 lists the exploitation status as unknown and the OpenJDK guidance as the temporary mitigation (NCSC.ch, 2026-10-22).
