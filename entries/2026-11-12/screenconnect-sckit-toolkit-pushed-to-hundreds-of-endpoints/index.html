    ScreenConnect SCKit: second wave hits on-prem; disable RMM+, update technician clients to 26.6.5+

    first published 2026-11-12 04:07 UTCupdated 2026-11-14 03:57 UTC

    Defender actions

    • On every ScreenConnect instance your organisation or its IT providers run, disable the RMM+ extension immediately, verify it stays disabled and do not re-enable or reinstall it (on-premises instances by hand; ConnectWise removed it from cloud-hosted ones), review Run Command and Toolbox history and the instance audit logs for executions nobody started, including before 2026-11-11, and check managed endpoints for a second ScreenConnect client service; open no interactive session to a suspect host, use EDR live response or WinRM, because a session can trigger the toolkit to spread to the technician's workstation; update every technician host client to ScreenConnect 26.6.5 or later, because a cloud-console update does not update them.

    Analysis

    On 2026-11-11 Huntress observed an operator using access to several cloud-hosted ScreenConnect panels to run commands as SYSTEM on groups of managed endpoints through the Run Command feature, hitting at least 288 hosts at 48 organisations within 90 minutes (Huntress, 2026-11-11). Each host installed an attacker-controlled second client and fetched SCKit, a 16-file toolkit delivered encrypted that sets the legitimate client to manual start so the attacker's copy replaces it and runs a per-host executable from a scheduled task (Huntress, 2026-11-11). A second wave on 2026-11-13 hit 205 hosts at 41 organisations with no follow-on executions observed (Huntress, 2026-11-13), and Blackpoint says it appears to target on-premises instances where mitigations are still pending (Blackpoint, 2026-11-13).

    Huntress's later update says the activity seems related to RMM+, a third-party extension that bypasses ScreenConnect's accounts, roles and MFA: versions 1.0.31 and 1.0.32 accepted a blank access key when an administrator had never set one (Huntress, 2026-11-11). ConnectWise, as CNA, published CVE-2026-127063 (CVSS 4.0 9.3) saying the extension uses a static API secret by default; it names no fixed version, removed the extension from cloud-hosted instances and tells on-premises customers to disable it and not reinstall it (ConnectWise, 2026-11-12).

    Microsoft describes the technician stage: RelayTrap, a replacement client compiled on the endpoint with the .NET C# compiler and designed to deliver a payload to the technician who connects, and browser-access code that searches Chrome, Edge and Opera profiles for cookies named .ASPXAUTH, with a component designed to queue payloads through the console's Shared Toolbox (Microsoft, 2026-11-13). ConnectWise says clients 26.6.5 and later block the transfer, and Microsoft adds that a cloud-console update does not update technician clients (Microsoft, 2026-11-13); Huntress and Blackpoint saw no successful technician compromise (Huntress, 2026-11-11; Blackpoint, 2026-11-13).

    Exposure
    A ScreenConnect instance whose panel can run commands on managed endpoints, run by the organisation or an IT provider; an RMM+ extension at any version, since ConnectWise's record names a static default secret, with versions 1.0.31 and 1.0.32 and a blank key as the condition Huntress describes; a technician host client older than 26.6.5; an endpoint with a second client service pointing at a foreign relay.
    Detection
    ScreenConnect instance audit logs, Run Command and Toolbox history for mass executions nobody started and RMM+ requests with no matching login (Huntress, 2026-11-11), and file-transfer-and-run events (event ID 201, per Blackpoint) (Blackpoint, 2026-11-13); process-creation telemetry with the ScreenConnect client service as parent of cmd, PowerShell or msiexec, curl or PowerShell downloads followed by a silent msiexec install (the Sophos pattern) (Sophos, 2026-11-11), a scheduled-task PowerShell watcher that compiles an executable with the .NET compiler (Microsoft, 2026-11-13), and a client service named like a Windows component (Huntress, 2026-11-13).
    Defender takeaway
    Treat Run Command or Toolbox executions you did not start as a compromise; disable RMM+ and the four other extensions the first notice named, update every technician host client to 26.6.5 or later, rotate ScreenConnect credentials and revoke active sessions and the browser and identity-provider sessions the toolkit could steal, and keep hosts and technician workstations out of service until the rogue client and persistence are gone (Huntress, 2026-11-11; Microsoft, 2026-11-13). Removing the rogue client alone leaves the persistence and the web sessions, and the cleanup script found in the kit must not be used (Microsoft, 2026-11-13).

    Cited evidence

    Updates2

    Update13 Nov 2026 04:04 UTC

    ConnectWise, as CNA, published CVE-2026-127063 (CVSS 4.0 9.3) on 2026-11-12: the third-party RMM+ extension "uses a static API secret by default", no fixed version has been announced, disabling is the mitigation, and ConnectWise has removed the extension from cloud-hosted instances while on-premises customers must disable it and not reinstall it (ConnectWise, 2026-11-12). This differs from Huntress's account of a blank key in versions 1.0.31 and 1.0.32, and a Huntress spokesperson told The Record that it has seen no evidence of a new vulnerability and that how the attacker got panel access is still unclear, while ConnectWise says the extension's API is protected by a passphrase the partner sets (The Record, 2026-11-12). Blackpoint reverse engineered the toolkit, saw unauthorised deployments through legitimate cloud-hosted instances but no successful propagation to a technician workstation, and calls the extensions' role in the first panel access unresolved (Blackpoint, 2026-11-12).

    Update14 Nov 2026 03:57 UTC

    Microsoft published on 2026-11-13 its analysis of SCKit, which includes RelayTrap, a malicious replacement for the ScreenConnect client on an affected customer endpoint that is designed to deliver a payload to a technician's workstation when they connect for support (Microsoft, 2026-11-13). A watcher on the endpoint enumerates the ScreenConnect client services and builds RelayTrap for each with the .NET C# compiler, and the toolkit's browser code searches Chrome, Edge, Opera and Opera GX profiles for cookies named .ASPXAUTH; a console-distribution component is designed to combine the cookie with the anti-forgery and access tokens, upload a payload, queue it through the Shared Toolbox and remove the uploaded item afterwards (Microsoft, 2026-11-13). Microsoft relays ConnectWise's statement that clients 26.6.5 and later block the transfer; in its own words the fix for CVE-2026-84869 was released on 2026-09-08 and a cloud-console update does not automatically update technician clients, and it advises live response or another out-of-band method instead of ScreenConnect on a suspected device, with connecting technician workstations in scope, invalidation of ScreenConnect web and identity-provider sessions, and no use of a cleanup script recovered from the kit (Microsoft, 2026-11-13). Blackpoint's own test found that a current Host client did not fetch or run the queued transfer, and it found no technical link between the extensions and RelayTrap or the browser routines (Blackpoint, 2026-11-13).

    Huntress's update of 2026-11-13 reports a second spike at 16:12 UTC that hit 205 hosts at 41 organisations with no follow-on executions observed, one incident at an organisation running a self-hosted RMM+, a rogue client persisting as a service called Windows Update Agent, and ConnectWise's updated advisory urging partners to verify that every technician client runs 26.6.5 or later (Huntress, 2026-11-13). Blackpoint's update says the second wave appears to target on-premises instances where mitigations remain pending (Blackpoint, 2026-11-13).
