    HIGHCVE-2026-123903 +3NATOA2vulnerability

    VMSA-2026-0011, VMware vCenter and ESX: a second Directory Service authentication bypass in vCenter (CVE-2026-123903) and two I/O filter service flaws in ESX that give code execution from network access (CVE-2026-123910, CVE-2026-123911), all CVSS 3.1 9.8; no workaround for vCenter, fixed in vCenter 9.1.2, 9.0.2.0300 and 8.0 U3m, no exploitation reported

    Broadcom VMSA-2026-0011: second vCenter auth bypass and ESX I/O filter RCE, all 9.8; the earlier fix does not cover 9.x

    first published 2026-11-25 04:41 UTC

    Defender actions

    • Update every ESX host to ESXi-9.1.2.0-25946735, ESXi-9.0.2.0200-25953133 or ESXi80U3m-25926933 and, on ESX 8.x hosts that must wait, restrict TCP 9080 on the host firewall to the vCenter Server address as KB463535 describes, because CVE-2026-123910 and CVE-2026-123911 give code execution from network access and the restriction resolves only a small portion of the advisory's issues.

    Analysis

    Broadcom's VMSA-2026-0011 of 2026-11-24 fixes 23 flaws across vCenter, ESX, Workstation, Fusion, VMware Tools and Avi Load Balancer, rated Critical, and Broadcom's questions and answers treat the critical issues as an emergency change (Broadcom, 2026-11-24). CVE-2026-123903 is an authentication bypass in vCenter's VMware Directory Service, CVSS 3.1 9.8, reachable with network access to vCenter and no credentials, with no workaround; Broadcom calls it a new and distinct issue from the exploited CVE-2026-123890 in the same component (Broadcom, 2026-11-24; Broadcom, 2026-11-24). CVE-2026-123910 (heap out-of-bounds write) and CVE-2026-123911 (use-after-free) are flaws in the ESX I/O filter service, each 9.8 with network access to the host, and CVE-2026-123912 is an out-of-bounds write in the XHCI USB controller that gives code execution as the VMX process to an administrator inside a virtual machine, CVSS 9.3 in Workstation and Fusion and 8.4 in ESX (Broadcom, 2026-11-24).

    Fixed builds: vCenter 9.1.2, 9.0.2.0300 and 8.0 U3m, VMware Cloud Foundation 5.x through 5.2.5 (KB88287), with no public fix for vCenter 7.0 or ESX 7.0; ESX ESXi-9.1.2.0-25946735, ESXi-9.0.2.0200-25953133 and ESXi80U3m-25926933; Workstation and Fusion 26H1u1 (Broadcom, 2026-11-24). Broadcom says a vCenter on 8.0 U3m from the earlier advisory needs no further update but vCenter 9.1.x does, and for 9.0.x the fixed version in the new advisory (9.0.2.0300) governs, so 9.1.1.0200 and 9.0.2.0200 do not carry the fix (Broadcom, 2026-11-24). For ESX 8.x only, KB463535 restricts TCP 9080, where the I/O filter service listens, to the vCenter address; Broadcom says limiting access to the service resolves only a small portion of the issues in the advisory and may affect cluster operation, and tells customers to apply the updates (Broadcom, 2026-11-24; Broadcom, 2026-11-24). Broadcom's release notes disagree with its response matrices in places: the vCenter 9.1.2 notes list only four vCenter CVEs, not the authentication bypass that the matrix says 9.1.2 fixes (Broadcom, 2026-11-24), the 8.0 U3m notes list only the earlier exploited flaw (Broadcom, 2026-11-19) and the 9.0.2.0300 notes list ESX flaws (Broadcom, 2026-11-24), and the questions and answers score CVE-2026-123912 at 8.5 for ESX where the response matrix prints 8.4, and Broadcom names the advisory as the source of truth for affected versions and patches (Broadcom, 2026-11-24). Neither the advisory nor the questions and answers say any flaw is exploited, and no source reports it as of 2026-11-25.

    Exposure
    Any vCenter Server reachable over the network, with the build shown in the appliance's version summary, and any ESX host whose I/O filter service port is reachable; on ESX 8.x that service listens on TCP 9080 and KB463535 says only vCenter should reach it.
    Detection
    Broadcom publishes no indicators. Flows to TCP 9080 on ESX hosts from any address other than the vCenter Server are outside the pattern KB463535 describes, and administrator sessions or account changes on a vCenter that was reachable before patching deserve the review described for the earlier Directory Service bypass.
    Defender takeaway
    Treat it as the emergency change Broadcom describes: move vCenter and ESX to the builds above, re-patch any 9.x vCenter that stopped at the earlier advisory's build, and keep management interfaces and the ESX I/O filter port off untrusted networks until then; vCenter 7.0 and ESX 7.0 have no public fix and Broadcom directs extended-support customers to its support, so isolation is the interim lever there.
