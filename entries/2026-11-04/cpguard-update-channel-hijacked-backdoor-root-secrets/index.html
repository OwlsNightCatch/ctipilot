    OPSSHIELD cPGuard: an attacker who registered as a customer reached the vendor's billing and licensing server and shipped a fake update on 2026-11-02 that ran as root on about 2,950 Linux servers, copying root secrets and leaving a root shell and a scheduled task

    cPGuard update channel pushed a fake root update to about 2,950 servers on 2 Nov; update, then rotate root secrets

    first published 2026-11-04 03:45 UTC

    Defender actions

    • On every Linux server that ran cPGuard on 2026-11-02, update to the latest version (the disclosure names 5.88.26 as the clean update), confirm that the hidden root shell and the scheduled task the fake update left are gone, then reset root and local passwords from a trusted environment and rotate the root SSH keys, the MySQL root password, any cloud storage keys and every secret in root's shell history; rebuild from a clean backup taken before 1 November any server the vendor tells you the attacker logged in to by hand.

    Analysis

    OPSSHIELD says the attacker registered a customer account under a false identity on the vendor's billing portal, studied how the cPGuard agent talks to the licensing system with a trial install, sent crafted requests to the portal's callback pages, gained the ability to run commands on the billing and licensing server, took the keys used to publish updates and shipped a fake update for about 70 minutes on 2026-11-02; the vendor's logs do not record the exact request that gave access (OPSSHIELD, 2026-11-03). cPGuard agents installed the fake update between 02:08 and 03:20 UTC, and it ran as root (OPSSHIELD, 2026-11-03). The script copied the local password hashes, root's SSH private keys and authorization files, the MySQL root password and root's shell history back to the attacker, and root's cloud storage keys on a small number of servers; it also left a hidden root shell and a scheduled task (OPSSHIELD, 2026-11-03). The vendor puts the affected servers at about 2,950 and the exposed billing-portal accounts, with name, company, postal address, e-mail and hashed password, at about 7,900 (OPSSHIELD, 2026-11-03). A clean update, 5.88.26, removes the hidden root shell and a follow-up update removes the scheduled task (OPSSHIELD, 2026-11-03), but credentials copied before cleanup may still be usable (OPSSHIELD, 2026-11-03). The shared exposure is every operator of a cPGuard server: BleepingComputer says hosting firms and server administrators commonly run it alongside panels such as cPanel, DirectAdmin and Plesk (BleepingComputer, 2026-11-03).

    Exposure
    Any Linux server on which cPGuard was installed and online between 02:08 and 03:20 UTC on 2026-11-02; the vendor's earlier advisory framed the exposure as an install of versions 5.88.12 through 5.88.19 shown by "Successfully updated" entries in the product's install log, which proves installation and not that the script ran (OPSSHIELD, 2026-11-03), and the later disclosure narrows the fake update to 02:08 to 03:20 UTC without repeating a version range or withdrawing that check (OPSSHIELD, 2026-11-03). Holders of a billing-portal account are exposed separately.
    Detection
    In the install log, the affected version entries of 2026-11-02; on the host, the hidden root shell and the scheduled task the update left, which the vendor says to confirm are gone after updating; in authentication logs, root logins and use of the copied SSH keys from new sources after 2026-11-02, on this server and on every server that trusted its keys; in egress logs, the update script's collection and outbound copy of root's files.
    Defender takeaway
    Treat any server that ran the fake update as compromised for credential purposes even after the update: reset root and all local passwords, from a trusted environment as the earlier advisory says (OPSSHIELD, 2026-11-03), create new root SSH keys and remove the old public keys from every server that trusted them, change the MySQL root password and any database passwords it holds, rotate every secret in root's shell history and any cloud storage keys, and treat servers reached with those keys as exposed; rebuild from a clean backup taken before 1 November any server the vendor says the attacker logged in to by hand, and reset the billing-portal password with two-factor login (OPSSHIELD, 2026-11-03).
