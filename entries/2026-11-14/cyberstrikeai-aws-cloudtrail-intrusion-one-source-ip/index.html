    CyberStrikeAI turned on AWS: Elastic reads one server's 16 days across eight identities in four accounts, 56 user-data reads in 141 milliseconds, and why six detections each rated medium or low and only the source address tied them together

    Elastic: CyberStrikeAI against AWS, six medium or low alerts joined only by source IP; alert on user-data bursts

    first published 2026-11-14 03:55 UTC

    Analysis

    Between 2026-09-30 and 2026-10-16 one server serving a CyberStrikeAI web interface used the credentials of eight AWS identities (five IAM users and three EC2 instance roles) across four accounts and generated 78 alerts, the first case Elastic has seen of this tooling turned on AWS (Elastic Security Labs, 2026-11-13). It started by validating identities: GetCallerIdentity on four IAM users in three accounts within 51 minutes, three of the calls in the same second (Elastic Security Labs, 2026-11-13). An instance role then read a secret, made one user-data request and fired 56 more in 141 milliseconds, spacing Elastic says fits tooling working through a prepared list of instance IDs (Elastic Security Labs, 2026-11-13). On 2026-10-02 another instance role read an encrypted Systems Manager parameter and issued a SendCommand 29 seconds later, which Elastic calls the highest-risk activity; the audit log does not show the command or its outcome (Elastic Security Labs, 2026-11-13). After 14 quiet days the server returned and revalidated credentials, including a user in a fourth account (Elastic Security Labs, 2026-11-13). Elastic does not know how the credentials were obtained and infers that the instance-role sessions, used from an outside address, were taken from the instances, for example through SSRF or host compromise (Elastic Security Labs, 2026-11-13). Team Cymru counted 21 unique addresses running CyberStrikeAI between 2026-01-20 and 2026-02-26 (Team Cymru, 2026-03-02).

    Exposure
    AWS accounts where IAM user keys or instance-role credentials can leave the account and the principals may read EC2 user data or Secrets Manager values or send Systems Manager commands; secrets in user data are readable by any such principal and Elastic says to treat them as exposed (Elastic Security Labs, 2026-11-13).
    Detection
    In cloud control-plane audit logs, a burst of user-data requests from one role session; a first-time GetCallerIdentity from one external address across several users or accounts within a minute; GetSessionToken or GetSecretValue from an instance-role session whose source address is neither the instance nor your NAT; and a decrypting GetParameter followed within a minute by an SSM SendCommand from the same role (Elastic Security Labs, 2026-11-13). Six rules fired at medium or low severity, and Elastic recommends correlating such alerts by source address over a flexible window, since the gaps between steps ran from 141 milliseconds to 14 days (Elastic Security Labs, 2026-11-13).

    Triage: each call is one a legitimate role makes every day, so the discriminators are the source address, the number of distinct identities, accounts or instances one address touches in minutes, and the decrypt-then-SendCommand pairing (Elastic Security Labs, 2026-11-13).

    Defender takeaway
    Correlate low and medium cloud alerts by source address, restrict ec2:DescribeInstanceAttribute for user data to the roles that need it, move secrets out of user data, and on a hit rotate instance-role credentials by replacing the instance profile or the instance, because stolen role credentials expire but can be reissued while the host stays compromised (Elastic Security Labs, 2026-11-13). As of November none of the three servers served the CyberStrikeAI interface, so the indicator addresses are for retrospective hunting (Elastic Security Labs, 2026-11-13).
